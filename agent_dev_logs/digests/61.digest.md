## 🎯 Goal

Logs are an event stream on stdout, configured once at the entrypoint, with a level a partner can set at deploy time. Nothing a partner needs to diagnose a failed request reachable only from inside a dead container.

## ⚠️ What changed under the previous revision of this digest

The 2026-09-10 measurement recorded that four of five services configured the root logger **nowhere** and that `LOG_LEVEL` was read in **exactly one place ecosystem-wide** (`alto/service/text_api.py:538`). That was correct when written. It is now obsolete in both halves.

[\#58](https://github.com/ufal/atrium-project/issues/58) ("port 8000 standard") landed on `origin/test` across all five tool repos and, while rewriting each `__main__`, **created the root-logger configuration block in four of them**. Three of those blocks carry an `(issue #61)` comment. `LOG_LEVEL` is now read in **five** places, not one.

So the headline argument of the old digest — "four of five services have no log-level control of any kind" — can no longer be made from the config sites. It survives, but for a different reason, and the reason is worse: **the knob is now wired in all five and works in two.**

> One consequence for the reader of a neighbouring plan: [`../plans/60.plan.md`](../plans/60.plan.md)'s status line asserts that "#58, #61 and #63 all landed". **#58 did; #61 did not.** #60's sequencing rests on that belief and should be re-checked against this digest.

### D1 — page-classification: the #61 fix is already written, and it is dead code

`service/api.py:16` imports the library module at **module scope**:

```python
try:
    from .inference import manager
except ImportError:
    from inference import manager
```

That import executes `service/inference.py:22`:

```python
# Setup logging
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)
```

…which installs a handler on the **root** logger. The `__main__` block at `service/api.py:360` then runs and calls `basicConfig` again — and `logging.basicConfig` is **documented to do nothing** when the root logger already has handlers and `force=True` is not passed.

The issue predicted "the first import wins over any later `basicConfig` in a real entrypoint." That is exactly right, and it has now actually happened. Three consequences, none visible unless you read both files together:

1. **Level pinned to `INFO`.** `LOG_LEVEL` is read at `api.py:361` and discarded.
2. **Stream is `stderr`**, `basicConfig`'s default — not the `sys.stdout` the block three lines below asks for.
3. **Format is the default** `%(levelname)s:%(name)s:%(message)s` — not the agreed alto string. **Format parity across the five already fails, silently.**

And `service/README.md:312` documents `LOG_LEVEL` as working. This is worse than an unimplemented knob: it is a knob that reads as implemented in code review, in a file whose `__main__` says `(issue #61)`.

Blast radius is small — only `service/api.py:16-18` and `tests/` import `inference.py`; the batch CLI path (`run.py`, `entrypoint.py`) does not. The `try/except` at `inference.py:15-20` means the module is importable under two names; both must reach a configured root after the fix.

### D3 — nlp-enrich's `processing.log`: the file is a symptom, the parent is the disease

The issue asks what `processing.log` is for and assumes it is file-only. **It is not**, and the answer is mechanical rather than a matter of policy.

`api_util/api_common.sh:41` — the helper every stage script logs through:

```bash
log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" | tee -a "$LOG_FILE"
}
```

`tee` writes the file **and stdout**. The shell pipeline already mirrors every record. They become unreachable one level up, in the Python parent at `service/enrichment.py:472-480`:

```python
proc = subprocess.run(cmd, cwd=..., env=..., capture_output=True, text=True)
rc = proc.returncode
tail = (proc.stdout + proc.stderr)[-4000:]
```

`capture_output=True` pipes the child's streams into the parent and **nothing relays them onward**. Only the last 4000 characters survive: on success as `stdout_tail` on the result object, on failure inside a `PipelineError` message. In a multi-stage run, early-stage diagnostics are truncated away — precisely the records wanted when stage 1 misbehaved and stage 7 is what finally raised.

Then `service/enrichment.py:532`:

```python
except Exception:
    if not _KEEP_WORKSPACES:
        shutil.rmtree(workspace, ignore_errors=True)
    raise
```

`_KEEP_WORKSPACES` (`enrichment.py:41`, from `API_KEEP_WORKSPACES`) is **off by default**, so on a failed job the workspace — and `processing.log` inside it — **is deleted**. The file exists on exactly the runs nobody needs it for, and is destroyed on the runs someone does. The same pattern guards the dry-run health path at `enrichment.py:402-413`.

So the issue's open question resolves on the evidence, without a policy decision: the records are already mirrored; the parent discards them. **Relay the child's streams and `processing.log` becomes a harmless per-job artifact** — no "keep it or delete it" call required. One caveat for whoever implements: `api_4_stats.sh:145` tees to `>&2`, so a relay must cover **stderr as well as stdout**.

The workspace-lifetime half of this remains [nlp#35](https://github.com/ufal/atrium-nlp-enrich/issues/35)'s (`API_JOBS_ROOT` is container-local, so the log is unreadable from any other replica regardless). Coordinate; do not decide it twice.
