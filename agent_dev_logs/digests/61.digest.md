## 🎯 Goal
Logs are an event stream on stdout, configured once at the entrypoint. Two counter-examples remain, and four of five services cannot have their log level changed at all.

## 🔎 Verified state

**The reference.** alto-postprocess states the rule in the file that obeys it — `service/text_inference.py:51-55`:

> `# (12-factor XI) No basicConfig() here. This module is imported as a library by …`

and configures the root logger in exactly one place, inside `__main__` (`service/text_api.py:537-541`):

```python
logging.basicConfig(
    level=os.getenv("LOG_LEVEL", "INFO").upper(),
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
    stream=sys.stdout,
)
```

**Counter-example 1** — `atrium-page-classification/service/inference.py:22` calls `logging.basicConfig(level=logging.INFO)` at **import** time, in a library module, immediately after a try/except import block. Consequences, in order of how they bite: the level is hardcoded so `LOG_LEVEL` cannot reach it; the first `basicConfig` call wins, so a real entrypoint configuring the root logger afterwards is silently a no-op; and every importer inherits root-logger handlers it did not ask for. This is the exact pattern alto documents against, in the same ecosystem, four files away.

**Counter-example 2** — `atrium-nlp-enrich/service/enrichment.py:234` writes `LOG_FILE` into the per-job workspace:

```python
"LOG_FILE": f'"{ws}/out/processing.log"',
```

A file on container-local disk, not an event stream. It compounds with [nlp#35](https://github.com/ufal/atrium-nlp-enrich/issues/35): the workspace root is `API_JOBS_ROOT` (default `TEMP/api_jobs`, container-local), so this log is unreachable from any other replica and dies with the pod that wrote it — including, and especially, when the pod dies for the reason someone wants the log.

**The claim that is stronger than the issue states.** `LOG_LEVEL` is read in exactly **one** place across all six repos — `atrium-alto-postprocess/service/text_api.py:538`. Grepping the ecosystem returns that single line. So this is not "four of five services have a suboptimal logging setup"; it is **four of five services have no log-level control of any kind**, and the fifth is the one that wrote the rule down. For a partner debugging a failing request on their own Kubernetes, that is the difference between `kubectl set env` and opening a support thread.

## ⏳ Open
- **What is `processing.log` for?** The issue asks and does not answer, and the answer changes the fix. If it is a pipeline **artifact** the caller downloads with their results, keep it and mirror the records to stdout. If it is service logging that happens to be written per-workspace, it should be stdout only. Nobody has stated which, and the file is written by config substitution (`enrichment.py:234` builds a config for a subprocess), so the subprocess's own logging setup is a third thing to check before deciding.
- **Format consistency.** alto's format string is `"%(asctime)s %(levelname)s %(name)s %(message)s"`. Whether the other four adopt it verbatim is unstated. They should — a partner tailing five services wants one shape — and it is the kind of detail that never gets unified later.
- **Structured logging is not on the table and should be named as such.** Factor XI asks for an event stream on stdout, not JSON logs. Say so in the issue so it is not proposed as a natural extension mid-implementation.
