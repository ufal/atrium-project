## 🎯 Goal

Complete the DMP-mandated external registration work in two gates:

1. settle the correct DOG submission artifact and register the **six current service identities** with the Digital Object Gateway;
2. once DOG onboarding is accepted, register the same current services in the **CLARIN Language Resource Switchboard tool registry** and promote them through its development → production process.

The important refinement is that the first action is **not** to write six `repo_config` files blindly. Current public DOGlib documentation describes `repo_config` as configuration for registered repositories/PID resolution, while the #56 issue asks for one config per service with **no PID**. That mismatch must be reconciled with DOG upstream before the six files are drafted.

## ⚠️ DOG-specific finding

The present external evidence changes the first step of the plan.

`clarin-eric/DOGlib` currently describes DOG as a service for **resolving referenced resources from metadata PIDs**; its registered-repository configurations live in `doglib/static/repo_configs/`, and its public schema is explicitly a repository/parser schema. The public DOG beta announcement likewise describes `sniff`, `fetch`, and PID parsing.

That is materially different from a generic “register this HTTP processing service, with no PID” record. The #56 DMP requirement may still be correct for the intended integration, but the current public DOGlib artefact model must not be assumed to be the submission format without confirmation.

**Therefore the next external conversation should be framed as a format/applicability check, not as a request to review six already-written JSON files.** The pilot should ask DOG maintainers whether:

* #56 really means `clarin-eric/DOGlib` `repo_configs`, despite the no-PID service requirement;
* DOG has a newer service-registration path not represented by the current DOGlib schema/examples; or
* the DMP wording needs an ATRIUM-specific interpretation / correction before implementation.

This is the main new blocker introduced by the research; it is preferable to discover it before a six-config PR series.

## 🔎 Switchboard baseline

The Switchboard side is much clearer. The current Switchboard repository states that tool metadata lives in the separate [`clarin-eric/switchboard-tool-registry`](https://github.com/clarin-eric/switchboard-tool-registry) repository. Its v2 onboarding process is explicit: create a tool JSON and logo, validate against the v2 schema, verify the Tool Call API, open a PR to `master`, verify the tool on beta, then request promotion from `master` to `production`.

That means #56 should eventually track **two distinct external review objects** rather than treating “Switchboard registration” as a generic manual checkbox:

1. DOG intake / acceptance, according to whatever current DOG artifact is confirmed with its maintainers;
2. one Switchboard tool-registry entry per service, with logos and v2 Tool Description metadata, followed by beta verification and production publication.
