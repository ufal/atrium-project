## 🧭 Current baseline — 2026-10-02

The 30 September meeting changed the service topology that #40 protects. The former
`atrium-alto-postprocess` was replaced by `atrium-ocr-postprocess`; keyword extraction was split out of
`nlp-enrich`/`llm-enrich` into `atrium-keyword-extract`; and the remaining born-digital functionality became
`atrium-digital-convert`. The old repositories are no longer the active six-tool CI set.

This matters directly to #40:

- the branch/tag trust boundary is now **six tools + hub**, not five tools + hub;
- the reusable-workflow pin sweep must cover **six callers × seven hub reusables = 42 caller references**, not 35;
- release immutability must cover the six current tool repositories;
- the hub's `release_trust.py` and `pin_hub_reusables.py` already enumerate the six current tools;
- the documentation pair for #40 and `docs/release_trust.md` still describe the previous five-tool baseline and therefore no longer match the implementation;
- the new repositories also mean that release/image/artifact assumptions inherited from the former repositories must be checked rather than copied blindly.

The current `test` workflow trees show the common CI surface has been carried into the new set: the six tools have
the shared contract, provenance, security, pre-commit, workflow-lint and Docker/release machinery, with
repo-specific additions such as translator integration, nlp TEITOK checks, and keyword/digital vocabulary
workflows. GPU workflow templates also exist in some current tool repositories, but their existence is not evidence
that a usable external GPU runner is available.

## 🛡️ What is already implemented in the hub

`scripts/release_trust.py` is not a five-repository script anymore. Its `TOOLS` tuple is:

`atrium-page-classification`, `atrium-ocr-postprocess`, `atrium-translator`, `atrium-nlp-enrich`,
`atrium-keyword-extract`, `atrium-digital-convert`.

Its trust model is:

- **tool tags:** `v*`;
- **hub tags:** `v1` and `doc-schema-v*`;
- **branch rules:** the default branch plus `test`;
- **immutable releases:** all six tool repositories;
- **workflow pinning:** all six tool repositories;
- **admin bypass:** retained and logged by GitHub.

`pin_hub_reusables.py` likewise enumerates the six current tools. It pins callers to the commit behind `v1`
and synchronizes the `hub-ref` used by `para-drift` and `workflow-lint`, preventing the two references from
drifting apart.

The code is therefore ahead of the documentation: the implementation knows about six tools, while the old #40
digest/plan and `docs/release_trust.md` still contain five-tool language.

## ⏳ Current open state

### Branch protection
**Not confirmed as applied.** The intended ruleset remains:

- default branch + `test` in every current repository;
- no deletion;
- no force/non-fast-forward updates;
- changes through pull requests;
- required status checks selected from the repository's actual current CI check names;
- tag protection for tool `v*`, and hub `v1` / `doc-schema-v*`.

The check names must be read from the current heads rather than copied from the pre-split five-repo baseline.

### Immutable releases
**Tooling is present; activation/evidence is not yet confirmed.** _(2026-10-05: on in 3 of 6, see the status block.)_

The old plan assumed that every tool release attaches `service_bundle.zip` in the same way. That assumption now
needs a six-repository re-check because the new `digital-convert` and `keyword-extract` repositories have their
own release workflows and artifact surfaces. The acceptance criterion is release immutability itself; the
asset/publication flow must be verified per current repository before enabling the setting.

### Reusable workflows
**Tooling is present; callers still use the moving channel until the sweep is landed.**

The expected post-sweep state is:

`uses: ufal/atrium-project/.github/workflows/<name>.reusable.yml@<40-char SHA>  # v1`

and, for `para-drift` / `workflow-lint`, the caller passes the same SHA as `hub-ref`.

With six tools and seven hub reusables, the expected sweep is **42 caller references**, subject to confirming the
actual current caller set. The important invariant is not the number itself but that every current caller resolves
the hub workflow and its secondary `hub-ref` to the same reviewed commit.

### GPU runner
**Deferred.**

The original acceptance criterion assumed a live CI-integrated runner. That is no longer the current architecture
or an AMČR pilot requirement. The presence of `gpu-inference.yml` in some current repositories does not change this:
there is no basis for treating a GPU runner as available, and no reason to make the release/pilot trust gate depend
on one.

If GPU testing becomes necessary later, the first step is to define which `slow` tests genuinely require GPU,
then select an external execution model (MetaCentrum/CERIT-class service or another approved option). Only then
should the workflow trigger/runner integration and acceptance criteria be rewritten.

## 🔗 Relationship to the repository split

The split makes #40 a **trust-boundary issue rather than a generic CI issue**.

The six current services have different operational responsibilities:

| Current repository           | Role relevant to #40                                                          |
|------------------------------|-------------------------------------------------------------------------------|
| `atrium-digital-convert`     | born-digital input → `atrium_document`; new release/image lineage             |
| `atrium-page-classification` | page classification; existing ML/Docker CI                                    |
| `atrium-ocr-postprocess`     | OCR/text quality post-processing; successor of `alto-postprocess`             |
| `atrium-nlp-enrich`          | LINDAT/NLP enrichment; now CPU-oriented and separated from keyword extraction |
| `atrium-keyword-extract`     | statistical + controlled keyword extraction; new service/release lineage      |
| `atrium-translator`          | translation service; existing release/integration surface                     |
| `atrium-project`             | canonical schemas, reusable workflows, trust tooling and cross-repo gates     |

The old repositories `atrium-alto-postprocess` and `atrium-llm-enrich` must not be counted as active #40 callers.
Their historical releases remain relevant as provenance, but they are not targets for the new branch/tag/pin sweep.
