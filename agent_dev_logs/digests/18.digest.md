## 🧠 Strategy (settled, unchanged)
Separate the **common ground** (reusable workflows, `on: workflow_call` — single source of truth in `atrium-project`) from the **per-repo differences** (thin caller workflows). Reuse rather than reinvent: `atrium_paradata.py` already reads `ATRIUM_RUNNER_IMAGE`/`REPO`/`REF`, so **GHCR-published, self-identifying containers** are the mechanism. motyc: orchestration to be discussed with rharasim; **no overall runtime wrapper needed** — containers are reachable via API. This scopes the issue to **packaging + CI**, not a runtime orchestrator.

## 🐞 Open — P0

**P0-1 — `docker.yml` was `startup_failure` in all five tool repos.** _(fixed, awaiting push)_

> `Error calling workflow '…/docker-tool.reusable.yml@test'. The nested job 'build-and-push' is requesting 'security-events: write', but is only allowed 'security-events: none'.`

A **regression introduced by Wave B**, not a pre-existing finding. The post-publish Trivy SARIF upload added to the reusable's `build-and-push` needs `security-events: write`, but the callers granted only `contents: read` + `packages: write` — and **a reusable workflow's job permissions are capped by the calling job's grant**. GitHub rejected the file at parse time, so nothing ran. Confirmed on alto-postprocess at 04:53 and translator run [`30515149397`](https://github.com/ufal/atrium-translator/actions/runs/30515149397). Everything else was green throughout.

Fixed by granting it in the five `docker.yml` callers (job-level in four; workflow-level in translator, which has no job-level block) rather than dropping the SARIF upload — the Security-tab findings were the point, and `security.yml` already makes the identical grant. A caller-vs-callee permission check now exists and passes for all 20 pairs; its absence is what let this through, since a parse error is invisible to local YAML validation.
