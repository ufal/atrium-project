## ✅ Write-scoped actions SHA-pinned (2026-07-31)

Every third-party action resolved through a **mutable tag**. That is not a theoretical worry here: `security.reusable.yml` already documented that `aquasecurity/trivy-action` tags ≤ 0.34.2 were force-pushed to credential-stealing malware on 2026-03-19 (GHSA-69fq-xp46-6x23, **76 of 77 tags**), and the comment recommended pinning to the release commit. The advice sat unacted-on; it is now applied.

**11 pins across 6 files in all 6 repos**, limited to actions holding write scope or pushing artifacts:

| Action                               | Tag       | Why it qualifies                                      |
|--------------------------------------|-----------|-------------------------------------------------------|
| `softprops/action-gh-release` ×5     | `v3`      | `contents: write` — creates releases, uploads bundles |
| `docker/build-push-action` ×3        | `v7`      | pushes to GHCR under `packages: write`                |
| `aquasecurity/trivy-action` ×2       | `v0.36.0` | the action with the documented compromise             |
| `peter-evans/create-pull-request` ×1 | `v8`      | `contents: write` + `pull-requests: write`            |

Read-only and upload-only actions (`setup-buildx`, `metadata`, `login`, `codecov`) stay on tags.

**A trap worth recording:** `v3` and `v0.36.0` are **annotated** tags, so `git ls-remote refs/tags/<tag>` returns the *tag object*, not the commit. Pinning that SHA fails. The deref — `refs/tags/<tag>^{}` — is required. Two of the four needed it.

Dependabot understands SHA pins and maintains both the SHA and the trailing `# v3` comment, so this hardens without freezing.

## ✅ Trivy `exit-code` policy settled (2026-07-31)

The last deferred policy call. Both scan paths were `exit-code: "0"` with a comment saying to decide once real findings existed to triage; two real digest scans now exist (translator `v0.10.1`, page-classification `v1.7.1-beta`).

Rather than flip the existing step, a **separate gate** was added to `docker-tool.reusable.yml`, which keeps two concerns apart:

- the **SARIF step is unchanged** — runs on every build, never blocks, so the full CRITICAL+HIGH picture always reaches code scanning;
- the **new step blocks**, and only in the narrow case worth blocking.

It sits **after** the SARIF upload on purpose: if it fails, the findings are already in the Security tab, so the failure is diagnosable there rather than only from the job log.

Three narrowings, each removing a way this could obstruct rather than protect:

| Narrowing                                  | Effect                                                                     |
|--------------------------------------------|----------------------------------------------------------------------------|
| `if: startsWith(github.ref, 'refs/tags/')` | day-to-day pushes and PRs untouched; it stops a *release*                  |
| `severity: CRITICAL`                       | HIGH stays report-only — too noisy to hold a release on                    |
| `ignore-unfixed: true`                     | an unpatchable CVE cannot wedge releases, since there is no action to take |

The weekly `security.reusable.yml` scan **stays report-only** — blocking a scheduled scan stops nothing from shipping.

**Not proven end to end:** the gate cannot fire without a tag push, and the code scanning alerts were not readable from this session, so the first tagged release is what tests it. Reverting is one value (`exit-code` → `"0"`).

## ✅ The hub now has CI of its own (2026-07-31)

The clobber above is the second copy-paste clobber in this issue (the first: `codeql.caller.example.yml` overwritten with the docker example). Both were found by a human reading files. Asking why nothing else caught them exposed the real gap:

**The hub had no caller workflows at all** — nine files, all `workflow_call` reusables plus the E2E and issue-log jobs. Nothing in CI parsed, linted or policy-checked the source of truth for **37 caller jobs**. Concretely: 9 workflow files unchecked, 11 Python files unlinted (the hub shipped `ruff.toml` and a pre-commit example *as templates* while applying neither to itself), and **`check_version.py` — the release gate for all five tool repos, held byte-identical in all six copies by `para-drift` — had no tests anywhere.**

| Added | What it does |
|---|---|
| `tools/ci/workflow_lint.py` + `workflow-lint.yml` | six checks, one per defect this issue actually hit — see below |
| `tests/test_check_version.py` | 16 tests, weighted to the negative cases, since the gate exists to block |
| `ruff.toml` (`extend`s the shared template) + `.pre-commit-config.yaml` | the hub is finally held to the config it publishes |
| `codeql.yml`, `pre-commit.yml` | thin callers of the hub's own reusables |

The linter's six checks: every file parses · write-scoped actions SHA-pinned **with a version comment whose tag really resolves to that SHA** · caller/callee permission pairs satisfied · no structural `secrets: inherit` · **no two workflows in a directory sharing a `name:`** · **a template only passes inputs its reusable declares**. The last two are the clobber detectors, and both real incidents are caught when replayed.

Each check was made to **fail on its own defect** before being trusted. Same for the tests: seven mutations of `check_version.py` are each detected — and an eighth initially **survived**, because the fixtures had `CITATION.cff` and `para_config.txt` agreeing, which makes the two tag comparisons redundant. Two tests now force them to disagree so each comparison is independently load-bearing. Enabling ruff surfaced exactly one finding (an unused import), so the gap was cheap to close — it had simply never been looked at.

`codeql.yml`/`pre-commit.yml` call by **local `./` path**, not `@v1`: that resolves against the ref being pushed, and a repo self-check pinned to its own released tag could never catch a broken reusable *before* release.

## ✅ Caller-example templates corrected (2026-07-31)

`codeql.caller.example.yml` had been a byte-identical copy of the Docker example — fixed upstream in `79e2b70`. A follow-up sweep of all ten templates then found a **worse** defect in `docker.caller.example.yml`: its `build` job declared an *explicit* permissions block of only `{contents: read, packages: write}`, while `docker-tool.reusable.yml`'s `build-and-push` requests `security-events: write` for the SARIF upload. Copying that template reproduced the **Wave B `startup_failure`** verbatim. No live caller used it, so nothing was broken in practice — but it is the file that teaches the pattern. Fixed, along with the leftover `secrets: inherit` and a missing tag-exempt `concurrency` block.

The distinction worth keeping: an **explicit** permissions block that omits a scope fails at parse time; **no** block at all inherits the repo default and is fine. `skill-validate.caller.example.yml` has no block and is correct — it flags on a naive check and is a false positive.

## ✅ Reusable pins moved to `@v1` (2026-07-30)

26 references migrated: **20 live callers** (4 files × 5 repos) and **6 documentation examples**. Plus a 27th that a find-and-replace would have got wrong — `para-drift.reusable.yml` hardcoded `ref: test` for the hub checkout supplying the canonical `docs/templates/shared/*` files. Left alone, the pin would have been half-done: workflow *logic* from the immutable tag, the *files it enforces* still from a mutable branch. It now takes a **`hub-ref` input** (default `v1`), so `@test` callers pass `hub-ref: test` and stay self-consistent.

Two channels now: **`@v1`** is what every repo pins — a moving major tag only a maintainer advances; **`@test`** is for validating a hub change before moving `v1`. Documented in `docs/docker_gha.md` §1.

## 🧩 Things worth remembering
- **`codeql.reusable.yml` / `pre-commit.reusable.yml` are deliberately deferred** behind the `@v1` pin. They would collapse ~325 duplicated lines but raise mutable-branch coupling from 20 refs to 30. The Wave B regression — one hub-side permission change that took down `docker.yml` in all five repos simultaneously — is the standing argument for that ordering.
- **The `@test` pin enforces across every branch.** `para-drift.reusable.yml` checks the hub out at `ref: test` and its callers fire on default-branch pushes, so the newest templates are enforced against branches that may not have the matching vendored files. This nearly bit when `check_version.py` parity landed while no default branch had the file; the merge delivered both together. Keep it in mind when adding a parity step.
- **llm-enrich's `docker.yml` carries a long `build-targets` comment for a reason.** The line was briefly lost in an edit, silently falling back to the reusable's `["base"]` default — which would have published an unrunnable image (the `base` stage has no ENTRYPOINT) and never published `-remote`/`-llm`. Restored.
- **Check the doc templates whenever a reusable's permissions change.** The templates are not covered by CI — nothing parses or runs them — so a hub-side permission change silently invalidates every example that grants an explicit block. That is precisely how `docker.caller.example.yml` kept a Wave-B-shaped `startup_failure` for a week after the live callers were fixed. Grep is the wrong tool here: `secrets: inherit` appears in the explanatory comments, so the check has to parse YAML.
- **`release: types: [published]` is in 4 of 5 live `docker.yml` callers,** alongside `push: tags`. translator is the lone exception. Worth a deliberate decision at some point (the pair can double-fire), but do not "normalise" it away by looking at one repo.
- **`git fetch --tags` does not move a tag that already exists locally** — it needs `--force`. This made a local `v1` read `fd62693` for a whole session after the real tag had moved to `6d3a337`, which is a silent way to reason about the wrong reusable. When checking what `@v1` serves, resolve it against the remote (`git ls-remote origin refs/tags/v1`) or fetch with `--force`.
- **Annotated tags need `^{}` to pin.** `git ls-remote refs/tags/v3` returns the tag *object*; the commit is `refs/tags/v3^{}`. Pinning the tag-object SHA does not work. Two of the four actions pinned above are annotated.
- **Copy-paste clobbers are this repo's characteristic failure, and they pass every ordinary check.** Twice now a file has been overwritten with another's contents — `codeql.caller.example.yml` by the docker example, `skill-validate.reusable.yml` by `security.reusable.yml`. Both were *well-formed YAML*, correctly pinned, correctly permissioned. Parsing, pin checks, permission checks and secret checks all pass happily on a perfectly valid file that is simply **the wrong file**. The two detectors are duplicate `name:` within a directory, and a template passing an input its callee does not declare; both are now in `workflow_lint.py`.
- **Redundant checks hide broken ones.** `check_version.py` compares the tag against *both* `CITATION.cff` and `para_config.txt`. When those two agree — the normal case — either comparison alone blocks a bad tag, so deleting one changes nothing observable. A mutation that removed the tag-vs-CITATION check passed the entire first draft of the test suite. Isolating it required fixtures where the two files deliberately **disagree**. Applies to any guard with overlapping conditions.
