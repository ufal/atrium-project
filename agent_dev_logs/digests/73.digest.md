## 🎯 Goal

Deliver the remaining record-level outputs required by the agreed S3 discovery scope, without turning the pilot into a broader NLP/LLM experiment:

1. **Statistical keywords in the `atrium_document` record**
   - KeyBERT is the default method.
   - YAKE remains selectable.
   - KER (`legacy`) remains a selectable statistical backend in the current implementation.
   - Every statistical keyword carries its own `method`, `score` and `rank`.
   - Both document-level and per-page statistical keywords are represented because the Digital Archive indexes each page as a document.
   - Statistical keywords stay separate from the controlled-vocabulary keywords in `enrichment`.

2. **Optional document-level quality summary**
   - Added only after the page/line quality baseline is stable.
   - Derived deterministically from already-stored page/line quality facts.
   - Contains numeric statistics/counts, **not quality bands**.
   - Does not introduce another model, threshold set, or routing/gating decision.
   - Page-level quality remains the authoritative stored signal; AMČR / Digital Archive compute configurable bands at index time.

The acceptance criteria remain those in the issue body: distinct keyword kinds, method + score on statistical keywords, discovery usability without LLM vocabulary, deterministic derived quality summary, no new quality gating, and compatibility with S3's lemma search, entity facets, keywords and configurable OCR-quality bands.

## 🔎 What the code and docs say today

### Statistical keywords

`atrium-keyword-extract` v1.0.0-beta already contains the intended statistical contract:

| Aspect                  | Current state                      | Evidence / consequence                                                                                                     |
|-------------------------|------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| Methods                 | ✅ **BUILT**                        | `keybert`, `yake`, `legacy`                                                                                                |
| Default                 | ✅ **ALIGNED**                      | service `DEFAULT_KW_METHOD = "keybert"` and CLI `DEFAULT_METHOD = "keybert"`                                               |
| Per-keyword provenance  | ✅ **BUILT in response**            | `Keyword` carries `keyword`, `score`, `method`, `rank`                                                                     |
| Per-page results        | ✅ **BUILT in response**            | `PageKeywords` carries `page` + `keywords[]` in page order                                                                 |
| Score semantics         | ✅ **EXPLICIT**                     | KeyBERT cosine; YAKE normalised inverted score; KER occurrence count                                                       |
| Record `keywords` block | ❌ **NOT BUILT**                    | current service explicitly says the record is read, not written; #73 owns this gap                                         |
| Controlled kind         | 🟡 **RESEARCH / MOVE IN PROGRESS** | `kind=controlled` returns 501; `kind=both` reports controlled as `skipped` in v1.0.0-beta                                  |
| Controlled record block | ✅ **EXISTS SEPARATELY**            | current `enrichment` is the successor-owned controlled-vocabulary block; it must not be merged into statistical `keywords` |

The current response contract is useful for the schema design because it already separates the two scopes:

```text
document statistical keywords
page statistical keywords
```

and already makes every statistical item self-describing.

### nlp-enrich after the move

`atrium-nlp-enrich` v1.0.0-beta is now the **LINDAT-only** stage. Its keyword extraction code and LLM stage have left. This changes the #73 implementation point completely:

- `keywords.py`, KeyBERT/YAKE dependencies and keyword request fields are gone from the production NLP service;
- `/enrich` remains the morphology/NER/TEITOK producer;
- `api_util/teitok_project.py` remains alive and is exactly where the new record block must be consumed;
- the projection code still contains pre-split names and interfaces such as `app-llm-enrich`, `app-kw` / `atrium-nlp-enrich-keywords`, and CLI arguments for external keyword CSVs;
- production projection must therefore be migrated from **local keyword tables** to the **record's `keywords` block**, while preserving the projection's role as an nlp-enrich-owned writer of TEITOK output.

This is a consumer/projection update, not a reason to restore keyword extraction inside nlp-enrich.

### Quality baseline

The repository split also changes who the quality producer is:

- `atrium-ocr-postprocess` is now the common OCR/text-bearing reader and line-quality owner;
- `digital-convert` is the born-digital positional-plane originator. It writes `needs_ocr`, `pages[].text_layer` (since `v1.1.1-beta`) and its decode verdicts `Garbage`/`Inverted` in `lines[].categ`; these are text-layer trust signals, not archive quality;
- since 2026-10-04/05 the common model also scores born-digital records: `POST /score_record` writes the `SCORING_FIELDS` on existing rows (W3), and the per-page OCR hand-off writes the OCR'd page's lines and quality (W4);
- the shared `atrium_document` contract field-splits `pages`, `lines` and `tables` between the two originators;
- `ocr-postprocess`'s established quality model maps line evidence to the stored categories and quality scores; its current calibration work remains in its own issue #3/#2 history;
- the #73 summary must **not** mistake a converter's text-layer trust/decoding check for a second archive-quality model.

So the common stored page/line semantics now exist on both branches, and the R6 prerequisite holds. The summary reads the stored fields and must not recompute a line/page score. On a born-digital record that was not scored, it can only count the converter's verdicts; whether such a record carries a summary at all is a design point for D.3.

### Shared schema / ownership

The hub `atrium_document.schema.json` is schema 1.0, frozen by `doc-schema-v1`. Post-freeze additions are explicitly allowed when registered as additive changes.

The current owner model already has:

- `keyword-extract` beside `llm-enrich` for the controlled `enrichment` block and related successor fields;
- `ocr-postprocess` beside `digital-convert` for the positional plane fields they each write under their respective origin paths;
- `nlp-enrich` for morphology/entities/TEITOK fields.

There is **no `keywords` top-level block yet**. Therefore #73's new statistical block is a genuinely new additive block owned by `keyword-extract`; it is not an ownership transfer of a previously written block.

## ✅ What's settled

- **Repository owner:** `keyword-extract`.
- **Statistical default:** KeyBERT.
- **Selectable alternatives:** YAKE and legacy KER remain available.
- **Per-keyword fields:** `method`, `score`, `rank` are part of the statistical contract.
- **Per-page statistical keywords:** wanted by AMČR and already returned by the producer.
- **Statistical vs controlled separation:** no merged keyword list; statistical keywords are the new `keywords` block, controlled vocabulary terms remain in `enrichment`.
- **Score comparison rule:** scores stay on method-native scales; rank is the portable ordering signal across methods.
- **Quality-summary semantics:** numeric statistics/counts only; no bands; no second quality model; no gating.
- **Page quality remains authoritative at page level.**
- **Current seven-repository map:** the new repositories are the current project state; old `alto-postprocess` / `llm-enrich` names are compatibility history.
- **No broad NLP/LLM expansion:** negation detection, editor suggestions, custom NER expansion, document-understanding work and vocabulary-gap experiments stay outside #73.

## ⏳ Open

1. **Exact schema shape of `keywords`.** The current service response suggests a natural separation into document keywords and page-keyword groups, but the exact JSON node names are not yet frozen.
2. **Whether method configuration metadata belongs in the record.** The minimum required contract is per-item `method` + `score` + `rank`; model/config metadata may be included if it materially improves reproducibility, but must not become a reason to delay the block.
3. **Whether the document-level quality summary is materialised in the record or computed only at index time.** The issue describes it as a record-level output, so this refresh assumes a stored additive block unless AMČR explicitly chooses otherwise.
4. **Exact owner of a stored quality-summary block.** The deterministic function should be hub/shared code. The writer should be the stage that owns the final, stable page/line quality pass, rather than a stage being made owner of fields it does not otherwise write.
5. **Controlled keyword service completion.** This is relevant to the eventual `kind=both` production path but does **not** block the statistical `keywords` block required by #73.
6. **Vocabulary release asset.** `keyword-extract` issue #1 still records the CC0 vocabulary release asset as unfinished; this is a #1/#72 dependency, not a reason to merge controlled and statistical output in #73.
7. **Seeded E2E readiness.** The hub's seeded E2E is green ([run 37297204777](https://github.com/ufal/atrium-project/actions/runs/37297204777)), and its keyword step calls keyword-extract's `-api` (`kind=statistical`, `method=yake`) and asserts `paradata`. Its output is not merged into the final record (`4_nlp.json`), because the block does not exist yet.
8. **Release of the V-6 filter.** keyword-extract's next tag should carry `6a6619d`; until then, a born-digital record's `Garbage`/`Inverted` lines reach KeyBERT/YAKE in the released image.
9. **Stale producer ids in nlp-enrich's projection.** `api_util/teitok_project.py:97-98` still names `app-llm-enrich` / `atrium-llm-enrich` and `app-kw` / `atrium-nlp-enrich-keywords` (plan action C).

## 🔄 Consequence for the old #73 plan

- it called `nlp-enrich` the owner of the new block;
- it proposed a single generic keyword `items[]` list that could blur document/page scope;
- it still treated per-page keywords as an unanswered question;
- it asked whether KeyBERT should be the default even though the current service and CLI are already aligned;

- it proposed TEITOK projection from nlp-enrich's own keyword outputs/CSV paths;
