# Digest — Issue #73: End-to-end record contract, paradata and RO-Crate

> Issue [#73](https://github.com/ufal/atrium-project/issues/73) · Labels: `integration`, `development`, `enhancement` · **Status: 🟡 OPEN**
> _Prepared 2026-09-30 from the ATRIUM CZECHIA NER grounding report and the adopted S1 pilot baseline._

## Context

Issue #73 collects the remaining S1 contract work needed between the AMČR storage/import side and the ÚFAL processing
services.

The target is not a new record schema. `atrium_document` 1.0 is already frozen and tagged `doc-schema-v1`; each tool owns its
own blocks and additive changes continue under the schema versioning rules.

The work here is instead about making the existing record usable as the stable input/output envelope of the processing chain:

- AMČR creates the baseline record before the first stage;
- every service accepts that baseline and preserves its identity;
- every service contributes its own run provenance;
- the resulting provenance is compatible with the agreed RO-Crate packaging;
- the same crate can be validated and embedded by the AMČR side.

The S1 boundary matters because the first imported paradata are written with the AMČR distribution import. The current target
pair is therefore **RO-Crate 1.2 + Process Run Crate 0.5**, i.e. the newest pair the validator can check at this stage.

## The adopted contract

### AMČR creates the baseline

Before the first processing stage, AMČR creates the initial `atrium_document` record with:

- `doc_id` equal to the AMČR file id;
- `source.sha512` equal to the Fedora digest;
- the original file name;
- the original media type.

The baseline is deliberately independent of the uploaded filename. AMČR remains on SHA-512 for the source identity.

### The processing services preserve identity

Every service accepts the seeded record on its first call and returns the processed record.

The service may add/update its own owned blocks, but it must preserve the AMČR-seeded identity fields. The source origin remains
owned by the first tool that reads the source.

A previous implementation bug returned the seed without the tool's results. The bug was fixed and re-verified in the five tools;
the development branches already exercise the seeded-record path.

### Every service contributes provenance

The production contract is one Process Run Crate `CreateAction` per service run.

The typed response already contains an optional paradata field. The remaining work is to populate that field consistently using
the same vocabulary and identity rules across all production services.

The paradata contract is JSON-LD and follows the Process Run Crate profile, with the agreed mappings to PROV-O and PREMIS 3.

### RO-Crate baseline

For S1, pin:

- RO-Crate 1.2;
- Process Run Crate 0.5.

The crate should use:

- `./` as the record-crate root;
- `version` rather than `softwareVersion` for tools;
- stable run identifiers;
- stable tool identifiers;
- tool authors as the `creator` of the tool;
- file size information;
- a fragment mode that can be embedded into the AMČR crate without creating a second root.

Upgrade to RO-Crate 1.3 / Process Run Crate 0.6 only when the validator supports that pair.

## Why this is not a schema issue

The shared record itself is already the frozen integration object.

The problem being closed here is provenance and identity, not another redesign of the record model. In particular:

- no replacement for `doc-schema-v1`;
- no new parallel per-line quality table;
- no service-specific record format;
- no filename-derived identity;
- no second provenance vocabulary.

The production envelope must stay the same record as it moves through Temporal activities.

## Remaining work / decision boundary

1. Complete seeded-record propagation across all production services and demonstrate it with one green seeded end-to-end run.
2. Populate the typed `paradata` response field consistently across all production tools.
3. Align `atrium_rocrate.py` with the S1 RO-Crate / Process Run Crate pair.
4. Add profile validation to CI and keep the supported pair pinned until the validator can verify the next pair.
5. Verify that the generated fragments can be composed by AMČR into the record-level crate without duplicate roots.
6. Keep record-only execution out of the S1 implementation unless a later concrete use case requires it.

> **Closure rule:** seeded identity is considered complete only after the service chain has been exercised end to end and the processed
> result, not the unchanged seed, reaches the final stage.

## S1 timing

The first paradata files are produced as part of the S1 import. The grounding report places S1 in October–November 2026, with
the record contract and storage/import work therefore preceding the S2 end-to-end pilot.

## Grounding notes

The AMČR side has already settled the storage model: processing services do not write to the repository; AMČR remains the single
writer and stores the resulting record/distributions and paradata.

Issue #73 should therefore finish the service-side half of that contract, not introduce repository credentials or direct storage
writes into the ÚFAL services.
