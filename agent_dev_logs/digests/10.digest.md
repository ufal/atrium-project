## 🧭 Current AMČR decision

The 2026-09-30 #10 comment settles the scope:

> reshape this into a bounded CI quality check rather than a general-purpose LLM code reviewer.

The check may inspect a defined set of repository properties, but it must remain deterministic enough for CI and must **not** become an additional production-quality gate for ATRIUM services.

That decision is now interpreted against the post-split architecture:

* **production repositories under the check:** `atrium-page-classification`, `atrium-ocr-postprocess`, `atrium-digital-convert`, `atrium-nlp-enrich`, `atrium-keyword-extract`, `atrium-translator`;
* **policy / reusable-workflow host:** `atrium-project`;
* **review unit:** one pull request into `test`, not a whole repository;
* **result:** advisory review comments with file/line evidence;
* **deterministic gates remain authoritative:** tests, OpenAPI/contract checks, `para-drift`, lint, security and release gates.

The previous wording "all six repositories" therefore remains correct only for the six **tool** callers. The old status tables must no longer treat `atrium-project` itself as one of those six.

### Post-split architectural consequences

The 2026-09-30 meeting changed the review target more than a rename would suggest:

* `alto-postprocess` is no longer the production repository; its successor is `ocr-postprocess`.
* `llm-enrich` is no longer one production stage. Its born-digital converter is now `digital-convert`; its LLM/vocabulary/keyword functionality is now `keyword-extract`.
* `nlp-enrich` is now the NLP/TEITOK stage and must not regain the keyword/LLM implementation merely because old files or references survive in history.
* The positional plane has two possible originators: `digital-convert` for born-digital sources and `ocr-postprocess` for OCR/text-bearing inputs, selected through `source.origin`.
* `keyword-extract` owns both statistical and controlled keywords; the hub's `keywords` record block is still an additive contract item from [#73](https://github.com/ufal/atrium-project/issues/73).
* `translator` is a terminal branch: its output is recorded, not consumed by another stage.

These are exactly the kinds of stale-boundary and ownership mistakes that the bounded LLM check should catch on the diff where they are introduced.

## 🔍 What the previous LLM review rounds established

The earlier rounds remain useful as **finding classes**, not as a standing backlog of repo-wide tasks.

### March / June review rounds

The initial rounds checked source code with multiple LLMs and then expanded the review scope from Docker/GHA into:

* merged pipeline and API service;
* unit-test coverage;
* program architecture;
* file-tree structure;
* `CONTRIBUTING.md` and release history;
* repository-specific review plans.

The resulting reviews were converted into repository-specific plans and executed across the tool set.

### 2026-08-06 / 08-19 rounds

The strongest repeatable lesson was not "there are bugs an LLM can spot" but:

> **A gate that only checks existence is not a gate.**

Examples found in the executed rounds included:

* a `/process` endpoint merging a key (`result["lines"]`) that no path actually returned, making the merge dead;
* output code that wrote a hardcoded one-page stub rather than the processed record;
* remote CLIs that re-keyed or discarded accumulated `.teitok.xml` / record content;
* a renamed schema test left stale in several places and red only when actually exercised;
* a Dependabot protection change that was reverted immediately and therefore gave a false sense of coverage;
* a service API that omitted `backend`, causing real uploads to fail although mocked endpoint tests stayed green;
* `canonical_doc_id()` and `validate_document()` existing as mechanisms without the expected production call sites;
* a partial `source` object silently preventing `origin` from ever being written, so a deferred provenance guard never became active;
* scheduled CI cancelled by push-triggered concurrency while still reporting no useful failure signal;
* tests skipping because imports were guarded while no CI lane actually installed the guarded dependency.

These findings define the **review vocabulary** for the new bounded check: look for a changed property whose implementation can silently become ineffective, contradictory, or bypassed.

## ✅ Contract baseline now available to the check

The pilot work after the 2026-09-26 baseline has made the deterministic side of this review much stronger.

### Record and provenance baseline

[#71](https://github.com/ufal/atrium-project/issues/71) establishes the seeded-record direction:

* the pipeline starts from an AMČR-seeded `atrium_document` record;
* `doc_id` and `source.sha512` are preserved;
* `source.origin` is owned by the stage that reads the source;
* each service returns typed Process Run Crate `CreateAction` paradata;
* the RO-Crate helper follows the agreed RO-Crate 1.2 / Process Run Crate 0.5 direction.

The bounded check should therefore flag a PR that locally changes one of these invariants without updating the corresponding contract or test.

### Typed API and OpenAPI baseline

[#32](https://github.com/ufal/atrium-project/issues/32) has now established the service shape used by the current six tools. The hub provides `api-contract.reusable.yml`, and **all six production tool repositories already call it from their own `api-contract.yml`** on PR/push to their development branches.

The deterministic API gate now covers, among other things:

* `/info`, `/health` and advertised endpoints;
* typed primary responses;
* a shared error envelope and registered reason codes;
* committed `service/openapi.json`;
* release-to-release OpenAPI compatibility;
* image/runtime checks for the served spec in Docker CI.

This matters for #10: the LLM review should **not duplicate these checks**. It should inspect a PR for semantic mismatches that a structural OpenAPI diff cannot see.

### Architecture / repository split

[#72](https://github.com/ufal/atrium-project/issues/72) and the hub repository map now establish ownership boundaries for the six production stages. A useful LLM finding is therefore a **boundary violation**, for example:

* moving keyword extraction back into `nlp-enrich`;
* adding a second positional-plane originator without changing the ownership table;
* making `digital-convert` call OCR over HTTP instead of returning `needs_ocr` to the orchestrating pipeline;
* making `translator` depend on a later service stage;
* copying a shared contract implementation without following the governed shared-layer mechanism.

The check should report these as semantic architecture findings only when the PR actually changes code/docs in the relevant area.

## ⚠️ Current migration-sensitive areas

These are **not** an automatic backlog for #10. They are context the LLM review must know so that it does not report the old architecture as current.

### `digital-convert`

The repository is newly established from the former `llm-enrich` codebase. Its current tree is transitional: the converter implementation exists, but inherited LLM/keyword service material and old service/image identifiers are still being removed. The production target is a born-digital `POST /reformat` service with record output by default.

A #10 review of migration PRs should therefore pay special attention to stale service ids, image names, OpenAPI, `para_config`, Compose entries, production-image manifests and references to keyword extraction.

### `keyword-extract`

This is a new production repository and now owns both statistical and controlled keywords. Its future record-level `keywords` block is an additive hub-schema item. A PR that changes keyword output must not silently merge the controlled and statistical kinds, and it must preserve the per-method semantics (`method`, `score`, `rank`).

### `ocr-postprocess`

This is the successor to `alto-postprocess` and is now the OCR/text-bearing positional-plane originator. The review must distinguish a repository transition from a functional regression and should be alert to old package/image/program references that would produce split-brain deployment or paradata.

### `nlp-enrich`

Its boundary is now narrower: NLP + TEITOK projection. In particular, keyword ownership moved out. The current open issues are about NER/annotation work, not a reason to reintroduce the old LLM stage.

### `translator`

The current production-integration issue remains separate from the #10 check. The bounded review should inspect changed service/API behaviour and record/provenance handling but should not turn the external production run into an LLM-gate requirement.

### `page-classification`

There are currently no open repository issues returned by GitHub search. Its current work is driven mainly by ecosystem contracts and integration issues rather than a local feature backlog. The check should continue to review changed model/service code and CI, but not invent an open defect list.

## 🧪 Current deterministic CI landscape

The six production repositories already have the same basic reusable-workflow shape for API contract checking:

```text
six tool repos
  └─ .github/workflows/api-contract.yml
       └─ uses: ufal/atrium-project/.github/workflows/api-contract.reusable.yml@v1
```

The hub also exposes reusable workflow families for Docker, security, pre-commit, `para-drift`, E2E and workflow-lint. #10 should follow that federation pattern rather than introduce a repository-local implementation in each tool.

The new LLM review workflow is **not implemented yet**; `llm-review.reusable.yml` exists only as the designed target in the current plan. Therefore the present issue state is:

* deterministic review infrastructure: ✅ mature and expanding;
* LLM review as a CI service: ⏳ not yet implemented;
* manual open-ended LLM review rounds: ⛔ superseded by the reshape decision.

## 🎯 Target check — agreed shape

| Property            | Target                                                                                                                                               |
|---------------------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| **What**            | One hub reusable workflow reviewing a PR diff with one configured LLM.                                                                               |
| **Callers**         | Six production tools: page-classification, ocr-postprocess, digital-convert, nlp-enrich, keyword-extract, translator.                                |
| **Host**            | `atrium-project`; owns prompt/schema, policy and reusable workflow.                                                                                  |
| **When**            | PRs into `test`; manual `workflow_dispatch` for controlled validation. No schedule.                                                                  |
| **Scope**           | PR diff, plus directly affected shared canonical files and record/OpenAPI schema context when the diff touches them. Never a whole-repository audit. |
| **Output**          | Advisory review comments with concrete file/line findings. No merge blocking.                                                                        |
| **Model**           | One model selected by repository variable; fixed token ceiling.                                                                                      |
| **Secret**          | Provider key supplied as an Actions secret. No secret on forks/Dependabot → neutral skip.                                                            |
| **Runtime**         | Fixed timeout; prompt and output size bounded.                                                                                                       |
| **Governance**      | Minimal permissions, PR-scoped concurrency, workflow-lint coverage and an immutable hub release channel (`@v1`) after rollout.                       |
| **Source of truth** | Deterministic CI remains authoritative; the LLM is a second-pass semantic reviewer.                                                                  |

## 📌 Current acceptance state

### Closed / superseded

* ✅ The open-ended "review all source with an LLM" operating mode is superseded.
* ✅ The 2026-08-19 six-repository review round is completed as historical evidence.
* ✅ The 2026-09-30 AMČR scope decision is adopted.
* ✅ The production repository set and ownership model were changed and documented after the 30 September meeting.
* ✅ The hub has a reusable-workflow federation pattern already used by API/contract checks.
* ✅ Six tool repositories already expose `test` PR workflows suitable for adding one thin caller.

### Open

1. **Implement `llm-review.reusable.yml` in the hub.**
2. **Define the bounded review brief/schema** so the model returns machine-checkable findings rather than prose-only advice.
3. **Add one caller to each of the six production repositories.**
4. **Define secret/skip behaviour** for forks and Dependabot PRs.
5. **Run the check against at least one real PR in every caller repo.**
6. **Verify that findings are actionable and line-anchored, while false positives remain advisory.**
7. **Promote the hub workflow to the immutable `@v1` channel only after all six callers are green.**

### Explicitly out of scope

* another whole-repository LLM audit;
* a scheduled LLM scan;
* a required merge check based on model opinion;
* an LLM-based replacement for `pytest`, OpenAPI validation, `para-drift`, workflow-lint, security or release guards;
* ranking repositories or estimating code quality globally;
* speculative refactoring generated by the model;
* model benchmarking as a project deliverable;
* production performance/load testing;
* GPU/model-quality validation unless a PR itself changes code whose correctness depends on a model and the existing deterministic test suite already requires it.
