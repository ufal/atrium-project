## 🧩 What this round found, by axis

### Axis 1 — JSON-based pipelines

The **CLI half is in good shape almost everywhere**: `--document-json` / `--document-json-out` is wired end-to-end in pc (`run.py`, all four inference paths), alto (`run_pipeline.py` + four `extract_*.py` + `classify_TEXT.py` + `aggregate_STAT.py`), nlp (`run_pipeline.py`, bridged onto the stats stage), translator (`main.py`), and llm (two of three entry points; `llm_run.py` uses a `DOCUMENT_JSON_DIR` config instead — a reasonable batch adaptation). Rule 3 (missing baseline → own part only) is handled correctly by all of them, mostly by leaning on the shared module rather than re-implementing it.

The **service half is inconsistent**, and that is where the damage is:

* translator and llm-enrich implement the contract properly — optional `document_json` part in, updated record out.
* **pc and nlp implement none of it.** Neither service accepts or returns `document_json`; nlp's service even shells out to `run_pipeline.py`, which *does* support the flags, without passing them.
* **alto implements it and it is broken** — see **J1**. This is the worst case, because it *looks* wired and silently writes junk.

### Axis 2 — `atrium_document` standard adaptation

Where the tools write blocks they own, **ownership discipline is genuinely correct** — and that is not trivial: `set_block()` vs `merge_block()` is chosen correctly for single-owner vs field-split blocks in every repo, declared field grants match `BLOCK_FIELD_OWNERS` exactly, stamping always goes through the object's own methods, and pc even pre-stringifies its page keys (side-stepping the row-forking bug the 08-03 hardening fixed). **No tool writes a block it does not own.**

But the **two hub-provided safety mechanisms have ~zero adoption**:

* **`canonical_doc_id()` is called from nowhere** — zero call sites outside `atrium_document.py` in *all five* repos. Every repo still hand-rolls its own derivation; there are at least **eleven** independent implementations across the ecosystem. This is precisely the Issue #13 defect the function was written to retire, reproduced *inside* individual repos.
* **`validate_document()` is called from nowhere** in any production write path, in any repo, or in the hub's own E2E asserts. `jsonschema` is not even a declared dependency in pc or nlp, so calling it today would hit its own fail-loud guard. The "no `doc.json` is emitted if validation fails" gate (Layer D) currently protects **zero** real writes.

And the §1a origin machinery — the newest, most safety-critical layer — is **dormant in production**: alto never sets `source.origin` (**D5**), and llm-enrich's `digital-convert` originator does not exist yet (`api_util/digital_to_json.py` absent; `digital_born/` is self-described Phase-0 exploration). The mixed-plane check is exercised only by synthetic tests. The upside: **the two-originator risk is latent, not active** — there is time to fix the guard before the second originator ships.

### Axis 3 — GHA workflows

Structurally the best state this ecosystem has been in:

* **The `@v1` pin migration is complete and verified** — 40/40 hub-workflow references across all five tool repos' default *and* `agent-skill` branches resolve to `@v1`; zero `@test`/`@main` stragglers. The one exception is an unused published template (**G7**).
* **The release path has finally run for real.** Carried as unexercised (N7/T4) through three digests. `translator/release.yml` now shows `success` on `v0.10.1`, `v0.10.2` and `v0.10.3`, and the 07-31 + 08-01 waves exercised all five repos' inline `version-guard`. **Closed.**
* Every workflow on every tool repo's `test` branch is currently green — *except* nlp's brand-new `teitok-schema.yml` (**G1**).

The defects are in the newest additions and in the hub's own self-governance: a red new workflow (**G1**), a dependency guard disabled minutes after being added (**G2**), a moving `v1` tag causing cross-repo false failures (**G4**), and three hub self-validation holes (**G5/G6/G10**).
