## 🔴 New finding: the container-probe step has been red since the retag

Both failures are in `docker-tool.reusable.yml`'s post-healthcheck probe — the mechanism #55 built and #61 extended with a log-format assertion: after Docker's own `HEALTHCHECK` reports `healthy`, the step greps `docker logs` for one record in the agreed `%(asctime)s %(levelname)s %(name)s %(message)s` shape, to prove "the root logger is wired and the format hasn't drifted" (issue #61). Both jobs pass `HEALTHCHECK` and the `/health`/`/ready` probes cleanly, then fail this grep — which is why the raw job log shows the failure message *before* the container's own stdout dump: the dump comes from the step's `EXIT` trap, firing after `exit 1`, not before it.

**llm-enrich — deterministic, not flaky, and not a regression from this issue.** `service/api.py`'s `lifespan()` logs `logger.info("llm-enrich engine ready...")` only on warmup success (`:204`); on failure it's `logger.warning(...)` only (`:208`). CI never injects `OPENROUTER_API_KEY` — correctly, it's `[required, secret]` per the very `.env.example` this issue just landed, which documents the consequence itself: *"The reference k8s manifest ships no Secret for OPENROUTER_API_KEY, which is why llm-enrich cannot be deployed from it unmodified (atrium-project#60; docs/k8s_deployment.md's 'Known limits')."* So warmup fails on every CI run, and the only root-logger record ever emitted is that one `WARNING` — never an `INFO` in the agreed shape, which is what the probe hardcoded to look for.

This is not new behaviour in the service — it is the **first time this probe has ever run against llm-enrich's `api` image**. The `api` build target and its `probe-targets` entry were only added alongside this round of env-contract work (llm-enrich's `docker.yml` comment: *"issue #55: `api` was declared in the Dockerfile but never built or published … Now published, and container-smoked"*). The #61 probe was designed and verified against services whose warmup always succeeds in CI; llm-enrich is the first probed service where that assumption is false by design, because its one required secret is — correctly — never available in CI.

**nlp-enrich — looks like a genuine race, unrelated to the above.** `PipelineManager.warmup()` does log `logger.info("KeyBERT model loaded.")` (`service/enrichment.py:387`), awaited inside `lifespan()` before `yield`, so it should precede uvicorn's "Application startup complete." The dumped log instead shows several seconds of HuggingFace Hub metadata calls straddling that line, with the KeyBERT completion record landing after it. Both Dockerfiles set `PYTHONUNBUFFERED=1`, so this isn't a buffering artifact — worth instrumenting further, not yet root-caused with the same confidence as the llm-enrich case.

**Fixed and committed — `daf230c`, on both `test` and this branch, two minutes before this digest's own previous edition was written.** A single-file patch to `docker-tool.reusable.yml` (i) widens the format check from `INFO`-only to any of the five standard levelnames — the actual invariant is "the configured root logger produced a correctly-formatted record," which a `WARNING` proves exactly as well as an `INFO` does — and (ii) polls for up to 15s instead of grepping `docker logs` once, covering the nlp-enrich race regardless of its exact cause. **The one thing still open is the retag**: `v1` still resolves to `455ba9b`, two commits behind `daf230c` — every push that builds llm-enrich's `api` target keeps failing in CI on every repo pinning `@v1` until `v1` moves. Re-verify llm-enrich's and nlp-enrich's `Docker Build & Publish` runs go green on `test` at `daf230c` (or later), then retag. One trade-off worth naming while retagging: llm-enrich never emits an `INFO` record when its required secret is absent, so the separate `LOG_LEVEL=WARNING` suppression step below now passes vacuously for it — real, but not this patch's to fix; see `docker-tool.reusable.yml:418-421`'s own comment for why that step exists.

## 🛡️ The guard — landed, and what it actually checks

`tests/test_env_contract.py` (hub-local + vendored, `para-drift`-verified for parity): documents-every-read, documents-nothing-imaginary, declared-omissions-are-still-read, declared-omissions-are-not-also-published, every-declaration-carries-a-reason, the-shared-core-is-in-the-scan, defaults-match-the-code, `.env`-is-gitignored, and two tests tying `service/README.md`'s own env table (the "sixth enumeration" the 09-11 digest flagged) to the same `.env.example` as a subset with matching defaults. `tests/test_logging_contract.py` does the equivalent for #61's format string.

What this guard **cannot** catch, and what the new finding above is: it is a static/import-time check. It does not start a container, so it has no way to see that a documented-and-correct `[required, secret]` variable, when genuinely absent (as it always is in CI), collides with a *different*, dynamic guard — the container probe — that assumed every probed service logs an `INFO` record regardless of warmup outcome. Two guards, both individually correct, built at different times against different assumptions.

## 🆕 This pass (2026-09-14, second edition) — five residual fixes, none blocking

The retag and the four items above were all that was genuinely open when this digest's
previous edition was written. A closer read of the ecosystem found five more, all fixed
in this pass and none of them CI-red before now:

1. **`docs/templates/env.example.template` did not exist.** Fourteen references across
   all six repos — including a clickable link in this issue's own `k8s_deployment.md`
   §"Environment variables" — pointed at that undotted path while the real file on disk
   was `docs/templates/.env.example.template`, hidden from a plain `ls` by its own
   leading dot. All fourteen references already used the correct (undotted) spelling;
   the file has been renamed to match, which is the only change fourteen call sites needed.
2. **alto-postprocess's "COMPLETE ledger" claim was false, and nothing could tell.**
   `text_util.py` reads ~95 `ATRIUM_TEXT_UTILS_*`/`ATRIUM_CLASSIFY_*` algorithmic scoring
   constants via `_get_float`/`_get_int`/`_get_str`/`_get_csv_set(section, key, default)`,
   which compose the variable name as an f-string (`f"{ENV_PREFIX}{section}_{key}"`) —
   invisible to `test_env_contract.py`'s literal-string `_ENV_READ` regex, since no
   `os.getenv` call site anywhere names one of these variables directly. Taught the
   canonical test a new generic resolver (`_prefix_reads`/`_prefix_composed_reads`) that
   walks a file's own function definitions to find this exact composition shape — direct
   or forwarded through up to 6 levels of same-shaped helper — and resolves every
   concrete name at every literal call site. Declared as two `NOT_PUBLISHED` entries in
   alto's `tests/env_contract_data.py` using a new prefix-wildcard convention
   (`"ATRIUM_TEXT_UTILS_*"`) rather than 95 individual names, since the reason is
   identical for the whole family (algorithmic, tuned via `setup/config.txt`, not a
   deployment knob — atrium-project#53's own out-of-scope line). All three tests that
   touch `NOT_PUBLISHED` (undocumented / stale-exemption / withheld-and-published) were
   made prefix-aware to support this, then each failure mode was deliberately broken and
   confirmed red before being trusted. Revendored to all five repos; the resolver finds
   nothing in the other four (this composition shape is alto-specific today) and all
   twelve tests stay green there.
3. **The manifest↔doc invariant `atrium-service.deployment.yaml` claims is now checked.**
   Its own `env:` block comment says *"a variable in one place and not the other is a bug
   … and atrium-project#60's CI guard fails on exactly that"* — untrue until this pass,
   since `test_env_contract.py` never opens either file. New hub-local (not vendored)
   `tests/test_env_doc_contract.py`: bidirectionally checks the manifest's Table-A region
   against Table A's own three-way state (set / commented / deliberately absent — three
   of Table A's nine rows are the last state, which a naive membership check would get
   wrong), checks the manifest's backing-services/secrets region against Table B, and
   checks every Table B name against its own repo's `.env.example`, skipping gracefully
   when a sibling checkout is absent. Each of the three checks was deliberately broken
   and confirmed red — the first attempt at the Table-A check silently passed a broken
   file twice, for two different regex bugs (`re.findall`'s `""` vs `None` for a
   non-participating group; `\s*` crossing a newline from a blank comment line into the
   next line's `- name:`) — worth naming because both are exactly the "a guard reports
   green over the part it cannot see" pattern this whole round is about, one level down
   in the guard meant to catch it elsewhere.
4. **Two small factual corrections.** `atrium-translator/service/README.md`'s
   `ALLOWED_ORIGINS` row claimed `.env.example` "ships a localhost list as a hardened
   example" — it ships `# ALLOWED_ORIGINS=*`, commented, same as the other four repos;
   corrected. `atrium-translator/.env.example` shipped `HOST=0.0.0.0` **active** where
   the other four comment it — the code default is 0.0.0.0 either way, so this bought
   nothing and broke the template's own "§1 is byte-identical across all five" claim;
   commented to match.

None of the five was CI-red — each is a "COMPLETE"/"one contract"/"byte-identical"
claim this issue's own artifacts make about themselves that a closer read found
slightly false. Fixed alongside the retag rather than filed as follow-ups, since all
five touch files the retag window already covers (the vendored `test_env_contract.py`)
or nothing CI-gated at all (docs, a hub-local test).
