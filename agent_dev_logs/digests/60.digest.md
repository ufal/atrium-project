## 🔴 New finding: the container-probe step has been red since the retag

Both failures are in `docker-tool.reusable.yml`'s post-healthcheck probe — the mechanism #55 built and #61 extended with a log-format assertion: after Docker's own `HEALTHCHECK` reports `healthy`, the step greps `docker logs` for one record in the agreed `%(asctime)s %(levelname)s %(name)s %(message)s` shape, to prove "the root logger is wired and the format hasn't drifted" (issue #61). Both jobs pass `HEALTHCHECK` and the `/health`/`/ready` probes cleanly, then fail this grep — which is why the raw job log shows the failure message *before* the container's own stdout dump: the dump comes from the step's `EXIT` trap, firing after `exit 1`, not before it.

**llm-enrich — deterministic, not flaky, and not a regression from this issue.** `service/api.py`'s `lifespan()` logs `logger.info("llm-enrich engine ready...")` only on warmup success (`:204`); on failure it's `logger.warning(...)` only (`:208`). CI never injects `OPENROUTER_API_KEY` — correctly, it's `[required, secret]` per the very `.env.example` this issue just landed, which documents the consequence itself: *"The reference k8s manifest ships no Secret for OPENROUTER_API_KEY, which is why llm-enrich cannot be deployed from it unmodified (atrium-project#60; docs/k8s_deployment.md's 'Known limits')."* So warmup fails on every CI run, and the only root-logger record ever emitted is that one `WARNING` — never an `INFO` in the agreed shape, which is what the probe hardcoded to look for.

This is not new behaviour in the service — it is the **first time this probe has ever run against llm-enrich's `api` image**. The `api` build target and its `probe-targets` entry were only added alongside this round of env-contract work (llm-enrich's `docker.yml` comment: *"issue #55: `api` was declared in the Dockerfile but never built or published … Now published, and container-smoked"*). The #61 probe was designed and verified against services whose warmup always succeeds in CI; llm-enrich is the first probed service where that assumption is false by design, because its one required secret is — correctly — never available in CI.

**nlp-enrich — looks like a genuine race, unrelated to the above.** `PipelineManager.warmup()` does log `logger.info("KeyBERT model loaded.")` (`service/enrichment.py:387`), awaited inside `lifespan()` before `yield`, so it should precede uvicorn's "Application startup complete." The dumped log instead shows several seconds of HuggingFace Hub metadata calls straddling that line, with the KeyBERT completion record landing after it. Both Dockerfiles set `PYTHONUNBUFFERED=1`, so this isn't a buffering artifact — worth instrumenting further, not yet root-caused with the same confidence as the llm-enrich case.

**Fixed, not yet merged.** A single-file patch to `docker-tool.reusable.yml` (i) widens the format check from `INFO`-only to any of the five standard levelnames — the actual invariant is "the configured root logger produced a correctly-formatted record," which a `WARNING` proves exactly as well as an `INFO` does — and (ii) polls for up to 15s instead of grepping `docker logs` once, covering the nlp-enrich race regardless of its exact cause. Sent as a chat attachment this session; not yet committed to `test` or retagged. Until it lands, **every push that builds llm-enrich's `api` target fails in CI**, on `v1`, for every repo that calls this reusable workflow — a live break, not a `test`-branch-only one, since the retag already happened.

## 🛡️ The guard — landed, and what it actually checks

`tests/test_env_contract.py` (hub-local + vendored, `para-drift`-verified for parity): documents-every-read, documents-nothing-imaginary, declared-omissions-are-still-read, declared-omissions-are-not-also-published, every-declaration-carries-a-reason, the-shared-core-is-in-the-scan, defaults-match-the-code, `.env`-is-gitignored, and two tests tying `service/README.md`'s own env table (the "sixth enumeration" the 09-11 digest flagged) to the same `.env.example` as a subset with matching defaults. `tests/test_logging_contract.py` does the equivalent for #61's format string.

What this guard **cannot** catch, and what the new finding above is: it is a static/import-time check. It does not start a container, so it has no way to see that a documented-and-correct `[required, secret]` variable, when genuinely absent (as it always is in CI), collides with a *different*, dynamic guard — the container probe — that assumed every probed service logs an `INFO` record regardless of warmup outcome. Two guards, both individually correct, built at different times against different assumptions.
