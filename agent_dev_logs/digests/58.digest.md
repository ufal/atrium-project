## 🔎 Verified state

### Finding 1 — the prescribed entrypoint crashes all four (comment 1, confirmed, reproduced)

`ENTRYPOINT ["python", "service/api.py"]` sets `sys.path[0]` to `/app/service` and leaves `__package__` empty. Reproduced against a minimal repro of each import shape:

```
A) python service/api.py    ->  ImportError: attempted relative import with no known parent package
B) python -m service.api    ->  imports OK; __package__='service'; sys.path[0]='<repo root>'
C) same, with __init__.py   ->  imports OK  (identical — the file is not what makes it work)
```

Which repo fails on which mechanism, read off the actual import graphs:

| Repo                       | Relative imports in `service/api.py`                                        | Repo-root imports                                                                                                | Fails `python service/api.py` on             |
|----------------------------|-----------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|----------------------------------------------|
| atrium-nlp-enrich          | `.atrium_service`, `.enrichment`, `.jobs`, `.rescale` — **no fallback**     | `api_util.validate_teitok_xml`                                                                                   | relative import, at line 20                  |
| atrium-llm-enrich          | `.atrium_service` — **no fallback**                                         | `atrium_document`, `atrium_paradata`, `llm_client_shared`, `openrouter_client`, `ollama_client`, `vocab_manager` | relative import, at line 32                  |
| atrium-translator          | `.atrium_service` (has a bare fallback)                                     | `main`, `atrium_paradata`, `processors.*`                                                                        | `from main import …` → `ModuleNotFoundError` |
| atrium-page-classification | `.inference`, `.document_json`, `.atrium_service` (all with bare fallbacks) | `model_registry` (via `service/inference.py:10`'s own `sys.path.append`)                                         | — survives, by accident of its fallbacks     |

**Why alto is not a counter-example.** alto's entrypoint *is* `python service/text_api.py` and it works — but only because of the 25-line `sys.path` bootstrap at `text_api.py:21-45`, which inserts *both* the repo root and `service/` before the first first-party import. That bootstrap is the thing making the pattern work, and the entrypoint line does not carry it. Copying the line without the bootstrap copies the half that does nothing.

**`python -m service.api` is the fix**, and it needs nothing else: no `__init__.py` (PEP 420 namespace packages give `__package__ = "service"` regardless — verified above, case C is identical to case B), no import rewrites, no `sys.path` bootstrap. Under `WORKDIR /app` it yields `sys.path[0] = /app`, which is **byte-for-byte the environment the current `uvicorn service.api:app` entrypoint already runs in** — so every repo-root import in the table above keeps resolving exactly as it does today. All six root-level modules were confirmed present at each repo root.

### Finding 2 — not an inert knob; it is an unhealthy-container knob (comment 2, confirmed)

`service/healthcheck.py:49` builds its probe URL from the environment:

```python
host = "127.0.0.1"  # always probe the local process, never the published interface
port = os.getenv("PORT", DEFAULT_PORT)
```

This file is **byte-identical across all five repos** (`md5 dc986ad6e6e6b1888d83bf18426cf300`), canonical at `docs/templates/shared/healthcheck.py`, and held there by `scripts/revendor_shared.sh` / `para-drift.reusable.yml`. So in the four non-conforming repos `PORT=9000` moves the *probe* to 9000 while the server stays on 8000: three failed probes past the start period and the container is marked **unhealthy, permanently**. Latent only because the manifest sets the default.

Two consequences the issue does not draw:

- **`healthcheck.py` needs no change.** It is already correct; it is the only component in the four repos that reads `PORT` today. This keeps the fix entirely outside the para-drift set — zero re-vendoring, zero canonical-file churn.
- **The acceptance test is nearly free.** Docker's own `HEALTHCHECK` runs `python /app/service/healthcheck.py` *inside* the container, with the container's environment. Start the probe container with `-e PORT=9000` and the existing wait-for-healthy loop in `docker-build-smoke` **is** the "run `healthcheck.py` at a non-default port" assertion the comment asks for. No new probe script, no second curl path.

### Finding 3 — 🆕 the manifest's own knob is not self-consistent, and this is the one that blocks acceptance

`docs/templates/k8s/atrium-service.deployment.yaml` sets `env: PORT: "8000"` at `:55-56` — and hardcodes `8000` in **four other places the `env:` block does not reach**:

```
:52   - containerPort: 8000
:53     name: http            <- a named port already exists, and nothing uses it
:72   startupProbe   httpGet.port: 8000
:85   readinessProbe httpGet.port: 8000
:98   livenessProbe  httpGet.port: 8000
:146-148  (commented Service: port/targetPort 8000)
```

A partner who does the obvious thing — change `value: "8000"` to `"9000"` — gets a pod whose container listens on 9000 and whose three probes all interrogate 8000. **Every probe fails, the startupProbe never passes, and the pod restart-loops.** Fixing the four services without fixing this ships a manifest that is *newly* broken in a way it was not before: today `PORT` is inert and the manifest at least works: after #58, `PORT` is live and the manifest's other four references silently disagree with it.

The fix is small and already half-written: `name: http` exists at `:53`, so the three probes become `port: http` and the only line that must track `PORT` is `containerPort`. That pairing wants a comment saying so. Note that **#53's own Files line for this item already included this manifest and `docs/k8s_deployment.md`** — #58's Files line dropped both. `docs/k8s_deployment.md` does not mention `PORT` anywhere at all (grepped: zero hits).

### Finding 4 — 🆕 the CI probe hardcodes the container port too

`docker-tool.reusable.yml:349` (job `docker-build-smoke`, added under #55):

```bash
cid=$(docker run -d -p 18080:8000 "$IMAGE")
```

The `8000` is the container side. The acceptance criterion asks for "one non-default-port start" — that means a **second** probe invocation with `-e PORT=9000 -p 18080:9000`, not an edit to the existing one. The existing default-port probe must stay exactly as it is: it is what proves the manifest and every `HEALTHCHECK` keep working unchanged, which is the issue's own second acceptance bullet. The input surface is already right — `probe-targets` (`:46`) is per-target opt-in and defaults to `'[]'`, and all five repos pass `'["api"]'`.

### Finding 5 — 🆕 the import-string form double-executes the module body

Under `-m service.api`, the module runs as `__main__`; `uvicorn.run("service.api:app")` then imports it **a second time** under its real name. Verified:

```
MODULE BODY RUNS: __name__='__main__'    __package__='service'
MODULE BODY RUNS: __name__='service.api' __package__='service'
second instance is the same module object as __main__?  False
```

Harmless in the four repos as they stand — every module-level construction is cheap (`PipelineManager.__init__` is one `mkdir`; imported modules are `sys.modules`-cached, so `_jobs` and `inference.manager` stay single-instance), and the served `app` is internally consistent with the second instance's `_state`. But it is latent: any future non-idempotent module-level statement runs twice, once orphaned.

alto has the same shape today (`"text_api:app"`). page-classification's existing `__main__` does **not** — it passes the app object, with a reasoned comment at `service/api.py:349-358` explaining that the README runs it from `service/` where the import string does not resolve. The issue's point 4 says to preserve that reasoning; this finding says it generalises. `__spec__` distinguishes the two cases exactly, with no cwd guessing — verified across all three launch contexts:

```
python -m service.api   ->  __spec__='service.api'  -> 'service.api:app'   (string; reload works)
python service/api.py   ->  __spec__=None           -> app object
python api.py  (from service/, pc's README step 1)  -> __spec__=None -> app object
```

(page-classification's documented `python3 api.py` from `service/` was checked and does work — `service/inference.py:10` appends the repo root to `sys.path` before `from model_registry import …`, so the `except ImportError` fallbacks all land. The issue's point 4 rests on a real, working path.)

### Finding 6 — `HOST` has one asymmetry worth a documented line

`healthcheck.py` deliberately probes `127.0.0.1` and **never reads `HOST`** — correct, since a health probe should interrogate the local process, not the published interface. The consequence: `HOST` is the one variable in this set where a plausible value (`127.0.0.1`) yields a container that reports *healthy* and is *unreachable from outside*. Not a bug to fix; a line to write in [\#60](https://github.com/ufal/atrium-project/issues/60)'s table.

## 🔎 What the implementation pass turned up (2026-09-11)

Three things the planning passes did not have, each found by building the change rather
than reading about it.

### Finding 7 — 🆕 two page-classification tests break on the fix

Neither is a false alarm; both were asserting the old mechanism and had to be re-pointed at
the new one, not weakened:

- `tests/test_service_runtime_deps.py:184-197` asserts `api_argv[0] not in _NOT_PIP_PROVIDED`.
  With `["python","-m","service.api"]`, `argv[0]` is `"python"`, which IS in that set — so
  the assertion fails. The equivalent claim for a `-m` launch is that the **module** resolves
  and that the ASGI server its `__main__` imports is declared, which is strictly stronger
  than the head check it replaces.
- `:210-213` asserts `"--timeout-graceful-shutdown" in dockerfile`. The flag moves into code,
  so this fails too. It now accepts either spelling — the flag or `GRACEFUL_SHUTDOWN_S` in
  the stage's `ENV` — because what must not regress is that the budget is declared somewhere,
  not which of the two carries it.

**This is the repo that catches things**, and it is worth noting *why* only page-classification
broke: it is the only one of the four with a test that reads its own Dockerfile at all.

### Finding 8 — 🆕 the missing test is the one that would have caught the issue's own prescription

alto has `tests/test_service_entrypoint.py` (126 lines), which executes the entrypoint's
import graph under the `sys.path` a real launch gets. **The other four have no equivalent** —
which is exactly why `ENTRYPOINT ["python", "service/api.py"]` could be written into an issue,
reviewed, and reach four Dockerfiles before anything objected.

A byte-identical `tests/test_service_entrypoint.py` now exists in all four. It uses
`runpy.run_module(..., run_name="_entrypoint_probe")` — verified: the module body executes
with correct package context while `run_name != "__main__"` keeps the `__main__` block inert,
so the test never starts a server. It asserts three things, and **two of them are static, so
they run in the fast lane with no service dependencies and no Docker**: that the `api`
entrypoint does not hardcode a port, and that the `__main__` block reads `PORT`/`HOST`/
`GRACEFUL_SHUTDOWN_S` from the environment. Confirmed failing on both regressions it exists
to catch, in 0.14s:

```
A) ENTRYPOINT ["uvicorn", …, "--port", "8000", …]  -> "the `api` stage hardcodes the port…"
B) ENTRYPOINT ["python", "service/api.py"]          -> "expected the `api` stage to launch the module…"
```

That is the fast-lane counterpart to the container probe in Finding 4 — same regression,
milliseconds instead of 5.5 minutes.

### Finding 9 — 🆕 exactly one of five frontends misroutes, and it is not an obvious one

`page-classification/service/frontend/script.js:99` read:

```javascript
const baseUrl = window.location.origin.includes('localhost') ? 'http://localhost:8000' : '';
```

Served from the API itself on `localhost:9000`, that still POSTs to `:8000`. The other four
frontend files are **correct as written** and were left alone: alto's two and pc's
`frontend-lindat` redirect only when the page is on a known dev-server port (`8080`/`5500`),
so a page served from the API uses `window.location.origin` and follows `PORT` automatically.
nlp-enrich's two use a relative path and never had the problem. The fix brings the one
outlier into line with its own siblings rather than inventing an idiom.

### One correction to Finding 5

The `__spec__` rule is gated on `reload`, not applied whenever `__spec__` exists:
`_app_ref = f"{__spec__.name}:app" if reload and __spec__ is not None else app`. Passing an
import string under `-m` re-imports the module while it is already running as `__main__` —
the body executes twice and uvicorn serves the second copy. Gating on `reload` means the
container (RELOAD off by default) takes the object path and never double-imports, while
`--reload` still works for the one case that genuinely requires a string. Same decision,
without its only cost.

## ⏳ Open
- **App reference form — object, string, or `__spec__`?** Recommend the `__spec__` rule (Finding 5): one identical block in all four repos, `RELOAD` works in the container, and page-classification's documented `python3 api.py` keeps working without being a special case. The plain 3-string-plus-1-object split the issue implies is the fallback if reviewers find `__spec__` too clever — at the cost of leaving `RELOAD` a dead knob in page-classification, which is the exact bug class this issue exists to close. **Not decided.**
- **Does alto change too?** Its `__main__` keeps `"text_api:app"` under the `__spec__` rule only if left alone — its entrypoint is a *path*, not a module, so `__spec__` is `None` there and the rule would silently disable its working `RELOAD`. Recommend leaving alto's block untouched (it is green, and #58's code scope is the four). The five then share the *pattern* — env-honouring `__main__` — not the literal line, which is what the issue title actually asks for. **Worth one sentence on the issue so it is not read as drift.**
- **Should `EXPOSE 8000` stay?** It is metadata only; `-p 9000:9000` works regardless. It matters for `docker run -P`, which nothing here uses. Recommend leaving it and stating in the manifest comment that it tracks the *default*, not the effective port.
- **`ENV PORT=8000` vs. code default.** The issue asks for both (`ENV` in the Dockerfile, `os.getenv("PORT", "8000")` in code). That is deliberate redundancy — the `ENV` makes `docker inspect` self-documenting and gives `healthcheck.py` a value even if the code default drifts. Keep both, as alto does.
- **nlp-enrich's `api` stage has no `CMD []`** (`Dockerfile:62` goes straight to `HEALTHCHECK`) while the other four declare it. Inherited `CMD` is reset by `ENTRYPOINT` in the same stage, so behaviour is identical — cosmetic, worth one line while the file is open.
