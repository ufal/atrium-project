# Digest — Issue #72: Production architecture, dependency and release hardening

> Issue [#72](https://github.com/ufal/atrium-project/issues/72) · Labels: `dependencies`, `development`, `enhancement` · **Status: 🟡 OPEN**
> _Prepared 2026-09-30 from the ATRIUM CZECHIA NER grounding report and the current hub issue state._

## Context

Issue #72 is the project-level cleanup required to turn the current ATRIUM tool set into a stable production service set. The
grounding report treats this as an S2 pilot concern: one production service per stage, governed shared layers, research kept
off the production release line, the undeclared AGPL dependency removed from page-classification, licence declarations
corrected, and immutable release handling completed.

The important boundary is that most of the generic service contract work is already established elsewhere. Since 28 September
the tools have typed request/response models, a common error model with stable reason codes, configurable limits exposed
through `/info`, and per-release `openapi.json` comparison. Eight shared contract modules are already byte-identical and
checked by `para-drift`. The remaining architectural concern is the larger duplicated implementation between `nlp-enrich`
and `llm-enrich`.

The release side is similarly partly converged. Branch-protection and immutable-release rules have been accepted as the
target, but immutable releases are not yet enabled. The GPU runner remains a separate infrastructure item and is explicitly
deferred from the pilot.

## What the grounding decision settles

### One production service per processing stage

The pilot architecture is not a single monolithic image and not a runtime orchestration layer embedded in the tool repositories.
The target is one production service for each stage:

- page-classification
- alto-postprocess
- nlp-enrich
- translator
- llm-enrich
- `api-digital`

Shared concerns become governed layers rather than independently diverging implementations.

### Three shared layers

The agreed shared architecture has three specific cross-service concerns:

1. one document reader;
2. one LLM engine/client;
3. one versioned vocabulary artifact.

The shared copies must be governed by the existing `para-drift` mechanism rather than left as informal synchronized duplicates.

### `nlp-enrich` / `llm-enrich` boundary

`nlp-enrich` should drop its separate LLM stage and vocabulary implementation. `llm-enrich` remains the LLM-specific production
stage, while research/benchmark code stays outside the production release line.

This is a release-architecture cleanup, not a request to eliminate experimental LLM work from the repository.

### Dependency and licence corrections

Page-classification's current `PyMuPDF` dependency is not acceptable under the agreed production licence posture because it
introduces AGPL-licensed code not declared by the component. The selected direction is `pypdfium2`, subject to the documented
label comparison.

The AMČR vocabularies and TEATER are CC0. The translator already reflects that decision; `nlp-enrich` and `llm-enrich` still
need their declarations corrected. The `flexiconv` licence is an upstream confirmation item rather than a licence assumption.

### Release trust boundary

ARUP-CAS forks are treated as pure mirrors of trusted upstream releases. The processing repository performs the actual trust
gate: contract tests, security/licence scans, and a diff review against the previous trusted release including the committed
`openapi.json`.

That makes immutable upstream releases important even though the pilot can currently protect itself with its own downstream
trust tags.

## Remaining work / decision boundary

1. Complete the shared-layer architecture without introducing a new cross-repository package that would create a second
   governance mechanism.
2. Remove the duplicate LLM/vocabulary implementation from `nlp-enrich` while preserving its current non-LLM enrichment
   responsibilities.
3. Keep research/benchmark code in `llm-enrich` outside production images and release artefacts.
4. Replace `PyMuPDF` in page-classification and record the dependency/licence comparison.
5. Correct the CC0 declarations in `nlp-enrich` and `llm-enrich`, and record the `flexiconv` upstream licence result.
6. Apply branch protection and enable immutable release tags/releases.
7. Keep the external GPU runner out of this issue's completion criteria; it remains infrastructure work tracked separately.

> **Not a blocker here:** the common typed API/runtime contract is already tracked by #32, limits by #53, health/SIGTERM by #55,
> and `$PORT` handling by #58. #72 should consume those baselines rather than reopen them.

## Grounding notes

The S2 baseline says the production core of each tool is the endpoint AMČR calls, its record hook, and its paradata. Everything
else remains experimental and off the release line. The architecture cleanup in this issue therefore exists to make that
production core small, repeatable and auditable rather than to absorb every existing experiment into the service images.
