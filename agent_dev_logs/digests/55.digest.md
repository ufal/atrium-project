## ✅ What's settled (this pass)
- **The probe split.** `/health` = liveness, 200 **even while draining**; new `/ready` = readiness,
  503 the instant `SIGTERM` lands. Not cosmetic: a liveness probe that fails during a graceful
  shutdown gets the pod `SIGKILL`ed before the drain finishes, which is this issue's own failure
  mode moved one layer up. Keeping shallow `/health` byte-identical is also what leaves the five
  existing `test_health_shallow_ok` assertions and `skill-validate.reusable.yml`'s live probe
  untouched.
- **Signal chaining, verified empirically.** `serve_lifecycle` installs a `SIGTERM`/`SIGINT` handler
  that flips `draining` and then **calls the previously registered handler**. Against a real uvicorn
  0.52 subprocess, that previous handler is uvicorn's own `Server.handle_exit` — chaining is what
  keeps uvicorn's drain working; replacing it would break shutdown outright.
- **Exit code 143 is the correct clean exit**, not 0. uvicorn's `capture_signals()` deliberately
  re-raises the captured signal after a graceful shutdown so a supervisor sees the real cause. The
  CI assertion and the docs say 143; asserting 0 would have been asserting the wrong contract.
- **One implementation, five repos.** Everything service-side lives in the canonical
  `docs/templates/shared/atrium_service.py` (+ new `healthcheck.py`), re-vendored byte-identically
  and enforced by `para-drift.reusable.yml`.
- **Already merged**, not sitting on a local branch — see 🔎 below for the landing commits.

## 🔎 What measuring the repos actually found (2026-09-07 pass)
The two claims in the issue body were both true. Five further findings, in the order they matter:

1. **Kubernetes never reads a Docker `HEALTHCHECK`.** The kubelet's probes are pod-spec fields,
   independent of the image directive. So `HEALTHCHECK` alone could not make `/health` "visible to a
   Kubernetes liveness probe" — the partner-facing half had to be a probe contract plus a reference
   manifest (`docs/k8s_deployment.md`, `docs/templates/k8s/atrium-service.deployment.yaml`).
2. **Four of five services had no runnable API image.** Only nlp-enrich published one. alto,
   translator and pc reached FastAPI only via a compose `entrypoint:` override on the *batch* image;
   llm-enrich's `api` stage was declared but never built (roadmap **B5**). With the handoff boundary
   fixed at "a Docker image, run at their own Kubernetes" (#40, motyc), **there was nothing for
   ARÚP/ARÚB to pull** — the acceptance criterion was unreachable by configuration.
3. **A request counter cannot see the work that actually gets killed.** nlp-enrich's `POST /jobs`
   returned `queued` and left the job in a bare `asyncio.create_task(...)` with the result
   discarded. The request was long gone while the job ran, so uvicorn saw nothing in flight and
   exited — the issue's own sentence, exactly, and untouched by `--timeout-graceful-shutdown`.
   Fixed with `ServiceState.track()`, which the drain awaits (and which also retains a task
   reference that was previously GC-eligible even with no shutdown involved).
4. **Three services blocked the event loop**, so shutdown could not work at all there. pc, alto and
   translator called blocking inference inline in `async def` handlers; uvicorn's signal handler is
   an event-loop callback, so it could not run until the request returned. Moving those to
   `asyncio.to_thread` was a prerequisite, not a cleanup.
5. **nlp-enrich's shallow `/health` spawned a subprocess on every probe** — `run_pipeline.py
   --dry-run`, called before the `deep` check, from an `async def`, with no `timeout=`. Aiming a
   30s-interval `HEALTHCHECK` at it would have meant a subprocess and a loop stall every interval.
   Converged onto the shared `attach_health` with the dry-run behind `?deep=true` and bounded.
