**Status**: 🔴 **Open — and far cheaper than it reads.** The verification pass found that **three of the four overrides are exact no-ops**: they replace each image's real `ENTRYPOINT` with a command identical to it. The fourth exists only to host the `pip install`. Removing all four is nearly free once alto#50 lands.

## 🎯 Goal
`.github/workflows/e2e-pipeline-smoke.yml` replaces the entrypoint on every stage but one, so no Dockerfile `ENTRYPOINT` is exercised in the ecosystem's only end-to-end lane — and one stage `pip install`s a dependency **inside the published image at run time**, overriding a commit pin with a moving `master`.

**The headline.** Stages 3, 4 and 5 override the entrypoint with a command byte-identical in effect to the entrypoint they override. They cost nothing at runtime and everything in assurance: the lane *reports* that it never exercises a real entrypoint, and in three cases it silently does. Deleting `--entrypoint python` from those three lines changes no behaviour and makes the lane honest — and it means "retire the entrypoint overrides" is not a project, it is three deletions plus whatever alto#50 decides.

Stage 1 is proof: page-classification has run for the life of this workflow passing arguments straight through to `ENTRYPOINT ["python3", "/app/entrypoint.py"]`, with no override at all.

## 🔎 The B9 breakage itself (owned by alto#50)

`:274`, inside Stage 2, against the already-published image:

```
pip install https://github.com/cneud/alto-tools/archive/refs/heads/master.zip
```

`atrium-alto-postprocess/setup/requirements.txt:8` pins `alto-tools @ git+…@1f4f01e5f6ac3562740e39948442973b9cb94be4`, and `alto/Dockerfile:38` installs that file at build time. So the lane overrides a commit pin with a moving ref, in the release artifact, at the moment of testing it. Whatever the E2E proves, it is not a property of the published image.

Root-cause hypothesis worth testing before anything is deleted: the build-time install runs as root (`USER atrium` only at `alto/Dockerfile:79`), so the console script lands in `/usr/local/bin`; the runtime patch installs `--user` into `/home/atrium/.local/bin` and re-exports `PATH` to reach it. The workaround may simply be stale. First command: `docker run --entrypoint alto-tools ghcr.io/ufal/atrium-alto-postprocess:<tag> --version`.

## ⏳ Open
- **Does the E2E lane still pass with the real entrypoints?** Three are no-ops, so yes by construction — but that is an argument, not a run. The change is cheap enough that the run is the proof.
- **Stage 2's `-w` working directory.** Every stage sets `-w /workspace/work/atrium-<tool>-main` (a fresh checkout), not the image's `/app`. That is a second, subtler build/release/run gap: the lane runs the image's *interpreter* against the *repository's* source, so a code change that never reached the image still passes E2E. Not in this issue's scope, worth a follow-up, and it is the reason the entrypoint overrides looked harmless for so long.
- **`docker-build-smoke` is the proven mechanism** (#55's `load: true` + `probe-targets`) and already starts these containers. Whether the E2E lane should move to it, or simply stop overriding, is undecided.
