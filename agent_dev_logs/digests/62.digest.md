## 🔒 What made the deletions safe — and it is not "they're no-ops"

"Identical by construction" is an argument. Two things turned it into evidence:

**1. The published images were checked, not the source.** This lane defaults to `image-tag: latest` — **the last release of each tool, not `test`** (see the workflow's own header note). So reading `Dockerfile` on `test` proves nothing about what the lane will actually pull. Checked at each repo's newest release tag before landing:

| Repo                | Newest tag | `ENTRYPOINT` at that tag        |
|---------------------|------------|---------------------------------|
| `atrium-translator` | `v0.10.5`  | `["python", "main.py"]`         |
| `atrium-nlp-enrich` | `v0.20.1`  | `["python", "run_pipeline.py"]` |
| `atrium-llm-enrich` | `v0.6.3`   | `["python"]` (`remote`)         |

All three match. This was the single way the change could have broken, and it is the check the "three no-ops, delete them" framing would have skipped.

**2. The duplicated script name.** With the interpreter forced as the entrypoint, `main.py` was argv[1] **to Python**. Without it, `ENTRYPOINT ["python", "main.py"]` already supplies the script, so leaving `main.py` in the command passes it as an argument **to `main.py`**. Stages 3 and 4 drop the script name along with the override; Stage 5 **keeps** `openrouter_client.py`, because llm-enrich's `remote` entrypoint is the bare interpreter and the script really is its first argument. Invisible to YAML linting, invisible to the new guard — only a run catches it, which is why the run is still the open item.

## 🛡️ The guard — `tests/test_e2e_entrypoints.py` (new)

Picked up for free by `hub-self-check.yml`'s existing `shared-tests` job. Two structural assertions over every hub workflow:

1. **No step's `run:` body overrides a container entrypoint**, unless the `(workflow, step)` pair is declared in an `ALLOWED_OVERRIDES` map *with a reason*. Empty today. This is the issue's own sentence — *"where it genuinely cannot, say why in a comment rather than leaving a silent override"* — in a form CI reads.
2. **No `docker run` command installs a dependency at run time.** The B9 defect itself, matched per logical line so a legitimate runner-side install in the same step is not implicated.

Plus a third test asserting the E2E lane is actually among the files scanned and still has five stages — without it, renaming the workflow would leave both checks passing vacuously.

**Parsed with PyYAML, not grepped**, so the long comment blocks explaining what was removed are not themselves offences. Both checks were confirmed **red** against purpose-built breakage — including the verbatim historical Stage 2 shim — before being trusted.

**Why this replaces the issue's literal grep.** `grep -c "pip install" == 1` is brittle in both directions: red the day someone adds a second legitimate runner-side install, and green if that one line ever moved *into* a container command. The structural form cannot be satisfied by accident. The count is still 1, and still the fastest way to eyeball the file.

**A trap worth recording**: `grep -c -- "--entrypoint"` counts **comments too**. The new and existing comment blocks deliberately say *"entrypoint override"* and never spell the flag, so the file can document itself without breaking its own acceptance criterion.

## 🔭 The successor finding — deliberately not folded in

**Every stage still runs the image's *interpreter* against a *fresh checkout*.** Each `docker run` sets `-w /workspace/work/atrium-<tool>-main`, an `actions/checkout` of the tool's default branch, rather than the image's `/app`. A source change that never reached the published image still passes E2E. Same class as B9, other axis, arguably larger.

It is also **why the overrides looked harmless for so long**: with `-w` pointing at the checkout, the forced interpreter and the real entrypoint resolved the same relative script, so nothing ever misbehaved.

This round is a prerequisite for closing it, not a partial fix — once `-w` goes, `ENTRYPOINT ["python", "main.py"]` resolves `/app/main.py`, which is the desired end state. **Needs its own issue.** Likewise undecided: whether the lane should migrate onto `docker-build-smoke`'s proven `load: true` + `probe-targets` mechanism (#55) instead of pulling published tags at all.
