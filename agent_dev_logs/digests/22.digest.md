## 🔬 Open questions, researched (11-04)

### OmniDocBench, checked at the source

The June review cited the paper. This is the benchmark as it stands today ([GitHub](https://github.com/opendatalab/OmniDocBench) README; the paper's evaluation section for the ignore rules):

| Topic              | Fact                                                                                                                                                                         | For #22                                                                                     |
|:-------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------|
| Version            | v1.7 (2026-04-30); 1,651 pages, 10 document types                                                                                                                            | Pin a v1.7 commit in the gold bundle                                                        |
| Licences           | Code Apache-2.0. Data "for research purposes only and not for commercial use"                                                                                                | The evaluator can run pinned or be vendored. Its data stays context only, in no deliverable |
| Gold, per element  | `category_type`, `poly` (4 corners), `order`, `anno_id`, `ignore`, `attribute`, `line_with_spans`, `merge_list`, and `text`, `latex` or `html`                               | Usable as is; ATRIUM additions (`script`, a region subtype) fit in `attribute`              |
| Gold, per page     | `page_info`: `page_no`, `width`, `height`, `image_path`, `page_attribute`                                                                                                    | `page_attribute` can carry the quality tier and the page-classification label               |
| Relations          | `extra.relation` links elements by `anno_id`, e.g. a caption to its figure or table                                                                                          | Keeps a caption bound to its figure (Alfie, 07-22) without a record schema                  |
| End-to-end input   | One Markdown file per page image, same name. Matched with `quick_match` (adjacency search; hybrid in v1.5, MGAM in v1.6)                                                     | The same as "models answer in Markdown" (10-29)                                             |
| End-to-end scores  | Text: NED (+ BLEU, METEOR). Tables: TEDS + NED. Formulas: CDM. Reading order: NED. Overall = ((1 − text NED) × 100 + TEDS + CDM) / 3                                         | Report the components. Overall includes formulas, which our pages rarely have               |
| Ignored in scoring | Headers, footers, page numbers, page footnotes and captions take part in matching but are not scored. Reading order counts text only: no tables, figures or ignored elements | Check 1 needs a second, all-element number (below)                                          |
| Layout detection   | COCO-style mAP/mAR over 10 classes. Header, footer, page number and page footnote map to `abandon`                                                                           | The secondary score for check 3                                                             |

**What this means for "MD vs JSON":** if the gold uses OmniDocBench's exact page JSON, its pinned evaluator scores a model's Markdown against it for text, tables and reading order. We do not need to write that part. Our own Markdown → JSON parser shrinks to what OmniDocBench does not score from Markdown: regions (check 3) and key-value fields (check 4), plus the round-trip test on `json_to_md`. `eval_metrics.py` keeps the CER/WER-by-tier view, which OmniDocBench does not report.

### Scoring per check, refined

| Check        | Refined proposal                                                                                                                                                                                        | Why                                                                                                                                                                                         |
|:-------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1. Order     | Two NEDs: (a) OmniDocBench's text-only order, comparable with public results; (b) an ATRIUM all-element order over text, titles, tables, figures and captions, without header/footer                    | (a) alone drops the order of figures and captions, which matters in excavation reports                                                                                                      |
| 3. Regions   | **Primary:** per-type presence/count P/R/F1 per page, and the error of each type's area share (area ÷ page area). **Secondary:** P/R at IoU ≥ 0.5 and COCO mAP, only where the output carries boxes     | The body asks for "presence of specific types and their area sizes", not localisation. A model's Markdown often names a figure without a box                                                |
| 4. Key-value | Field P/R/F1 on exact (key, normalised value); [ANLS\*](https://github.com/deepopinion/anls_star_metric) ([arXiv:2402.03848](https://arxiv.org/abs/2402.03848)) as the fuzzy score; a per-key breakdown | ANLS\* extends DocVQA's ANLS to dictionaries and lists from generative models. It penalises missing and invented keys, and equals ANLS where both apply. Check its licence before vendoring |

**Text-input runs and check 3.** A model given Markdown sees figures only as `![figure]` placeholders. These come from `xml_to_md` on the ALTO path; `json_to_md` writes none, because the record has no figures. At `minimal` the placeholders carry no box. For those runs, check 3 only asks whether the placeholders survive. Regions proper are scored on image-input runs and on the baseline's ALTO boxes.

**Code note for the parser:** the docstring of digital-convert's `layout_md.image()` (`api_util/layout_md.py:383`) says `BBOX: [x,y,w,h]`, but the function emits corner boxes `[x_min, y_min, x_max, y_max]` (`bbox()` just above it; `_alto_box`, `xml_to_md.py:124`). A parser that computes areas must read corners. The docstring needs a one-line fix in digital-convert.

### Region types: the 10-29 list, revised

Handwriting is a script, not a region. page-classification's labels already keep three axes apart: graphics (`DRAW`, `PHOTO`), script (`_HW`, `_P`, `_T`) and tabular layout (`LINE`, `_L`) (its `docs/reference/categories.md`). With the script as an attribute, the axes stay apart, and a page's label can be checked against its regions: if every text region is handwritten and none is tabular, the page is `TEXT_HW`.

| Type (proposed)                     | `script` attribute | OmniDocBench                      | DocLayNet                | Record today                                  | page-classification      |
|:------------------------------------|:------------------:|:----------------------------------|:-------------------------|:----------------------------------------------|:-------------------------|
| text                                | yes                | `text_block`                      | Text, List-item          | every line on the ALTO path                   | `TEXT*`                  |
| title                               | yes                | `title`                           | Title, Section-header    | `style.heading_level` (digital-convert)       | —                        |
| table / form                        | yes                | `table` (`html`)                  | Table                    | `tables`, `forms`                             | `LINE_*`, `_L`           |
| photo                               | —                  | `figure`                          | Picture                  | —                                             | `PHOTO*`                 |
| drawing / map                       | —                  | `figure`                          | Picture                  | —                                             | `DRAW*`                  |
| caption                             | yes                | `figure_caption`, `table_caption` | Caption                  | —                                             | —                        |
| header / footer (incl. page number) | yes                | `header`, `footer`, `page_number` | Page-header, Page-footer | `style.region` = `page_header`, `page_footer` | —                        |
| footnote                            | yes                | `page_footnote`                   | Footnote                 | `style.region` = `footnote`                   | —                        |
| stamp / label                       | yes                | — (ATRIUM extension)              | —                        | —                                             | — (#58's "OCRed labels") |

- **Against the 10-29 list:** handwriting becomes an attribute, `footnote` is added (the record, OmniDocBench and DocLayNet all have it), and page numbers go with header/footer. Still nine types.
- **"Label"** means a physical tag or sticker on a find or a box, as in page-classification#58. It is not the `_L` suffix, which means a table-like layout.
- **Comparability:** photo and drawing/map collapse to `figure` / Picture for public numbers.
- **Baseline coverage:** the born-digital baseline can be scored on title, header/footer and footnote (`style.*`). On the ALTO path these come out n/a, and figures are untyped `Illustration` / `GraphicalElement` boxes.
- **HTR ecosystem:** SegmOnto, the vocabulary used with eScriptorium/Kraken (the TuzkaOCR context of 06-26), also types zones by form rather than content, keeps zone and line types apart, and has a stamp zone. Its zone list could not be fetched from this session; compare before freezing.

## 🧩 MD vs JSON: a proposal for the open question

- **JSON is the gold and the scoring format; Markdown is what models emit.** That is how OmniDocBench works. Its ground truth is page JSON (per element: category, polygon, reading-order index, text, tables as HTML), and its end-to-end evaluation matches one Markdown file per page against that JSON. _Checked against v1.7 on 11-04 (section above)._
- **Record → Markdown exists**: `api_util/json_to_md.py` renders the record as a pure function at three detail profiles (digital-convert `docs/reference/markdown.md`). **Markdown → JSON exists nowhere** in the seven repositories.
- **The gap for "interchangeable"**: `json_to_md` writes GFM tables. Merged cells need HTML tables (Alfie, 07-22). The record can already hold them (`rowspan`/`colspan`), but the renderer cannot write them.
- **Proposal**:
  - gold in OmniDocBench-style page JSON, plus a key-value sidecar for forms;
  - a converter record → gold-format JSON to score the baseline;
  - OmniDocBench's pinned evaluator to score model Markdown for text, tables and reading order (refined 11-04);
  - a benchmark-side parser only for what that evaluator does not score: figure placeholders and typed regions, and key-value lines, with the round-trip test on `json_to_md` output.
  - The record schema stays as it is; a regions block would take the additive route described above (#71 is closed). An HTML-table option for `json_to_md` would be a digital-convert proposal.

## 🧪 Groundwork already present

- **Sampling**: `sample_stratify.py` sorts pages into `clean` (`avg_quality_score` ≥ 0.85 and valid-line ratio ≥ 0.50), `degraded` (≥ 0.60), `hard` (< 0.60) and `text_poor` (no scoreable lines). Seed 42, roughly equal draws per tier, 80/10/10 split per tier.
- **Scoring**: `eval_metrics.py` has CER, WER, NED, micro entity P/R/F1 on (type, normalised surface) and an optional TEDS hook. `bench_compare.py` turns `<doc>/<doc>-<page>.txt` prediction folders into byte-identical page, tier and Markdown reports, and counts missing pages for each model.
- **Representation cost**: `--detail full|standard|minimal`. The lines are identical across profiles; only the cues change. Characters saved compared with `full` (`scripts/detail_budget.py`, digital-convert `docs/reference/markdown.md`):

  | Input                      | `standard`    | `minimal`     |
  |:---------------------------|--------------:|--------------:|
  | the two hub E2E ALTO scans | −35 % / −53 % | −52 % / −64 % |
  | the two PDF fixtures       | −30 % / −41 % | −52 % / −53 % |
  | the DOCX fixture           | 0 %           | −1 %          |

  These are size measurements, not quality results.
- **Complex-layout evidence**: Docling ran on Dana's 15 AMČR PDFs ([digital-convert#5](https://github.com/ufal/atrium-digital-convert/issues/5)). On 10-19, digital-convert's reader found 1,217 headings against Docling's 1,597, and more than Docling in three reports. These are counts, not quality scores.
- **Leak guard**: the renderer never reads `enrichment`, so a model is not shown an earlier answer.
