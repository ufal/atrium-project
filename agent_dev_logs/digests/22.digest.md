## 🔄 What changed since the previous #22 refresh

The September/October repository split changes #22 from a broad “where should all LLM/DU code live?” issue into a **benchmark/evidence issue over the current architecture**.

Three boundaries are now explicit:

1. **OCR model evaluation is not #22.** `olmOCR` and `archivatorium` were removed from this benchmark scope; `olmOCR` is to be considered in AMČR's backup-OCR evaluation, while the maintained OCR stage is now [`atrium-ocr-postprocess`](https://github.com/ufal/atrium-ocr-postprocess).
2. **Complex-layout parser bake-off is not #22.** The Docling/MinerU work now belongs to [`atrium-digital-convert#4`](https://github.com/ufal/atrium-digital-convert/issues/4), in its dedicated W7 / complex-layout phase. #22 may consume the resulting evidence, but should not duplicate that implementation or decision.
3. **The Markdown detail/token-cost bake-off remains in #22.** The `full` / `standard` / `minimal` representation comparison was implemented in the former LLM stack and is now present in `atrium-digital-convert/test` as part of the repository migration. Its **cost half is measured**; its **quality half still needs the real gold set**.

The result is a much narrower and cleaner question:

> **After the pilot, on a representative in-domain archaeological gold set, what do out-of-the-box document-understanding models actually deliver versus the established deterministic/OCR+NLP pipeline, and what representation detail is justified by the measured quality/cost trade-off?**

The issue no longer needs to decide the production repository layout, the OCR engine, the complex-layout parser, or the location of the keyword service.

## 🧩 Canonical representation after the repository split

The current code makes one point especially important for #22: **there is no longer a reason to treat Markdown as the system of record.**

The established data path is:

```text
source / OCR / born-digital input
          │
          ▼
   atrium_document JSON
          │
          ├── deterministic NLP / TEITOK projection
          ├── keyword-extract
          └── optional Markdown projection for model input
```

The record is the canonical integration object. Markdown is a derived, regenerable model-facing representation.

Current `atrium-digital-convert/api_util/json_to_md.py` explicitly:
- uses the same cue vocabulary as the TEITOK/ALTO/PDF/DOCX front-ends;
- renders the same source lines for `full`, `standard` and `minimal` profiles and drops only selected layout cues;
- preserves page ordering and page labels, including non-numeric labels when the record carries a page index;
- can omit lines already judged untrustworthy through the shared `Garbage` / `Inverted` / `Trash` semantics;
- **does not read `enrichment`**, deliberately preventing a second LLM run from seeing its own previous answer.

That last rule is important for the benchmark: **entities, keywords and other prior semantic outputs are record data, not hidden prompt context.** The gold evaluation must therefore compare a candidate model with the source record/gold set, not with a pre-enriched Markdown projection that has already leaked the answer.

## 🧪 Benchmark groundwork that is already present

### Stratified sampling

`atrium-digital-convert/sample_stratify.py` now implements the original #22 sampling idea using the per-page statistics produced by the OCR/text-quality path.

Current default tiers:

| Tier        | Current definition                                                                                      |
|:------------|:--------------------------------------------------------------------------------------------------------|
| `clean`     | `avg_quality_score >= 0.85` and valid-line ratio (`Clear + Noisy`) >= 0.50                              |
| `degraded`  | `avg_quality_score >= 0.60` but below `clean`                                                           |
| `hard`      | scored pages below `0.60`                                                                               |
| `text_poor` | no scoreable `Clear`/`Noisy` text (`avg_quality_score` absent) — the explicitly difficult/VLM-only tail |

The sampler is deterministic with a seed (`42` by default), allocates roughly equal numbers across present tiers, and then applies an 80/10/10 train/dev/test split per tier. This is inspired by the page-classification methodology but is a separate benchmark sampler; it should not be described as reusing the page-classification dataset split itself.

### Scoring

`atrium-digital-convert/eval_metrics.py` provides the current #22 scoring primitives:

- CER;
- WER;
- normalized edit distance;
- micro entity precision/recall/F1 over `(type, normalized surface)` tuples aligned with CNEC/TEATER conventions;
- optional TEDS table scoring, with the table scorer intentionally kept as an optional dependency.

`bench_compare.py` wraps these into deterministic per-page and per-tier comparison reports. Its prediction convention is deliberately simple: named prediction roots containing `<doc>/<doc>-<page>.txt`, with optional `.entities.tsv` sidecars.

The harness therefore already supports the essential experiment shape:

```text
quality stats
    ↓
sample_stratify.py
    ↓
annotation manifest
    ↓
gold transcriptions + optional entities
    ↓
legacy/current baseline + candidate predictions
    ↓
bench_compare.py
    ↓
page / tier / model metrics + Markdown report
```

### Markdown detail/cost measurement

The representation track now has three profiles: `full` (default), `standard`, and `minimal`.

The existing `detail_budget.py` measurements recorded in the current planning logs show the scale of the possible token/input reduction **in characters**:

| Input family                                  |          `standard` vs `full` |           `minimal` vs `full` |
|:----------------------------------------------|------------------------------:|------------------------------:|
| Two real hub E2E scans                        |         about **−35% / −53%** |         about **−52% / −64%** |
| Digital fixtures                              |            about **−20…−41%** |            about **−52…−63%** |
| DOCX fixtures                                 |                           ~0% |                           ~0% |
| Pilot-shaped ALTO records without bbox/canvas | only the `OCR` cue is dropped | only the `OCR` cue is dropped |

These are **representation-size measurements, not quality results**. The quality side is deliberately waiting for the in-domain gold set.

## 🎯 What #22 should now evaluate

The benchmark should contain three related but separate evidence tracks.

### Track A — Out-of-the-box DU model/tool vs. established pipeline

This is the core of #22.

The benchmark should compare one or more exact-version, reproducible OOTB document-understanding candidates against the current deterministic baseline on the same pages/documents. The previous research named CHURRO-family, Qwen2.5-VL and SmolDocling as candidate examples; those names should be treated as **candidate starting points, not a frozen 2026 model lineup**. The lineup should be re-validated when #22 is reopened.

The baseline should be stated in current-architecture terms. Historically it is the ABBYY ALTO + post-processing + NLP-enrich chain; in current repository terms the maintained baseline is the OCR/text-reader + `ocr-postprocess` quality semantics + `nlp-enrich` TEITOK/NLP path, with the shared record as the contract.

### Track B — Model-facing representation detail

Where a candidate consumes rendered Markdown, compare `full`, `standard` and `minimal` on the **same source record and same model/configuration**.

The question is not “which Markdown profile looks nicer”. It is:

> How much layout information can be removed before transcription, structure/ordering, entity or citation performance measurably changes?

The output needs to report both representation cost and task quality. The character reductions above are already known; the missing measurement is the quality delta.

### Track C — Structured semantic outputs

Entity extraction may be included where the candidate actually produces typed entities and the annotation set exists, using the CNEC/TEATER-aligned entity sidecars supported by the harness.

Keyword extraction, however, should not be turned into a second implementation of #73. `atrium-keyword-extract` owns the production keyword service and record block; #22 can report a DU model's semantic-extraction evidence only when it can be scored independently against a gold annotation, without changing that production contract.

## ⚠️ Important migration residue

The current `atrium-digital-convert/test` tree still contains `llm_run.py`, `llm_client_shared.py`, `openrouter_client.py`, `ollama_client.py`, vocabulary builders, benchmark helpers and related documentation inherited from `atrium-llm-enrich`.

This is **not** a new architectural decision. It is migration residue currently visible on `test` while the repository is converging on the born-digital converter role. #72 explicitly makes research code an off-release-line concern and requires one production image per stage. Therefore:

- #22 may continue to use the existing benchmark utilities while they are convenient;
- the production `digital-convert` image must not become the vehicle for the old LLM/DU stack;
- the old `atrium-llm-enrich` repository remains a historical predecessor, not a current owner;
- a future dedicated `atrium-doc-understanding` research repo is optional infrastructure, not a precondition for reopening the benchmark.

## ✅ What is already decided

- #22 is **deferred until after the AMČR pilot**.
- The benchmark requires an **in-domain archaeological gold set**; generic benchmark scores are not enough.
- The existing sampling/scoring harness is substantially implemented.
- The canonical record is `atrium_document`; Markdown is a derived model-facing representation.
- `full` remains the default Markdown detail profile until the quality measurement says otherwise.
- OCR engine competition is outside #22.
- Complex-layout parser selection is outside #22.
- Keyword ownership is outside #22 and belongs to `keyword-extract` / #73.

## ⏳ Remaining / next

1. **Create and annotate the in-domain gold set** after the pilot decision to resume #22. No pages have yet been annotated in the current benchmark workflow.
2. **Freeze the benchmark manifest and annotation protocol** before running any model comparison; keep the sample stratification deterministic and preserve the exact source/record provenance.
3. **Run the established baseline** on the same pages and export predictions in the harness format.
4. **Run the chosen OOTB DU candidates** with exact model revisions/configuration and identical page/document inputs.
5. **Complete the `--detail` quality half** on the same gold material, reporting quality deltas next to the already measured character/input reductions.
6. **Produce the tiered report** (clean/degraded/hard/text_poor; overall; split where applicable) with CER/WER/NED and entity F1, plus TEDS only for the subset that has table gold data.
7. **Record operational evidence**: model revision, inference backend, hardware, context/input settings, runtime/cost proxy and data/weight licence constraints.
8. **Decide only from the measured evidence** whether a heavyweight DU path, lighter Markdown profile, or later fine-tuning/routing work is justified. No production routing change is implied by a benchmark result alone.
