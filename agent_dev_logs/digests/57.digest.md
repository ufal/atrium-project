## Context

Issue #57 was opened on 2026-09-09 against the then-current repository set. Its original scope was to separate repository Markdown documentation into GitHub Pages, include not only the README but meaningful documentation distributed through the repository and the `agent_dev_logs` summaries, and build an interlinked documentation system.

That repository set is now obsolete. The 30 September architecture change recorded in #72 split the former `llm-enrich` implementation, introduced `keyword-extract` as the owner of the keyword/LLM/vocabulary work, moved the born-digital converter to `digital-convert`, and replaced `alto-postprocess` with `ocr-postprocess` as the current OCR stage. The resulting six-stage production layout is page classification, OCR post-processing, born-digital conversion, NLP enrichment, keyword extraction and translation.

The Pages issue therefore needs to be refreshed at the architecture level, not merely by changing a few hyperlinks. A site generated for the old six-repository input list would immediately reintroduce stale repository names, stale navigation, and stale GitHub Pages URLs.

## Existing Pages scaffold

The current `atrium-project` repository already contains the main documentation-site scaffolding: `INDEX.md`, `PAGES_SETUP.md`, `mkdocs.yml` and `docs_site/`, alongside `agent_dev_logs/`. This means #57 should **refresh the existing Pages system** rather than create a second, incompatible documentation framework. citeturn287447view3

The intended model remains an interlinked set of repository sites with a hub-level index. `atrium-project` owns the cross-repository map and common documentation structure; each service repository owns its own technical details.

## Documentation content boundary

The original issue explicitly asks for more than the core README: it calls for `agent_dev_logs` summaries, additional Markdown files spread through the repository, and other meaningful documentation, with an interlinked page system. citeturn761515view3turn761515view4

The refreshed scope should therefore include, where present:

1. Core repository README and contribution/development guidance.
2. `docs/` and service/API documentation.
3. Meaningful root-level Markdown files and runbooks.
4. Curated `agent_dev_logs/digests/*.md` and `agent_dev_logs/plans/*.md` as the project's development-history layer.
5. Release/version history that is useful to readers, while leaving Git tags/releases themselves as the authoritative release record.
6. Explicit architecture and repository-lineage notes for renamed/split repositories.

Generated issue dumps, raw experiment logs and very large machine-generated files should not be copied wholesale merely because they have a `.md` extension; the Pages site is a documentation surface, not a mirror of the entire repository tree.

## Site model

The intended documentation system is:

```text
atrium-project Pages
├── Project overview
├── Current six-stage architecture
├── Repository / service map
├── Shared contracts / schemas / integration
├── Development and release documentation
└── Links to six service sites
    ├── page-classification
    ├── ocr-postprocess
    ├── digital-convert
    ├── nlp-enrich
    ├── keyword-extract
    └── translator
```

Each service site should have the same broad navigation vocabulary where the repository has matching material:

```text
Overview
Architecture / scope
Service or CLI usage
API / integration
Development
Research / experiments (when applicable)
Agent development logs
Releases / version history
```

The navigation should be consistent without forcing repositories that do not have a given section to create empty placeholder pages.

### `atrium-project`

The hub site should be the canonical place for the current repository map, six-stage architecture, common schemas/contracts, release/trust documentation and links to all service sites. It should not duplicate every service README; the service sites remain the detailed source for component-specific documentation.

## Grounding notes

#57 is a documentation-handover task. The current repository reorganisation therefore changes its input set and its navigation graph, but does not change the fundamental requirement from the original issue: documentation must be separated from code-oriented repository browsing into an interlinked, maintained Pages surface, while the repository history and the `agent_dev_logs` material remain traceable.

The refreshed implementation should follow the architecture already established in the hub (`PAGES_SETUP.md` / `mkdocs.yml` / `docs_site/`) and should use the current six-stage repository identities as the navigation baseline. The old `alto-postprocess` and `llm-enrich` identities remain useful only as historical lineage where the code/documentation actually originated there.
