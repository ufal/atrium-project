## 🎯 Goal
Turn the ecosystem's markdown into six published GitHub Pages sites — one per repository — drawing
on README content, the documentation scattered through non-obvious folders, and a per-repo
`agent_dev_logs` summary, and wire them together as one interlinked system rather than six
unrelated sites.

## 🔎 What's already known (surveyed against the tree, not from this thread)

**The corpus is large and badly reachable.** ~2.9 MB of markdown across 6 repos, effectively
navigable only by scrolling a README or browsing the file tree.

**Six structural findings that shape any solution:**

1. **The READMEs cannot simply be rendered.** `alto-postprocess`'s `## 🛤️ Workflow Stages` is 41 KB
   — **78 % of its README** — and nests five heading levels; `nlp-enrich`'s LLM-enrichment section
   is 30 KB. Meanwhile `llm-enrich`'s README is already flat (16 `##`, none over 7.4 KB). A single
   uniform split rule fits none of them.
2. **Every CONTRIBUTING is mostly one table.** `## 📦 Release History` is **56–81 %** of each file
   and is a *single* markdown table with cells 728–1,335 characters wide (alto: 42 rows, 56 KB).
   Rendered verbatim it is one unreadable, horizontally-scrolling page.
3. **Footnotes are defined only at EOF** — 30 in nlp-enrich, 19 in page-classification, 9 in alto
   (numbering skips `[^3]`), 8 each in translator and llm-enrich. Any split orphans every `[^n]`
   reference in the file.
4. **77 relative links and 9 anchor-bearing links** cross file and directory boundaries. Some are
   *already* broken: `alto-postprocess/service/README.md` links `../README.md#composite-quality-score`,
   but that section moved to `docs/categorization_logic.md`. Emoji headings make GitHub's slugs and
   a generator's slugs disagree, so anchors need an explicit map, not a convention.
5. **Four files are byte-identical between nlp-enrich and llm-enrich** (`prompts/RUNBOOK.md`,
   `data_samples/vocab/RUNBOOK.md`, and two decision packages), and the CONTRIBUTING middle
   sections are near-identical across all five tool repos (`🔁 Contributor Workflow` is 413 B in
   four of them). Publishing each copy separately would re-create the duplication that every
   CONTRIBUTING's own "Repository Documentation Management" rule forbids.
6. **Not all of it is publishable.** `docs/arub-p_contacts.md` is a bare list of **personal email
   addresses of named ARÚP/ARÚB partners**; `plan_repo_review.md` carries the maintainer's personal
   email; two `nlp-enrich` decision packages are open memos addressed to named individuals;
   `llm-enrich/digital_born/README.md` calls itself a "Phase 0 exploration scratch space"; and
   `tools/quality_model/EXPERIMENTS.md` is an unfilled results table. Exclusion has to be an
   explicit, tested step — not a judgement call made once and forgotten.

**Scope settled with the maintainer this session:** READMEs and CONTRIBUTING files stay
full-length and canonical (the sites are *additive*, nothing moves); `agent_dev_logs` contributes
**one hand-written summary page per repo**, not 44 digest pages; the generator is **MkDocs
Material**, deployed by a hub reusable workflow with a thin caller per repo; and each site
publishes from its repo's default branch, with `test` pushes building but never deploying.

**The design consequence** of "nothing moves" is that pages must be *derived* at build time rather
than authored: a hub-canonical assembler slices the untouched sources into pages on every build,
so the split can never drift from the README it came from. That is the core of the plan.
