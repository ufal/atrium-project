## 🎯 Goal

The durable goal of #51 is narrower than the original issue wording:

> **Use SKOS semantics internally to reconcile ATRIUM-authored controlled labels with AMCR/TEATER source concepts, while preserving the sources' own identifiers and making no premature publication/namespace commitment.**

The internal SKOS layer answers four questions that ordinary string fields could not answer safely:

1. which controlled labels exist and which repository/stage owns them;
2. which ATRIUM labels are merely facets or collections rather than hierarchy;
3. which source concepts have real source URIs and external mappings;
4. which relationships are exact identity mappings versus broader, related or merely cited information.

The issue is **not** the place to decide vocabulary content governance, train a new model, or publish a DARIAH vocabulary.

## ✅ What is already settled / built

### 1. Namespace policy

**No DARIAH namespace request is pursued from #51.** The future publication namespace/PIDs belong to the wider SKOSification project. Current AMCR and TEATER concepts keep their source identifiers.

ATRIUM-authored concepts use one swappable base:

```python
SKOS_BASE = "https://w3id.org/atrium/"
```

The registry and current docs deliberately avoid minting an ATRIUM URI for a harvested AMCR/TEATER concept. This is the key design property that makes the future PID handover cheap: a source term already has the identifier it should retain.

Registering the `w3id.org/atrium` redirect is optional and does not block the pipeline. It is an identifier/dereferenceability matter, not the namespace request rejected by @motyc.

### 2. Hub-canonical ATRIUM registry

`atrium-project/docs/templates/shared/atrium_vocab.py` is the canonical registry for ATRIUM-authored controlled labels and their SKOS representation. The current strategy's self-test records **6 schemes, 64 concepts, 5 collections and 75 mappings**.

The registry covers the cross-repository contract surfaces such as:

- 11 page categories;
- 7 line categories across two authorised originators;
- quality bands;
- entity-type/CNEC mappings;
- ATRIUM's 11 harmonisation themes;
- collection/facet membership where a category can belong to multiple orthogonal dimensions.

The page-classification and OCR-postprocess trees now explicitly carry the registry so these values are not merely duplicated prose.

### 3. Source vocabulary SKOS view

The vocabulary build already serialises the harvested AMCR+TEATER source concepts into a deterministic `union.skos.ttl` artifact. Current documentation records:

- **1,460 AMCR concepts** and **4,134 TEATER concepts**;
- **707 `skos:exactMatch` URIs on 668 AMCR concepts** captured from the source data;
- **5,594 source concepts** in the union view;
- **55,188 RDF triples** in the documented SKOS artifact.

The important rule is not the numbers but the identity model: the source concepts stay under their AMCR/TEATER URIs; only the ATRIUM-owned schemes/concepts receive ATRIUM URIs.

The serializer is deterministic and is checked by the existing `--check` drift mechanism. The strategy documentation records zero SKOS integrity violations, Turtle/JSON-LD isomorphism, byte stability, and a tamper check that makes the drift gate fail when the committed artifact is altered.

### 4. Meaning of hierarchy and mappings is explicit

The current strategy deliberately does **not** flatten all source relationships into `skos:broader`:

- AMCR `hierarchie_vyse` is treated as associative `skos:related` because all 1,176 measured edges cross heslář boundaries and are not a thesaurus hierarchy;
- TEATER's ancestor chain is handled as one direct `skos:broader` plus the corresponding `skos:broaderTransitive` links;
- TEATER AAT quotations are citations (`dcterms:source`), not identity assertions;
- `same_as` is a label-shape heuristic, not `owl:sameAs` or `skos:exactMatch`;
- the JSON record fields remain open strings where the contract requires runtime label validation rather than a brittle schema enum.

These are semantic safeguards, not serialisation preferences.

### 5. Provenance reaches the record without changing the prompt

The source concept URI and mapping information are read from flat artifacts through `concept_index()` / `resolve_pid()`. They are deliberately **not** added to the nested prompt structure because `nested_keep` becomes part of the LLM prompt payload.

The current vocabulary manager documentation records **4,952 indexed labels**, with **432 labels resolving to a Getty AAT concept**. `entities[].pid` can therefore carry source/AAT identifiers without spending context budget on raw URI lists.

`enrichment.items[].teater_category_uri` similarly gives the record/crate a place to carry the source concept URI without changing what the model sees.

## 🐞 Defect / follow-up register after the repository split

### V-1 — cross-originator line filtering ✅ fixed

`lines[].categ` has disjoint producer sets. The old filter knew only `Garbage` and `Inverted`; the OCR producer emits `Trash`. The shared `UNTRUSTWORTHY_LINE_CATEGORIES = ("Garbage", "Inverted", "Trash")` now covers both origins, and the OCR path has a regression test.

**Important nuance:** this is the one vocabulary-alignment fix that changes model input. The fix is therefore already landed, tested, and kept attributable to its own change.

### V-2 — page-classification sample/data mismatch ✅ fixed

`collect_images()` now derives categories from actual sub-directories rather than every directory entry, preventing files such as `LICENSE` from being interpreted as category folders and protecting the class-index binding. The 11-category set remains tied to `model_registry.CATEGORIES` and the hub `page-category` scheme.

### V-3 — duplicate vocabulary harvesting ⚠️ partially addressed / now an architecture item

The original duplicate was between the enrichment and translator paths. The later repository split added another important boundary: the vocabulary implementation is now intended to exist **once in `atrium-keyword-extract`**.

Current state:

- `keyword-extract` contains `vocab_sources.py`, `vocab_build.py`, `vocab_manager.py` and the vocabulary artifacts;
- the runbook makes `vocab_build.py` the only writer of the committed vocabulary directory;
- `vocab_build.py --from-flat --skos --check` is the reproducible, offline rebuild path;
- `translator/load_vocab.py` still exists as a legacy harvester and consumer path, but the target architecture is that translator consumes the released artifact;
- `digital-convert` still contains the old vocabulary manager/build stack and must lose it before its production image is the final born-digital stage;
- `nlp-enrich` is no longer the production owner of the vocabulary code.

So the remaining problem is now **ownership and release governance**, not whether SKOS can be serialised.

### V-5 — source label versus ATRIUM theme ⚠️ mitigated, unresolved contract

`enrichment.items[].teater_category` is written as a raw source label such as `kostel`. The current production path carries `teater_category_uri` when the source identity is known, and the crate prefers that source URI rather than minting `w3id.org/atrium/theme/kostel`.

The remaining question is semantic:

- should `teater_category` stay the source label and the ATRIUM theme be derived through `HESLAR_TO_THEME` / `TEATER_BRANCH_TO_THEME` when needed; or
- should `teater_category` be changed to carry the theme, with the source label moved to a sibling field?

This should remain an explicitly owned contract decision. It is not a reason to reopen namespace work.

### F4 / F5 / F7 — the old SKOS follow-ups

The strategy still records:

- **F4:** verified CNEC 2.0 definitions/glosses are still not available from the current source materials, so definitions must not be invented;
- **F5:** registering the `w3id.org/atrium` redirect is still optional and non-blocking;
- **F7:** a fresh network re-harvest is required before the weaker mapping fields (`close_match`, `broad_match`, `citation_uri`) can populate committed artifacts from live source data.

These do not reopen the external namespace decision.

## 📌 Bottom line

#51 has effectively become a **design-and-handover checkpoint**:

- **Do not** request or depend on a DARIAH namespace from ATRIUM now.
- **Do** preserve AMCR/TEATER source IDs and source URIs as the identity of harvested concepts.
- **Do** keep `atrium_vocab.py` as the hub-canonical authority for ATRIUM-authored labels and the cross-repo semantics that produced the V-1/V-2 defects.
- **Do** finish the architecture transition to one vocabulary implementation and one versioned release artifact, with `atrium-keyword-extract` as the owner.
- **Do not** let translator, digital-convert or any other consumer become a second source of truth.
- **Do** carry the unresolved `teater_category` semantics as an explicit contract question, rather than silently changing its meaning.
- **Then** hand the source-vocabulary publication/PID work to the external SKOSification project when its namespace/PID policy is ready.

The remaining work is therefore primarily **release/ownership convergence**, not SKOS design. The old issue wording "needs a namespace first" is no longer an accurate description of the current ATRIUM work.
