## 🧭 What changed in the #32 thread after the previous refresh

The last refresh was written while round 2 was still described as a five-service API contract. The live thread then established three additional facts.

### 1. The contract is now the typed pilot contract

AMČR accepted:

1. typed requests/responses, including the shared `AtriumDocument`, optional typed `CreateAction` paradata, and effective `/info` limits;
2. the common `{status, reason, detail}` error body and a published reason-code registry;
3. `service/openapi.json` as the contract artefact attached to every release, with its `.sha256` digest and compatibility comparison against the previous release.

The intention is that Temporal activities can be generated from the **trusted release asset** and may read `/openapi.json` from a running service only to verify that the deployed image matches that release.

No additional API redesign is intended for the pilot baseline.

### 2. The service boundary changed

The latest #32 comment explicitly supersedes the earlier five-repository ownership assumptions:

- `nlp-enrich` no longer owns the keyword service;
- `keyword-extract` owns the keyword endpoint and both statistical and controlled keyword kinds;
- `digital-convert` owns the born-digital service;
- `ocr-postprocess` is the successor to `alto-postprocess`;
- `kw_method`, `num_keywords`, and the old `keywords` response field in nlp-enrich are transitional only and must not be used by new activities.

The current six-stage shape is therefore:

```text
page-classification
        │
        ├── scanned/image route
        ▼
ocr-postprocess
        │
        ├── shared text/quality record
        ▼
nlp-enrich
        │
        ▼
keyword-extract
        │
        ▼
translator

digital-convert
        │
        ├── born-digital record
        └── pages marked `needs_ocr` enter the same downstream route
```

Temporal, rather than an upstream service calling another tool's HTTP endpoint directly, owns the stage chaining.

### 3. New service identities need the same contract, not a fork of it

The repository moves are **new repositories**, not GitHub renames in all cases. Therefore the hub has to distinguish:

- a genuine service-id rename (`alto-postprocess` → `ocr-postprocess`), where the previous id is an explicit compatibility relation;
- a new repository inheriting a predecessor implementation (`keyword-extract`), where the lineage is useful but the current service is independently versioned;
- a new stage implementation (`digital-convert`), where the currently committed old contract must be replaced before it can be trusted.

The current `x-atrium-service-previous` support in `atrium_openapi.py` is the mechanism for the first two cases. It must not be used as permission to leave the old API active.

## 🎯 Goal

Every **current production service** in the six-stage ATRIUM pipeline should expose an API contract that:

- can be used to generate a client without guessing request or response shapes;
- uses the same `/info`, `/health`, `/ready`, limits, error, and provenance conventions;
- carries the frozen `atrium_document` schema and its version/hash reference;
- publishes stable reason codes instead of forcing clients to parse error strings;
- has a committed, reproducible `service/openapi.json`;
- releases the exact same spec as `openapi.json` plus `openapi.json.sha256`;
- fails CI/release on an incompatible change unless the service makes the required major-version change;
- records a service rename explicitly when old records or old deployed clients still need to be understood.

The domain endpoint names remain stage-specific. #32 standardizes the **contract around them**, not the stages themselves.

## 🧩 Contract baseline that remains current

### Shared helper

The canonical [`docs/templates/shared/atrium_service.py`](../../docs/templates/shared/atrium_service.py) is the single source for:

- `build_info`;
- `attach_health` and `GET /ready`;
- upload limits and CORS conventions;
- the shared error body and `AtriumHTTPError`;
- `read_tool_version`;
- bounded input reads;
- `CreateAction` and `AtriumDocument` response components;
- `attach_openapi_contract`;
- `openapi_digest`.

`docs/templates/shared/MANIFEST.json` records `atrium_service.py` as issue #32 material, and `para-drift` enforces byte parity in the repositories that vendor it.

### Published reason codes

The current shared registry covers:

| Reason                   | Allowed status  | Meaning                                                                                      |
|:-------------------------|:----------------|:---------------------------------------------------------------------------------------------|
| `limit_exceeded`         | 413 / 422 / 504 | an input, result or time budget was exceeded                                                 |
| `busy`                   | 429             | no processing slot is available; retry using `Retry-After`                                   |
| `unsupported_media_type` | 415             | the input media type is not accepted                                                         |
| `invalid_record`         | 422             | the `document_json` part cannot be parsed as the supported record family                     |
| `ocr_text_layer`         | 422             | the digital source contains an OCR text layer that must be re-acquired through the OCR route |

The registry deliberately keeps `reason` as `string | null` rather than an OpenAPI enum. Adding a new reason must not break an older generated client merely because it sees an unfamiliar string; the CI/release gate is what prevents a published code from disappearing or changing meaning.

`digital-convert#2` additionally requires **`source_digest_mismatch`** for a seeded source whose `source.sha512` does not match the bytes received. That code is not yet part of the shared current registry and must be added before `api-digital` can claim full contract conformance. The same rule applies to any new pilot-facing reason: register it centrally before the service ships it.

### Typed record and paradata

Every primary response now has the optional typed `paradata` slot reserved for the Process Run Crate `CreateAction`. The record itself is represented by the shared `AtriumDocument` component tied to `doc-schema-v1`.

The AMČR seed path is therefore part of the API contract:

- a service accepts a `document_json` seed;
- the document identity travels with the record;
- `source.sha512` is preserved and verified where the service owns the source bytes;
- a record with an unsupported major schema version is refused with `invalid_record`;
- a record that parses but does not fully validate the schema can still be carried as input, with `document_json_schema_error` rather than being silently discarded.

### OpenAPI release chain

The current hub tooling already provides the intended chain:

```text
service code
    │
    ├── atrium_openapi.py export/check
    │
    ▼
committed service/openapi.json
    │
    ├── stamp
    │     ├── openapi.json (canonical bytes)
    │     └── openapi.json.sha256
    │
    ├── baseline (highest earlier release carrying a spec)
    │
    └── compare --require-oasdiff
```

The previously found digest inconsistency is now reflected in the current hub tooling: `stamp` writes the canonical serialized form, and the `.sha256` line is the digest of the actual release asset bytes. Therefore `sha256sum -c openapi.json.sha256`, `/info.openapi_sha256`, and the release asset can agree on one value.

The compatibility rule remains:

> a breaking contract change fails unless the service raises its major version; for `0.x`, a breaking change moves to `1.0`.

A published reason code must not be removed or renamed.

### Keyword stage

The current `atrium-keyword-extract` README is explicit that:

- KeyBERT is the default statistical method;
- YAKE is selectable;
- legacy KER is retained;
- document and page keywords carry `method`, `score`, and `rank`;
- controlled vocabulary extraction is still a research/partial-service target;
- the record-level `keywords` block is still tracked separately by #73.

This is enough to keep #32's API contract stable; it is **not** enough to call the whole controlled-keyword production path complete.

### NLP stage

The current nlp repository is the LINDAT/TEITOK stage. The latest #32 decision makes the ownership boundary explicit:

- new activities must not depend on `kw_method`;
- new activities must not depend on `num_keywords`;
- new activities must not expect the old keyword response from nlp-enrich;
- the transitional fields are deprecated before their final removal.

The keyword service is now the only place to define the keyword endpoint.

### OCR successor

`atrium-ocr-postprocess` is not a cosmetic rename. Its current spec uses:

```text
x-atrium-service: atrium-ocr-postprocess
x-atrium-service-previous: atrium-alto-postprocess
```

This lets the release gate distinguish an intentional successor from an undeclared service-id change. Existing records retaining `alto-postprocess` provenance remain readable.

### Born-digital stage

`atrium-digital-convert` is the outstanding contract migration. The agreed API identity is:

```text
service: atrium-digital-convert
endpoint: POST /reformat
image family: ghcr.io/ufal/atrium-digital-convert-*
record block owner: digital-convert
```

The service should return the shared `atrium_document` record by default. Markdown is an optional derived output rather than the canonical service response.

It must also implement the source-seed rules from #2:

- preserve `doc_id`;
- verify `source.sha512`;
- return `source_digest_mismatch` on mismatch;
- mark pages requiring OCR with `needs_ocr`;
- use `ocr_text_layer` for the agreed whole-document refusal case;
- leave downstream OCR quality/NLP to the shared later stages.
