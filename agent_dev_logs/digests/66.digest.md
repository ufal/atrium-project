**Status**: 🟡 **Scope settled; wrapper work not started.** The original five-tool framing is obsolete after the 30 September repository split. #66 now targets the six current ATRIUM processing repositories, but they are at different levels of Galaxy readiness. The remaining external blocker is the target Galaxy instance/publication route and access; the internal blocker is aligning the new repository/service map and the Galaxy documentation before publishing wrappers.

The repository transition therefore changes #66 in two ways: the old `alto-postprocess` / `llm-enrich` names are no longer the target wrappers, and `digital-convert` / `keyword-extract` are now first-class target repositories — but **their production maturity differs**.

## 🎯 Goal

Make the six current ATRIUM processing stages available to external users as **Galaxy tools and actionable workflows**, using the same released production service images that the ATRIUM system deploys. The Galaxy layer is a reusable user-facing sandbox; it is **not** a second implementation of the production Temporal workflow.

The canonical workflow description remains on the hub GitHub Pages. Each Galaxy workflow should be derived from that description and, where applicable, linked to the corresponding SSH Open Marketplace workflow record.

## 🔎 Evidence from the current repositories and hub docs

### 1. The wrapper must follow the new production-image contract

Issue [#72](https://github.com/ufal/atrium-project/issues/72) established **one production service image per stage**, with each repository declaring the files reachable from that image in `.github/production-image.json`. The six current repositories now expose `-api` production images, while their batch/research images are not the production baseline.

That matters for #66 because the earlier Galaxy plan proposed wrappers around the batch images. The current settled direction is stronger: **Galaxy should wrap the same released production service images**. The Galaxy sheets therefore need to be updated from references such as `ghcr.io/ufal/atrium-page-classification:<version>` / `ghcr.io/ufal/atrium-translator:<version>` to the corresponding released `-api` image contract, while preserving the tool's documented API behaviour.

### 2. `digital-convert` is part of the target set, but it is not yet wrapper-ready

The current workflow page [`docs_site/workflows/digital-convert.md`](https://github.com/ufal/atrium-project/blob/test/docs_site/workflows/digital-convert.md) describes the intended born-digital route correctly at the workflow level: PDF/DOCX → ATRIUM document record, `needs_ocr` hand-off where required, then downstream processing.

However, the repository's current [`atrium-digital-convert#2`](https://github.com/ufal/atrium-digital-convert/issues/2) is still the work item for the independent `api-digital` production service. Its first `v1.0.0-beta` release explicitly retains the old `atrium-llm-enrich` service/image identity until the converter release. The current production-image manifest on `test` still reflects the transitional controlled-keyword API target. Therefore a Galaxy wrapper should be **planned now but published only after the final `api-digital` service image and identity are released**.

### 3. `keyword-extract` is production-ready only for its statistical kind

The new repository's `v1.0.0-beta` provides `POST /extract_keywords` and a production `-api` image for statistical KeyBERT / YAKE / KER extraction. Its README and release notes explicitly state that `kind=controlled` is not yet implemented in the service; `kind=both` reports the controlled part as skipped, and the controlled LLM code remains a research target in the `llm` image.

For #66 this means the Galaxy contract must name the capability precisely: the first published keyword workflow can expose **statistical keyword extraction**. The controlled vocabulary/LLM route should remain a documented follow-up rather than being advertised as already available.

### 4. `nlp-enrich` is now a clean LINDAT stage

The current production-image manifest removes the former keyword/LLM functionality and defines the stage as UDPipe + NameTag + TEITOK/record projection. Its production service is CPU-oriented and uses network access to LINDAT. The hub workflow page reflects this split, but currently supplies only a stable-core description rather than the full Galaxy field sheet.

For Galaxy this is a normal remote-service wrapper problem: inputs/outputs and the lack of a Galaxy-native CoNLL-U datatype must be stated explicitly. The existing hub narrative already says CoNLL-U maps to Galaxy `tabular`.

### 5. `ocr-postprocess` is the successor of `alto-postprocess`

The new repository and production image are established, and the pipeline itself was preserved. Issue [`ocr-postprocess#6`](https://github.com/ufal/atrium-ocr-postprocess/issues/6) explicitly included updating the Galaxy wrapper among the rename acceptance items. Nevertheless, hub workflow provenance still contains pre-rename references and the old stable-core source release. Those references are documentation debt for #66: the Galaxy-facing sheet should be regenerated from the current successor repository and image identity before publication.

### 6. `translator` and `page-classification` are the best first pilots

Both already have full workflow narratives with Galaxy sheets. The translator narrative defines ALTO/XML inputs, optional vocabulary CSV, target/source language, backend, replace/append mode and XSD validation; the page-classifier narrative defines image inputs, model revision/ensemble, Top-N outputs and the Hugging Face or staged-model dependency.

The translator's AMČR-compatible pilot setting is `replace`, not `append`. The page classifier's current production image has moved to `pypdfium2`; the workflow narrative still contains stale PyMuPDF wording and therefore needs a documentation refresh before being treated as the external wrapper specification.

## 🌐 Galaxy route: what is known and what remains external

Current public ATRIUM Galaxy infrastructure is still centered on [`DARIAH-ERIC/atrium-galaxy-tools`](https://github.com/DARIAH-ERIC/atrium-galaxy-tools), which provides a Docker Compose Galaxy instance, ATRIUM tool wrappers and example workflows. The open issue research also found a separate possible route through `usegalaxy-eu-tools` for the public usegalaxy.eu service.

The following are **not yet settled in #66** and should remain explicit questions rather than assumptions:

1. Which Galaxy instance is the actual "ATRIUM Galaxy space" for this work: DARIAH's own deployment or `ssh.usegalaxy.eu`?
2. Should the six tools be contributed through `atrium-galaxy-tools`, through the public ToolShed / `usegalaxy-eu-tools` route, or through both with one designated as the primary publication target?
3. Are the released GHCR `-api` service images accepted directly by the target Galaxy, and what thin wrapper mechanism is expected around a service image?
4. Do jobs have outbound access to LINDAT / Hugging Face / other required services, or must models and data be staged inside Galaxy?
5. What GPU destination is available for page classification and future GPU-backed keyword/LLM runs?
6. Which workflow metadata convention should be used for annotations, creators/ORCIDs, licence, step labels and test data?
7. Can the three requested project accounts be granted access to the agreed space?

## 📚 Documentation state relevant to #66

The hub already has a Workflows section under `docs_site/workflows/`, with pages for all six current repositories. The older #66 plan assumed that the Galaxy sheet on each page was the complete specification, but after the repository split the coverage is uneven:

- **Full Galaxy sheets:** `translator`, `page-classification`.
- **Stable-core pages with only partial Galaxy information:** `digital-convert`, `ocr-postprocess`, `nlp-enrich`, `keyword-extract`.
- **Required refresh before external publication:** production image names (`-api`), renamed service/program identities, current release provenance, and any stale dependency/licence statements.

This does not require a second `operations/galaxy.md`; the existing Workflows pages remain the canonical per-tool documentation surface. #66 should extend those pages only where the new service/repository split made their Galaxy sheet insufficient.
