## 🎯 Goal
Figure out how to run MiniMax-M3 (FP8, ~440 GB checkpoint) on a single node using multiple GPU
cards, specifically an H100 node.

## 🧵 Thread trail
- **2026-06-20, K4TEL** — opened: "MiniMaxM3 FP8 444Bg" — figure out multi-GPU single-node
  execution.
- **2026-06-21, K4TEL (research comment)** — identifies the model precisely: MiniMax-M3, released
  June 1 2026, ~428B total parameters / ~22B active (MoE, A22B), the "444Bg" figure being the FP8
  checkpoint's on-disk/VRAM footprint in GB, not a literal parameter count. Recommends:
  - **Confirm node topology first** — `nvidia-smi --query-gpu=name,memory.total --format=csv` and
    `nvidia-smi topo -m`, since the recipe below assumes the standard 8×80GB SXM5 NVLink/NVSwitch
    DGX/HGX configuration, not a PCIe-only or fewer-card layout.
  - **Tensor-parallel across all 8 GPUs** (~55GB weights/card, ~25GB/card headroom for KV
    cache/activations) is the right shape for ~440GB of weights against 640GB total VRAM.
  - **Framework: vLLM or SGLang, not Ollama** — Ollama's layer-split does not do true multi-GPU
    tensor parallelism with NVLink collective ops; it isn't built for cooperatively sharding a
    single 428B model. This is the key strategic call.
  - Concrete recipe:
    ```bash
    vllm serve MiniMaxAI/MiniMax-M3 \
      --trust-remote-code \
      --tensor-parallel-size 8 \
      --enable-expert-parallel \
      --block-size 128 \
      --kv-cache-dtype fp8 \
      --max-model-len 131072 \
      --tool-call-parser minimax_m3 \
      --reasoning-parser minimax_m3 \
      --enable-auto-tool-choice
    ```
  - `--tensor-parallel-size 8` is required just to fit the weights with any KV-cache headroom;
    `--enable-expert-parallel` spreads MoE expert weights instead of replicating routing/non-expert
    weights on every GPU (plain TP would waste VRAM on a MoE model); `--max-model-len 131072` is a
    deliberately practical cap, not the model's full 1M-token claim; `--kv-cache-dtype fp8` buys
    back headroom the TP-8 split otherwise spends thin.
  - Support for this exact configuration is **brand-new** (the model shipped weeks before the
    comment) — recommends using the vLLM nightly build or a maintained Docker image rather than a
    pinned release, and budgeting for rough edges.

## ⏳ Open
- **No captured run yet.** Nothing in this issue or any repo indicates the recipe above has been
  exercised on real H100 hardware — no startup log, no throughput numbers, no confirmation the
  `minimax_m3` tool/reasoning parsers actually work end-to-end with `--enable-auto-tool-choice`.
- **Node topology unconfirmed** — the whole recipe assumes 8×80GB SXM5; if the actual available
  node differs (fewer cards, PCIe-only interconnect), the tensor-parallel degree and expected
  throughput both change.
- **Coordination with #26** — #26's own plan.md (§F) already flags this: tensor/expert-parallel
  sharding (this issue) and CPU offload (#26) are complementary, not competing — TP consumes all
  local VRAM first, offload tops up the remainder for cases (like this one) that need both. #26's
  plan recommends documenting them together rather than as separate options; this issue has not
  yet been updated to reflect that framing.
