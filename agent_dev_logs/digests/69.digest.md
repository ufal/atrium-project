## 🧩 Current findings after the repository-set change

### B2 — image naming: still a valid finding, but the old evidence is incomplete

The live issue names `nlp-enrich` and `llm-enrich`. The latter is no longer a current product repository, so an old `llm-enrich` Compose mismatch must not be treated as a current-service defect or as a reason to keep that repository on the production CI matrix.

The current audit target is all six present product repositories. The canonical image vocabulary should be explicit:

```text
ghcr.io/ufal/atrium-<tool>:<version>
ghcr.io/ufal/atrium-<tool>-api:<version>
```

where an API target exists. This is consistent with the current page-classification documentation, which explicitly describes the API image as `ghcr.io/ufal/atrium-page-classification-api:<version>` and notes that the release version is used **without** the leading `v` in the registry tag. The same base/API distinction is present in the translator repository.

The action item is therefore not "fix the old five-tool Compose files". It is:

1. inventory every current `docker-compose*.yml`/`.yaml` and every Docker release target;
2. compare the exact image name used by Compose with the exact image name pushed by CI;
3. make one current naming convention authoritative in the hub docs and reusable workflow;
4. remove predecessor-only exceptions from the current roadmap.

### B3 — image provenance: this is now more important because of #71

The mismatch between GitHub release refs and GHCR tags is not merely cosmetic. #71 requires every production service to return an instrument describing the tool and image. If the recorded image tag does not exist, the paradata cannot identify the deployed artifact unambiguously.

The clean separation is:

- release identity keeps the public release form, e.g. `v1.9.0-beta`;
- the registry tag is normalized to the published form, e.g. `1.9.0-beta`;
- `ATRIUM_RUNNER_IMAGE`, Docker labels and `CreateAction.instrument` all use the **actual pushed image reference**;
- the immutable release URL may still retain the `v` in the GitHub tag.

This should be solved once in the shared/reusable CI layer and then verified independently in all six product repositories.

### B6 — writable `data/`: now a partial finding rather than a blanket statement

The #69 body says that no repository has a `data/` directory. The current `test` tree of `atrium-page-classification` already documents `./data` and `./data/output` as part of the clone and uses an explicit `ATRIUM_UID` mapping in Compose. That means the original B6 wording is now at least partly stale.

The correct current question is narrower:

> For every current service that writes to `/data`, does the Compose contract guarantee that the mounted host path is writable by the runtime user without root-owned directory creation?

The fix should be standardized rather than copied blindly: either ship the host-side directory, pre-create it before `docker compose`, or use a named volume where appropriate. The runtime uid/gid rule must remain explicit. Read-only services should not be forced into a writable-data requirement merely to satisfy the old finding.

## 🌐 Current six-stage production model and CI implications

The current architecture is not one linear Compose stack for every input:

```text
scanned / OCR path:
page-classification → ocr-postprocess → nlp-enrich → keyword-extract → translator

born-digital path:
digital-convert → the same downstream record/enrichment path
```

The exact Temporal topology belongs to the processing/trust-gate repository, not to #69. For CI, however, this distinction matters: `digital-convert` must be covered as a current service even though it is an entry branch, and `keyword-extract` must be covered as a current production service even though its code lineage comes partly from the old LLM repository.
