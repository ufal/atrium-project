## 🎯 Goal
Factor IV asks that backing services be attachable — swappable by configuration, without a code change. Four call sites reach LINDAT-hosted services through hardcoded constants, in two repos that both already do this correctly elsewhere.

## 🔎 Verified state

### atrium-nlp-enrich — two siblings, two different answers

`api_util/call_nametag.py:202-206` — correct:

```python
parser.add_argument(
    "--url",
    default=os.environ.get("NAMETAG_URL", NAMETAG_URL),
    help="NameTag API endpoint URL.",
)
```

`api_util/call_udpipe.py:73` — its sibling, same directory, same shape of script:

```python
response = session.post(UDPIPE_URL, data=data, timeout=timeout)
```

No `--url`, no env read; `UDPIPE_URL` is a module constant. And `config_api.txt:19-20` **already declares both URLs** — so the configuration surface exists and only the shell path consumes it for UDPipe.

### atrium-translator — every dial except the host

`processors/lemmatizer.py:40` and `processors/translator.py:129` hold LINDAT endpoints as class constants:

```python
URL = "https://lindat.mff.cuni.cz/services/udpipe/api/process"          # lemmatizer.py:40
BASE_URL = "https://lindat.mff.cuni.cz/services/translation/api/v2"     # translator.py:129
```

Meanwhile the same file env-tunes LINDAT's **transport** in detail — `LINDAT_MIN_INTERVAL_S` (`:119`), `LINDAT_MAX_RETRIES` (`:121`), `LINDAT_BACKOFF_BASE_S` (`:123`) — and the same repo treats its LLM backend as fully attachable (`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`). Someone thought carefully about rate-limiting a shared public endpoint and never about pointing at a different one.

### The paradata wrinkle

`service/api.py:215` re-hardcodes the translation URL into the paradata record:

```python
if backend_name == "lindat":
    para_config["translation_api"] = "https://lindat.mff.cuni.cz/services/translation/api/v2/"
```

It is inside a `backend_name == "lindat"` guard — so it is already backend-aware (a comment at `:214` credits finding M1 for that), and it is *still* a literal. The moment the URL becomes configurable, this line records a host the request may not have gone to. **A paradata record naming the wrong endpoint is worse than one omitting it**: paradata is the project's provenance claim, and a provenance record that is confidently wrong is a data-integrity problem, not a cosmetic one. This line must change in the same commit as the constant, not after.

## 🔗 Coupling

- **Naming matters across repos.** nlp-enrich uses `UDPIPE_URL`/`NAMETAG_URL` (declared in `config_api.txt:19-20`). The translator must use the same names for the same services, or the ecosystem gets two spellings of one endpoint and #60's table has to explain why.

## ⏳ Open
- **`LINDAT_BASE_URL` vs `TRANSLATION_URL`.** The issue proposes `LINDAT_BASE_URL`. That name binds the variable to a *provider*, not a *role* — and the existing `LINDAT_*` transport variables set that precedent already. But the point of factor IV is that the backing service is swappable, and a self-hosted UDPipe is not "LINDAT". Recommend role-named variables (`UDPIPE_URL`, `TRANSLATION_URL`) matching nlp-enrich, with the `LINDAT_*` transport names left alone. Not yet decided.
- **Two UDPipe endpoints, one name.** nlp-enrich's `UDPIPE_URL` and translator's `lemmatizer.py:40` are both UDPipe, reached for different purposes, in different repos. Sharing the variable name is right; whether they are ever set to different values in one deployment is worth a sentence in #60's table.
- **The `config_api.txt` half.** `config_api.txt:19-20` declares both URLs and the shell path reads them. After this change there are two ways to set the UDPipe endpoint in nlp-enrich (config file, environment) and no stated precedence. Decide it — env wins is the factor-III-consistent answer — and write it in the file.
