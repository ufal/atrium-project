### atrium-nlp-enrich — two siblings, two different answers

`api_util/call_udpipe.py:73` — its sibling, same directory, same shape of script:


No `--url`, no env read; `UDPIPE_URL` is a module constant. And `config_api.txt:19-20` **already declares both URLs** — so the configuration surface exists and only the shell path consumes it for UDPipe.

### atrium-translator — every dial except the host

`processors/lemmatizer.py:40` and `processors/translator.py:129` hold LINDAT endpoints as class constants:

```python
URL = "https://lindat.mff.cuni.cz/services/udpipe/api/process"          # lemmatizer.py:40
BASE_URL = "https://lindat.mff.cuni.cz/services/translation/api/v2"     # translator.py:129
```

Meanwhile the same file env-tunes LINDAT's **transport** in detail — `LINDAT_MIN_INTERVAL_S` (`:119`), `LINDAT_MAX_RETRIES` (`:121`), `LINDAT_BACKOFF_BASE_S` (`:123`) — and the same repo treats its LLM backend as fully attachable (`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`). Someone thought carefully about rate-limiting a shared public endpoint and never about pointing at a different one.

### The paradata wrinkle

`service/api.py:215` re-hardcodes the translation URL into the paradata record:

```python
if backend_name == "lindat":
    para_config["translation_api"] = "https://lindat.mff.cuni.cz/services/translation/api/v2/"
```

It is inside a `backend_name == "lindat"` guard — so it is already backend-aware (a comment at `:214` credits finding M1 for that), and it is *still* a literal. The moment the URL becomes configurable, this line records a host the request may not have gone to. **A paradata record naming the wrong endpoint is worse than one omitting it**: paradata is the project's provenance claim, and a provenance record that is confidently wrong is a data-integrity problem, not a cosmetic one. This line must change in the same commit as the constant, not after.

## ⚙️ What implementation found

### The `source` clobber — the finding that resizes the issue

`api_2_udp.sh:5` and `api_3_nt.sh:5` open with `source "${ATRIUM_CONFIG:-config_api.txt}"`, and `run_pipeline.py:120` hands the stage `dict(os.environ)`. **Bash keeps the export attribute of an already-exported variable across re-assignment**, so a bare `UDPIPE_URL="https://…"` in the config file overwrites *and re-exports* an operator's value:

```
UDPIPE_URL unset in env → sourced value stays a plain shell var → python sees nothing → constant
UDPIPE_URL set in env   → sourced value OVERWRITES it, still exported → python reads the FILE
```

The second case is the one deployments are in. Measured on the pre-fix tree: both stage redirects fail with **0 stub hits**, and `api_3_nt.sh` **exits 0** while sending its data to the host the operator redirected away from — a silent wrong answer, not a failure.

This is why the issue's own acceptance criterion is insufficient: it invokes `call_udpipe.py` **directly**, bypassing the shell, so it passes while the deployed pipeline stays unattachable.

### NameTag was never "already correct"

The issue treats `call_nametag.py` as the reference implementation. Its Python body is correct; the feature was not. NameTag sat behind the same clobber, `api_3_nt.sh:37-42` **never passed `--url`** (so `config_api.txt:20` was inert too — *both* declared config surfaces were decorative), and `service/enrichment.py:327-351` → `service/api.py:341-346` HEAD-probed the file's value. Fixed in lockstep with UDPipe.

### Two more sites the issue does not name

- **`main.py:58`** (translator) wrote the LINDAT URL into CLI paradata **unguarded** — every CLI run on the LLM or CT2 backend already claimed an endpoint it never contacted. `service/api.py` has had that guard since M1.
- **Compose never forwarded the variables.** Compose injects only what a service's `environment:` block lists, and neither repo listed them — so the endpoints were configurable inside the process and unreachable from outside the container. `atrium-translator`'s `translator-batch` service had no `environment:` block at all, and it is the one whose entrypoint both calls the services *and* writes the paradata.

## ✅ Settled

- **`TRANSLATION_URL`** is the documented name; **`LINDAT_BASE_URL`** is accepted as an alias and loses when both are set. `UDPIPE_URL` / `NAMETAG_URL` are reused verbatim across repos. The `LINDAT_*` transport dials keep their names.
- **Precedence, stated in `config_api.txt` and both READMEs**: `--url` / constructor arg > environment > config file > module constant. An **empty** variable counts as unset everywhere — the case a compose container is always in.
- **Two UDPipe call sites, one variable name.** Deliberate; a deployment may still set them apart per workload, and the k8s template says so.
- **`ATRIUM_<XX>_URL` is not a competing convention** — it is *inbound* (where a skill's client finds the ATRIUM service); these are *outbound*. Orthogonal. This digest previously implied a conflict; there is none.
