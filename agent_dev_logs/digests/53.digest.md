## 🧱 Factor III — AMČR configurable limits are complete

The last substantive addition to #53 came from AMČR in [issue comment 5847715129](https://github.com/ufal/atrium-project/issues/53#issuecomment-5847715129): every operational service limit must be visible and changeable by the caller, must not silently truncate an input, and must be reported through `/info`.

That requirement is implemented in the five original service implementations and is now carried by the successor repositories as part of their common contract.

### Common mechanism

The shared `atrium_limits.py` module and each repository's `tool_limits.py` establish one declaration for each service limit. The effective value is read from the environment; malformed values fail at startup and identify the variable; `/info` exposes both `limits` and `limits_meta`.

A limit is handled in one of two ways:

1. the request/input is refused with the harmonised `limit_exceeded` error and a status appropriate to the cause; or
2. the service processes the input in full and records the effect in `limits_applied` (and paradata where available).

The important result is that a caller no longer has to reverse-engineer an implementation constant to know whether a document will be accepted or how a bounded operation shaped its result.

### Current evidence in the successor trees

The current `test` trees visibly retain this contract:

- `page-classification/tool_limits.py` declares upload, PDF-page, render-DPI and image-pixel limits, with matching `.env.example`, README and `/info` documentation.
- `translator/tool_limits.py` declares the request, language-identification, LINDAT, UDPipe, LLM and CT2 budgets; its README also documents `limits_applied` and the header transport.
- `nlp-enrich/service/api.py` reads its concurrency, queue, upload, word-count, timeout and rescale limits from `tool_limits.py`; its process-local `/jobs` state remains an explicit operational exception.
- `ocr-postprocess/tool_limits.py` covers upload, archive/member, page/line and reader-time budgets; the README states that over-limit inputs are refused or processed in full with an explicit note.
- `keyword-extract/tool_limits.py` covers upload, document words, keyword count and KeyBERT chunk budgets; the current README exposes `/info`, `limits_applied` and the distinction between statistical and controlled kinds.
- `digital-convert` also carries `atrium_limits.py` + `tool_limits.py`, exposes limits in `/info`, and its API entrypoint reads the common port and shutdown settings.

This is now **baseline infrastructure**, not new #53 work. The architecture issues must retain it when moving or splitting code.

## 🔬 Current successor repositories — relevant findings

### `atrium-digital-convert`

`atrium-digital-convert` now owns the born-digital stage. Its current Dockerfile already has a dedicated `api` target, `PORT`/`GRACEFUL_SHUTDOWN_S`, `STOPSIGNAL`, a healthcheck and `python -m service.api`; its service code exposes `/info` and `tool_limits`.

The important qualification is that the repository still contains inherited LLM infrastructure and naming while `digital-convert#1` and `#2` complete the split. The current production architecture must therefore distinguish:

- the born-digital converter (`api-digital`) as the stage;
- the inherited LLM/keyword implementation as migration material;
- the future keyword-extractor service as the production owner of keyword/LLM enrichment.

That cleanup is #72 / `digital-convert#1` / `digital-convert#2`, not #53.

### `atrium-page-classification`

The API image follows the common baseline: `python:3.11-slim`, `EXPOSE 8000`, `STOPSIGNAL SIGTERM`, `PORT`/`GRACEFUL_SHUTDOWN_S`, `python -m service.api` and `HEALTHCHECK`. The service README documents the common `PORT`, `HOST`, `RELOAD` and limits contract. The current tree also contains the AGPL/PyMuPDF cleanup already identified in the architecture work.

The remaining risks are product/release concerns under #72, not twelve-factor gaps.

### `atrium-translator`

The translator is now a fully instrumented API service with common lifecycle/configuration/limit contracts. Its current `tool_limits.py` covers the formerly hard-coded chunk and language-ID budgets as well as LINDAT, UDPipe, LLM and CT2 limits.

Two functional follow-ups remain explicitly outside #53:

- unsupported language pairs still fall back to `cs → en` instead of refusing the request;
- a newline re-join inside metadata fields remains to be handled.

Those are correctness issues, not factor compliance work.

### `atrium-nlp-enrich`

`nlp-enrich` is now deliberately the CPU/LINDAT/TEITOK stage. Its API still contains a process-local `_jobs` registry and container-local workspaces; this is the documented exception to pure statelessness, with concurrency/replica semantics spelled out in the hub deployment docs.

The repository is being simplified further under #72 and `keyword-extract#1`: keyword extraction and the duplicated LLM/vocabulary stack leave the production image. The remaining architecture work is therefore about responsibility boundaries and image closure, not Factor VI/VIII.

### `atrium-ocr-postprocess`

The former ALTO service is now `ocr-postprocess`. The production API retains the common service contract and `tool_limits`, while the underlying readers cover several OCR/text-bearing formats rather than ALTO alone.

The rename is consequential for provenance: the new service id/program id is the current writer, while historical `alto-postprocess` records must remain readable. This is part of the record/schema/repository-split work tracked by #71 and `ocr-postprocess#6`.

### `atrium-keyword-extract`

The current API service already follows the #53 baseline: `PORT`, `HOST`, `GRACEFUL_SHUTDOWN_S`, `RELOAD`, `/info`, `limits`, health/readiness and typed paradata are present. Statistical extraction is implemented with KeyBERT (default), YAKE or legacy KER, and every keyword carries method/rank/score.

However, the 30 September architecture decision changes ownership again: `keyword-extract#1` moves **both** statistical and controlled keyword extraction into a new `atrium-keyword-extractor` repository. Until that split is complete, this repository is the transitional source of the stage, not the final architectural boundary.

### `atrium-project`

The hub now owns the common service baseline and the policy around it:

- `docs/templates/shared/` canonical service modules;
- `para-drift` parity and self-tests;
- the Kubernetes manifest and acceptance runbook;
- `docs/k8s_deployment.md` service map;
- `docs/docker_gha.md` and #69 CI roadmap;
- release trust / immutable release mechanisms in #72/#40;
- the `doc-schema-v1` record contract and its seed/paradata rules.

The correct role of #53 at this point is to mark the **established operational contract** that all these layers depend on.

## 🎯 Practical conclusion for future readers

Treat #53 as the **operational baseline issue**, not the current umbrella for every service change.

The baseline is:

> **Every production service is independently deployable, environment-configurable, observable through `/health`/`/ready`/`/info`, explicit about limits and errors, graceful on shutdown, and guarded by shared CI contracts.**

The current architecture then adds stage ownership and release trust on top of that baseline:

```text
AMČR seed
   │
   ├── scanned path
   │      page-classification
   │          ↓
   │      ocr-postprocess
   │          ↓
   │      nlp-enrich
   │          ↓
   │      keyword-extract → future keyword-extractor
   │          ↓
   │      translator
   │
   └── born-digital path
          digital-convert (api-digital)
              ↓
          nlp-enrich
              ↓
          keyword-extract → future keyword-extractor
              ↓
          translator
```

The next architectural work must preserve the baseline while removing duplicate responsibilities and stale repository identities. It should not reopen the twelve-factor audit unless a concrete regression is found.
