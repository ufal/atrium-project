## ✅ What's settled

### 1. The issue ownership did not move

#17 remains the issue for the **workflow-level SSHOMP description**, not the implementation of the processing tools.

The AMČR baseline in [#67](https://github.com/ufal/atrium-project/issues/67) is still the useful ownership rule:
`0xSpVP` is AMČR-owned, while ÚFAL supplies and maintains its own tool/workflow records.

### 2. `0xSpVP` remains the single full-chain description

The later #4 discussion settled an important documentation rule:

> tool-local workflow records should describe only their own tool and link `0xSpVP` for the full AMČR chain.

That means `0xSpVP` should remain the place where the complete chain is told. The new translator workflow `13eHAZ` and the future page-classifier workflow should not duplicate the entire AMČR chain.

### 3. The current tool-record identities are mostly persistent

Reuse the existing SSHOMP item where the same conceptual tool continues under a successor repository:

- `RER7Fw` — page-classification
- `YParYU` — `alto-postprocess` → `ocr-postprocess`
- `EMhu3X` — `nlp-enrich`, narrowed to the current NLP scope
- `j9fqxo` — `llm-enrich` → `keyword-extract`
- `CizIUW` — translator

Create a genuinely new record for `atrium-digital-convert`, because that is now a separate current repository/stage.

### 4. The two split links are the main `0xSpVP` change

`0xSpVP` step 6 should eventually point to the **new digital-convert record**.

`0xSpVP` step 8 should point to the **same persistent `j9fqxo` record after it is repointed to keyword-extract**.

The current #4 comment explicitly says the old `j9fqxo` record should be repointed rather than duplicated, and the born-digital stage gets its own record.

### 5. The keyword semantics are now settled

The current `keyword-extract` workflow is the owner of both:

- statistical keywords (KeyBERT, YAKE, legacy KER);
- controlled AMČR/TEATER vocabulary keywords.

The two kinds remain distinct. The current implementation already returns statistical keywords at document and page level with `method`, `score` and `rank`; the controlled part and the record-level `keywords` block are still being completed under [#1](https://github.com/ufal/atrium-keyword-extract/issues/1) and [#73](https://github.com/ufal/atrium-project/issues/73).

The SSHOMP workflow should describe the stage's **stable conceptual role** and not claim unreleased implementation details as completed facts.

### 6. `nlp-enrich` no longer owns keyword extraction

Its current workflow is:

UDPipe → NameTag → TEITOK / NLP record projection.

Keyword generation is downstream in `keyword-extract`. The `nlp-enrich` record should therefore remain at step 7 only.

### 7. `ocr-postprocess` is the current name, but `YParYU` remains the record

The repository moved from `atrium-alto-postprocess` to `atrium-ocr-postprocess`. The pipeline itself and the ALTO-focused scripts stayed in place, while the accepted input scope broadened considerably. Existing records remain readable through the successor mapping.

Thus #17 does not need a new record ID for the OCR stage. The **record content** under #4 needs the identity/scope refresh; `0xSpVP` can continue to point at `YParYU`.

## ⚠️ Current-state nuances that matter for #17

### `0xSpVP` `106039` is not yet the final current-tool map

GitHub evidence shows it was submitted, not that it has been approved. More importantly, it was written before the 1 October repository split.

So the correct closure condition is **not** simply “version 106039 becomes visible”.

It is:

> the live AMČR workflow must point its two split stages at the current tool owners while retaining the agreed overall 11-step structure.

### The keyword record and the born-digital record are different tasks

The former `llm-enrich` record covered two unrelated responsibilities.

After the split:

- `j9fqxo` becomes keyword-extract;
- a new record is created for digital-convert.

Do not let the new keyword record keep born-digital conversion text just because that content remains historically present in `llm-enrich`.

### The hub workflow pages are the preferred stable-core text, not a substitute for release verification

The Workflows pages intentionally keep fast-changing model/version/threshold details out of their core narratives. For SSHOMP edits, use:

1. the hub Workflow page for the stable step narrative;
2. the repository README/current service docs for current interfaces;
3. the released tag for version claims;
4. #4 for the actual SSHOMP record IDs and moderation state.

This matters especially because some hub workflow prose can lag a just-landed implementation detail. Do not blindly copy a branch-only version number, old model default, or pre-split repository identity into SSHOMP.
