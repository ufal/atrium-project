## 🧵 What the #24 thread actually established

The original issue was deliberately broad: “Various tasks to do with LLMs launched locally or accessed remotely”. The issue comments then established three concrete lines of work.

### 1. Remote LLM access

On **2026-06-25**, the issue recorded that OpenRouter requests worked with a secret key and that Python routines, file attachments and local-only/data-sovereignty routing should be explored.

That work was subsequently implemented in the old `atrium-llm-enrich` tree as an OpenRouter client with provider data-collection routing and optional file attachment. The implementation survives as research/controlled-enrichment material in the new keyword repository during the migration; it is no longer a reason to keep a separate `llm-enrich` production stage.

### 2. Separate LLM work from the NameTag/UDPipe pipeline

On **2026-06-29**, the issue proposed a focused LLM repository. A draft `ufal/atrium-llm-enrich` was created on **2026-07-02** and built out with local `transformers`/vLLM, OpenRouter, Ollama, a shared torch-free client layer, vocabulary handling, and document-to-Markdown conversion utilities.

That repository decision was subsequently superseded by the 2026-09-30 production architecture review. The focused LLM implementation is still valuable, but its production ownership is now part of `atrium-keyword-extract`, while the born-digital converter becomes `atrium-digital-convert`.

### 3. Three-format data contract for LLM-facing processing

On **2026-08-01**, #24 recorded the three-format decision inherited from `atrium-llm-enrich#13`:

1. **JSON / `atrium_document`** is the canonical record containing the accumulated machine-readable information from all processing stages.
2. **Markdown (+ HTML/CSS cues)** is a derived, LLM-friendly textual projection: full usable text, simplified layout/table cues and figure-region information, without trying to be pixel-faithful or to become a second record database.
3. **TEITOK XML** is the spatially faithful linguistic/rendering representation tied to the page image. Its default form contains the NLP layer; keywords, topics, page categories and line-quality signals remain record data rather than being silently duplicated into the normal TEITOK output.

That decision still stands, but its implementation is now distributed across the current repositories instead of the old `llm-enrich` repository.

## 🔍 State of the three-format TODO

The final comment on #24 asked for JSON-2-MD and TEITOK-2-MD to work on fully and partially enriched inputs. The work is now partly implemented and partly re-scoped.

### JSON → Markdown

`json_to_md.py` exists in the former LLM conversion code and provides page-sectioned Markdown with page boxes, page-size and paragraph cues. It falls back to `content.text` when line data are unavailable and deliberately does not consume the `enrichment` block.

The reason for the latter is architectural: the Markdown is an LLM input projection, while entities/keywords are model output and should remain in the canonical record rather than being fed back into the model as if they were source text.

### TEITOK → Markdown

`xml_to_md.py --format layout` was rebuilt around the current TEITOK format-2 page model. The implementation handles page labels, print-space/page cues and sentences crossing page breaks, and has a pinned real `nlp-enrich` sample fixture.

### What is still missing

There is **no dedicated stress suite yet for fully accreted records and complex TEITOK files**. The corresponding work is now tracked as [`atrium-digital-convert#3`](https://github.com/ufal/atrium-digital-convert/issues/3), not as a new implementation stream in #24.

Its acceptance criterion also needs the corrected interpretation already recorded in that issue: entities and keywords are **not expected to be copied into Markdown**. The stress test should instead ensure that source text, page/line order and spatial/layout cues survive the conversion, while entities and keywords remain intact in the JSON record.

## 🧩 What moved where after the 2026-09-30 decision

### `atrium-nlp-enrich`

The production role is now LINDAT NLP + TEITOK/record projection. Its README explicitly says keyword extraction is no longer part of the repository; the production release line removed the keyword dependencies and LLM stage. TEITOK format-2 conformance, XSD validation and the upstream reader/writer round-trip gate are already green in its current work.

This means #24 should no longer describe `nlp-enrich` as an LLM engine owner.

### `atrium-keyword-extract`

This is the current home of both keyword kinds:

- **statistical**: KeyBERT by default, YAKE selectable, legacy KER retained;
- **controlled**: AMČR/TEATER vocabulary terms selected by an LLM, with supporting semantic/entity information.

The released service is already `POST /extract_keywords`. The statistical path is released; the controlled path remains a research/active-development target. Current open work includes the controlled service wiring, its evaluation gate, the record-level `keywords` block under [#73](https://github.com/ufal/atrium-project/issues/73), the versioned CC0 vocabulary release asset, and hub E2E.

`atrium-keyword-extract#2` is now the concrete controlled-vocabulary LLM workstream. Its current test branch carries active vocabulary/prompt development and a still-open evaluation/rubric gate. Therefore #24 should reference this as an owner issue, not try to reproduce that detailed design here.

### `atrium-digital-convert`

This repository is now the born-digital stage. Its current test tree still contains much of the former LLM repository because the migration is unfinished. The repository therefore currently has a transitional identity in code and Docker metadata even though the intended architecture is already settled:

- born-digital input → `atrium_document`;
- production API → `POST /reformat`;
- `digital-convert` remains the record program id;
- OCR-required pages are marked for downstream OCR routing;
- downstream stages are orchestrated outside the converter;
- the old keyword/LLM implementation must leave this tree.

The detailed migration is owned by [`atrium-digital-convert#1`](https://github.com/ufal/atrium-digital-convert/issues/1) and [`#2`](https://github.com/ufal/atrium-digital-convert/issues/2), with the architecture rule in [#72](https://github.com/ufal/atrium-project/issues/72).

### `atrium-ocr-postprocess`

The former `atrium-alto-postprocess` pipeline is now the OCR post-processing stage. It owns OCR/text extraction and the final quality categorisation on the OCR branch, and it is the intended owner for governed shared reader components under #72.

This is adjacent to #24 because the LLM input and quality filtering depend on the record produced by the OCR path, but there is no current reason to put LLM application logic back into this repository.

### `atrium-page-classification`

This remains the page-image routing/classification stage. It supplies page categories and routing information; it is not an LLM application owner for the current pilot architecture.

### `atrium-translator`

This remains the XML/ALTO and XML-metadata translation stage. Its own issue #4 explores future translation models, but that is a distinct model-selection stream and should not be folded back into the broad #24 implementation scope.

## 📦 Current state by acceptance theme

### LLM engine/client

The old repository proved the local `transformers`/vLLM and remote OpenRouter/Ollama execution patterns, plus schema-constrained output and a torch-free remote front-end. The local multi-GPU experiment is no longer a pilot dependency.

The current architecture retains the **LLM capability needed for controlled keyword extraction**, but the maintained ownership is being converged on `atrium-keyword-extract`. Production deployment is expected to keep the heavy/research LLM target separate from the statistical production API image unless the service contract explicitly requires otherwise.

### Vocabulary

AMČR and TEATER controlled-vocabulary handling is now part of the keyword stage. The vocabulary data are declared CC0 in the current keyword repository, but a **versioned release asset is still an open acceptance item**. #72 treats that asset as the governed shared vocabulary artefact for the ecosystem.

### Data sovereignty / remote routing

OpenRouter provider-data-collection routing and file attachments remain useful implementation capabilities from the original #24 work. They are not, by themselves, evidence that a production LLM service is ready: provider/model licensing, output provenance, and the approved service boundary still have to be satisfied by the owning issue.

### Research code

The current architecture explicitly keeps experimental benchmark/evaluation code outside production images. This includes the document-understanding benchmark utilities carried forward from the old LLM tree. Their presence in the repository is compatible with the plan; their presence in the production service image is not.

## ⚠️ Important current nuances

1. **#24 is now an umbrella/history issue, not the production LLM service issue.** Do not revive a standalone `atrium-llm-enrich` implementation path merely because the historical code still exists.
2. **The old LLM tree is not yet fully eliminated.** `atrium-digital-convert` still contains the inherited LLM/vocabulary code and stale identity metadata. That is migration residue tracked by #72 and digital-convert#1, not a second intended production owner.
3. **`atrium-keyword-extract` is not yet a completed controlled-LLM production service.** The statistical service is released; controlled extraction is still under active evaluation and integration in #1/#2/#73.
4. **The record is canonical.** Markdown is a derived LLM input view; TEITOK is the spatial linguistic view; neither should become an accidental second source of truth for keywords or quality.
5. **The “nothing lost” claim for Markdown is scoped.** Source text/layout cues must survive. Entities and keywords remain in the record by design.
6. **The repository set is six production stages, not seven.** `atrium-project` is the coordination hub; `atrium-llm-enrich` and `atrium-alto-postprocess` are predecessor identities.
7. **Release/repository hygiene is still part of the migration.** #72 still tracks immutable release mechanics, shared-layer pins, the final digital-convert image, the versioned vocabulary asset, and retirement/archiving of predecessor repositories.
