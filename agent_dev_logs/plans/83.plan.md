## Form and content: who decides what (2026-11-09)

An archive document has a **form** (what it is: a report, a site photograph, a trench plan, a map, an object drawing;
printed, typed or handwritten; a table or a form; its paper and its condition) and a **content** (what it is about:
periods, sites, features, finds, materials, methods, places). AMČR keeps the two apart: `dokument_typ` and the other
`dokument_*` lists describe the record, TEATER and the content hesláře describe its subject. The decision models
follow the same split, by what each tool can see:

| Tool                | The model sees       | Decides                                                                                                                                                                                              | Options from                                                                                                                     | Never                                                   |
|---------------------|----------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| page-classification | a scanned page image | **form**: layout and script (B1/B2), page elements and processors (B3), condition and orientation (B4); Track 2: AMČR picture type, object count, **depicted objects** (Artefact, Material, Feature) | hub `page-category`; AMČR `dokument_typ` picture types (digital-convert's list, when Track 2 is written); TEATER's visual facets | text input; genre; dating, culture, find context, place |
| digital-convert     | rendered PDF pages   | **form**: AMČR `dokument_typ`. A page: its medium (`group`) and picture type; a document (first ≤ 4 pages): the full type, the written genres included                                               | AMČR `dokument_typ`, 32 of 41 terms                                                                                              | the text layer; content terms                           |
| keyword-extract     | OCR text lines       | **content**: a TEATER ∪ AMČR term by descent, or meta-text                                                                                                                                           | the union vocabulary, without AMČR's `dokument_*` lists and without 22 form-like TEATER terms                                    | images; document type; form terms                       |
| ocr-postprocess     | OCR text lines       | **text quality**: ten symptoms, a 0–4 score, the line category                                                                                                                                       | hub `line-category`                                                                                                              | images; the page's orientation or script; content       |

- **Form terms inside the content vocabulary.** TEATER has no form facet, but some content branches name a kind of
  record: `dokumentace` and its kinds, `nálezová správa`, `fotografie`, `kresba`, the kinds of map, the
  remote-sensing products. A line naming one is mostly a caption or a reference to the archive's own documentation,
  so keyword-extract withholds these 22 terms from its decision tree (not from the vocabulary or the pilot's prompt).
  Scripts, written artefacts and the aerial methods stay: a line names them as content.
- **The written genres** (field report, annex, expert or client report, brief report, other text) are form, but
  only reading tells them apart. They are asked by digital-convert of a whole document, from its first page images,
  where the title page shows them; a page is asked only its medium and, for a picture, its picture type.
- **Depicted objects** are the one content an image tool decides, and only what can be seen (Artefact, Material,
  Feature), in page-classification's Track 2. A picture's label text is transcribed and goes on as text.
- **Cross-checks, never inputs.** Where two tools see the same item, their answers are compared in the evaluation:
  digital-convert's `group` against page-classification's label, ocr-postprocess's inverted-letter symptom against
  B4 orientation. One tool's answer is never sent to another's model.
- **Gold follows the split.** Form gold: AMČR's catalogue type per document, and annotators looking at images.
  Content gold: keyword-extract's `gold_workbook.csv`, labelled from text.

## The shared client

- **What it is:** `decision_client.py`, written in page-classification (#58 Phase 0). It is a single file with no
  torch, using the standard library and `requests`.
- **How it is pinned** (`docs/shared_components.md`):
  - **Rule 1:** one owner, page-classification. Consumers never edit the copy.
  - **Rule 2:** each consumer records `VENDORED` (the SHA-256) and `ADOPTED` (`owner`, `commit`, `release`) in
    `tests/test_vendored_decision_parity.py`.
  - **Rule 3:** adoption is a reviewed change, made in each consumer's own pull request.
- **The row it gets** in the table "Who owns what":

  | Component                                    | Owner               | Consumers                                         | Role in the consumer                                                                                                                           | Adopted revision recorded in                                          |
  |----------------------------------------------|---------------------|---------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
  | `decision_client.py` (decision-model client) | page-classification | ocr-postprocess, digital-convert, keyword-extract | experimental: offline CLIs (`tools/decide_lines.py`, `tools/decide_documents.py`; `dm_run.py`'s line mode, not yet written); not in the images | `ADOPTED` in each consumer's `tests/test_vendored_decision_parity.py` |

- **The client is a tool-to-tool copy,** not a hub-canonical file, so it is not in `docs/templates/shared/MANIFEST.json`.
- **In digital-convert** it enters the service image with the stage, so it is listed in that repository's
  `.github/production-image.json`. Elsewhere it stays out of the images.
- **Its class:** the client changes no record and no service response, so a client change is class (a).
  digital-convert's new report fields are class (b) for its `/describe` contract. A record field would be class (c).

## Out of scope

- A change to the pilot set, a production default or the record.
- Hosted inference on archive data: Workers AI, OpenRouter or any external API.
- Fine-tuning, including Cloudflare's tuning service, before a zero-shot result justifies it.
- Using the endpoint's generative model as a candidate. It can be a separate comparison in a child, if proposed there.
- A question asked from the wrong input: form from text, content an image cannot show, or text sent to an image
  tool's model ("Form and content").
