# Strategy — Issue #27: H100 node — running models on multiple GPUs

> Issue [\#27](https://github.com/ufal/atrium-project/issues/27) · Labels: `development` · Milestone: Q4 [WP3] · **Status: 📝 Recommendation posted (2026-06-21), not yet validated on real hardware**

## Context
MiniMax-M3 (~428B params, ~440GB FP8 checkpoint) needs multi-GPU tensor-parallel sharding to fit
on any single card. The research comment on this issue already picked the mechanism (vLLM/SGLang,
`--tensor-parallel-size 8 --enable-expert-parallel`) and ruled out Ollama's layer-split (compute,
not memory, offload — wrong tool for cooperative sharding). What's missing is exactly the same gap
#26 had before its own plan.md: **a real run on real hardware**, plus explicit coordination between
the two issues, since #26's plan already names this issue as its complementary counterpart.

## Strategic actions

### A — Confirm node topology before anything else
Run `nvidia-smi --query-gpu=name,memory.total --format=csv` and `nvidia-smi topo -m` on the actual
target node. If it isn't the assumed 8×80GB SXM5 NVLink/NVSwitch configuration, the
`--tensor-parallel-size` and expected throughput both need recalculating before the recipe is
trustworthy.

### B — Validate in practice (the deliverable that moves this off "recommendation only")
Launch the drafted `vllm serve` command (nightly build or maintained Docker image, per the
comment's own caution about brand-new support) against the actual node, and capture: startup logs,
confirmation the `minimax_m3` tool/reasoning parsers and `--enable-auto-tool-choice` work
end-to-end, and basic throughput (tokens/s) at the chosen `--max-model-len`.

### C — Reconcile framing with #26
#26's plan.md §F already states the intended relationship: TP/EP sharding (this issue) consumes
all local VRAM first; CPU offload (#26) tops up the remainder for cases needing both — the 235B/
444B-class models named in both issues. This plan should be read alongside #26's rather than in
isolation, and any future write-up of "how ATRIUM runs oversized models" should present both
mechanisms together.

### D — Document once validated
No README/docs location currently mentions this recipe. Once §B produces a real run, the natural
home is the same place #26's CPU-offload documentation was recommended to land — a shared
"running models larger than available resources" section, covering both TP/EP sharding and offload
as complementary tools rather than two separate stories.
