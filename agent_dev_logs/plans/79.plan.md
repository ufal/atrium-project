## Context

The technical content exists and is mostly tested. What is missing is the order a reader meets it in. Four READMEs are over 1,100 lines, most headings carry emoji, and 26 in-page links are broken because GitHub keeps U+FE0F in heading ids. Measurements, dated decisions and full service tables sit in the user path. The work is editorial: move, shorten and link, keeping every fact.

What can be reused:
- the ownership rule in `docs_site/contributing-standards.md:102-106`;
- #77's service README outline (`docs/templates/skill/serviceREADME.template.md`) as the operations layer;
- each repo's committed `service/openapi.json` as the one API contract;
- each CONTRIBUTING.md "Release History" as the changelog (no new CHANGELOG files);
- `tools/runbook_check.py` as the model for a stdlib check over the six repos.

## Done-criteria
1. The guide and the skeleton are in the hub and linked from the site and from the six READMEs.
2. Each README answers the six questions of the issue within the skeleton, at about 250 lines or less.
3. Each repo has a copy-and-run example with its expected result, checked at a release tag.
4. Rules, parameters, measurements and decisions sit in reference, evaluation or decision pages; each PR has a relocation map showing nothing was dropped.
5. `tools/docs_check.py` passes on the six repos at their tags.
6. One contract, one home: the README links the service README and `service/openapi.json`.
7. **(c)** A newcomer per repo reports the quick start works and the reference is findable.
8. The per-repo PRs are listed on #79.
