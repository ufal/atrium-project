## Context
WP4 asked for the tools as Galaxy *actionable workflows*: a workflow described on the SSH Open Marketplace that can
also be run. The reviewer (Mark A. Greenwood, DARIAH) marked them green. The issue's first step is information: what
the wrap-up needs, published before any Galaxy record exists. The research of 2026-09-25 found two things that shape
everything after it:

1. **The pattern already exists in ATRIUM.** DARIAH's
   [`atrium-galaxy-tools`](https://github.com/DARIAH-ERIC/atrium-galaxy-tools) wraps other ATRIUM components as local
   Galaxy tools and pairs the T4.2.1 Galaxy workflow with its SSH Open Marketplace narrative `IrpmkB`.
2. **ssh.usegalaxy.eu is usegalaxy.eu** under another name. Getting a tool there means ToolShed publication and a PR to
   `usegalaxy-eu/usegalaxy-eu-tools`, which is a different route from DARIAH's repository.

So the first question for DARIAH is not "what does ssh.usegalaxy.eu need" but "which Galaxy, and which route".

## Strategic actions

### A — Ask (user, one message to Mark A. Greenwood)
1. **Which Galaxy** is "ATRIUM's Galaxy space": DARIAH's own instance (the one `atrium-galaxy-tools` deploys to), or
   ssh.usegalaxy.eu?
2. **Which route** for ÚFAL's tools: a PR adding wrappers to `atrium-galaxy-tools` (`tools/` + `atrium_tools.xml`), or
   ToolShed publication and a `usegalaxy-eu-tools` PR — or both, DARIAH's first?
3. **Containers or conda.** Our tools ship as images on GHCR (`ghcr.io/ufal/atrium-<tool>:<version>`) and are not
   conda packages. Is `<container type="docker">` with a GHCR image acceptable on the target server?
4. **Network and models.** page-classification downloads model weights from the Hugging Face Hub; the translator
   calls LINDAT's translation and UDPipe services and downloads a FastText model. Do jobs have outbound network, or
   should models be staged (the `huggingface` data table)?
5. **GPU** for page classification on large collections and for the LLM stages later — available, and how requested?
6. **Workflow metadata.** Our `.ga` files will carry an annotation, creators with ORCIDs, a licence and labelled
   inputs and outputs, from the narratives. Does DARIAH want the same for theirs, or a shared convention?
7. **Access** for the three accounts named in the issue.

### D — The rest, in pipeline order, when each tool's workflow settles
alto-postprocess (`alto`/`json` → `tabular`, `txt`), nlp-enrich (`tabular` + `alto` → `tei`, CoNLL-U as `tabular`),
llm-enrich (`tabular`/`tei`/`markdown`/`pdf`/`docx` → `json`). Between steps the record passes as a `json` dataset
(`--document-json` / `--document-json-out`). Closest existing tools, which also bound what is worth wrapping:
Kraken/Tesseract upstream of alto-postprocess; `stanza_nlp` beside nlp-enrich; DARIAH's
`atrium_pdf_text_extraction` + `atrium_t4_1_2_ie` and `llm_hub` beside llm-enrich.
