> ## 🧭 2026-10-02 — six repositories, one Galaxy rule
>
> - The target set is now `digital-convert`, `page-classification`, `translator`, `nlp-enrich`, `ocr-postprocess`, and `keyword-extract`.
> - **Galaxy wraps the same released production service images as ATRIUM.** It does not duplicate the production Temporal workflow.
> - The first wave is `translator` + `page-classification`, because their workflow narratives already contain full Galaxy sheets.
> - `ocr-postprocess`, `nlp-enrich`, and statistical `keyword-extract` follow after their Galaxy sheets are brought to the new service/repository contract.
> - `digital-convert` is deliberately last until `api-digital` is the actual released production service. Its `v1.0.0-beta` still has the former `atrium-llm-enrich` identity.
> - The controlled LLM keyword kind is **not** a production Galaxy capability yet; `keyword-extract` `v1.0.0-beta` exposes the statistical service while the controlled kind remains a research target.

## Context and settled boundary

WP4 asked for the developed tools as Galaxy *actionable workflows*. The 30 September integration note settled the architectural boundary:

> **Galaxy is the external-user sandbox, not the production workflow. Galaxy should wrap the same released service images as the ATRIUM tools and expose actionable workflows where useful. The full production chain remains Temporal-based and is not being duplicated in Galaxy.**

This means #66 is an integration/documentation/publication task, not a request to redesign the six services for Galaxy.

The current public ATRIUM Galaxy implementation pattern is [`DARIAH-ERIC/atrium-galaxy-tools`](https://github.com/DARIAH-ERIC/atrium-galaxy-tools). A second possible publication route is the public usegalaxy.eu ToolShed / [`usegalaxy-eu-tools`](https://github.com/usegalaxy-eu/usegalaxy-eu-tools) path. Which one is authoritative remains an external question for Mark A. Greenwood.

## Phase A — Freeze the integration contract before writing wrappers

### A1 — Use the new repository set everywhere

Replace every #66 reference to the former five-tool set with:

```text
atrium-digital-convert
atrium-page-classification
atrium-translator
atrium-nlp-enrich
atrium-ocr-postprocess
atrium-keyword-extract
```

The retired repositories `atrium-alto-postprocess` and `atrium-llm-enrich` remain historical sources only. Do not create new Galaxy wrappers under those identities.

### A2 — Make the `-api` production image rule explicit

The wrapper source of truth is the service image selected by `atrium-project#72` and declared in each repository's `.github/production-image.json`.

The Galaxy layer must therefore:

1. pin a concrete released service image/tag;
2. call only the documented service endpoint or the thin runner required by the target Galaxy integration;
3. avoid copying the processing implementation into the Galaxy repository;
4. carry the same input/output contract, limits and error semantics as the service;
5. record the exact image tag in Galaxy tool metadata/test definitions.

The batch images (`…-translator`, `…-page-classification`, etc.) and the research `keyword-extract-llm` image are not the #66 production baseline.

### A3 — Keep capability scopes honest

- `keyword-extract`: publish the **statistical** workflow first. Controlled vocabulary/LLM is a future capability.
- `digital-convert`: document the intended workflow now, but do not publish a wrapper until `api-digital` is the released production identity.
- `translator`: default workflow mode should be the AMČR-compatible `replace` mode; keep `append` only as an explicit option if the Galaxy contract needs it.
- `page-classification`: document GPU as an acceleration option, not a hard prerequisite.

## Phase D — Build the wrappers in two publication waves

### D1 — First wave: translator + page-classification

These are the two tools with the most complete Galaxy-facing narratives and the clearest sample data.

For each tool:

1. create/update the Galaxy tool definition in the chosen publication repository;
2. pin the released `-api` service image/version;
3. map Galaxy datatypes to the API inputs/outputs defined in the workflow page;
4. expose only stable service parameters;
5. add `test-data/` from the existing repository samples or a minimal deterministic derivative;
6. write `-tests.yml` / Planemo test coverage for the normal path and one meaningful validation/error case;
7. create the actionable `.ga` workflow from the narrative step sequence;
8. link the Galaxy workflow to its SSHOMP workflow record and vice versa where the record exists.

**Translator-specific:** make `replace` the pilot/default path because that is the AMČR-compatible mode.

**Page-specific:** use image collections (`png`/`jpg`) as the primary Galaxy input; treat PDF rendering as a documented service capability rather than duplicating the renderer in Galaxy.

### D2 — Second wave: OCR + NLP + statistical keyword extraction

Follow the actual processing dependency chain:

```text
ocr-postprocess → nlp-enrich → keyword-extract (statistical)
```

For each:

- use the released `-api` image;
- expose the stable production endpoint only;
- preserve the service's output formats and limits;
- record network dependencies explicitly;
- use the repo's current samples as wrapper tests;
- make the renamed identities visible in every Galaxy-facing label and image reference.

**OCR post-process:** the broad text-bearing input contract now covers ALTO, PAGE XML, hOCR, ABBYY and JSON through the current reader layer; the Galaxy tool can expose the supported stable subset agreed with the actual test data rather than inventing new conversions.

**NLP enrichment:** represent CoNLL-U as `tabular` because Galaxy has no dedicated CoNLL-U datatype; keep ALTO/image inputs only where they are needed for positional TEITOK output.

**Keyword extraction:** first wrapper is `kind=statistical`. Do not make the workflow depend on the research `llm` image.

## Phase E — Finish `digital-convert` only after `api-digital` is real

Track [`atrium-digital-convert#2`](https://github.com/ufal/atrium-digital-convert/issues/2) to completion:

- independent `api-digital` production service exists;
- final service id / program id / image names are stable;
- `.github/production-image.json` describes the converter rather than the transitional keyword target;
- final release is published;
- hub workflow page is refreshed to the released implementation.

Then add the Galaxy tool and workflow:

```text
PDF / DOCX → digital-convert → ATRIUM document JSON
```

The converter itself does not call page-classification or OCR; the orchestration decides what happens to pages marked `needs_ocr`. Galaxy should reflect that separation rather than embedding a hidden multi-tool pipeline into the converter wrapper.

## Phase F — SSH Open Marketplace / workflow linkage

Maintain one source-text direction:

```text
Repository service contract
        ↓
Hub Workflow narrative
        ↓
Galaxy tool + actionable .ga workflow
        ↕
SSH Open Marketplace workflow record
```

For records that already exist, update links to the new successor repository/image names. For the new repositories without a current workflow record (`digital-convert`, `keyword-extract`) do not block internal Galaxy tool development on a fabricated record; instead create/refresh the corresponding SSHOMP workflow item when the external record workflow is available.

Keep version numbers in tool/release metadata rather than hard-coding them into durable narrative prose, matching the existing hub Workflows convention.

## Out of scope

- Reimplementing any processing algorithm for Galaxy.
- Making Galaxy the production orchestration layer.
- Publishing the research `keyword-extract-llm` target as a production Galaxy service.
- Publishing `digital-convert` against the transitional `atrium-llm-enrich` image identity.
- Creating a separate duplicate Galaxy documentation system outside `docs_site/workflows/`.
- Adding GPU dependence to the Galaxy pilot merely because some tools can use a GPU.
