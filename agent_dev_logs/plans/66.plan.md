- Two page-classification bugs found on the way: an unreadable image shifts every later prediction onto the
  wrong file in a directory run; with `-tn 1`, SCORE-1 holds the class number. The wrapper guards against both.


## Scope and guardrails

- Wrap the same **released `-api` image** and documented endpoint for each selected stage; do not copy internal processing code into Galaxy wrappers.
- Scope the initial work to the translator and page classifier; then add OCR post-processing, NLP enrichment, statistical keyword extraction and born-digital conversion.
- Keep the production orchestration Temporal-based. Galaxy exposes selected steps/workflows for external users; it must not claim to replace the AMČR production chain.
- A Galaxy image requirement likely supports GHCR containers on the DARIAH instance and probably on `ssh.usegalaxy.eu`, but portability is not guaranteed. Verify how the HTTP service image is started and called from a per-job tool wrapper.
- Use precise capability boundaries: statistical `keyword-extract` only initially; controlled keywords are out until its model-backed path is evaluated. GPU support on `ssh.usegalaxy.eu` is unverified; DARIAH has no GPU.

## Phase B — Wave 1 tool contracts and prototype

The current hub `test` pages for `translator` and `page-classification` already provide full Galaxy sheets. Use them as the contract source and refresh their release/source lines when the wrappers are authored.

### Translator

- Pin `ghcr.io/ufal/atrium-translator-api` to a specific tested released tag (latest release observed: `v1.5.0-beta`; use the corresponding concrete image tag format verified in the tool release).
- Wrap `POST /translate`; honour the page's supported XML/ALTO inputs and optional vocabulary, XPaths/mode, and outputs (translated source structure, CSV log, paradata/record outputs as documented).
- Default to the backend configuration already documented; identify outbound-network requirements (LINDAT/UDPipe, Hugging Face language ID, vocabulary release asset) and decide how the Galaxy environment will satisfy them.
- Include one successful test and one invalid-input/unsupported-language error test.

### Page classification

- Pin a specific tested tag of `ghcr.io/ufal/atrium-page-classification-api` (latest release observed: `v1.9.5-beta`; verify the tag format).
- Wrap the documented image/document prediction endpoint(s) and ensure input collection semantics, output table/JSON mapping, batch sizing and error messages fit Galaxy expectations.
- Test on DARIAH's CPU-only runner first. Do not assume a GPU is available or required for the first working wrapper.
- Include one normal-path and one validation/error-path Planemo test with repository test data.

### Validation common to both

- Demonstrate that the `-api` image actually runs inside a Galaxy job in the intended container model: service process lifecycle, localhost/network binding, request execution, file hand-off, timeouts, and clean exit must be proven.
- Planemo-test every tool; assert output files and meaningful error behaviour, not merely a zero exit code.
- Pin image tags and record the tested release, wrapper commit, target instance, runtime and resource limits.
- Check data handling/licence assumptions, particularly when an external service or model provider is involved.

## Out of scope

- Re-implementing or replacing the Temporal production chain in Galaxy.
- Treating a Docker image declaration alone as proof that an HTTP service container is correctly callable.
- Exposing the controlled keyword extraction path before its backend, key/configuration and evaluation requirements are met.
- Assuming GPUs, outbound network or public ToolShed availability without confirmation.
- Updating remote repositories or creating PRs as part of this plan; those actions remain with the project maintainers.
