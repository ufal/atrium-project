## T2 — `@v1` pin migration — ✅ DONE

26 references moved from `@test` to `@v1`: **20 live callers** (4 files × 5 repos) and **6 doc
examples**. Leaving the examples behind would have reintroduced the mutable pin in whichever repo
next adopted a template.

Plus the 27th, which a find-and-replace would have got wrong: `para-drift.reusable.yml` hardcoded
`ref: test` for the hub checkout supplying the canonical `docs/templates/shared/*` files. Left alone,
the pin would have been half-done — workflow *logic* from the immutable tag while the *files it
enforces* still came from a mutable branch, defeating the pin for the one reusable whose whole job is
comparing files. Now a **`hub-ref` input** defaulting to `v1`; `@test` callers pass `hub-ref: test`.

**Two channels**, documented in `docs/docker_gha.md` §1:

| Channel | Who uses it                              | Mutability                                      |
|---------|------------------------------------------|-------------------------------------------------|
| `@v1`   | every caller in every tool repo          | moving major tag; only a maintainer advances it |
| `@test` | pre-release validation before `v1` moves | branch — moves on every merge                   |

**Prerequisite for the hub-ref default to take effect:** `v1` must be moved onto the commit carrying
the `hub-ref` input. Until then `@v1` resolves to `ef339ab`, which lacks it — harmless, since the
default only matters once it exists, but the two disagree until the tag moves.

**Remaining:** branch protection on the hub's `main`/`test` is a repo-settings action, not code.

## T6 — caller-example templates — ✅ DONE (2026-07-31)

The ten templates in `docs/templates/workflows/` are **not covered by CI** — nothing parses or runs
them — so they drift silently when a reusable changes. Two defects, both now fixed:

1. **`codeql.caller.example.yml` was a byte-identical copy of the Docker example** — wrong `name:`,
   wrong reusable, page-classification Docker inputs. Fixed upstream in `79e2b70`.
2. **`docker.caller.example.yml` under-granted permissions.** Its `build` job declared an *explicit*
   block of only `{contents: read, packages: write}`, while `docker-tool.reusable.yml`'s
   `build-and-push` requests `security-events: write` for the SARIF upload. Because a reusable's job
   permissions are capped by the calling job's grant, copying this template reproduced the **Wave B
   `startup_failure`** exactly. No live caller used it, so nothing broke in practice — but this is
   the file that teaches the pattern. Also dropped the leftover `secrets: inherit` (Wave C never
   reached the template) and added the tag-exempt `concurrency` block all five live callers carry.

**The distinction to remember:** an *explicit* permissions block that omits a scope fails at parse
time; **no** block at all inherits the repo default and is fine. `skill-validate.caller.example.yml`
has no block and is correct — it flags on a naive check and is a false positive, not a third bug.

Checked by YAML parse, not grep: the explanatory comments legitimately contain the literal string
`secrets: inherit`, so grep reports the opposite of the truth here.

## T4 — Remaining decisions

- ~~**Trivy blocking severity.**~~ ✅ **DECIDED 2026-07-31.** Rather than flipping the existing step,
  a **separate gate** was added to `docker-tool.reusable.yml`, keeping two concerns apart: the SARIF
  step still runs on every build and never blocks, so the full CRITICAL+HIGH picture always reaches
  code scanning; the new step blocks, and only where blocking is worth it. It sits **after** the SARIF
  upload deliberately — if it fails, the findings are already in the Security tab, so the failure is
  diagnosable there and not only from the job log.

  | Narrowing                                   | Effect                                                     |
  |---------------------------------------------|------------------------------------------------------------|
  | `if: startsWith(github.ref, 'refs/tags/')`  | pushes and PRs untouched; it stops a *release*             |
  | `severity: CRITICAL`                        | HIGH stays report-only — too noisy to hold a release on    |
  | `ignore-unfixed: true`                      | an unpatchable CVE cannot wedge releases indefinitely      |

  The weekly `security.reusable.yml` scan stays report-only — blocking a scheduled scan stops nothing
  from shipping. **Caveat:** the code scanning alerts were not readable from the session that made
  this change, so the design was chosen to fail safe rather than from a triaged list, and it cannot
  fire without a tag push. The first tagged release is the real test; reverting is one value.
- ~~**gitleaks.**~~ ✅ Done — template deleted 2026-07-30. `docs/docker_gha.md` and
  `docs/plan_repo_review.md` §Phase 4 updated to record the decision rather than leave it "paused".
- ~~**SHA-pin write-scoped third-party actions.**~~ ✅ **DONE 2026-07-31.** 11 pins across 6 files in
  all 6 repos: `softprops/action-gh-release` ×5 (`contents: write`), `docker/build-push-action` ×3
  (GHCR push under `packages: write`), `aquasecurity/trivy-action` ×2, and
  `peter-evans/create-pull-request` ×1 (`contents` + `pull-requests: write`). Read-only and
  upload-only actions stay on tags.

  The precedent is in this repo's own history: `security.reusable.yml` already documented that
  trivy-action tags ≤ 0.34.2 were force-pushed to credential-stealing malware on 2026-03-19
  (GHSA-69fq-xp46-6x23, 76 of 77 tags) and recommended pinning to the release commit. That advice had
  been sitting unacted-on.

  **Trap:** `v3` and `v0.36.0` are *annotated* tags, so `git ls-remote refs/tags/<tag>` returns the
  tag object, not the commit — pinning that SHA does not work. The `^{}` deref is required, and two
  of the four needed it. Dependabot maintains SHA pins and the trailing `# v3` comment, so this
  hardens without freezing.
