> **Status: 🟡 Not started. Two mechanical fixes; the sweep is already done ([`../digests/64.digest.md`](../digests/64.digest.md)) and it narrows the second one to a single file — with one file in the same repo that must be left alone.**

## Context

Factor X asks that development, staging and production stay similar. Two divergences remain after #53's sweep, and the third thing it recorded under factor X — that CI never starts the image the way production does — was split out as [\#62](https://github.com/ufal/atrium-project/issues/62).

Neither remaining item is architecturally interesting. Both are the kind of thing that stays broken for a year because it is too small to schedule, and each produces a real failure: one gives a partner a copy-pasted command that cannot work, the other tests the product on a runtime it never runs on.

## Strategic actions

### A — Pin the translator lane to 3.11

`scheduled-smoke.yml:51` → `python-version: '3.11'`. Every image is `python:3.11-slim`; every other lane in every other repo is already 3.11.

Expect this to surface something. A suite that has only ever run on 3.12 in this lane may have absorbed a 3.12-only behaviour, or may start failing on a 3.11 deprecation it never saw. **That is the finding, not an obstacle** — it is precisely the parity gap the issue is about, and it should be fixed in the product, not by reverting the pin. Run the job manually after the change rather than waiting for the schedule.

### B — Answer D1 in the same PR, even if the answer is "no change"

The job runs `pytest tests/ -rs` where roadmap D1 expects the slow subset (`-m slow`). The issue defers this ("decide separately"), which is how it got filed in the first place.

Two defensible outcomes:

1. **Narrow to `-m slow`** — the job becomes what its name says, runs faster, and stops duplicating the PR lane.
2. **Stay broad** — a scheduled full run catches environment drift the PR lane cannot, which is a real reason.

Either is fine; leaving it undecided is not. If it stays broad, put the reason in a comment above the `run:` line so the next person auditing it does not re-file D1.

### C — Fix the B7 header, and do not sweep

`atrium-nlp-enrich/docker-compose.gpu.yaml:1-3` — four references to `docker-compose.yml` / `docker-compose.gpu.yml` in a header documenting two files that are `.yaml`:

```
# GPU override — combine with docker-compose.yml:
#   docker compose -f docker-compose.yml -f docker-compose.gpu.yml run --rm nlp
#   docker compose -f docker-compose.yml -f docker-compose.gpu.yml --profile llm run --rm nlp-llm
```

Both printed commands fail with "no such file". Fix the four references. `llm-enrich`'s equivalent header (`docker-compose.gpu.yaml:1-2`) is already correct and is the model.

**Do not run a find-and-replace in nlp-enrich.** The repo contains `annotation/docker-compose.yml` — a genuine `.yml` file for the standalone Label Studio / Doccano campaign deployment, with its own `annotation/env.example`, documented at `annotation/README.md:14`. A repo-wide rename breaks a working deployment. This is a four-line edit to one comment.

The sweep the issue asks for has been run and is in the digest: three repos use `.yml`, two use `.yaml`, and nlp-enrich is the only one whose header disagrees with its own directory.

### D — Leave the extension split alone

Recommend explicitly **not** converging the ecosystem on one extension. Docker Compose accepts both; nothing is failing because of the split; B7 was caused by a header not matching its directory, not by the split itself. Converging means touching five repos' docs, compose invocations and CI for no functional gain, in a project heading into a pre-closure architecture review.

If someone wants to converge anyway, that is a separate issue with its own justification — not a rider on a header fix.

### E — Consider making the version stick

After §A, `python-version: '3.11'` holds by convention alone, and the next workflow added can differ silently — which is how the current lane happened.

A grep-based check (every `python-version` in every workflow must match the Dockerfile base) is a few lines and closes the loop. Same argument [\#59](https://github.com/ufal/atrium-project/issues/59) makes about `SHARED_FILES` and [\#60](https://github.com/ufal/atrium-project/issues/60) makes about the env tables: a fact maintained by hand in several places will drift. Optional for this issue; recommended if the check is trivial in the hub's existing `tools/ci/` layout.
