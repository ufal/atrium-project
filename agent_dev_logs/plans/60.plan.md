# Strategy — Issue #60: publish the environment-variable contract

> Issue [\#60](https://github.com/ufal/atrium-project/issues/60) · Labels: `enhancement`, `development` · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor III)
> **Status: 🟡 Not started, and correctly last in its dependency chain. The measured variable inventory — the hard part of the deliverable — is in [`../digests/60.digest.md`](../digests/60.digest.md).**

## Context

The ecosystem reads configuration from the environment in 178 places and documents that fact nowhere a partner will look. `docs/k8s_deployment.md` — the reference ARÚP/ARÚB deploy against — contains the string "env" zero times, while the manifest it documents sets `PORT` and comments out `ALLOWED_ORIGINS` and `MAX_UPLOAD_MB`. One `.env.example` exists in the ecosystem, in alto-postprocess, four lines long.

This is the least urgent of #53's findings and the one most likely to be done badly, because "write documentation" invites writing down whatever is currently true rather than deciding what the contract *is*. Two decisions have to precede the writing, and one hard ordering constraint applies.

## The ordering constraint

**Do not document `PORT` as a working knob until [\#58](https://github.com/ufal/atrium-project/issues/58) lands.**

`PORT` is read in all five `service/` trees — but by `service/healthcheck.py:49`, not by the server, in four of them. Setting it today moves the health probe and not the listener, so the container reports unhealthy at any non-default value (#58, Finding 1). A table that lists `PORT` as supported would be documenting a bug into the partner-facing reference, immediately before the acceptance round that reference exists for.

The same applies more mildly to two other rows: `HOST` and `GRACEFUL_SHUTDOWN_S` exist only in alto today and arrive in the other four **via #58**; `LOG_LEVEL` exists only in alto and arrives via [\#61](https://github.com/ufal/atrium-project/issues/61). And `UDPIPE_URL`/`LINDAT_BASE_URL` arrive via [\#63](https://github.com/ufal/atrium-project/issues/63), which the issue already notes.

So the real dependency order is **#58 → #61 → #63 → #60**, not the "#63 → #60" the issue states. Writing #60 first means writing four rows that are false at the time of writing and true later, which is worse than writing them once.

## Strategic actions

### A — Decide what belongs in the contract, then write it

The inventory has 34 names. Roughly a third are not deployment configuration and must not be published as if they were:

- **Publish**: `PORT`, `HOST`, `ALLOWED_ORIGINS`, `MAX_UPLOAD_MB`, `LOG_LEVEL`, `GRACEFUL_SHUTDOWN_S`, `HEALTHCHECK_PATH`, the backing-service URLs (`OLLAMA_HOST`, `OPENROUTER_*`, `LLM_BASE_URL`, and #63's additions), and the operational limits a partner will actually need to change (`API_JOB_TIMEOUT`, `MAX_CONCURRENT_JOBS`).
- **Do not publish as config**: `GPT2_MODEL_NAME`, `LAYOUT_MODEL_PATH`, `LANGID_CONFIG`, `LR_CHUNK_SIZE`, `LR_MIN_CHUNK_SIZE`, `MAX_WORDS`, `MAX_RESCALE_DIM`, `DEFAULT_KW_METHOD`, `LLM_CONTEXT_WINDOW`, `VOCAB_PATH`. These are algorithmic parameters that happen to be env-readable. #53's plan is explicit that factor III does not ask for them, and listing them in a partner-facing table invites tuning that the project cannot support.
- **Deprecated, name as such**: `MAX_UPLOAD_BYTES` (`service/atrium_service.py:350-359` prefers `MAX_UPLOAD_MB`; the byte form is a compatibility fallback). Documenting both as equals would introduce an ambiguity the code does not have.
- **Do not publish at all**: `RELOAD` — a filesystem-watcher switch in a production image (roadmap B8's subject). It exists; it should not be advertised.

### B — Write the five `.env.example` files against a fixed shape

Use alto's as the template and nlp-enrich's `annotation/env.example` for the comment idiom it already established:

```
# Copy to .env and edit before `docker compose up -d`. Do not commit .env.
```

Rules that keep these useful rather than decorative:

- Service-layer variables only. Not batch-pipeline knobs — the `api` image is what partners run.
- Every entry carries its **default**, and the default in the file is the default in the code.
- Credential-shaped keys (`OPENROUTER_API_KEY`) get placeholder values and never a real one. This is the one line of these files that has a security consequence.
- page-classification's file will be nearly the common block alone (four variables). That is the correct output, not an omission.

### C — One table in `docs/k8s_deployment.md`, cross-referenced from the manifest

Structure: a shared table (the four common variables plus the operator set #58/#61 add), then a short per-repo delta. Cross-reference it from the `env:` block in `docs/templates/k8s/atrium-service.deployment.yaml:54-56` so a reader arriving from the manifest lands on the table, and add the reverse pointer.

The runbook matters too: `docs/k8s_acceptance_runbook.md` walks ARÚP/ARÚB through the deployment. Any variable they need in order to complete it belongs in the table before that round runs.

### D — Make the tables checkable, not just written

The issue's own acceptance bullet says to check with a script "or the tables rot within a release". Treat that as required. Five `.env.example` files plus one doc table is six new hand-maintained enumerations of facts that live in code — structurally the same failure [\#59](https://github.com/ufal/atrium-project/issues/59) exists to fix for canonical files, being created deliberately here.

Minimum viable check: a test that greps `os.getenv`/`os.environ.get` literals under each repo's `service/`, subtracts the documented "do not publish" set from §A, and fails when the remainder is not covered by that repo's `.env.example`. It runs in seconds and it is the only thing that will keep these files true.

## Verification / done-criteria

- [ ] Each of the five tool repos has a repo-root `.env.example` covering every **publishable** service-layer variable it reads, with correct defaults.
- [ ] `docs/k8s_deployment.md` documents every variable the reference manifest sets or comments out, and every variable the acceptance runbook needs.
- [ ] The check in §D exists, runs in CI, and **fails** when a new `os.getenv` is added to a `service/` module without a matching entry. Verify by adding one and watching it go red.
- [ ] No published variable is false at the time of publication — in particular `PORT` is documented only after #58 lands, and `LOG_LEVEL` only after #61.
- [ ] No credential-shaped key in any committed `.env.example` carries a real value.
- [ ] A reader with only the manifest and `k8s_deployment.md` can find every knob without opening a source tree. Test this on someone who has not read the code.

## Out of scope

- **Converting algorithmic parameters to environment variables.** Factor III is about deployment-varying config. Thresholds, model registries and chunk sizes are correct in files; moving them would make five config surfaces worse, not better.
- **Moving `translator/config.txt`'s `input_path`/`output`/`translation_backend` into the environment.** Named in the issue as file-held deployment config, unclaimed by any issue, and a behaviour change rather than a documentation one. Raise separately if it matters.
- **`atrium-nlp-enrich/annotation/env.example`.** Different deployment, different audience, already has its own template. Leave it alone and do not let a repo-root `.env.example` collide with it.
