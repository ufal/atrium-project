# Strategy — Issue #40: CI/CD: Enforce Branch Protection (GH) & Enable GPU Runner (GHA)

> Issue [\#40](https://github.com/ufal/atrium-project/issues/40) · Labels: `enhancement`, `development`, `ci`, `github_actions` · Milestone: Q3 [WP8/WP7] · **Status: 🟡 GPU half reframed by @motyc; branch-protection half stalled**

## Context
This issue bundles two originally-independent tasks that turned out to have very different shapes
once discussed. Branch protection is a straightforward GitHub-settings change with no external
dependency. The GPU runner task, as originally framed ("configure the external GPU runner"),
assumed a self-hosted runner reachable from UFAL's GitHub Actions — @motyc ruled that out on
governance grounds (ARUP/B data-handling boundary: GH Actions must not be wired to any ARUP/B
environment; the boundary is a Docker image built and run entirely inside ARUP/B's own fork/
Kubernetes cluster). The GPU half is therefore not "blocked on hardware" — it's "blocked on which
outside-infrastructure GPU service to use and how testing integrates with a service ATRIUM doesn't
control."

## Strategic actions

### A — Branch protection (independent, no blocker, do this first)
Apply GitHub branch-protection rules to `main` and `test`: require PR review, require the hub's
own CI checks (`hub-self-check`, `all-repos-smoke`, `codeql`, `pre-commit`) to pass, disallow force
pushes. This has no dependency on the GPU decision and is the cheaper of the two tasks — it should
not continue waiting on the GPU half to resolve. Owner: @stranak.

### B — Decide what "GPU testing" is actually for, before applying anywhere
Before applying to Metacentrum or evaluating CERIT's services, get an explicit answer to: which
`slow`-marked tests actually need a GPU (vs. just needing more wall-clock time), and does CI need
to *run* them on every push/schedule, or is an occasional manual/`workflow_dispatch` run on an
outside service enough? The original task assumed "wire CI to a runner"; @motyc's ruling makes that
the wrong default shape — a nightly/weekly manual trigger against an outside Metacentrum job is a
very different integration than a live self-hosted runner label.

### C — If Metacentrum is the answer, submit the application
`metavo.metacentrum.cz/en/application/form` is the concrete next step if §B concludes an outside
GPU grid is worth the integration cost. Whoever owns this should also check what CI-integration
pattern Metacentrum supports (does it expose anything GitHub Actions can dispatch to, or is this
purely a manual/offline validation path run by a person, with results posted back as evidence?).

### D — Re-scope the acceptance criteria
The original acceptance criteria ("workflows targeting the GPU runner successfully spin up,
execute `slow` tests, and tear down without hanging") assumed a live CI-integrated runner. If §B/C
land on a manual-trigger, outside-infrastructure model instead, the acceptance criteria need
rewriting to match — e.g., "a documented, repeatable manual procedure exists for running the
`slow` suite on Metacentrum, with the last run's result linked from this issue."

## Verification / done-criteria
- Branch protection live on `main`/`test`, verified by attempting (and having rejected) a direct
  push without a passing PR.
- Either: a self-hosted-runner-free GPU testing procedure is documented and has been run at least
  once with results posted here, or the ecosystem has made an explicit, recorded decision that GPU
  testing isn't worth pursuing at all for the remainder of the project.

## Out of scope
- The specific `slow`-marked tests themselves and which repos own them — see each tool repo's own
  DEVLOG (alto owns the one real GPU-concurrency test per the 2026-09-07 cross-repo digest).
- Model-serving GPU questions (#26, #27) — those are about production inference sizing, not CI.
