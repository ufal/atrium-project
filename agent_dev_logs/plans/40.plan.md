## A′ — Branch protection: current six repositories

**Owner:** @stranak / repository administrators

### A′.1 Scope

Apply the same protection model to:

- the default branch of each of the six tool repositories;
- `test` in each of the six tool repositories;
- the default branch of `atrium-project`;
- `test` in `atrium-project`.

Use the GitHub ruleset model already implemented by `scripts/release_trust.py`:

- changes through pull requests;
- no deletion;
- no force/non-fast-forward updates;
- required status checks where appropriate;
- administrator bypass retained and therefore auditable.

The ruleset should target `~DEFAULT_BRANCH` rather than assuming the default branch is literally `main`.

### A′.2 Required checks

Do **not** copy the pre-split list of required checks mechanically.

First run:

```bash
python3 scripts/release_trust.py checks --repo <repo> --branch test
```

for every current repository and record the actual check names. Select the stable repository-local checks that
represent the protected CI gate. The hub and each tool may have different check names because the current set
contains repository-specific workflows such as translator integration, nlp TEITOK validation and vocabulary
checks.

The required-check list must be stable enough that ordinary development is not blocked by optional/scheduled
jobs, while the core Docker, contract, provenance, security and formatting gates remain enforced.

### A′.3 Verification

For every repository:

- confirm the ruleset is active;
- confirm its refs cover the default branch and `test`;
- confirm deletion and force-push are prohibited;
- confirm the selected status checks are present;
- verify the ruleset with `release_trust.py status`;

Do not claim branch protection is complete from the existence of the script alone.

## F — Pin every hub reusable by commit

**Owner:** K4TEL / tool-repo maintainers

### F.1 Scope

The hub currently provides seven reusable workflows to the tool ecosystem. The current six repositories therefore
form a **42-reference nominal sweep** (6 × 7), rather than the former 35-reference five-tool sweep.

The actual invariant is:

> every `uses: ufal/atrium-project/.github/workflows/...` caller in the six current tool repositories names
> a 40-character commit SHA, with `# v1` retained as the human-readable channel marker.

The hub itself does not call its own reusable workflows as a tool-repo caller.

### F.2 Move `v1`, then pin

The pin must be the commit that the hub's `v1` tag points to:

```bash
git fetch --tags origin
git rev-parse 'v1^{commit}'
```

Then, from the hub checkout:

```bash
python3 scripts/pin_hub_reusables.py \
  --sha "$(git rev-parse 'v1^{commit}')" \
  --check
```

Review the list first. Then perform the sweep without `--check` and commit the resulting workflow changes
in the six tool repositories.

### F.3 Keep the second reference in lockstep

`para-drift` and `workflow-lint` do not only execute the reusable workflow; they also check out the hub using
`hub-ref`. Therefore the caller must carry the same SHA in both places:

```yaml
uses: ufal/atrium-project/.github/workflows/para-drift.reusable.yml@<sha>  # v1

with:
  hub-ref: <sha>
```

and equivalently for `workflow-lint`.

The existing linter already has the relevant invariant: a mismatched `hub-ref` must fail.

### F.4 Make SHA pinning mandatory

After all six repositories are pinned and green, enable the mandatory mode in the workflow-lint path:

```text
--require-sha-pins
```

The moving `v1` tag remains a release/channel pointer for maintainers, but it must no longer be a runtime
dependency of a caller.

### F.5 Verification

From each current tool repository:

```bash
grep -RIn "uses: ufal/atrium-project" .github/workflows \
  | grep -vE '@[0-9a-f]{40}([[:space:]]+# v1)?$'
```

must return no unpinned hub reusable.

Also verify that every `para-drift` / `workflow-lint` caller has a matching `hub-ref`.

Then run the normal workflow-lint and repository CI.

## G — Protect release tags

The tag ruleset is part of the same trust boundary.

Run:

```bash
python3 scripts/release_trust.py tag-rules
```

with the current repository set.

Expected scope:

- six tool repositories: `refs/tags/v*`;
- hub: `refs/tags/v1` and `refs/tags/doc-schema-v*`.

The rule must prevent tag update and deletion while retaining the documented administrator bypass.

This is especially important for AMČR's model: a production image is built from a reviewed release tag, so
retargeting that tag after review would defeat the release-trust guarantee.

## H — GPU runner: explicitly deferred

The original #40 GPU requirement is no longer part of the pilot completion gate.

### H.1 What remains decided

- GitHub Actions in the UFAL profile must not be wired to ARUP/B infrastructure.
- A GPU runner, if needed, must come from an external service/infrastructure path.
- MetaCentrum/e-INFRA.cz remains the concrete candidate mentioned in the thread.
- The current production/integration gate does not depend on live GPU CI.
- Existing GPU workflow templates do not prove that a usable runner exists.

### H.2 Do not reopen prematurely

Do not make branch protection, release immutability, or release-tag trust wait for GPU infrastructure.

If a future requirement establishes that specific `slow` tests genuinely need GPU execution, first document:

1. which tests need GPU;
2. why CPU execution is insufficient;
3. whether execution must be automatic or manual;
4. which external service can provide it;
5. how results return as CI evidence.

Only then should a runner label, trigger, or external dispatch integration be introduced.
