> _Refreshed 2026-10-02 against the live issue and the current repository map established by [#72](https://github.com/ufal/atrium-project/issues/72) and [#57](https://github.com/ufal/atrium-project/issues/57). The current product set is `page-classification`, `ocr-postprocess`, `digital-convert`, `nlp-enrich`, `keyword-extract` and `translator`; `atrium-project` is the hub. `alto-postprocess` is historical predecessor state; the former `llm-enrich` responsibilities were split across current repositories._

## Context

#69 was split from #18 so the ATRIUM project could finish its **own** CI/Docker roadmap after the ARUP-CAS fork-wrapper requirement stopped being the target architecture. The live issue still lists B2, B3 and B6 plus waves W1–W6.

The repository architecture changed after that plan was written. The authoritative current service map is now six production services:

```text
page-classification
        │
        ▼
ocr-postprocess
        │
        ▼
nlp-enrich
        │
        ▼
keyword-extract
        │
        ▼
translator

born-digital documents enter through digital-convert and then use the shared downstream record path
```

This is a **CI matrix**, not a demand that every run use one linear Compose stack. `digital-convert` must be tested as a current service even when it is a separate entry branch. `keyword-extract` must be tested as a current service even though its implementation lineage includes former LLM/vocabulary code. `ocr-postprocess` replaces the old OCR repository identity.

The plan therefore has two jobs in sequence:

1. make the roadmap itself truthful for the current repository set;
2. execute the work that remains, with pilot-critical items separated from post-pilot hardening and from work owned elsewhere.

## Objectives

1. Freeze the seven-repository CI matrix and eliminate predecessor-only assumptions from active CI documentation.
2. Close the current forms of B2/B3/B6 across all applicable current services.
3. Land the hub guardrails in W1 and make them repository-set aware.
4. Decide the exact disposition of W3–W6 instead of leaving them as unexecuted prose.
5. Align production-image hardening with #72 without duplicating #72's architecture work.
6. Keep #69 independent from #40's branch-protection/immutable-release/GPU work, except where #69 needs to record the dependency.
7. Make the roadmap itself the final evidence ledger for closure.

## Phase A — Freeze the current repository set and reclassify historical findings

### A.1 — Replace the old matrix in `docs/docker_gha_roadmap.md`

Make the six current product repositories a named CI matrix and keep `atrium-project` as the governing hub.

The roadmap should explicitly record:

- `atrium-alto-postprocess` → historical predecessor of `atrium-ocr-postprocess`;
- `atrium-llm-enrich` → historical source whose former responsibilities were split between `atrium-digital-convert` and `atrium-keyword-extract`;
- no current workflow, Compose file or release checklist should require a live `llm-enrich` image solely because an old finding mentions it;
- historical links are allowed in migration notes and provenance documentation.

### A.2 — Build one authoritative service-image table

For every current repository record:

| Field           | Required value                               |
|-----------------|----------------------------------------------|
| repo            | current UFAL repo name                       |
| service id      | current production-stage identity            |
| base image      | exact GHCR repository if published           |
| API image       | exact GHCR API repository if applicable      |
| release tag     | exact registry tag form                      |
| API port        | governed service convention where applicable |
| health endpoint | `/health` or the agreed equivalent           |
| data mount      | whether `/data` is actually writable/used    |
| GPU             | yes/no; whether #40 applies                  |
| provenance id   | current program/repository identity          |
| predecessor     | historical only, where applicable            |

This table should be consumed by the roadmap, not copied separately into six repo-specific documents by hand.

### A.3 — Search for stale repository identities

Run a repository-set search for:

```text
atrium-alto-postprocess
atrium-llm-enrich
ARUP-CAS/atrium-alto-postprocess
ARUP-CAS/atrium-llm-enrich
```

Classify each hit as:

1. **current operational reference** — must be changed;
2. **release/provenance migration reference** — keep, but mark as predecessor/successor;
3. **historical documentation** — keep only if it is clearly historical;
4. **dead reference** — remove.

This prevents the CI roadmap from becoming a second source of repository-name drift while #57/#72 are being refreshed.

## Phase B — Close B2: image naming

### B.1 — Establish the canonical registry convention

Use one explicit convention for the current six services:

```text
ghcr.io/ufal/atrium-<tool>:<version>
ghcr.io/ufal/atrium-<tool>-api:<version>   # only where an API image exists
```

Do not mix this with the historical alternative `atrium-<tool>:<version>-api`.

The current page-classification `test` documentation already exposes the `...-api:<version>` form, and the translator repository follows the same base/API image split. Treat this as the compatibility target for the current set unless a deliberate #72 release decision changes it.

### B.2 — Audit Compose vs CI in all six product repositories

For each repo:

1. enumerate every `docker-compose*.yml` / `.yaml` image reference;
2. enumerate every Docker build target and every `docker/build-push-action` target;
3. enumerate image names emitted by `docker/metadata-action` or the reusable workflow;
4. compare the literal repository names and tag positions;
5. exercise one published tag through `docker pull` for each image type.

The acceptance artifact is a small machine-readable or Markdown table attached to the roadmap showing:

```text
compose reference == pushed image reference
```

for every current target.

### B.3 — Remove predecessor-only B2 checks

If `llm-enrich` has an image-tag mismatch that no current service consumes, record it as historical and move it out of #69. Do not spend CI closure work on a repository that is no longer in the current production set.

### B.4 — Add a low-cost regression test

The hub workflow linter/self-check should reject a caller or Compose file whose API image name violates the canonical `<repo>-api:<version>` convention.

This is preferable to relying on another manual sweep the next time a repository gets a Docker target.

## Phase C — Close B3: image provenance / `ATRIUM_RUNNER_IMAGE`

### C.1 — Normalize release and registry identities

Keep the human-facing GitHub release tag with `v`:

```text
v1.9.0-beta
```

Normalize the GHCR tag to the actually published value:

```text
1.9.0-beta
```

The release URL may retain the `v`; the **container image and paradata must use the registry spelling**.

The preferred shared implementation is equivalent to:

```bash
IMAGE_TAG="${GITHUB_REF_NAME#v}"
```

with the result used consistently by `docker/metadata-action`, `ATRIUM_RUNNER_IMAGE` and any generated provenance metadata.

### C.2 — Verify the real image exists

For each current service that publishes a tagged image:

1. trigger the release build on the candidate tag;
2. inspect the pushed GHCR tag;
3. construct the `ATRIUM_RUNNER_IMAGE` value that the service receives;
4. `docker pull` the exact reference;
5. inspect the resulting paradata/`CreateAction.instrument` and ensure it names the same reference.

### C.3 — Keep release URLs stable separately

Do not remove the `v` from GitHub release URLs merely to solve the image-tag mismatch. There are two different identity systems:

- source release/tag identity;
- immutable container-registry identity.

#69 closes B3 when they are deliberately linked rather than accidentally conflated.

### C.4 — Regression guard

Add a unit-level or workflow-level assertion that a release ref `vX.Y.Z` cannot produce an `ATRIUM_RUNNER_IMAGE` ending in `:vX.Y.Z` when the published tag is `:X.Y.Z`.

This should be tested centrally so all six product repositories inherit the same rule.

## Phase D — Close B6: writable data contract

### D.1 — Identify which services actually write `/data`

Do not assume every image needs a writable data directory just because the historical Docker template mounted one.

For each current service document:

- files created below `/data`;
- whether `/data` is required at startup or only during a run;
- whether the API image or batch image writes there;
- whether the directory is persisted between runs.

### D.2 — Standardize host-side ownership

The preferred bind-mount rule is:

```text
host directory exists before compose starts
        ↓
compose maps it to /data
        ↓
container runs as the explicit runtime uid/gid
```

For page-classification the current documentation already uses the pattern of repository-owned `./data` plus `ATRIUM_UID`; use it as the reference implementation rather than recreating root-owned directories inside the container.

### D.3 — Do not force writable mounts on read-only services

If a current service only reads static resources or writes to a different volume, its Compose file should not gain a fake `/data` write requirement merely to satisfy the historical B6 wording.

### D.4 — Integration test

For each current service that writes `/data`:

```bash
mkdir -p data
ATRIUM_UID="$(id -u)" docker compose up ...
```

Run the smallest write operation and verify from the host that the result is owned by the invoking user (or by the explicitly documented service uid), not root.

## Phase E — Execute W1: hub guardrails

### E.1 — Make the workflow linter current-set aware

The hub `workflow_lint.py` should have an explicit input matrix covering:

```text
atrium-project
atrium-page-classification
atrium-ocr-postprocess
atrium-digital-convert
atrium-nlp-enrich
atrium-keyword-extract
atrium-translator
```

Avoid hard-coding the old repository count in the linter or tests.

### E.2 — Guardrails to enforce

Retain the issue's W1 rules:

- required `timeout-minutes` where appropriate;
- workflow-level `permissions`;
- `concurrency` where a duplicate-run policy is expected;
- action-version floor;
- reusable-workflow reference hygiene;
- deterministic caller/reusable-workflow inputs.

### E.3 — Test the linter itself

Add one fixture for each failure class and one current-real-world fixture per repository family.

The hub PR self-check should run the linter from the **checked-out PR revision**, not from a moving `@v1` reference when validating the change that defines the linter itself.

### E.4 — Current-set acceptance

W1 is done only when a single hub self-check proves that the six current product workflows and the hub conform to the same guardrails without requiring predecessor repositories.

## Phase F — Decide and execute/retire W3

W3 introduces an `:edge` image channel and parameterises E2E execution.

### F.1 — Keep `edge` explicitly non-production

If implemented, `:edge` must mean "current development HEAD", not "trusted production artifact".

The trust-gate chain must continue to consume immutable release tags or downstream verified images as defined by #40 / the processing repository.

### F.2 — Parameterise E2E by image reference

The E2E workflow should accept:

```text
IMAGE_REF=<immutable tag or edge tag>
```

and use that value consistently for all current services.

### F.3 — Test both entry paths

At minimum, the parameterised E2E design should support:

1. scanned/OCR entry path;
2. born-digital `digital-convert` entry path.

Do not create a fake linear test that inserts `digital-convert` between page classification and OCR.

### F.4 — Scope decision

If the pilot does not need mutable `edge` images, mark W3 explicitly **post-pilot** and move its implementation to a follow-up. Do not leave it ambiguously "pending" forever.

## Phase G — Decide and execute/retire W4

### G.1 — Inventory current workflow families

For all six product repos, list:

- release workflows;
- scheduled smoke workflows;
- shellcheck workflows;
- pull-request checks;
- GPU-specific workflows;
- reusable caller workflows.

### G.2 — Merge only genuine duplication

Do not merge workflows solely because their filenames match.

Preserve separate paths when they have different:

- hardware requirements;
- credentials;
- runtime duration;
- release triggers;
- artifact contracts.

The desired result is **less duplicated YAML**, not a single giant workflow.

### G.3 — Split `slow` and `gpu` deliberately

The test markers should remain explicit and discoverable. A long test should not become a GPU test merely because both are excluded from the default fast lane.

### G.4 — Scope decision

If this cleanup is not required for the pilot, record W4 as post-pilot and create/attach the owning maintenance issue rather than letting #69 accumulate an unbounded refactor.

## Phase H — Execute W5: production-image and supply-chain items

This is the W5 subset that can materially affect the pilot.

### H.1 — Pin tooling

Review every Docker build for unbounded tool installs such as:

```text
pip install <tool>
apt-get install <package>
model/resource download from mutable default branch
```

Where the installed artifact affects a production image, pin it to an explicit version/revision.

### H.2 — Pin model/resource fetches

The old roadmap calls out the ALTO weight fetch. After the repository move, the same rule applies to current successor repositories:

- OCR resource/model fetches;
- page-classification HF model revision;
- keyword/LLM/vocabulary resources;
- any downloaded converter/resource artifact used at runtime.

Where technically possible, record both a stable revision and a checksum/digest.

### H.3 — Make `pip-audit` a real gate

A passing informational report is not sufficient for the W5 acceptance criterion. Decide whether the gate applies to:

- runtime/production dependency manifests;
- test-only dependencies;
- research dependencies.

Do not force research-only packages into production image vulnerability gates.

### H.4 — Separate test/research dependencies from production images

This is especially relevant after the `llm-enrich` split: production `keyword-extract` and `digital-convert` should contain only the packages required by the current service image.

### H.5 — Lockfiles

Use lock files or equivalent reproducible dependency pins where the repository already has a suitable mechanism. Do not create a second incompatible lock system solely for #69.

### H.6 — W5 disposition

The pilot-critical subset is:

- production image contents;
- actual model/resource revision pins;
- provenance of the image/resource;
- `pip-audit` where it gates a deployed image.

The remaining dependency-hygiene work can move to #72 or a dedicated follow-up if it does not change pilot artifacts.

## Phase I — Execute W6: readiness and ShellCheck convergence

### I.1 — Health/readiness

#72 already treats common `/health`, `/info`, limits and error-contract conventions as established service requirements. #69 should verify that the Docker/Compose implementation exposes them correctly rather than redefine them.

For every current API service:

1. start the container;
2. wait for readiness;
3. query the health endpoint;
4. assert the container is serving requests before the E2E job starts.

### I.2 — Compose `HEALTHCHECK`

Where the Dockerfile can safely own the check, use `HEALTHCHECK`.

Where readiness requires external startup coordination, keep that logic in Compose/workflow assertions.

Do not treat a process being alive as equivalent to the API being ready.

### I.3 — ShellCheck

Re-audit the six current repos. The issue's old page-classification ShellCheck gap must be re-tested on the current `test` trees rather than copied into the refreshed digest unchanged.

Any ShellCheck-only defect should be fixed in the current repository or explicitly marked already solved; do not reopen a predecessor repository to close #69.

### I.4 — GPU overlay boundary

GPU runner and GPU scheduling remain #40 work. #69 may validate that the current GPU compose files remain syntactically/contractually valid, but it should not own the runner implementation.

## Phase J — Hygiene / security pass

### J.1 — Secret scanning

Apply the same scan policy to the six current product repositories plus the hub.

The minimum objective is to catch:

- committed API tokens;
- placeholder-but-real-looking credentials;
- tokens embedded in shell scripts or `.env` examples that are not clearly dummy values.

### J.2 — `update_issues.sh`

Remove any token literal from the script. The supported pattern is environment/CI secret injection, e.g.:

```bash
: "${GITHUB_ACCESS_TOKEN:?Set GITHUB_ACCESS_TOKEN in the environment}"
```

### J.3 — Formatting policy

Keep the line-length / formatter policy consistent in every current production repository. Do not mention `llm-enrich` as a current target in the final roadmap unless the note is explicitly historical.

## Verification / done-criteria

1. **Repository-set proof**: the roadmap and hub linter name exactly the seven current repositories and no predecessor as an active CI target.
2. **B2 proof**: every current Compose image reference resolves to the exact image repository/tag that CI publishes.
3. **B3 proof**: `ATRIUM_RUNNER_IMAGE` and `CreateAction.instrument` resolve to an existing pushed image with the actual registry tag spelling.
4. **B6 proof**: every current service that writes `/data` completes a host-visible write under the documented runtime uid/gid; services that do not use `/data` are not artificially made dependent on it.
5. **W1 proof**: hub `workflow_lint.py` passes against all current callers, including the PR-local hub self-check.
6. **W2 proof**: B2/B3/B6 have no unresolved predecessor-only references and their current-set evidence is linked from the roadmap.
7. **W3 proof**: either `IMAGE_REF`-parameterised E2E exists, or the wave is explicitly moved to a named post-pilot owner. A mutable `:edge` tag must never be treated as the trust-gate production artifact.
8. **W4 proof**: current workflow duplication is either consolidated with tests or explicitly moved to a named follow-up.
9. **W5 proof**: production-image dependency/resource pins and the agreed vulnerability gate are evidenced for the current six services.
10. **W6 proof**: current API services report readiness correctly and current ShellCheck state is green or explicitly waived with a documented reason.
11. **Hygiene proof**: secret scanning is enabled for the current set and `update_issues.sh` contains no token literal.
12. **Roadmap proof**: `docs/docker_gha_roadmap.md` records a final status for every W1–W6 item, with a reason and owning follow-up for everything not implemented in #69.
