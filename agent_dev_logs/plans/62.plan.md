# Strategy — Issue #62: retire the E2E entrypoint overrides

> Issue [\#62](https://github.com/ufal/atrium-project/issues/62) · Labels: `enhancement`, `development` · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor V) · Split with [alto#50](https://github.com/ufal/atrium-alto-postprocess/issues/50)
> **Status: 🔴 Not started. Three of the four overrides are exact no-ops and can be deleted today, independently of anything else. Evidence in [`../digests/62.digest.md`](../digests/62.digest.md).**

## Context

`.github/workflows/e2e-pipeline-smoke.yml` is the ecosystem's only end-to-end lane. It replaces the entrypoint on four of five stages, so #53's sweep recorded that "no Dockerfile `ENTRYPOINT` is exercised in that lane" — true as written, and it made the issue look like a workflow rewrite.

Verification changed the picture. Stages 3, 4 and 5 override the entrypoint with a command that is **identical in effect to the entrypoint they override**. They are no-ops. Only Stage 2 has a real override, and it exists solely to host a `pip install` — which is B9, and which is [alto#50](https://github.com/ufal/atrium-alto-postprocess/issues/50)'s to fix.

So this issue is: three deletions now, one restructure after alto#50, and a decision about a rider that has no owner.

## Strategic actions

### A — Delete the three no-op overrides (unblocked, do it first)

Remove the `--entrypoint python` line from `:289`, `:311` and `:336`. The arguments below each line are already exactly what the image's `ENTRYPOINT` expects:

- translator: `ENTRYPOINT ["python", "main.py"]` + args `main.py /workspace/…` → drop the override **and** the now-duplicated `main.py` argument.
- nlp-enrich: `ENTRYPOINT ["python", "run_pipeline.py"]` + args `run_pipeline.py --config …` → same, drop the duplicated script name.
- llm-enrich: `ENTRYPOINT ["python"]` (`remote` stage, `Dockerfile:63`) + args `openrouter_client.py --input …` → drop the override only; the script name is a genuine argument here.

**The duplicated script name is the one place to get this wrong.** With `--entrypoint python`, `main.py` is argv[1] to the interpreter. Without it, `ENTRYPOINT ["python", "main.py"]` already supplies it, so leaving `main.py` in the command passes it as an argument *to* `main.py`. Stage 1 shows the correct shape: image name, then arguments only.

This changes no runtime behaviour and makes the lane exercise what it ships. It is independently mergeable and does not wait on alto#50.

### B — Restructure Stage 2 after alto#50 lands

Stage 2 (`:268-274`) is the only stage where the override does work: `--entrypoint /bin/sh` exists to run `pip install … && export PATH=… && python run_pipeline.py …` as a shell command.

Once alto#50 makes the published image carry a working `alto-tools` (whether by vendoring or by fixing the install), all three parts fall away and Stage 2 becomes the shape of Stage 1:

```yaml
- name: Stage 2 - ALTO Postprocess
  run: >
    docker run --rm -v ${{ github.workspace }}:/workspace
    -w /workspace/work/atrium-alto-postprocess-main
    ghcr.io/ufal/atrium-alto-postprocess:${{ inputs.image-tag || 'latest' }}
    --config /workspace/work/config_e2e_alto.txt
    --document-json /workspace/work/doc_json/1_pc.json
    --document-json-out /workspace/work/doc_json/2_alto.json
```

Do not land this before alto#50 — the stage fails without a working `alto-tools` in the image, and a red E2E lane blocks every other repo's merges.

### C — Resolve the orphaned flexiconv rider

#62's rider lists three unpinned git refs. alto#50's copy correctly narrows to `alto/Dockerfile:42` (layoutreader). Nobody owns the other two:

- `atrium-nlp-enrich/requirements_flexiconv.txt:1` — `flexiconv @ git+https://github.com/ufal/flexiconv.git`, no ref
- `atrium-llm-enrich/requirements_flexiconv.txt:1` — same

They are cited in this issue's acceptance bullet ("every `git+` requirement in the ecosystem carries an explicit ref") and cannot be fixed from this repo. Pick one: open a one-line issue in each repo, or strike the bullet from #62 and record the two as known-unpinned. An acceptance criterion nobody can satisfy is how issues stay open forever.

Note this is genuinely low-risk to fix: `flexiconv` is a UFAL repository, so pinning it is a decision about which commit, not a negotiation with an upstream.

### D — Do not let the acceptance criteria drift between the two issues

#62 and alto#50 carry the same four acceptance bullets. Two belong here (`no --entrypoint override`, `grep -c "pip install"` = 1), two belong there (vendored code referenced in the alto README with licence; every `git+` pinned). Whoever closes one should not tick the other's boxes. The digest carries the division table.

## Verification / done-criteria

- [ ] `grep -c -- "--entrypoint" .github/workflows/e2e-pipeline-smoke.yml` returns **0**.
- [ ] `grep -c "pip install" .github/workflows/e2e-pipeline-smoke.yml` returns **1** — the runner-side `tools/e2e/requirements.txt` line at `:102`, which is correct and stays.
- [ ] The full E2E lane passes end to end with the real entrypoints. Three of the changes are no-ops by construction; the run is still the proof, because the duplicated-script-name trap in §A is invisible until execution.
- [ ] Each stage's command is arguments-only after the image name, matching Stage 1's shape.
- [ ] A deliberate break confirms the lane is now sensitive to entrypoints: change one repo's `api`/base `ENTRYPOINT` locally, rebuild, and confirm the stage fails. This ecosystem has twice been caught by a green check measuring something else — and this issue exists because a lane looked like it was testing entrypoints and was not.

## Out of scope

- **The alto-tools dependency itself** — [alto#50](https://github.com/ufal/atrium-alto-postprocess/issues/50). §B waits on it; it is not this issue's work.
- **The `-w` working-directory gap.** Every stage runs the image's interpreter against a *fresh checkout* (`-w /workspace/work/atrium-<tool>-main`) rather than the image's `/app`. So a source change that never reached the image still passes E2E. This is a real second build/release/run gap, it is arguably larger than the entrypoint one, and it deserves its own issue rather than being folded in here.
- **Migrating the E2E lane onto `docker-build-smoke`.** #55's mechanism is proven and might eventually replace this lane; that is a design question, not a fix for B9.
