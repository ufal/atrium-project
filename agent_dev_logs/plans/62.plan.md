## Context

`.github/workflows/e2e-pipeline-smoke.yml` is the ecosystem's only end-to-end lane. It replaced the entrypoint on four of five stages, so #53's sweep recorded that *"no Dockerfile `ENTRYPOINT` is exercised in that lane"* — true as written, and it made the issue look like a workflow rewrite.

Verification changed the picture twice.

**First**, three of the four overrides turned out to be **exact no-ops** — each replaced the image's real `ENTRYPOINT` with a command byte-identical in effect to the `ENTRYPOINT` it replaced. Only Stage 2 was doing real work, and that work was the B9 defect: a `pip install` of `alto-tools` from a moving `refs/heads/master.zip` **inside the already-published image**, overriding that image's own commit pin at the moment of testing it.

**Second**, by the time this strategy was executed, **the expensive half had already landed.** alto#50 retired the dependency by vendoring (`6ddabf7`), and hub `6ba4807` dropped the Stage 2 shim; run [#130](https://github.com/ufal/atrium-project/actions/runs/34567086963) is green on that. What remained of #62 was three deletions, two duplicated arguments, an orphaned rider, and the question of how to stop any of it coming back.

## Strategic actions

### A — Delete the three no-op overrides, and the argument each one hides

The deletions themselves are trivial. **The duplicated script name is the one place to get this wrong**, and it is the reason this is a strategy and not a `sed` command:

- With the interpreter forced as the entrypoint, `main.py` is argv[1] **to Python**.
- Without it, `ENTRYPOINT ["python", "main.py"]` *already supplies the script*, so leaving `main.py` in the command passes it as an argument **to `main.py`**.

So translator and nlp-enrich drop the script name along with the override. **llm-enrich does not**: its `remote` stage entrypoint is `["python"]` — the bare interpreter — so `openrouter_client.py` is a genuine first argument, not a duplicate. Stage 1 is the shape to converge on: image reference, then arguments only.

Nothing catches this but a run. Not YAML linting, not the new guard, not `grep`.

### B — Check the *published* images, not the source

This is the step that separates "the overrides are no-ops" from "the deletions are safe", and it is the one most likely to be skipped as obvious.

The lane defaults to `image-tag: latest`, which the workflow's own header note is emphatic about: **that is the last RELEASE of each tool, not `test`.** Reading `Dockerfile` on `test` therefore proves nothing about what the lane will pull. The entrypoints had to be confirmed at each repo's newest release tag:

| Repo                | Newest tag | `ENTRYPOINT` at that tag        | Matches? |
|---------------------|------------|---------------------------------|----------|
| `atrium-translator` | `v0.10.5`  | `["python", "main.py"]`         | ✅        |
| `atrium-nlp-enrich` | `v0.20.1`  | `["python", "run_pipeline.py"]` | ✅        |
| `atrium-llm-enrich` | `v0.6.3`   | `["python"]` (`remote`)         | ✅        |

All three match, so the change is sound at `latest` as well as `test`. Had any not matched, the correct move would have been to hold the deletion for that stage until its next release — **not** to flip the lane's default to `test`, which is a separate decision the header note already reasons about.

### C — Make a silent override impossible to reintroduce

The issue asks for exactly this: *"where it genuinely cannot [run as built], say why in a comment rather than leaving a silent override."* A comment is the right answer and an unenforced one; `tests/test_e2e_entrypoints.py` is that sentence with CI behind it. Two structural assertions over every hub workflow:

1. **No step's `run:` body overrides a container entrypoint**, unless the `(workflow, step)` pair appears in an `ALLOWED_OVERRIDES` map *with a reason*. Empty today — and the map's own comment tells the next author to check first whether the image's `ENTRYPOINT` is simply what they were about to hand-write, since three of the four this replaced were exactly that.
2. **No `docker run` command installs a dependency at run time** — the B9 defect itself, matched per *logical* line (continuations joined) so a legitimate runner-side install elsewhere in the same step is not implicated.

Plus a third test pinning that the E2E lane is among the files scanned and still has five stages: without it, renaming the workflow leaves both checks passing over nothing.

Three design choices worth keeping:

- **Parse, don't grep.** PyYAML drops comments, so the long blocks explaining what was removed are not themselves offences. A text scan would punish the file for documenting itself.
- **Structural, not the issue's literal count.** `grep -c "pip install" == 1` is brittle in both directions — red the day a second legitimate runner-side install appears, green if that one line ever moved *into* a container command. The count is still 1 and still the fastest eyeball check; it is just not the thing to automate.
- **Confirm the guard goes red.** Both checks were run against purpose-built breakage — including the verbatim historical Stage 2 shim — before being trusted. A guard never seen red is not known to work, which is the failure mode `test_check_version.py` was written to avoid.

**A trap this issue sets for itself**: `grep -c -- "--entrypoint"` counts comments. Prose explaining the removal would break the acceptance criterion. Both the existing Stage 2 block and the new Stage 3 block say *"entrypoint override"* and never spell the flag.

### D — Close the orphaned flexiconv rider by fixing it

K4TEL's comment put it precisely: the bullet *"every `git+` requirement in the ecosystem carries an explicit ref"* covers `flexiconv` in nlp-enrich and llm-enrich, *"which can't be fixed from this repo and have no issue in either. Either open two one-liners or strike the bullet."*

Both framings accept that the work does not get done. Taken as a third option — **do it**, since both repos were in hand. Both files now pin `@v0.3.10`, a published tag rather than a bare SHA so the intent stays readable, with the resolution recorded beside it the way `workflow_lint.py` already requires for action SHAs:

```
#     v0.3.10 = a982b88f363828bd6c71478d72d4f4e56a555677   (highest published tag)
#     main    = a4f0fd9ce472c4e4d9ccd2827751e417b4480783   (ahead of it, untagged)
flexiconv @ git+https://github.com/ufal/flexiconv.git@v0.3.10
```

`flexiconv` is a UFAL repository, so this was always a decision about *which commit*, not a negotiation with an upstream. **An ecosystem-wide sweep for `git+` and `git clone` now returns those two pinned lines and nothing else.**

Blast radius, stated rather than assumed: no Dockerfile installs either file; only llm-enrich's `scheduled-smoke.yml:86` does, behind a `|| echo` fallback; both repos' `test_flexiconv_convert.py` *skip* when the tool is absent. **llm-enrich's nightly is therefore the only place a bad pin surfaces** — which is why the verification below installs it explicitly in both repos rather than trusting CI to notice.

### E — Do not let the acceptance criteria drift between the two issues

Two belong here (no entrypoint override, `pip install` = 1), one belongs there (README attribution + licence), and one is now jointly satisfied (every `git+` pinned — alto's layoutreader there, flexiconv here). Whoever closes one should not tick the other's boxes. The digest carries the division table.

## Out of scope

- **The `-w` working-directory gap.** Every stage runs the image's *interpreter* against a *fresh checkout* (`-w /workspace/work/atrium-<tool>-main`) rather than the image's `/app`, so a source change that never reached the image still passes E2E. It is a real second build/release/run gap, arguably larger than the entrypoint one, and it is **why the overrides looked harmless for so long** — with `-w` pointing at the checkout, the forced interpreter and the real entrypoint resolved the same relative script, so nothing ever misbehaved. This round is a *prerequisite* for closing it (once `-w` goes, `ENTRYPOINT ["python", "main.py"]` resolves `/app/main.py`, the desired end state), but it deserves its own issue rather than being folded in here.
- **The alto-tools dependency itself** — [alto#50](https://github.com/ufal/atrium-alto-postprocess/issues/50), resolved by vendoring. §B of the original plan waited on it; that wait is spent.
- **Migrating the E2E lane onto `docker-build-smoke`.** #55's `load: true` + `probe-targets` mechanism is proven and might eventually replace this lane; that is a design question, not a fix for B9.
