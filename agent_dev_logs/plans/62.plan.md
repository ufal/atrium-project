Between `598621e` and `f675943` there have been **15 consecutive green runs** (#135 → #149), and

workflow's own header note at `:51` is emphatic about, and it is the *harder* of the two cases,
because a release can lag the branch whose Dockerfile was read. The duplicated-script-name trap —
the one failure mode no grep, no YAML lint and no structural guard can see — is empirically cleared.

What is left is genuinely small and genuinely untested. **The lane has never been dispatched**:
147 runs, **0** of them `workflow_dispatch`. And the deliberate-breakage check the previous plan
added for itself was never performed, so 15 green runs remain consistent with a lane that is
sensitive to entrypoints *and* with one that is not.

## Strategic actions

### A — Dispatch the lane once at `image-tag: test`

This is the last unproven item in the acceptance **as filed**, and it is one click. Both input
declarations default to `latest` (`workflow_call` `:12-18`, `workflow_dispatch` `:25-29`), so `test`
has to be typed — which is presumably why, in 147 runs, it never has been.

What the run has to show, and it is the same bar the `latest` case already cleared: stages 3, 4 and
5 at non-trivial durations rather than skips, and *Assert Final Document Contract* green.

**Check one precondition first, or the run will red on something unrelated.** The header note ends
by stating it outright (`:62-66`): `:test` *"starts being published only once each repo has pushed a
branch commit under the issue #10 `docker-tool` change, so the tag does not exist for every repo
yet."* If any of the five `:test` tags is missing, the dispatch dies on an image pull and proves
nothing about entrypoints. Confirm `docker pull ghcr.io/ufal/atrium-<tool>:test` resolves for all
five before spending the run.

**Expect a different failure mode here, and do not misread it.** At `test` the images are built from
each tool's `test` branch, so this run exercises code that has not been released. A red stage is
therefore more likely to mean "a tool's `test` branch has a defect" than "the entrypoint deletions
were wrong" — the entrypoints themselves are already proven against the harder, released set. The
header note at `:35-66` reasons about exactly this asymmetry in the other direction and is worth
re-reading before interpreting the result.

**Do not flip the lane's default to `test` to get this run.** The header note refuses that
explicitly and gives the condition under which it should be reconsidered (`:65-66`, "flip it once
`docker pull …:test` succeeds for all five"). Making the change as a side effect of closing #62
would silently alter what every hub push means.

### B — Break one entrypoint on purpose, once

This is not in #62's filed acceptance — the previous plan added it for itself, correctly, and then
did not do it. Change one repo's base `ENTRYPOINT`, rebuild, confirm the stage fails, revert.

This is not ceremony. **This ecosystem has twice been caught by a green check measuring something
else, and #62 exists because a lane looked like it was testing entrypoints and was not.** Fifteen
green runs prove the stages execute; they do not prove the lane would notice if an entrypoint were
wrong. Those are different propositions and only one of them has evidence.

Pick translator: its `base` stage entrypoint is a single line (`Dockerfile:60`), its stage is among
the cheapest in the lane at 10 s, and it is one of the two that dropped a script name — so a break
there tests the exact edit most likely to have been subtly wrong.

**Caveat that makes this weaker than it looks, and is the reason §C matters.** With `-w` pointing at
a checkout, a local rebuild only proves the lane notices a changed *interpreter*, not a changed
*baked script*. Run it anyway — a negative result would be a serious finding — but record the
caveat rather than overstating the conclusion.

### C — Open the workspace issue, and put the alto proof in the body

The roadmap has asked for this issue since 2026-09-11 — §9's *The successor finding — not closed
here* (`docs/docker_gha_roadmap.md:651`) ends *"It needs its own issue"* (`:661-662`). It still does
not exist: hub numbering stops at #64 and #65 returns 404.

Two corrections to how the previous records stated the finding, both of which belong in the issue
body:

1. **It is four stages, not five.** `-w` appears at `:298`, `:348`, `:370` and `:414`, each pointing
   at an `actions/checkout` of the tool's default branch with no `ref:` (`:272-275`, `:304-307`,
   `:356-359`, `:377-381`). **Stage 1 has no `-w`** and runs pc's
   `["python3", "/app/entrypoint.py"]` from the image — so one stage is already correct, and it is
   the model for the other four, exactly as it was for the entrypoint deletions.
2. **There is now a dated, concrete instance instead of a hypothetical.** Stage 2 pulls
   `ghcr.io/ufal/atrium-alto-postprocess:latest`, built from `v1.4.7-beta` (2026-09-09). The
   vendored `alto_tools.py` landed in `6ddabf7` (2026-09-10) and **does not exist at that tag**.
   Stage 2 runs green at 57 s regardless, because `-w` puts the checkout's copy in front of the
   image's. **The published alto image has never executed the module alto#50 shipped.** That is the
   whole defect, in one sentence, with a tag and a commit date behind it.

And a third thing worth writing down, because it turns the issue from a complaint into a small task:
**the fix already has a working model in this repository.** `e2e-digital-smoke.yml` starts its
containers with **zero** `-w` flags — data in via `/workspace`, code from each image's own `/app`.
The pipeline lane has four. The sibling lane is the target shape.

This round is a prerequisite for that issue rather than a partial fix: once `-w` goes,
`ENTRYPOINT ["python", "main.py"]` resolves `/app/main.py`, which is the end state.

## Out of scope

- **The `-w` working-directory gap itself.** Four of five stages run the image's *interpreter*
  against a *fresh checkout* rather than the image's `/app`, so a source change that never reached
  the published image still passes — and the alto case above proves it has already happened. It is a
  real second build/release/run gap, arguably larger than the entrypoint one, and it is **why the
  overrides looked harmless for so long**. §C opens it; it does not get folded in here.
- **The `alto-tools` dependency.** [alto#50](https://github.com/ufal/atrium-alto-postprocess/issues/50),
  resolved by vendoring (`6ddabf7`) and closed 2026-09-15. The previous plan's §B waited on it; that
  wait is spent.
- **Changing the lane's default `image-tag`.** §A needs one dispatch at `test`, not a new default.
  The header note at `:35-66` already reasons about that trade-off, and names the precondition for
  revisiting it. It is a decision of its own.
- **Migrating the E2E lane onto `docker-build-smoke`.** #55's `load: true` + `probe-targets`
  mechanism is proven and might eventually replace this lane's pull-published-tags model — which
  would dissolve the `-w` gap as a side effect. A design question, not a fix for B9.
- **Replacing the guard's structural checks with the issue's literal greps.** `grep -c "pip install"
  == 1` is brittle in both directions: red the day a second legitimate runner-side install appears,
  green if that line ever moved *into* a container command. The count is still 1 and still the
  fastest eyeball check; it is just not the thing to automate.
