## Context

The issue bundles two tasks that differ in kind. (1) Tightening `required` is a schema-only
change whose whole difficulty is proving it does not break anything — the previous draft called
it "a small, low-risk correctness fix — no behaviour change for any conforming producer", and
**that framing is wrong twice over**, in ways §A below sets out. (2) The RO-Crate export is new
packaging work with no prior art in any of the six repos; the design question it actually poses
is not "how do we emit JSON-LD" but "what may a crate reference", and the record already answers
that.

They should still be sequenced separately, and (1) should land first, since it is the freeze
gate. But (1) is a **cross-repo change with a per-repo fixture checklist and a tag-ordering
constraint**, not a one-file edit.

# A — Tighten `required` (the actual freeze gate)

## A.1 · The change

```json
"required": ["schema_version", "record_type", "doc_id", "provenance", "assembled"]
```

plus two assertions a flat list cannot express:

* **`anyOf` — a record must carry evidence that something was written into it**: either
  `source`, or at least one entry in `assembled.blocks` (`minProperties: 1`).
* **`allOf` — stamp/payload coherence**: every name in `assembled.blocks` must exist as a
  top-level property. Eleven `if`/`then` clauses — the nine content blocks plus `derived_from`
  and `regenerable`. An unknown name has no clause and passes, which is rule 6's spirit.

A full drafted `atrium_document.schema.json` accompanies this plan.

## A.2 · Why the floor is exactly five keys — and why the obvious sixth is wrong

`DocumentRecord.to_dict()` emits all five on every path with no skippable branch:
`schema_version`/`record_type` are `setdefault` in `__init__` (`:435-436`), `doc_id` is assigned
unconditionally (`:443`, and `__init__` raises on a falsy one at `:418`), and `to_dict()` itself
always assigns `provenance` (`:922`) and always sets `assembled.had_baseline`/`note` (`:923-925`).
`merge_document_records()` hardcodes all five (`:1198-1211`). **So no record any tool has ever
written is newly rejected.**

`source` is not in the floor. Four of the five tools never call `set_source()` at all —
`page-classification`, `translator`, `nlp-enrich`, `llm-enrich` — and `page-classification` is
stage 1 of the scanned pipeline. Requiring it would refuse a legitimate rule-3 standalone run of
most of the ecosystem.

**The correction that matters most.** The natural expression of the issue's own words — "a stage
that produces nothing still validates" — is *require `assembled.blocks`, non-empty*, because
`_stamp()` (`:872`) runs only where a payload is written and `finalize()` already warns
`contributed no block`. **That would break the pipeline at stage 1.** `set_source()` deliberately
does not stamp (`:526-574` contains no `_stamp` call), so
`atrium-alto-postprocess/page_split.py:540-553` — the originator — emits exactly
`schema_version, record_type, doc_id, source, provenance, assembled` with **no `blocks` key at
all**, and hands it straight to a hard gate (`document_hook.py:119 _validate_own_output`). Hence
the `anyOf`: `page_split`'s record satisfies branch one, everything else satisfies branch two,
and only a record with neither origin information nor a contribution satisfies neither.

## A.3 · What this newly rejects — verified, not assumed

Verified by running `jsonschema` 4.26.0 over the drafted schema against every per-stage record
shape traced from production code. **16 cases, 0 mismatches.**

Still valid (unchanged): the committed example fixture · `page_split` source-only ·
alto `extract` (`pages`+`content`) · alto `classify_TEXT` (`lines`) · alto `aggregate_STAT`
(`pages`) · page-classification standalone · translator standalone · nlp-enrich standalone (with
`entities: []`) · llm-enrich standalone · digital-convert originator · `merge_document_records()`
output.

Newly rejected — all four are defects:

| Shape                                          | Why it is a defect                                             |
|------------------------------------------------|----------------------------------------------------------------|
| `{"schema_version","doc_id"}`                  | today's literal minimum: a file that says nothing              |
| `{floor}` with no `source`, no stamp           | a stage that ran and contributed nothing                       |
| `assembled.blocks.lines` with no `lines[]`     | a stamp claiming a payload the record does not carry           |
| floor minus `record_type` / minus `provenance` | not producible by the module; a truncated or hand-built record |

**One production call site is in the third and second categories, and it is a real bug.**
`atrium-alto-postprocess/classify_TEXT.py:1109`'s `write_document_block()` call sits *outside*
the `if not df.empty` guard, so an empty CSV yields `merge_blocks={"lines": []}` — truthy, so it
passes `document_hook.py:184`'s guard, then fails `document_hook.py:202`'s `if records:`. The
`with` block runs, contributes nothing, and writes a five-key record. In a real pipeline the
baseline exists and its blocks pass through, so this only bites a standalone run — but that is
exactly the case rule 3 exists to support. **Fix at the call site, not in the schema.**

## A.4 · The part the previous draft missed entirely: baselines, and a gate that silently demotes

Five repos implement the same two-step Layer D policy, and the second step is conditional on the
first:

| Repo                | baseline check                   | own-output gate        |
|---------------------|----------------------------------|------------------------|
| alto-postprocess    | `document_hook.py:92`            | `document_hook.py:119` |
| translator          | `main.py:119`                    | `main.py:180`          |
| page-classification | `atrium_document_adapter.py:153` | `:217-230`             |
| llm-enrich          | `llm_client_shared.py:1177`      | `:1229-1243`           |
| nlp-enrich          | `api_util/document_hook.py`      | called at `:340`       |

An **invalid baseline** warns and sets a per-process latch, and the latch **demotes the own-output
gate from `raise` to `warn`**. So a schema that newly rejects a hand-built baseline does not
merely fail a test — for that run it *weakens the output gate the freeze exists to strengthen*.

Real baselines are safe (every writer goes through `to_dict()`). Hand-built ones are not, and
the ecosystem has **ten**, two of which assert the un-demoted behaviour and will flip:

- [ ] `atrium-page-classification/tests/test_atrium_document_adapter.py:266,285` — `:285` is
      `test_valid_baseline_does_not_demote_the_own_output_check`; its "valid" baseline has no
      `record_type`/`provenance`/`assembled` and would stop being valid
- [ ] `atrium-nlp-enrich/tests/test_document_hook.py:34,271,284` — `_VALID_STUB_RECORD` is
      literally `{schema_version, record_type, doc_id}`; `_VALID_BASELINE` backs
      `test_invalid_own_output_raises_and_writes_nothing`
- [ ] `atrium-nlp-enrich/tests/test_run_pipeline.py:156` — writes exactly today's two-key minimum
- [ ] `atrium-translator/tests/test_atrium_document.py:558` — the missing-`jsonschema` test's record
- [ ] `atrium-llm-enrich/tests/test_json_to_md.py:14` — `_write_record()`, the most minimal
      generator in the tree
- [ ] `atrium-llm-enrich/tests/test_service_document_json.py:79` — `_baseline()`
- [ ] `atrium-page-classification/tests/test_service_document_json.py:78` — `_upstream_baseline()`
- [ ] `atrium-project/tests/test_document_record_doc_id.py:154` — `{schema_version, pages}`, no
      `doc_id` (deliberately: it is the id-less-baseline case)
- [ ] `atrium-llm-enrich/tests/test_digital_to_json.py:262-270` — the only hand-built
      `assembled.blocks` map in any tool repo. It is stamp-coherent (it stamps `page_categories`
      and carries it), but has no `provenance`, so it fails the floor. Found on a second sweep;
      it was missing from the first version of this list.
- [ ] `docs/templates/shared/test_document_originators.py:304` — **vendored, so one edit lands in
      six repos and must go through `revendor_shared.sh`**

Most need one line: add `record_type`, `provenance: {}`, `assembled: {"blocks": {...}}`. The two
gate-policy tests need their intent re-expressed, not just their fixture padded — the thing they
pin ("a valid baseline must not demote the gate") is still true and still worth pinning.

**Do this pass BEFORE the schema lands**, in the same window. A period in which the tightened
schema is live and the fixtures are not is a period in which five repos run with a demoted gate.

## A.4b · A second failure class: a test that deletes a block and orphans its stamp

Found by running the hub suite with the tightened schema, which the first pass had not done:
**`tests/test_e2e_assert.py::test_schema_invalid_record_fails_on_the_schema_first` fails**
(`190 passed, 1 failed, 1 skipped`).

The test deliberately breaks a record twice — `record["doc_id"] = 42` and `del record["pages"]` —
then asserts the reported failure is the schema one. `del record["pages"]` leaves
`assembled.blocks["pages"]` in place, so stamp/payload coherence now reports it too, and the
test's last line used the bare word `"pages"` as a proxy for "we got the block-missing error".

**The behaviour under test never broke.** Ordering is guaranteed by the exception *type* —
`assert_schema_valid()` raises `SystemExit`, block assertions raise `AssertionError`, and the
test catches `SystemExit`. Only the string proxy is now wrong.

**The schema is right and the test is the odd one out.** That file deletes a block in eight
places and **seven already remove the stamp as well** (lines 95/96, 103/104, 155/156, plus 147
doing the deliberate opposite). Line 205 is the only one that orphans a stamp — exactly the
incoherence the rule exists to catch, constructed by accident. Nothing else in the six repos
does it.

Fix: keep the record incoherent, and match the block assertion's own wording
(`"Contributions were erased"`, `e2e_assert.py:355`) instead of the bare word. Full before/after
in the accompanying `test_e2e_assert.patch.md`. Verified: 13/13 in that file, and the whole hub
suite green with every #54 change staged (`tests/` 81 passed, `docs/templates/shared/` 110
passed 1 skipped — 192 total, matching the failing run's count).

# B — The RO-Crate export

## B.1 · What the design question actually is

Not "how do we emit JSON-LD" — `atrium_vocab.to_jsonld()` (`:954-999`) already does exactly that,
hand-rolled, deterministic, stdlib-only, with a `--selftest` and a companion JSON Schema. That is
the template, and copying its shape is most of the work.

The real question is **what a crate may reference**, and the record already answers it. The
reference-discipline rule — *"only the original input and persistent step outputs; transient
artifacts are never referenced"* — maps one-to-one onto RO-Crate's own hard rule that everything
in `hasPart` must actually be in the crate:

| ATRIUM         | RO-Crate                                 | Because                                    |
|----------------|------------------------------------------|--------------------------------------------|
| `derived_from` | `hasPart` data entities                  | persistent step outputs; they exist        |
| `regenerable`  | contextual entities, **never `hasPart`** | recipes for files that do not exist        |
| `source`       | root `isBasedOn`, contextual             | archive-managed; carries no path by design |

A crate that put `regenerable` in `hasPart` would be invalid for the same reason the record
forbids storing the Markdown: the file is not there. `atrium_rocrate.py`'s `--selftest` asserts
this directly.

## B.2 · The mapping — every field already exists

| RO-Crate                 | ATRIUM source                                                                                                           |
|--------------------------|-------------------------------------------------------------------------------------------------------------------------|
| root `license`           | `provenance.license_url`/`license` — already the most-restrictive union from `para_licenses.merge_effective_licenses()` |
| root `author`            | the four ORCID `Person`s identical in every `CITATION.cff`                                                              |
| root `about`             | every controlled term as a `DefinedTerm`, `@id` from `atrium_vocab.concept_uri()`                                       |
| root `datePublished`     | the record's **own newest block stamp** — never the clock, so the crate is reproducible                                 |
| `CreateAction`           | one per `provenance.contributors[]` entry (`program`, `run_id`, `paradata_ref`, `blocks`, `at`)                         |
| `CreativeWork` per block | one per `assembled.blocks[…]` stamp — the accretion granularity, preserved rather than flattened                        |
| `SoftwareApplication`    | paradata `tool_version` / `repository` / `docker_image` / `runner_ref` / `python_version`                               |

Two crates, one function each:

* `document_crate(record, paradata=None)` — the primitive, one crate per `doc_id`.
* `run_crate(records, run_paradata=None)` — one crate per run, whose `hasPart` **references** the
  per-document crates rather than re-describing them, so a run crate is the same size for five
  documents as for five thousand. That matters at the DMP's stated 1.2-million-page scale, and it
  is the same reasoning that got CIDOC-CRM and PROV-O rejected for the raw-extraction layer
  (`digests/project_state_2706.md:409-411`) — **this export must not quietly reverse that
  decision**, and it does not: the crate is built once, at export time, from records already on
  disk, and adds nothing to the pipeline's hot path.

A drafted `atrium_rocrate.py` accompanies this plan. Verified here: `--selftest` clean (0
problems), byte-identical across processes, and it produces a 46-entity crate from the committed
`fixtures/atrium_document.example.json` with all five tools appearing as `CreateAction`s.

## B.3 · Distribution

Hub-canonical, joining `docs/templates/shared/`. That is not free — see §D — but it is the
project's established way of making something a contract, and the module imports `atrium_vocab`,
which already lives there. The alternative (hub-only, under `tools/`) is cheaper to land and
leaves the tool repos unable to emit a crate from their own service endpoints; take it only if
§D's registration cost is judged too high for this milestone.

## B.4 · What the crate cannot yet say, and should not pretend to

Recorded rather than papered over:

- **No git SHA.** Paradata carries `runner_ref`, not a commit. A crate's software provenance is
  therefore "this ref" not "this commit".
- **No output checksums.** `sha256` exists only on `source`. Every `hasPart` file is named
  without a hash.
- **No DOI or PID anywhere** — not on any repo's `CITATION.cff`, not on any record.
- **`atrium-project` has no `CITATION.cff`** at all, though all five tool repos do.

Each is a small, separable piece of work, and each makes the crate materially more useful. None
blocks a first crate.

# D — Rollout, in order, because the order is load-bearing

`para-drift.reusable.yml` compares each tool repo's vendored copy against the hub at
`inputs.hub-ref`, **default `v1`**, and all five callers pin `@v1` with no override
(`<repo>/.github/workflows/para-drift.yml:17`). So:

1. Edit **only** the hub copies in `docs/templates/shared/`.
2. Land the fixture pass of §A.4 in all six repos **first** (it is valid under both schemas).
3. `scripts/revendor_shared.sh --check`, then `scripts/revendor_shared.sh`. It copies (`cp -p`)
   and re-verifies; it never commits, pushes or tags.
4. Commit the hub edit **and** the five vendored copies **in one window** — the script's own
   header says so (`revendor_shared.sh:207-208`), and the #13 digest records the live incident
   where a four-minute gap turned `para-drift` red in one repo.
5. **Then** move the `v1` tag. Not before: a moving `v1` mid-flight makes identical commits pass
   in one repo and fail in another.

Adding `atrium_rocrate.py` needs **three** registrations or it travels nowhere and is enforced
nowhere: a `SHARED_FILES` row (`revendor_shared.sh:60-73`), a `diff -u` step plus a `--selftest`
step in `para-drift.reusable.yml`, and a `[format] exclude` entry in every repo's `ruff.toml`
(without which `ruff format` reflows the vendored copy and para-drift fails — the trap
`force-exclude = true` was added for).

**The E2E constraint, which is the real reason to keep the floor minimal.**
`e2e-pipeline-smoke.yml` and `e2e-digital-smoke.yml` validate records produced by **published
`:latest` GHCR images**, and `:latest` only moves on a version tag — so a schema tightening that
any published image violates cannot be greened from `test`; it costs a release cycle per owning
repo (`e2e_assert.py:88-95` says as much). The floor is safe here precisely because every
published image contains the same `atrium_document.py`, and that module's `to_dict()` emits the
five keys unconditionally.

Note also that `e2e-pipeline-smoke.yml` is **currently red** for an unrelated, real reason —
`'enrichment' block missing from llm-enrich stage` on the CLI/`-remote` path (tracked as #49,
whose guidance text is stale). Do not read a red E2E after this change as caused by it without
reading the traceback.

# E — Cut the freeze tag once A lands

Do not wait for B. The schema freeze is the WP3/T3.3 deliverable; RO-Crate is DMP-mandated but
additive and can ship after.

**`v1` is not the freeze tag.** `v1` is the moving tag the reusable workflows are called at;
moving it is step 5 of §D and says nothing about the schema. The freeze needs its own immutable
marker — a `schema/v1.0` tag or a hub release — and conflating the two would make the freeze
un-referenceable the next time `v1` moves for an unrelated workflow change.
