## Context

The original issue asked for a formal DARIAH Vocabs namespace before publishing the harmonised AMCR+TEATER vocabulary as SKOS. That dependency was explicitly rejected as a current ATRIUM blocker by @motyc on 2026-09-04:

- AMCR+TEATER SKOSification is a wider project led by @petrpajdla on an approximately 18-month horizon;
- current source IDs remain valid and will later become PID references to the published SKOS versions;
- #51 must not hold up the production pipeline;
- **using SKOS internally as an alignment framework is desirable and can proceed now.**

The previous plan treated the first sentence correctly but the last three too narrowly. Internal SKOS alignment has since been implemented. The repository split on 30 September adds a second architectural requirement: the vocabulary itself must also have **one governed production owner and one released artifact**.

That second requirement is now tracked in #67/#72/#1, not by reopening the namespace request in #51.

## Strategic actions

### A — Keep the namespace decision closed

No action in #51 should request a DARIAH namespace.

The current policy is:

```python
SKOS_BASE = "https://w3id.org/atrium/"
```

Rules:

1. ATRIUM may mint URIs only for ATRIUM-authored concepts, schemes and collections.
2. Harvested AMCR and TEATER concepts keep their source identifiers.
3. If the future external SKOS project supplies durable PIDs, there is no ATRIUM concept migration to perform.
4. Dereferencing the `w3id.org/atrium` identifiers may be enabled later; that is optional and non-blocking.

This is intentionally stronger than "wait for the namespace": it means the current implementation already respects the future publication boundary by construction.

### B — Keep the hub registry authoritative

`docs/templates/shared/atrium_vocab.py` remains the source of truth for ATRIUM-authored controlled labels. Consumer repositories may keep local model-order lists where order is load-bearing, but they must compare them to the registry rather than silently invent a second vocabulary.

Examples already enforced by the current tree:

- page-classification ties its 11 page labels to the hub `page-category` scheme but preserves `model_registry.CATEGORIES` order for checkpoint compatibility;
- ocr-postprocess carries the two authorised line-category originators and uses the shared `UNTRUSTWORTHY_LINE_CATEGORIES` set;
- the registry distinguishes facets/collections from semantic hierarchy;
- mappings and source references are represented explicitly rather than as string conventions.

When a label set changes:

1. change the authority / hub registry in the hub;
2. run `scripts/revendor_shared.sh`;
3. update every affected consumer in the same integration window;
4. let `para-drift` prove byte parity.

Do not patch a vendored copy in one service as a local fix.

### C — Converge on one production vocabulary owner

This is the major new work created by the repository split.

**Owner: `atrium-keyword-extract`.**

It already contains:

- `vocab_sources.py` for the AMCR/TEATER harvest layer;
- `vocab_build.py` for deterministic artifact construction;
- `vocab_manager.py` for runtime concept lookup and provenance;
- `data_samples/vocab/*` as the committed artifact set;
- `union.skos.ttl` as the SKOS view;
- prompt/configuration controls for the controlled-keyword research target.

The runbook explicitly makes `vocab_build.py` the only writer of the vocabulary directory and provides:

```bash
python3 vocab_build.py --from-flat
python3 vocab_build.py --from-flat --skos
python3 vocab_build.py --from-flat --skos --check
```

The last command is the reproducibility gate. A source refresh may require network access, but the shipped artifact must be rebuildable offline from the committed flat data.

**Required architectural outcome:** every production consumer uses the released artifact; none maintains its own semantic definition of AMCR/TEATER terms.

### D — Finish the vocabulary-artifact handover

#67 R7 and #72 make the artifact a governed production dependency. The outstanding work is:

1. choose and document the exact release asset form;
2. publish it from `atrium-keyword-extract` under the agreed CC0 metadata;
3. put an immutable version/reference beside the artifact;
4. make translator consume that exact release rather than live-harvesting;
5. wire the same artifact into the hub E2E / pilot path;
6. make `para-drift` / release checks fail if a consumer's pinned copy diverges.

The current #72 plan calls this **one vocabulary artefact** and records that the artifact is built in `keyword-extract` but the CC0 release asset has not yet been published.

Until that asset exists, it is correct to say the internal SKOS design is built but the **production vocabulary distribution contract is not finished**.

### E — Retire duplicate harvest/build paths

#### Translator

`atrium-translator/load_vocab.py` still implements an independent AMCR/TEATER harvesting path. The earlier `--from-flat` work is the bridge, not the final architecture.

Target state:

- translator no longer decides what the canonical vocabulary is;
- the released vocabulary artifact is its input;
- `load_vocab.py` is either retired or reduced to a compatibility/rebuild utility that cannot silently become a second production source;
- release/E2E tests prove that the translator uses the pinned artifact.

The old observation that the live GraphQL harvest produced **5,087** rows while the reproducible snapshot produced **4,952** remains important historical evidence: a second harvester can change content without anyone changing an ATRIUM contract. The correct lever is the governed source snapshot / release artifact, not letting consumers choose their own harvest strategy.

#### Digital-convert

The current `test` tree still carries `vocab_manager.py` and the older vocabulary stack. This is explicitly contrary to the post-30-September architecture: digital-convert is the born-digital conversion stage, while the LLM/vocabulary implementation moves to keyword-extract.

Before the converter becomes the production image pinned by the pilot:

- remove its LLM/vocabulary code and dependencies;
- remove any production endpoint that exposes the old keyword/vocabulary path;
- preserve the record shape and converter behaviour that belong to the born-digital stage;
- update image-closure metadata and release docs so the production image cannot accidentally pull the research stack back in.

### F — Keep source mappings/provenance separate from prompt content

This remains non-negotiable.

Do **not** add `exact_match`, `uri`, or other large identity fields to the nested prompt payload merely because they are useful to the record or crate.

The intended route is:

```text
flat source artifact
      │
      ├── prompt vocabulary (labels only)
      │
      └── concept_index()/resolve_pid()
                │
                ├── enrichment.items[].teater_category_uri
                └── entities[].pid.{amcr,aat,...}
```

The model should not receive thousands of identifiers whose purpose is provenance rather than language understanding.

### G — Resolve V-5 as an explicit contract change, not by inference

Keep the current mitigation: if the record has the source concept URI, use it; do not mint an ATRIUM theme URI for a source label.

Then get an owner to decide one of these two contracts:

**Option 1 — preserve source label:**

```text
teater_category = source label
teater_category_uri = source concept URI
theme = derived / separately stored when needed
```

**Option 2 — store theme in the field:**

```text
teater_category = ATRIUM theme
source label + source URI = sibling provenance fields
```

Do not silently switch semantics just to make `validate_labels("theme", ...)` quiet. The schema description and current production output currently favour the first interpretation, while the registry field declaration still reflects the second.

### H — Preserve the semantic SKOS choices

The following are now part of the implementation contract and should not be reopened without a concrete vocabulary-curation reason:

- AMCR `hierarchie_vyse` → `skos:related`, not `skos:broader`;
- TEATER ancestor chains → direct `skos:broader` plus `skos:broaderTransitive` for the remaining ancestors;
- TEATER AAT quotes → `dcterms:source`, not `skos:exactMatch`;
- `same_as` label-shape scoring → not `owl:sameAs`;
- source identifiers stay source identifiers;
- ATRIUM facets use collections rather than invented hierarchy;
- labels that are operationally open strings stay open strings unless the whole producer/consumer contract is changed deliberately.

The purpose of #51 is to preserve these distinctions while the rest of the production stack evolves.

### I — Keep publication with the external SKOSification project

When @petrpajdla's project provides the publication/PID policy, the ATRIUM-side work should be:

1. identify the external PID mapping for source concepts;
2. verify that current records already carry the source identifiers needed to refer to them;
3. update the artifact/export metadata, not the historical records, wherever possible;
4. repoint the ATRIUM-authored `w3id` redirect or the single `SKOS_BASE` constant if that is the chosen publication arrangement;
5. rerun the deterministic SKOS/drift/record verification.

The critical property is that this should be a **handover**, not a second migration project.

## Verification / done-criteria

### Already-established acceptance for the internal SKOS layer

The strategy records these checks as successful and they should remain regression gates:

1. `atrium_vocab.py --selftest` — current recorded result: 6 schemes, 64 concepts, 5 collections, 75 mappings.
2. Turtle and JSON-LD generated from the same triple generator are isomorphic under `rdflib`.
3. SKOS integrity checks report zero violations for the declared constraints.
4. `atrium_vocab.schema.json` accepts the JSON-LD registry.
5. `union.skos.ttl` parses successfully and has no concept with more than one direct `skos:broader` where the strategy disallows it.
6. `vocab_build.py --from-flat --skos --check` returns clean on an untouched tree.
7. Tampering with the committed SKOS artifact makes the drift gate fail.
8. Consecutive builds are byte-stable.

### Required after the 2026-09/10 repository split

The following checks are now additionally required before treating the vocabulary architecture as finished:

1. **Single-owner check:** no production repository except `keyword-extract` contains the canonical vocabulary build/harvest implementation that can act as an independent source of truth.
2. **Digital image closure:** `atrium-digital-convert` production image does not carry the research LLM/vocabulary stack.
3. **NLP image closure:** `atrium-nlp-enrich` production image remains LINDAT/TEITOK only.
4. **Artifact identity:** translator and E2E reference one versioned vocabulary asset, not live source endpoints.
5. **Artifact provenance:** the release asset exposes source refs, taxonomy/config identity and a stable artifact digest.
6. **Consumer parity:** `para-drift` proves that vendored shared layers and pinned artifacts are the versions intended by the production tag.
7. **Record provenance:** `teater_category_uri` / `entities[].pid` preserve source identities without changing prompt content.
8. **V-1 regression:** `Trash` continues to be filtered on OCR-derived input, and the shared line-category registry remains the only source for the untrustworthy set.
9. **V-5 contract gate:** once an owner chooses the field semantics, the registry, schema description, validators and crate exporter must agree in one change.
10. **Pilot E2E:** the AMČR path consumes the same published artifact that the production tools are expected to pin.

## Proposed order

```text
A  Keep namespace / source-ID policy frozen
│
├── B  Keep hub SKOS registry canonical
│
├── C  Make keyword-extract the single vocabulary owner
│     │
│     ├── D  Publish versioned CC0 vocabulary artifact
│     │      │
│     │      ├── translator consumes pinned artifact
│     │      └── E2E consumes the same artifact
│     │
│     ├── E  Remove duplicate vocabulary paths
│     │      ├── translator harvester → compatibility/retirement
│     │      └── digital-convert LLM/vocab stack → removed
│     │
│     └── F  Keep provenance out of the prompt
│
└── G  Decide V-5 field semantics and align registry/schema/crate
       │
       └── H  Preserve SKOS relationship semantics + regression tests

I  External SKOSification project supplies publication/PID policy
└── handover: map source identifiers, repoint/regen, re-run gates
```

The order deliberately separates **stable semantic policy** from **repository migration** and from **external publication**. The latter must never be allowed to force a second rewrite of the internal contract.

## Out of scope

- Formal DARIAH Vocabs namespace acquisition from this issue.
- Publishing AMCR/TEATER as an ATRIUM-operated external vocabulary service.
- Inventing definitions, facets, exclusions, equivalences or hierarchy that the source vocabularies do not assert.
- Turning `teater_category` into a different semantic field without an explicit contract decision.
- Training or evaluating a new controlled-keyword model.
- Owning the `keywords` record block here; that belongs to #73 / `keyword-extract`.
- Keeping parallel production harvesters alive “for convenience”.
- Treating a live network harvest as a substitute for a versioned production artifact.

## Exit condition for #51

#51 can remain open as a deferred cross-reference until the external publication/PID work resolves. The internal part of the issue can be considered operationally complete when all of the following are true:

1. the current SKOS strategy remains consistent with the six-repository production architecture;
2. `keyword-extract` is the sole production vocabulary owner;
3. one versioned vocabulary artifact is published and consumed by translator/E2E;
4. duplicate production harvest/build paths are gone or explicitly demoted to offline migration tools;
5. V-5 has an owned contract decision and all consumers agree;
6. the existing SKOS/drift/provenance regression gates stay green.

At that point the only remaining reason to keep #51 open is the external publication/PID handover. The issue should not be closed by creating a new local namespace merely to satisfy the original September wording.
