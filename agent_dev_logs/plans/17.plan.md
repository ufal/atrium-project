> **Status: 🟡 AMČR-owned workflow review.** `0xSpVP` v`106039` was submitted on 2026-09-24, but the repository split on 2026-10-01 changed the owners behind two of its steps. The implementation direction is therefore **link refresh, not workflow redesign**.
> _Refreshed 2026-10-02. Evidence: [`../digests/17.digest.md`](../digests/17.digest.md). Current-state inputs: hub #4/#67/#71/#73, six current processing repositories, and `atrium-project/docs_site/workflows/*`._

## Context

#17 was opened to separate two activities that had initially been mixed together:

1. ÚFAL creates descriptions for the tools used in the ATRIUM workflows.
2. @motyc updates the AMČR workflow record `0xSpVP`.

The first activity has been handled in the related #4 work. The second is the actual completion item on #17.

The situation changed after the 30 September AMČR meeting because the processing topology was split into six current repositories:

- `atrium-page-classification`
- `atrium-ocr-postprocess`
- `atrium-digital-convert`
- `atrium-nlp-enrich`
- `atrium-keyword-extract`
- `atrium-translator`

The old two-repository responsibilities:

```text
atrium-alto-postprocess
atrium-llm-enrich
```

are now historical predecessors. In particular, `llm-enrich` was split into:

```text
born-digital conversion  →  atrium-digital-convert
keyword extraction       →  atrium-keyword-extract
```

This means the 11-step `0xSpVP` structure already proposed by @motyc remains useful, but the links for the born-digital and keyword steps are now stale.

The hub's current `docs_site/pipelines.md` and `docs_site/workflows/*.md` provide the stable process descriptions. They show the same architecture from another angle:

```text
scanned route:
page-classification
    ↓ routing
ocr-postprocess
    ↓ lines / record
nlp-enrich
    ↓ record
keyword-extract
    ↓
optional nlp-enrich projection / TEITOK

born-digital route:
digital-convert
    ↓ record
keyword-extract
```

The translator is a downstream XML/ALTO product path. `0xSpVP` is the chain-level narrative tying these tool stages together.

### AMČR ownership rule

The later #67/#4 discussion established that:

- `0xSpVP` is maintained by AMČR;
- it should stay free of issue numbers, dates and tool version numbers;
- tool-local workflow records should describe only their own tool and point back to `0xSpVP`;
- the complete AMČR chain should not be duplicated in every tool workflow record.

#17 therefore should not become a second repository/project planning issue. Its job is to identify and verify the **correct current chain links** and the wording needed for the AMČR record.

# Strategic actions

## A — Freeze the current `0xSpVP` step structure

Do not redesign the 11-step flow solely because the repositories moved.

The current submitted chain remains the working structure:

1. AMČR repository
2. Orchestration
3. Page classification
4. Segmentation and ATR
5. ALTO post-processing and QC
6. Born-digital branch
7. NLP enrichment → TEITOK
8. Vocabulary keywords
9. Optional custom NER training
10. XML translator
11. Discovery

The refresh is about **who is linked to steps 5–8**, not about inventing different steps.

### A.1 — Preserve the AMČR-owned wording rule

Do not add:

- GitHub issue numbers;
- implementation dates;
- repository release versions;
- branch names;
- temporary CI details.

Those belong in `agent_dev_logs`, not in `0xSpVP`.

---

## B — Replace the old born-digital link with `atrium-digital-convert`

The current hub workflow page describes `atrium-digital-convert` as:

> reading born-digital PDF/DOCX directly into the ATRIUM document record, checking the text layer, marking pages that require OCR, and optionally rendering the record to Markdown.

The converter does **not** itself call page-classification or ocr-postprocess. The AMČR orchestration decides the route. That distinction should be preserved in the SSHOMP workflow.

### B.1 — Dependency

The corresponding SSHOMP tool record is a separate #4 task. It does not yet have a persistent item ID in the researched current state.

Therefore #17 should not invent or hard-code an ID.

### B.2 — Required action

Once the new `digital-convert` record exists and is visible:

- replace the old `llm-enrich` reference at step 6;
- keep the step as the born-digital branch of the same AMČR workflow;
- do not create a second workflow solely for born-digital input.

This follows motyc's explicit September decision: born-digital is a **branch**, not a second `0xSpVP`.

### B.3 — Verification

Check that the linked record's scope is born-digital conversion only:

```text
PDF / DOCX
    ↓
text-layer check
    ↓
atrium_document
    ↓
keyword-extract
```

It must not still describe the old LLM keyword service.

---

## C — Repoint `j9fqxo` to `atrium-keyword-extract`

The existing `j9fqxo` item should be reused.

The current repository has become the single semantic keyword stage:

- KeyBERT (default statistical method);
- YAKE;
- legacy KER;
- controlled AMČR / TEATER vocabulary mapping when the controlled path is enabled.

### C.1 — Scope boundary

The public description must separate:

**statistical keywords**

from:

**controlled-vocabulary keywords**.

Do not flatten the two into a single undifferentiated list. The current #73 decision also requires that the keyword output retain the method, score and rank; scores are not comparable across methods.

### C.2 — Remove obsolete born-digital content

The old `j9fqxo` description was written when `llm-enrich` still combined:

- controlled keyword extraction;
- born-digital PDF/DOCX conversion.

After the split, only the first remains at `j9fqxo`.

### C.3 — Controlled-stage maturity wording

The current repository's released `v1.0.0-beta` already has the statistical service surface and document/page statistical output.

The controlled vocabulary path is still under active development in `keyword-extract#2` and is not equivalent to “fully completed production functionality”.

SSHOMP wording must therefore describe the stable conceptual role without turning a research/implementation target into a falsely completed release claim.

### C.4 — Required `0xSpVP` action

After `j9fqxo` is repointed:

- step 8 should link to it as the current keyword stage;
- the wording should identify the keyword stage, not the old `llm-enrich` repository;
- no second keyword record should be created.

---

## D — Keep `YParYU`, but make the tool identity current

The repository is now `atrium-ocr-postprocess`. The pipeline itself remains the same family of functionality, but the scope is no longer ALTO-only.

Current repository documentation covers:

- ALTO XML;
- PAGE XML;
- hOCR;
- ABBYY/DjVu XML;
- OCR JSON;
- PDF/DOCX and other text-bearing inputs;
- page splitting;
- text extraction;
- line classification;
- quality aggregation;
- paradata.

The SSHOMP tool record should be refreshed under #4, but **#17 does not need a new record ID**.

### D.1 — `0xSpVP` step 5

The current AMČR workflow can still call the step:

> ALTO post-processing and QC

because that describes the concrete AMČR route.

The underlying tool record must, however, identify the current repository as `atrium-ocr-postprocess`.

### D.2 — Do not overload #17 with the licence discussion

#6 remains the place for the detailed component/licence decisions. #17 only needs to verify that the public workflow description does not contain an obsolete or contradictory licence claim.

## E — Keep `EMhu3X`, but make its scope NLP-only

The current `nlp-enrich` workflow is stable:

```text

    ↓ UDPipe
morphology / syntax
    ↓ NameTag

    ↓
```

Keyword extraction is no longer a current feature boundary of the repository.

### E.1 — Required SSHOMP consequence

Do not replace `EMhu3X`.

Instead:

- keep it at step 7;
- remove old current-feature claims about KER, YAKE, KeyBERT or controlled vocabulary extraction;
- retain TEITOK as a central output;
- retain the relationship to the downstream keyword stage.

### E.2 — Record vs workflow distinction

`EMhu3X` is a **tool record**, while `0xSpVP` is the **full AMČR chain**.

Do not duplicate the chain inside the nlp-enrich record.

---

## G — Treat the hub Workflows pages as the documentation source, with release verification

Before any SSHOMP edit, run this simple provenance check:

```text
hub workflow page
        ↓
current repository README / service docs
        ↓
released tag
        ↓
SSHOMP tool record
        ↓
0xSpVP link
```

The purpose is to prevent two classes of drift:

1. copying the old pre-split repository identity into a current record;
2. copying a branch-only or soon-to-change implementation detail into a workflow record that is supposed to be stable.

The hub Workflows pages are intentionally stable-core descriptions. They should not be treated as proof that every branch-only feature has already reached a public release.

---

## H — Keep tool-local workflow records subordinate to `0xSpVP`

Two related workflow records are still part of the broader #4 documentation set:

- translator workflow `13eHAZ`;
- page-classifier workflow record still to be created.

They should both:

- describe their own tool;
- contain their own inputs/outputs/activities;
- relate to their tool record;
- link `0xSpVP` for the complete AMČR chain;
- not duplicate the 11-step AMČR narrative.

These are related deliverables, but they do **not** require #17 to invent another full chain.
