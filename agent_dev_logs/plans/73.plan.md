## Context

The Digital Archive's agreed S3 scope requires two remaining record-level capabilities:

1. statistical keywords that can be indexed without depending on LLM-generated controlled vocabulary; and
2. an optional document-level quality summary derived from the page/line quality already present in the record.

The repository split changes the implementation boundary:

```text
page-classification ─┐
                     ├─► positional plane / page facts
ocr-postprocess ─────┘
          │
digital-convert ───────► born-digital positional origin / needs_ocr
          │
          └────────────► common `atrium_document` record
                                │
                         nlp-enrich
                         (UDPipe / NameTag / TEITOK)
                                │
                         keyword-extract
                         (statistical + controlled keywords)
                                │
                         translator
                         (terminal translation branch)

(In the hub's E2E and `docs_site/pipelines.md` the translator actually runs as stage 3, after ocr-postprocess on the page ALTO; the order above is illustrative only.)
```

The important #73 consequence is:

> **`keyword-extract` is now the producer, `nlp-enrich` is only the upstream linguistic stage and downstream TEITOK projector, and `ocr-postprocess` is the current quality-stage owner.**

The statistical extractor itself is no longer a design task. `keyword-extract v1.0.0-beta` already provides:

- KeyBERT / YAKE / KER;
- KeyBERT as the default in service and CLI;
- document and per-page results;
- `method`, `score` and `rank` on every statistical keyword;
- a separate controlled-kind outcome.

The missing artifact is the record block.

The current issue thread also settles an important representation rule:

> **Statistical and controlled keywords must never be merged into one list.**

Therefore the new `keywords` block is the **statistical** block. The controlled-vocabulary result remains in the successor-owned `enrichment` block. There is no reason to force a common score vocabulary onto LLM-selected controlled terms.

## Design constraints

### 1. The record is additive

The hub's `doc-schema-v1` is the pilot baseline. `keywords` and an eventual `quality_summary` are additive nodes:

- no `SCHEMA_VERSION` bump;
- no re-attribution of a previously written block;
- new ownership entries are explicit;
- `POST_FREEZE_CHANGES`, the schema changelog and producer record-shape tests are updated in one hub schema round;
- the shared files are re-vendored to all six processing repositories participating in the production chain.

### 2. Old and new program ids coexist during the pilot

The shared record already accepts:

```python
PROGRAM_SUCCESSORS = {
    "alto-postprocess": "ocr-postprocess",
    "llm-enrich": "keyword-extract",
}
```

The #73 implementation must use `keyword-extract` as the new block owner from day one. Existing records keep their old `llm-enrich` stamps unchanged.

### 3. Statistical and controlled keywords stay separate

Use:

```text
record.keywords      = statistical keywords only
record.enrichment    = controlled-vocabulary enrichment
```

Do **not** create one mixed array such as:

```json
"keywords": [
  {"kind": "statistical", ...},
  {"kind": "controlled", ...}
]
```

That would conflict with the explicit AMČR request to keep the two kinds apart and would make the score semantics needlessly ambiguous.

### 4. Scores are method-native

The current producer contract gives:

- `keybert`: cosine similarity in `[0, 1]`;
- `yake`: inverted YAKE score normalised per document to `[0, 1]`;
- `legacy`: occurrence count.

A score is therefore meaningful only together with its `method` and within its own method/list. The portable ordering signal across methods is `rank`.

Do **not** normalise all methods into a fake common scale solely for #73.

### 5. Page keywords are part of the intended record output

The current service already returns:

```text
document keywords
page 1 keywords
page 2 keywords
...
```

and AMČR explicitly asked to keep the page-level output. The Digital Archive's per-page indexing makes this a direct discovery requirement.

### 6. Quality is a signal, not a gate

The summary:

- does not create categories;
- does not create thresholds;
- does not route documents;
- does not decide whether OCR is needed;
- does not replace `pages[].quality_score`;
- does not add `quality_band` values.

AMČR / the Digital Archive compute index-time bands from the stored numeric data and their configured thresholds.

## Strategic actions

### A — Add the statistical `keywords` block to the hub record contract

**Goal:** make the current keyword-extract response a stable additive record block.

1. Add a top-level `keywords` property to `docs/templates/shared/atrium_document.schema.json`.
2. Declare `keyword-extract` as the sole owner of this new block.
3. Keep `enrichment` as the separate controlled-vocabulary block, with the existing successor relationship from `llm-enrich` to `keyword-extract`.
4. Register the addition in `POST_FREEZE_CHANGES`; add the matching `## Changelog — <date>` entry to `docs/document_schema.md`; update `tests/test_document_required.py` / producer shapes as required.
5. Keep the new node optional so records written before #73 remain valid.
6. Re-vendor the shared document/schema files to all six processing repositories and let `para-drift` enforce one contract.

#### Proposed minimum shape

The exact property names are still a schema decision, but the semantic shape should mirror what the producer already exposes:

```json
"keywords": {
  "document": [
    {
      "keyword": "hradiště",
      "method": "keybert",
      "score": 0.71,
      "rank": 1
    }
  ],
  "pages": [
    {
      "page": "3",
      "keywords": [
        {
          "keyword": "sonda",
          "method": "keybert",
          "score": 0.64,
          "rank": 1
        }
      ]
    }
  ]
}
```

Rules:

- the block contains **statistical** keywords only;
- every statistical item requires `method`, `score`, `rank`;
- document and page results remain separately addressable;
- page keys remain strings because the current producer follows `lines[].page`;
- no controlled vocabulary term is inserted into this list;
- method-specific score semantics are documented beside the block;
- optional method metadata may be added later, but it must not be needed for the minimum acceptance contract.

Do not add `lemma` unless the consumer contract demonstrates a concrete need; the current service response does not expose it and #73 does not require it.

**Done when:** the new block validates independently, can coexist with `enrichment`, and is accepted by both the frozen schema and the current schema as an additive change.

### B — Make `keyword-extract` write the block

The statistical implementation exists; the work now is record accretion.

1. Extend the `/extract_keywords` path so that the statistical result can be converted into the new `keywords` block.
2. Preserve the current response fields during the transition if they are useful for diagnostics, but make the accreted `document_json`/record the canonical pipeline output, following the service conventions established by #71.
3. For `kind=statistical`, write `keywords` without requiring the controlled kind.
4. For `kind=both`, eventually write:
   - statistical results to `keywords`;
   - controlled results to `enrichment`;
   - never combine them into one array.
5. Do not let a temporarily unavailable controlled implementation prevent a statistical-only call from producing a valid record.
6. Preserve the current per-page results by default for record output, because they are already available and are explicitly wanted for the Digital Archive.
7. Stamp the block with the service's #71 `CreateAction` / `assembled.blocks` provenance in the same manner as the other production writers.
8. Ensure the producer's `program` is `keyword-extract`, not `llm-enrich` or `nlp-enrich`.

#### Producer tests

Add record-level tests for at least:

- document-only statistical result;
- document + multiple page results;
- multiple methods across runs;
- `method`, `score`, `rank` presence;
- empty-page keyword list where a page has no usable terms;
- input filtering follows `atrium_vocab.UNTRUSTWORTHY_LINE_CATEGORIES` (`Garbage`, `Inverted`, `Trash`) plus `Empty`, as on `test` since `6a6619d` (V-6);
- controlled and statistical blocks coexist without merging;
- old `llm-enrich` enrichment records survive a subsequent keyword-extract write;
- AMČR seed identity and other existing blocks remain unchanged.

**Done when:** the real service returns/accumulates a record whose `keywords` block is exactly the statistical output required by #73, while all unrelated record blocks pass through untouched.

### C — Move TEITOK keyword projection to the new record contract

`nlp-enrich` remains the projection owner; it must stop behaving as though it produced the keywords itself.

1. Change `api_util/teitok_project.py` to read the record's `keywords` block.
2. Use the document-level and page-level lists directly from the record; do not regenerate statistical keywords.
3. Retain `@scheme="#kw-<method>"` and `@n=rank` for statistical terms.
4. Change the producer/application identifiers from the stale pre-split values:
   - `app-kw` / `atrium-nlp-enrich-keywords`
   - `app-llm-enrich`
   to identifiers that describe the actual `keyword-extract` producer.
5. Keep controlled-vocabulary TEATER/AMČR projection tied to the separate `enrichment` data and the actual keyword-extract provenance.
6. Make the projection order explicit:
   ```text
   nlp-enrich /enrich
       ↓
   keyword-extract /extract_keywords
       ↓
   nlp-enrich /project_record        (opt-in TEITOK projection)
   ```
7. Remove the production dependency on the old CLI keyword CSV inputs. If the CSV flags are kept temporarily for research/backward compatibility, document them as legacy and ensure the production record path cannot silently fall back to them.
8. Update `config_api.txt`, `run_pipeline.py`, the README, fixtures and projection tests so that no documentation claims an internal `keywords` stage still exists in nlp-enrich.

**Done when:** an opt-in TEITOK projection made from a post-keyword record reproduces the current desired document/page keyword annotations, while nlp-enrich itself remains torch-free and keyword-model-free.

### D — Define and materialise the document-level quality summary last

The prerequisite holds since 2026-10-05: one quality model scores OCR lines and born-digital lines (W3), and OCR'd born-digital pages carry the same fields (W4). This action is still last (after A, B, E), per the 27 September leaning.

#### D.1 Common quality prerequisite

Before #73 writes a summary:

- `ocr-postprocess` remains the authoritative quality-model owner;
- the born-digital path must distinguish text-layer trust / `needs_ocr` detection from the archive's common quality semantics;
- `digital-convert` must not accidentally become a second quality-model owner;
- the field-split record contract must remain intact: reading another stage's quality field does not transfer ownership of `pages`, `lines`, `content` or `tables`.

The #73 summary should use the **final stored page/line quality facts**, not a raw converter-only decode-sanity metric.

#### D.2 Pure deterministic computation

Add a hub/shared helper such as:

```python
quality_summary(record) -> dict
```

The helper must:

- read only existing record facts;
- have no model dependency;
- have no thresholds of its own;
- be deterministic;
- return numbers/counts;
- never compute or store discovery bands.

A minimal shape is:

```json
"quality_summary": {
  "pages": {
    "n": 42,
    "scored": 40,
    "mean": 0.83,
    "median": 0.87,
    "min": 0.12
  },
  "lines": {
    "n": 1830,
    "by_categ": {
      "Clear": 1500,
      "Noisy": 200,
      "Trash": 30,
      "Non-text": 20,
      "Empty": 80
    },
    "derived_from": [
      "pages[].quality_score",
      "lines[].categ"
    ]
  }
}
```

The exact statistic set can stay small. The issue requires page-quality statistics and line counts by category; it does **not** require a new quality scale or a band.

Use the category values already present in the record rather than inventing a second enum merely for the summary.

#### D.3 Materialisation policy

The issue describes the summary as a record-level output, so the default implementation should materialise it in the record **after the common quality pass**.

Do not make `ocr-postprocess` co-owner of digital-convert's entire page/line blocks. Instead:

- the shared function computes the summary;
- the quality-stage write path owns only `quality_summary`;
- it reads `pages[]` / `lines[]` without changing their existing owners;
- on a digital-born document, the summary can include the final common quality facts after the route has applied the quality stage.

If AMČR explicitly chooses an index-only representation instead, keep the same shared function and omit the stored block; that would be a contract decision, not an implementation shortcut.

#### D.4 Tests

Require:

- same record in → byte-equivalent summary out;
- changing one `pages[].quality_score` changes only affected page statistics;
- changing one `lines[].categ` changes only category counts;
- changing unrelated blocks does not change the summary;
- no `quality_band` is emitted by the summary;
- no service branch reads the summary to decide routing or gating.

**Done when:** the summary is a deterministic, additive read-out of the authoritative quality fields and adds no new processing decision.

### E — Make the hub E2E prove the record contract

The current hub E2E already has a keyword step, but its own comments acknowledge that the `keywords` block is missing, so it is not yet a formal record stage.

Upgrade the E2E as follows:

1. Seed the normal record as in #71.
2. Run the production six-stage chain with the current successor identities.
3. After nlp-enrich, call keyword-extract against the record produced by the pipeline.
4. Assert:
   - document statistical keywords exist when the fixture contains usable text;
   - page-level keyword groups exist and resolve to actual page labels;
   - every statistical keyword has `method`, `score`, `rank`;
   - the `keywords` block is owned by `keyword-extract`;
   - `enrichment` is still separate;
   - no statistical score is stored under controlled vocabulary fields.
5. Keep the E2E's explicit extraction method stable for CI. If the hub continues using YAKE to avoid an external model download / Hub rate-limit dependency, this is an explicit test override, **not** a change to the production default, which remains KeyBERT.
6. Add a separate API contract test that asserts the server default is still KeyBERT.
7. Once D lands, assert the deterministic `quality_summary` if AMČR elects to store it.
8. Retain the existing #71 identity and provenance assertions after every stage.

**Done when:** the final record generated by the real pipeline contains both #73 outputs (or the single output if AMČR declines storage of the summary), and the E2E fails if the producer/owner or statistical-vs-controlled separation is wrong.

## Cross-repository contract

The intended current chain is:

```text
1. page-classification
      │
      ├─ scanned path ─► ocr-postprocess
      │
      └─ page-category facts
                   │
2. digital-convert ─┘   (born-digital origin path; no page classifier)
                   │
3. nlp-enrich
      │  entities / lemmas / TEITOK
      ▼
4. keyword-extract
      │  keywords (statistical)
      │  enrichment (controlled, when available)
      ▼
5. nlp-enrich /project_record   (optional TEITOK projection)
      │
      ▼
6. translator
```

The numeric ordering is illustrative, not a new rigid orchestration rule. In particular:

- `digital-convert` is an alternative originator, not a compulsory predecessor of scanned records;
- `ocr-postprocess` may be invoked for selected digital-born pages according to the #2 route;
- the final route/orchestration layer remains responsible for selecting which branch runs;
- the record ownership table, not the visual pipeline order, is authoritative.

## Verification / done-criteria

1. **Record distinguishes the two keyword kinds.**
   - `keywords` contains statistical items only.
   - `enrichment` contains controlled-vocabulary output.
   - No mixed keyword array exists.

2. **Every statistical keyword is self-describing.**
   - `method`, `score`, `rank` are required.
   - Score semantics are documented per method.
   - Cross-method comparisons use rank, not numeric score.

3. **Per-page discovery works.**
   - the record contains document keywords and per-page keyword groups;
   - page identifiers resolve to actual `pages[]` entries;
   - omitting per-page output is only an explicitly agreed performance fallback, not the normal contract.

4. **The producer is correct.**
   - `assembled.blocks.keywords.program == "keyword-extract"` on new records;
   - old `llm-enrich` stamps in pre-split records remain untouched and valid through the successor map.

5. **Statistical extraction is independent of controlled vocabulary.**
   - `kind=statistical` can produce the block alone;
   - controlled-kind unavailability does not block discovery's statistical keyword path.

6. **TEITOK consumes the record block.**
   - the projection no longer needs nlp-enrich's old keyword CSVs for the production record path;
   - statistical method/rank/score survive in the TEITOK header;
   - controlled terms are still separately represented.

7. **Quality summary is deterministic.**
   - it is derived only from the final authoritative page/line quality data;
   - it contains numeric statistics/counts, not bands;
   - changing unrelated record blocks does not change it.

8. **No new quality gating exists.**
   - no service rejects, reroutes or suppresses a document because of the summary;
   - no new threshold is introduced.

9. **Schema compatibility holds.**
   - the additions are registered post-freeze;
   - every current tool repository has the same shared contract after re-vendoring;
   - old `doc-schema-v1` records remain loadable.

10. **The seeded E2E is green.**
    - identity and `source.sha512` survive;
    - each stage's `CreateAction` remains valid;
    - new and old successor program ids are handled correctly;
    - the final record passes the current schema and, through #71's validation path, the crate checks.

## Open decisions to keep explicit

1. **Exact JSON node names for the `keywords` block.**
   The semantic contract is settled; names and nesting should be frozen once the schema patch is written.

2. **Record vs index-only materialisation of `quality_summary`.**
   Default plan: record block, because #73 is explicitly about record-level outputs. Index-only remains the only material alternative.

3. **Exact statistic set.**
   Keep it minimal and numeric. The issue requires page-quality statistics and line category counts, not a second banding system.

4. **Controlled keyword production milestone.**
   `keyword-extract#2` remains the implementation thread. #73's statistical block must not be coupled to a successful LLM run.

5. **E2E method.**
   Default remains KeyBERT. The hub may use an explicit YAKE request for deterministic CI/network reasons; this must be documented as a test override, not a policy change.

## Out of scope

- custom NER and annotation tooling;
- negation detection for entities/keywords;
- machine-written AMČR editor suggestions;
- broad document understanding / new LLM applications;
- vocabulary-gap experiments;
- changing the statistical ranking algorithms merely to force cross-method score comparability;
- new OCR/quality models or quality gates;
- moving keyword extraction back into nlp-enrich;
- re-opening the repository split / rename itself;
- changing page-classification or translator semantics beyond shared-contract propagation;
- RO-Crate versions beyond the #71 pilot baseline;
- record-only execution mode from #67 R3.
