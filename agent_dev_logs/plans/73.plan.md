# Strategy — Issue #73: End-to-end record contract, paradata and RO-Crate

> Issue [#73](https://github.com/ufal/atrium-project/issues/73) · Labels: `integration`, `development`, `enhancement` · **Status: 🚧 IN PROGRESS / PLANNED**
> _Plan prepared 2026-09-30 from the grounding report. Target: S1 contract completion before the S2 pilot._

## Context

The purpose of #73 is to make the shared `atrium_document` record a reliable processing envelope between AMČR and the ÚFAL
services.

The record schema itself is not being redesigned here. The implementation target is:

```text
AMČR seed
    ↓
stage 1 service
    ↓
stage 2 service
    ↓
...
    ↓
final record + per-service provenance
```

Every stage receives the current record, updates its owned content and returns the current record together with the provenance
of that invocation.

The contract must work equally for OCR-derived documents, stored ALTO inputs and the future born-digital route.

---

## Workstream A — Seeded record acceptance

### A1. Define the seed as the first-stage input

Treat the AMČR-created record as the canonical input to the first service.

Required source fields:

- `doc_id` = AMČR file id;
- `source.sha512` = Fedora digest;
- source filename;
- source media type.

The service must not reconstruct these values from the uploaded filename.

### A2. Preserve identity through every stage

For every production service verify:

- `doc_id` is preserved;
- `source.sha512` is preserved;
- filename/media type remain available to downstream processing;
- `source.origin` is set by the tool that reads the source and then preserved.

A service may update only the record blocks it owns.

### A3. Regression coverage for the original read-back bug

The known failure mode was:

```text
seeded record → service → unchanged seed returned
```

The regression test must instead assert:

```text
seeded record → service → seed identity preserved + service result present
```

This must be checked on the actual production request path, not only by calling an internal helper.

### Verification

- Each production service accepts a valid seeded `atrium_document`.
- Each service preserves `doc_id` and `source.sha512`.
- The service result contains the expected newly produced block(s).
- A malformed/unreadable record still fails explicitly rather than being silently returned.

## Workstream B — Per-service Process Run Crate paradata

### B1. Use the existing typed response field

The typed service response already contains an optional paradata field.

Populate that field rather than adding another transport field or a parallel endpoint.

### B2. One `CreateAction` per service invocation

Each service run emits one provenance action describing that processing invocation.

The action should expose the agreed Process Run Crate fields:

- action identity;
- tool/instrument identity;
- tool version;
- creator/author;
- object/input;
- result/output;
- run start/end;
- action status.

The exact property mapping follows the shared RO-Crate / Process Run Crate vocabulary rather than a repository-specific invention.

### B3. Stable identities

The run and tool identifiers must be stable and machine-readable.

Do not use transient container IDs as the logical tool identity.

The tool version corresponds to the actual release/image used for the run.

### B4. Keep provenance composable

The returned service paradata must be suitable for AMČR to compose into its final per-file/process crate.

AMČR may still add job-level context around the service response, but it should not have to reverse-engineer the service invocation from logs.

### Verification

- Every production service emits one valid `CreateAction` for each successful run.
- The `instrument` identifies the actual tool/version used.
- The result/object references are internally consistent.
- A failed invocation has a meaningful action status if it produces paradata.
- The same service run can be incorporated into the AMČR crate without custom per-tool transformation.

## Workstream C — `atrium_rocrate.py` S1 alignment

### C1. Pin the supported profile pair

Use:

- RO-Crate 1.2;
- Process Run Crate 0.5.

Do not move to 1.3/0.6 until the validator supports the new pair.

### C2. Align tool metadata

For tool entities:

- use `version`;
- use stable tool identifiers;
- record tool authors as `creator`.

For file entities:

- retain file size information.

For the record crate:

- use `./` as the root.

### C3. Add embeddable fragment mode

`atrium_rocrate.py` must be able to emit the provenance fragment required by the service response without manufacturing a second
crate root.

This mode is important because AMČR composes the service results into the archived record crate.

### C4. Preserve the agreed vocabulary

Keep the existing JSON-LD vocabulary aligned with:

- schema.org `CreateAction`;
- RO-Crate Process Run Crate;
- PROV-O mappings;
- PREMIS 3 mappings.

Do not introduce project-local equivalents for fields already covered by these vocabularies.

---

## Workstream D — Validation and CI

### D1. Validate every generated profile

Add CI validation for:

- the RO-Crate 1.2 record crate;
- the Process Run Crate 0.5 fragment/action output.

The validator version itself must be pinned.

### D2. Provide representative fixtures

Keep small fixtures that exercise:

- one normal successful run;
- one multi-stage crate;
- one fragment without a new root;
- one file entity carrying size;
- one tool entity with `version` and `creator`.

The fixtures should be deterministic and suitable for regression testing.

### D3. Test composition

Add one test that takes service-level paradata from multiple tools and composes them into a single record crate.

The point is not to reproduce the full Temporal pipeline in CI; it is to prove that the independent service fragments compose without
semantic or structural conflicts.

---

## Workstream E — Seeded end-to-end pilot verification

Once A–D are implemented, perform one real integration run across the current tool chain.

### E1. Start from an AMČR-style seed

Use a realistic `atrium_document` seed containing:

- AMČR `doc_id`;
- SHA-512 source identity;
- source filename/media type.

### E2. Run through the production sequence

At minimum exercise the current text path far enough to prove that:

```text
seed → processing service → next service → final record
```

does not lose identity or provenance.

### E3. Inspect the final crate

Confirm:

- the seed identity is unchanged;
- each stage's provenance is present;
- each tool is identifiable by version;
- there is one record root;
- there are no duplicated roots from fragment insertion;
- the final output is validator-clean.

### E4. Record the result

Store the exact release/image versions and the fixture used in the corresponding integration/dev log so future changes can be
compared against a known S1 baseline.

## Execution order

### Phase 1 — record contract

- implement/verify seeded-record acceptance;
- ensure identity propagation;
- add regression tests for the old read-back failure.

### Phase 2 — provenance

- populate typed `paradata` on every service;
- align identifiers and tool metadata;
- verify service-specific provenance against the shared vocabulary.

### Phase 3 — RO-Crate implementation

- align `atrium_rocrate.py`;
- implement fragment mode;
- pin the validator-supported profile pair.

### Phase 4 — CI

- add deterministic fixtures;
- validate record and Process Run Crate outputs;
- test multi-service composition.

### Phase 5 — integration run

- run the seeded record through the current production chain;
- inspect the final record and provenance;
- record versions/results;
- close the issue only after the complete seeded path is green.

## Explicitly deferred

### Record-only mode

Do not implement record-only execution merely to handle imported outputs.

The adopted AMČR workflow is that imported PSNC ALTO and later HPC OCR outputs receive a normal `alto-postprocess` run so that
the current quality/category models are applied. Record-only execution may be introduced later if another task demonstrates a
need for it.

### Schema redesign

No schema redesign is part of #73. Any additive `atrium_document` change follows the existing schema-versioning process and
belongs with the schema work rather than being introduced as an incidental provenance change.
