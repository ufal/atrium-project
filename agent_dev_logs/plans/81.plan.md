## Context

The CI works; what it promises is not written down. The hub has no tiers and no rule for skips, so each workflow decides for itself: `para-drift` fails a skipped parity test, `api-contract` turns "nothing collected" into success, and the E2E lanes downgrade missing inputs to warnings that never reach a summary. The release and image workflows both fire on a tag and never meet, so a release cannot say which image it belongs with.

What can be reused:
- docker-tool's skip summary and `max-skips` ceiling (`docker-tool.reusable.yml:203-248`) and `para-drift`'s fail-on-skip (`para-drift.reusable.yml:166-171`) as the skip pattern;
- `e2e-digital-smoke.yml:596-646` (a body marker, comment on the open issue) as the alert pattern;
- `tools/ci/workflow_lint.py` and its tests for any new rule;
- `release_trust.md` as the one home for pins, rulesets and immutable releases;
- `docker_gha.md` as the current-state reference; the policy links it, not the reverse duplication.

## Execution plan

### A.1 — The policy (a), hub
1. **`docs/ci_policy.md`**, about 200 lines, normative:
   - **Four tiers:** (1) PR: fast and deterministic, no GPU, no network beyond package installs; (2) integration: a named set of candidate images and revisions; (3) release: tag-triggered validation and publication; (4) monitoring: scheduled external services, dependencies, models and published images.
   - **The check record:** owner, guarantee (what failing means), tier and trigger, inputs, and status: blocking, advisory or optional.
   - **Skip rules:** a blocking check fails if it ran nothing it is named for; an allowed omission is written to the step summary with its reason, not only an annotation; optional work is labelled optional in the job name or summary.
   - **Workflow shape:** orchestration in YAML; logic over about 30 lines goes to `tools/ci/` with tests; comments state intent and invariants; history goes to `docs/decisions/`.
   - **Release semantics:** the decision from A.3.
   - **Pins, rulesets, immutability:** one paragraph pointing to `release_trust.md`.
   - **The change checklist:** why, what it proves, when it runs, what it blocks, what it costs, where it lives.
2. **The responsibility map** in the same file, one row per real check family, in the issue's columns: pre-commit; docker-tool `test`; api-contract (+ openapi-compat); para-drift; workflow-lint; docker-build-smoke; build-and-push with the Trivy gate; release.yml; security; codeql; scheduled-smoke; the two E2E lanes; all-repos-smoke; hub-self-check; pages; skill-validate; the tool-specific ones (keyword-extract's vocab and controlled lanes, nlp-enrich's teitok-schema, translator's integration, the two gpu-inference). ### A.3 — Release ↔ image (a), a proposal first
1. **Recommendation:** a release certifies both its source and contract assets and its production image (`-api`), by digest. AMČR runs the images and mirrors only immutable release tags (#72), and the pilot page lists pinned versions (#77 E).
2. **Mechanism:**
   - one tag workflow per repo: the release job `needs` the image job, so a failed build, probe or CRITICAL gate means no release;
   - the release records the digest(s) of the promoted images (an `images.json` asset with its sha256, and a line in the notes);
   - `workflow_run` is not used: it runs the default branch's file, while the tools work on `test`;
   - the `release: published` trigger in five `docker.yml` files is removed (it most likely never fires, since the release is created with `GITHUB_TOKEN`); translator's `v*.*.*` is aligned to `v*`;
   - the existing scan-by-digest before promotion stays as it is.
3. **Proof on one repo:** digital-convert (smallest assets; its `release.yml` is code-identical to nlp-enrich's). A `workflow_dispatch` dry run, plus one run with a forced probe failure that must end with no release. Then the other five.
4. **If the answer is "independent":** each workflow writes its own outcome to the summary, the release notes say the image is separate, and the "fire in sequence" headers are corrected.
