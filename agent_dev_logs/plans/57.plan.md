## Context

4.37 MB of markdown is spread across six repositories with no navigation, no search and no cross-repo
entry point. **⚡2026-09-21: Pages is no longer disabled on all six** — four serve a static landing
card, one is switched off with its branch already pushed, and the hub's is enabled against the wrong
source and failing. The issue asks for that corpus to become
published documentation — README content, the docs scattered through `service/`, `tools/`, `prompts/`,
`annotation/`, `schemas/` and `data_samples/`, and an `agent_dev_logs` summary per repo — wired
together as *one system of interlinked pages*.

The 2026-09-17 TODO added three requirements that change the design rather than extending it: strip the
repeating blocks; give the hub a page explaining the **external tools and services** a newcomer would
not recognise; and give it a page of **in-detail pipeline narratives**, every workflow beginning to end.

Five boundaries are now settled with the maintainer:

| Boundary         | Decision                                                                                                              |
|------------------|-----------------------------------------------------------------------------------------------------------------------|
| Sources          | **Nothing moves.** READMEs and CONTRIBUTING files stay canonical and full-length; the sites are additive.             |
| Topology         | **Hybrid** — one aggregate hub site, plus a stub site per tool repo that lands the reader in that repo's hub section. |
| De-duplication   | **Site-only.** The assembler renders each shared block once; no source file is collapsed or rewritten.                |
| `agent_dev_logs` | **One history page per repo, derived from `DEVLOG.md`** — not hand-written.                                           |
| Generator        | **MkDocs Material.**                                                                                                  |

"Nothing moves" is what makes this non-trivial. Rendering a 90 KB README as one page is not a system of
interlinked pages, and copying its sections into `docs/` would create exactly the duplication that
every CONTRIBUTING's own "Repository Documentation Management" rule forbids — `README.md` is named
there as the single owner of the project overview. **The resolution is to derive the page split at
build time from untouched sources.** A hub-canonical assembler slices `README.md`, `CONTRIBUTING.md`
and the scattered docs into site pages on every build; the split is regenerated, never stored, and so
cannot drift from what it came from.

# A — Topology: one aggregate site, six front doors

## A.1 · The question the previous draft got wrong, and why it matters

The previous draft specified six independent sites at `ufal.github.io/<repo>/`, each built by a hub
reusable workflow with a thin caller per repo. That reading takes the issue's six checkboxes literally,
and it has one defect that is fatal to the issue's actual ask.

**The issue asks for "a system of interlinked pages". Under six sites, not one of those interlinks can
be checked.** A link from the translator site to the hub's RO-Crate page is an absolute URL to another
origin; `mkdocs build --strict` sees an external URL and passes it. Every cross-repo link — and the
interlinking *is* the deliverable — would ship unvalidated, in a corpus that already contains a
demonstrably broken cross-file anchor (`alto-postprocess/service/README.md:93`, §B.3). Six sites make
the one class of error this design exists to prevent structurally invisible.

Under an aggregate site every cross-repo link is **internal**, and `--strict` fails the build on any
that does not resolve. That is the whole argument. Everything below is secondary to it.

## A.2 · The aggregate build is an existing pattern, not new machinery

The objection to a hub-side aggregate is that it needs the hub to check out five other repositories.
It already does, twice:

* `.github/workflows/all-repos-smoke.yml` — a `strategy.matrix` over `page-classification`,
  `alto-postprocess`, `translator`, `nlp-enrich`, `llm-enrich`, each step
  `actions/checkout@v7` with `repository: ufal/atrium-${{ matrix.repo }}`, no `ref:` (so: default
  branch).
* `.github/workflows/e2e-pipeline-smoke.yml` — four named checkouts into `work/<repo>-main`.

A docs aggregator is the **third instance**, and the cheapest of the three: it reads markdown, runs no
containers, needs no GPU and no `HF_TOKEN`.

## A.3 · What the hybrid costs, and what it retires

**Retired: `vit` as a prerequisite.** The previous draft's ⚡ note re-filed
`atrium-page-classification`'s `vit` default branch from "out of scope" to "prerequisite", on the
reasoning that Pages publishes from the default branch. Under the aggregate that reasoning no longer
applies: the site publishes from the **hub's** `main`, and page-classification's documentation is
merely *read* at a ref the manifest names. Its stub site does publish from `vit`, so `vit` appears
exactly once, as the trigger branch in one caller. **Re-filed again: desirable hygiene with its own
owner, not a #57 blocker.**

**Cost: six Pages enablements, not one.** The stubs keep every checkbox honest and give each repo its
Pages tab. They are cheap — one generated `index.html` per repo with a meta-refresh plus a visible
landing card (a bare redirect is hostile to anyone who arrives from a search result).

**Cost: the aggregate can lag a tool repo's push.** See A.4.

**~~Unchanged: permissions.~~ ⚡2026-09-21 — this paragraph was wrong when written, and it is the
correction that matters most in this plan.** The permission facts hold: `admin: false` on **all six**,
plus `maintain: false` on `atrium-project` and `atrium-llm-enrich`. The conclusion drawn from them
does not.

`actions/configure-pages` **cannot enable Pages on a repository where Pages is already enabled as a
branch source, and cannot repoint one.** Its `findOrCreatePagesSite` **GETs the existing site first**
and returns whatever it finds; it POSTs `build_type: workflow` only when that GET fails. On the hub —
Pages on since 09-21, `main` / `/docs`, legacy builder — the GET succeeds, the action is a no-op, and
a subsequent `actions/deploy-pages` fails because the site is not of type `workflow`. Calling it "the
only path" inverted the truth: it is **not a path at all** for the one repository the plan most needed
it for.

What is left:

* **One owner-level dropdown per repository** — Settings → Pages → Branch `gh-pages` / `/ (root)`.
  This is what actually happened on the five tool repos, and it is what the hub needs. It costs one
  person thirty seconds and it is the recommended route.
* **`PUT /repos/{owner}/{repo}/pages` with a `pages: write` token**, which could in principle repoint
  the site from CI. **Not attempted.** `docs.github.com` is unreachable from the authoring environment
  (the same blockage `PAGES_SETUP.md` recorded on 09-18), so the permission requirement could not be
  verified, and mutating an organisation repository's settings from CI on an unverified guess is a
  worse trade than a dropdown.

The five stubs need no enablement path at all any more — four are already on.

## A.4 · Freshness without a cross-repo token

A tool repo's push cannot notify the hub: `repository_dispatch` needs `contents: write` on the target,
i.e. a PAT or App token this account cannot mint for the hub. Inventing a secret for a docs rebuild is
disproportionate, and there is no cross-repo dispatch anywhere in the ecosystem to copy.

So the hub's `pages.yml` triggers on **push to `main`** (hub-owned docs change immediately),
**`workflow_dispatch`** (rebuild on demand after a tool-repo merge), and a **daily cron staggered off
the existing slots** — the ecosystem already spaces `02:00` / `04:00` / `06:00`; take `07:00`. Each
tool repo is read at its default branch by default, with `docs/site.yml` able to pin a per-repo `ref`
when a reproducible build matters.

Worst-case staleness is 24 h on a tool-repo docs change, and zero on a hub change. State the built ref
per repo in the site footer so a reader can always see what they are looking at.

## A.6 · ⚡2026-09-21 · Where a stub card is allowed to point

Each deployed card carries **eight** links into the hub site — the eyebrow, the "Documentation →"
button, "ATRIUM docs home", the footer, and **four sibling links** in the pipeline strip — across
`index.html` and `404.html`. Times five repositories that is **90 hub links, every one of them a 404**
for as long as the hub site does not exist.

The four sibling links are the ones that did not need to be hub links at all. They now point at
`https://ufal.github.io/<slug>/` — **the neighbour's own published page**, which four of the five
have been serving since 09-19 — and each of those carries its own "Documentation →" button into the
hub section, so nothing is lost beyond one hop. **40 links move; 50 stay.**

The rule, stated so it is not re-litigated: **a link between two tool repos resolves between the tool
repos. A link that is genuinely about the aggregate points at the aggregate.** The card's own four
hub links are deliberately left pointing at the hub — they are the reason the hub site has to come
up, not a workaround for it being down, and rewriting them would have removed exactly the pressure
that surfaced the broken build.

`_generators/make_stubs.py`'s `pipeline_html()` is the single place this is decided; regenerating
reproduces all five trees. **It also emits each branch's `README.md`, and the five deployed copies
carry hand formatting the generator does not reproduce** — when copying a regenerated tree onto a
branch, take `index.html` and `404.html` only.

# B — The assembler, and the defect each capability answers

`tools/docs/assemble_docs.py`, driven by a `docs/site.yml` manifest. Every capability below answers a
defect the survey actually found, with a measurement attached; none is hypothetical.

## B.1 · The manifest: reuse #59's trio, do not invent a second convention

#59 landed `docs/templates/shared/MANIFEST.json` + `tools/shared_manifest.py` +
`tests/test_shared_manifest.py`, and that trio is the house answer to precisely the problem
`docs/site.yml` poses: **one registration drives every consumer, and a test asserts they all agree** —
because, in #59's own words, *"a guardrail cannot see what it is supposed to hold."*

So `docs/site.yml` imitates `MANIFEST.json`'s shape exactly:

* a top level of two keys — a `_comment` array documenting the manifest in itself, and a non-empty
  `files`/`sections` array;
* one reader, `tools/docs/site_manifest.py`, exposing `load_manifest(path) -> list[dict]`, a
  `ManifestError`, and a CLI with `--json` / `--tsv`, mirroring `tools/shared_manifest.py`'s 109-line
  surface;
* validation that raises on an empty list, a missing required field, a duplicate source, or a
  duplicate destination path — the same five checks, for the same reason;
* a `--check` mode that **verifies and writes nothing**, taking its contract verbatim from
  `scripts/revendor_shared.sh`: *"exit 0 when every destination matches … re-running on an already-built
  tree is a no-op."*

`tests/test_docs_manifest.py` carries the four patterns that make `test_shared_manifest.py` load-bearing:

1. **bidirectional agreement** — every manifest entry names a file that exists, *and* every publishable
   file on disk is either in the manifest or in its `exclude:` block. Neither direction alone is enough;
2. **a deliberately-broken fixture** — a `tmp_path` manifest with a duplicate destination, asserting
   `pytest.raises(ManifestError)`, because *"a validator with no failing fixture is indistinguishable
   from one that is not wired up"*;
3. **a structural "no hand-written list survived" regex** — asserting no second enumeration of pages has
   reappeared in the workflow or the theme config;
4. **a prose-count citation test** — the pattern of
   `test_ruff_toml_prose_count_matches_the_manifest`, so a sentence in the docs claiming "these N
   sections" cannot silently fall behind. This is not academic: **`docs/templates/workflows/para-drift.caller.example.yml:7`
   says "currently 16 files" while the manifest holds 17**, and nothing catches it.

Precedent for making this test **hub-local and *not* vendored** is `tests/test_env_doc_contract.py`,
whose reasoning transfers verbatim: *"this file compares two hub-owned documents against each other …
a copy in each tool repo would just re-run the same hub-side comparison five times."*

## B.2 · Split at declared depth — and be fence-aware, or the pilot breaks first

Section sizes are wildly uneven. `alto-postprocess`'s `## 🛤️ Workflow Stages` is **42,775 B — 72 % of
its README** — and nests five levels; `nlp-enrich`'s LLM-enrichment section is **29,907 B**;
`llm-enrich`'s whole README has no section over **7,345 B**. The manifest declares split depth per
section; the assembler never guesses.

**And the splitter must track fence state.** There are **218 heading-looking lines inside fenced code
blocks** corpus-wide. At `##`/`###` split depth the damage is concentrated and, notably, lands on the
hub:

| File                                          | phantom `##` | phantom `###` | cause                                                                                    |
|-----------------------------------------------|-------------:|--------------:|------------------------------------------------------------------------------------------|
| `atrium-project/docs/agent_skill_strategy.md` |        **5** |         **3** | the SKILL.md skeleton quoted in `## Appendix A` (fence opens at line 598, closes at 669) |
| `atrium-llm-enrich/README.md`                 |        **1** |             0 | a quoted heading in an example block                                                     |

A regex over `^## ` would emit five bogus pages from one appendix and truncate Appendix A itself — in
`atrium-project`, the pilot. There are no `~~~` fences in the corpus, so tracking ``` ``` `` alone is
sufficient; assert that in the test rather than assuming it forever.

## B.3 · Anchors, TOCs, and the 132-link problem the previous draft did not count

The previous draft counted **77 relative links and 9 anchor-bearing**; measured today it is **92 and
14**. But the dominant job is one it did not count at all: **every tool README carries a
hand-maintained Table of Contents** — 33 (page-classification) / 24 (alto) / 28 (translator) /
28 (nlp-enrich) / 19 (llm-enrich) = **132 in-page anchors**. A split turns every one of them into a
cross-page link.

Three consequences:

1. **Rewrite intra-file anchors to cross-page links** through the same slug map as inter-file anchors.
2. **Suppress the hand-written TOC sections entirely.** MkDocs generates both a nav and a per-page TOC;
   rendering the hand-written one as well gives every page a dead duplicate nav. The manifest marks
   them `role: toc` and the assembler drops them — one of the few places the site deliberately shows
   *less* than the source.
3. **Build an explicit GitHub-slug → site-slug map.** Emoji headings slug differently in the two
   renderers; `translator/README.md` embeds a badge image *inside* an `##` heading
   (`## Project Structure & Architecture ![Python 3.11](…)`); page-classification carries the corpus's
   only `<a name="…">`. A convention will not cover these — a map will, and an unresolved entry is a
   build failure.

The corpus already contains a **broken** anchor that proves the value: `alto-postprocess/service/README.md:93`
links `../README.md#composite-quality-score`, but the only `## Composite Quality Score` heading is at
`docs/categorization_logic.md:214` — the README merely *links* to it (line 619).

> **⚡2026-09-21 — `--strict` does *not* catch this, and did not.** MkDocs defaults
> `validation.links.anchors` to `info`, and `--strict` promotes *warnings*, not info. Only
> `validation.links.not_found` and `validation.nav.not_found` default to `warn`. So the sentence
> "`--strict` catches this on the first build" — and the same claim in `mkdocs.yml`'s own header
> comment, where it is the stated justification for `strict: true` — described an intention, not a
> check. `mkdocs.yml` now carries
>
> ```yaml
> validation:
>   links:
>     anchors: warn
> ```
>
> which makes both true. Three lines. Verified on mkdocs 1.6.1 / mkdocs-material 9.7.7:
> `mkdocs build --strict` over the 38-page draft tree exits 0 with them in place.

|---------------------|-------:|------------------:|-------------:|---------:|
| page-classification | 49,475 |            79.5 % |           27 |    1,658 |
| alto-postprocess    | 56,510 |            81.1 % |           40 |    1,299 |
| translator          | 23,446 |            62.4 % |           23 |      799 |
| nlp-enrich          | 41,371 |            74.4 % |           31 |    1,219 |
| llm-enrich          | 24,569 |            75.7 % |           12 |    1,694 |

Two parsing hazards, both real: **page-classification's rows contain `|` inside code spans**, so a
naive `split('|')` reads a 3-column row as 5 — split on unescaped, non-code-span pipes only; and
**translator's section carries 17 non-table lines** (block-quote expansions between rows) that a
table-only transposer would silently drop. Assert row counts before and after.

## B.5 · Footnotes, images, and link classes

* **Carry footnote definitions.** Every README defines its footnotes in one EOF block — 30 in
  nlp-enrich, 19 in page-classification, 9 in alto (numbering skips `[^3]`), 8 each in translator and
  llm-enrich. The assembler collects the block and re-emits, on each page, only the definitions that
  page references. Without it, every split page loses every `[^n]`.
* **Allowlist images; never copy directories.** `atrium-page-classification` holds **266 image files
  (~59 MB)**; exactly **17 are referenced from markdown** — 11 confusion-matrix plots under
  `result/plots/` and 6 figures under `supplementary/figures/`. The rest is `small_data_samples/`
  training imagery. The allowlist is *derived* by parsing image references, not written by hand. The 11
  plot references are URL-encoded (`result%2Fplots%2F…` — 60 `result%2F` and 134 `%2F` occurrences in
  that README); GitHub tolerates it, a static generator does not, so decode on ingest.
* **Rewrite links by target class.** doc→doc to site paths; doc→code and doc→CI to absolute GitHub blob
  URLs at the built ref; links into `agent_dev_logs/` likewise, since the raw records are not published.

## B.6 · Fail loudly

An unresolved link, a missing split heading, a manifest entry naming a vanished file, an image
reference outside the allowlist, or a release-table row count that changed across transposition → **
non-zero exit**. Together with `mkdocs build --strict`, a future README refactor that would silently
gut a page turns the Pages build red instead of shipping a hollow site.

## C.2 · The mechanism: render once, transclude, never copy

the model: five near-identical copies whose *only* deltas are three example branch names and

* **The five tool repos do not vendor `docs/templates/CONTRIBUTING.md`.** It is a 9,288 B skeleton with
  `«placeholders»`; it is not in `MANIFEST.json`, not in `revendor_shared.sh`, and not diffed by

## C.3 · What is deliberately *not* de-duplicated

Saying this explicitly is part of the deliverable; the TODO's premise is that duplication is everywhere,
and it is not.

* **The READMEs.** Whole-file similarity between any two of the five is **0.012–0.108**; exact shared

* **The vendored shared code.** 17 canonical files × 5 repos ≈ **1.49 MB of intentional redundancy**,

## F.1 · ⚡2026-09-21 — the exclusion list stopped being hypothetical
