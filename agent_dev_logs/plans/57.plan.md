## Context

#57 was originally specified as a documentation extraction task: move repository Markdown into GitHub Pages, include the core README plus meaningful documentation distributed through the repository and `agent_dev_logs`, and connect the pages into one navigable system.

The design now has to follow the repository reorganisation captured by #72. The production graph is six stages:

```text
page-classification
        │
        ▼
ocr-postprocess ───────┐
        │              │
        ▼              │
   nlp-enrich          │
        │              │
        ▼              │
keyword-extract ◄──────┘
        │
        ▼
translator

born-digital documents enter through digital-convert
```

The exact processing topology above is only an orientation diagram; the authoritative six-stage service table lives in #72. For #57 the important point is the documentation ownership: each current repository gets its own documentation site, while `atrium-project` provides the shared map and the cross-repository entry point.

The hub repository already contains the Pages-oriented scaffolding (`PAGES_SETUP.md`, `mkdocs.yml`, `docs_site/`, `INDEX.md`). #57 should complete and refresh that system rather than introduce a second generator or another documentation governance layer.

## Objectives

1. Publish a maintained `gh-pages` site for the current repository set.
2. Replace the old #57 navigation list with the seven current repositories.
3. Keep repository-specific documentation owned by the repository that implements the stage.
4. Make `agent_dev_logs` digests/plans discoverable as a development-history layer without exposing every raw work file as navigation.
5. Preserve repository lineage for the `alto-postprocess` → `ocr-postprocess` move and the `llm-enrich` split into born-digital conversion and keyword/LLM work.
6. Remove stale Pages links and stale repository names from the public documentation/navigation.
7. Keep the hub site as the canonical cross-repository index while avoiding duplicated copies of component documentation.

### A.2 — Define the site-wide navigation contract

Every site should expose a top-level link back to the hub and links to the other current repositories. The hub should expose the six service sites in the same stage order everywhere.

Recommended shared navigation vocabulary:

```text
ATRIUM Project
├── Overview
├── Architecture
├── Services / Repository map
├── Shared contracts & schemas
├── Development / Releases
└── Components
    ├── Page classification
    ├── OCR post-processing
    ├── Born-digital conversion
    ├── NLP enrichment
    ├── Keyword extraction
    └── Translation
```

Component sites may add their own sections below this common shape.

### A.3 — Define the historical-lineage rule

Use current names in page titles, navigation and URLs. Use old names only in a clearly marked migration/history paragraph or historical reference.

Do not build permanent current navigation links to:

- `atrium-alto-postprocess` as an active OCR service;
- `atrium-llm-enrich` as the current owner of the LLM/keyword stack.

Where a document is copied from old material, add a short provenance note rather than silently rewriting history.

## B — Inventory and curate documentation per repository

The source inventory is broader than README files because the original #57 body explicitly requests `agent_dev_logs` summaries and additional Markdown distributed through repository folders.

For every repository:

1. Collect root-level `*.md` that are genuine documentation rather than generated data.
2. Collect `docs/**/*.md` and service/API documentation.
3. Collect runbooks and meaningful operational guides located under non-`docs/` folders.
4. Collect the useful subset of `agent_dev_logs/digests/` and `agent_dev_logs/plans/`.
5. Include release history / contributing information when it is maintained in Markdown.
6. Exclude raw generated logs, large machine-generated reports, temporary scratch notes and duplicated copies that do not add navigational value.

The goal is **documentation completeness with curation**, not a byte-for-byte mirror of every Markdown file.

### B.1 — `agent_dev_logs` publication rule

Use the same two-level organisation already used by the working logs:

```text
Agent development
├── Digests
│   └── issue-specific current-state summaries
└── Plans
    └── issue-specific implementation strategies
```

The Pages site should link each current digest/plan pair together and back to its GitHub issue. Historical revisions inside long-running issue digests remain part of the digest history; they do not need separate top-level pages.

### B.2 — Component-specific content

Use the repository's current architecture to decide what is prominent:

- page-classification: versions/models, inference, API, data preparation, evaluation and development;
- ocr-postprocess: extraction methods, page splitting, text conversion, quality/scoring, categorisation, service and operational runbooks;
- digital-convert: born-digital PDF/DOCX conversion, record construction, text-layer checks, engines, service and integration;
- nlp-enrich: NLP pipeline, LINDAT calls, NER/morphology, TEITOK and record hooks;
- keyword-extract: statistical methods, service contract, controlled-keyword research boundary, vocabulary assets and output schema;
- translator: ALTO/XML modes, translation backends, API, vocabulary handling, output/retry behaviour and deployment;
- project: six-stage architecture, shared files/contracts, integration, release trust, project-level decisions and the component index.

Current public repository material supports these boundaries. In particular, `keyword-extract` describes itself as the 2026-10-01 assembly point for both keyword and LLM/vocabulary work, while `nlp-enrich` keeps the LINDAT-based NLP stage; `ocr-postprocess` is the current OCR repository and `digital-convert` documents born-digital record creation. citeturn761515view2turn761515view1turn761515view0

## C — Implement the seven Pages publications

### C.1 — `gh-pages` branches

For each of the seven repositories:

1. Ensure a `gh-pages` branch exists.
2. Ensure the branch is the publication branch, not an independent documentation-authoring branch.
3. Build/publish from the agreed source tree so the site can be regenerated when the `test` branch documentation changes.
4. Use the repository's own Pages URL (`https://ufal.github.io/<repo>/`).
5. Set the GitHub repository Website / Pages metadata to that same URL.

The web cache did not give a reliable branch listing for all seven current repositories; therefore branch existence should be verified directly during implementation rather than assumed from the repository metadata.

### C.2 — Keep source-of-truth on `test`

The `gh-pages` branch should be treated as the generated/publication artifact. Do not create a second manually maintained copy that can drift from `test`.

The publication process should therefore be:

```text
repo/test Markdown + selected assets
            │
            ▼
      documentation build
            │
            ▼
        gh-pages
            │
            ▼
       GitHub Pages
```

For #57 this means the main documentation changes remain ordinary repository changes and reviewable on `test`; Pages publication is the delivery step.

### C.3 — Build from the existing hub design

Use the existing `atrium-project` Pages setup as the reference implementation. Do not introduce a second static-site generator unless the existing setup is demonstrably insufficient for a specific repository.

The key invariants are:

- one navigation model;
- one URL convention;
- one set of current repository identities;
- stable relative links inside a site;
- explicit absolute links only where crossing repository boundaries;
- no stale predecessor repository in current navigation.

## E — Interlinking rules

### E.1 — Hub → components

`atrium-project` must link to exactly the current six component repositories in the production-stage table:

1. page-classification
2. ocr-postprocess
3. digital-convert
4. nlp-enrich
5. keyword-extract
6. translator

### E.2 — Components → hub

Every service site gets a persistent "ATRIUM Project" link back to the hub and a link to its own GitHub repository.

### E.3 — Components → components

Cross-links should be used when a downstream/current architecture dependency is meaningful. Avoid turning every README into a dense mesh of unrelated repository links.

### E.4 — Historical links

Historical links to `atrium-alto-postprocess` and `atrium-llm-enrich` may remain in migration notes, release history, or provenance notes. They must be visibly historical and must not appear in the current component selector.

## F — Pages content quality and link hygiene

Run one repository-local documentation audit before publication and one cross-site audit after all seven sites are published.

### F.1 — Repository-local checks

For each site:

- landing page loads;
- every navigation entry resolves;
- local relative links resolve;
- images/assets used by the docs resolve;
- headings render correctly;
- code blocks and tables render without raw-template leakage;
- no page references a removed repository as the current owner;
- the footer/header contains the correct repository identity.

### F.2 — Cross-site checks

From the hub:

- all six component sites resolve;
- all six component sites link back to the hub;
- all three newly introduced/current identities (`ocr-postprocess`, `digital-convert`, `keyword-extract`) have working links;
- predecessor URLs appear only in historical contexts;
- the repository selector contains no `alto-postprocess` or `llm-enrich` active-stage entry;
- all seven Pages URLs are the expected `https://ufal.github.io/<repo>/` form.

### F.3 — Documentation freshness check

Record the source branch / commit used for the publication in the site footer or generation metadata so it is possible to answer "which repository revision does this site describe?" without guessing.

A Pages site that is green but built from a stale repository revision is not considered complete.

## G — Release / maintenance workflow

The documentation handover is useful only if the sites remain maintainable.

The maintenance rule should be:

```text
Documentation change on test
        │
        ├── code/contract change → ordinary repository review
        │
        └── docs-only change     → ordinary repository review
                     │
                     ▼
             Pages publication
                     │
                     ▼
           updated gh-pages site
```

The central hub should own the common documentation-site mechanics; component repositories should own component content. The mechanism must not require manually editing seven independent sites for every repository-map change.

### G.1 — Changes to the repository set

Whenever the production repository set changes, update in one coordinated change:

1. hub repository map;
2. hub Pages navigation;
3. current component's Pages metadata;
4. component-site cross-links;
5. historical successor map, when a repository is renamed/replaced/split;
6. any project-level diagrams or architecture pages.

#57 is therefore not a one-time "copy Markdown" job: its acceptance must include a repeatable repository-set update path.

## Out of scope

- Re-architecting the six production services themselves; that remains in #72 and its implementation issues.
- Moving or rewriting source code solely to make documentation easier to render.
- Replacing the existing project Pages generator without evidence that the current scaffold cannot serve the requirement.
- Publishing raw experiment outputs as first-class documentation pages.
- Making `atrium-alto-postprocess` or `atrium-llm-enrich` active component sites again merely to preserve an obsolete navigation graph.
- Treating GitHub Releases/tags as documentation content that can replace the Pages history; Pages should link to those release records, not duplicate them as a second source of truth.

## Questions / decisions still worth recording

1. Exact publication trigger: automatic build on `test` push, manual publication, or a protected release/documentation workflow using the existing hub workflow machinery.
2. Whether every component site should expose identical navigation labels or only the shared top-level project link plus repository-local navigation.
3. Whether historical predecessor sites should receive explicit redirect-only pages after their identities are removed from the active map.
4. Whether the final Pages source revision should be shown as a commit link in the footer or only stored as build metadata.

These are implementation choices around the already-settled repository map; they must not re-open the six-stage architecture decision from #72.
