## Context
The pilot hands AMČR one record per document and one `CreateAction` per run. AMČR seeds the record before the first stage (`doc_id` = its file id, `source.sha512` = the Fedora digest, file name, media type), calls the services from Temporal, and writes the result once.

The grounding baseline remains **RO-Crate 1.2 with Process Run Crate 0.5**. A seeded run is the acceptance proof: identity must survive every stage, each stage must contribute its own machine-readable provenance, and the final record crate must validate in CI.

The repository split from #72 changes one important implementation detail: the final production chain uses a successor map for renamed stage producers. The plan must therefore treat `atrium-ocr-postprocess` as a first-class contract participant while retaining compatibility with the old `alto-postprocess` id until the final contract freeze.

## Strategic actions

### A — Pin the seed contract and successor identity

**State 2026-10-01:** ✅ A.1–A.3, A.5–A.8 on `test` (hub `v1` = `b0128bc`) and released with the four tags above. A.4 (seed filename warning level) not changed. A.6 landed with `keyword-extract`, not `keyword-extractor`: the name AMČR kept (#72).

1. **`source.sha512`**: add optional `^[a-f0-9]{128}$` field beside `sha256` in `atrium_document.schema.json`. Under the freeze rule, record the additive change in `POST_FREEZE_CHANGES`, `docs/document_schema.md`, and the shared schema register. Keep the same `doc-schema-v1` tag; no version bump.
2. **Define `seed`** in `document_schema.md`: `schema_version`, `record_type`, `doc_id`, `source`, nothing else. State plainly that a seed is valid **input**, while service-emitted records remain subject to the full schema.
3. **Pin the keep rule**: `doc_id`, `sha512`, filename and media type from the seed are immutable; tools may add their own `sha256` and `origin`.
4. **Fix the seed filename warning semantics**: decide whether the existing seed value suppresses the derived filename or whether the log level changes from WARNING to NOTE when the seed is authoritative. This does not block the acceptance criteria.
5. **Seed test**: in `tests/`, send an AMČR-style seed through `open()` → `set_source()` → block write → `finalize()`, and assert that the four seed fields survive and the tool's `sha256`/owned block are added.
6. **Successor map**: introduce one canonical mapping, at minimum:
   ```python
   PROGRAM_SUCCESSORS = {
       "alto-postprocess": "ocr-postprocess",
       "llm-enrich": "keyword-extractor",
   }
   ```
   Add the successors beside their predecessors in block-owner/originator tables and make every program-name comparison use the map.
7. **OCR-specific compatibility**: the new `atrium-ocr-postprocess` tree currently still contains the old repository/provenance identity in places such as the Docker fallback `ATRIUM_RUNNER_REPO`, README/CONTRIBUTING references and the program-level metadata. Update those references deliberately: the new repo is the successor, while the old id remains accepted only through the successor map until the pilot contract is frozen.
8. The hard-coded OCR hand-off check (`self.program == "alto-postprocess"`) must resolve through the successor/alias mechanism rather than string-matching the legacy name.

### B — Align `atrium_rocrate.py` with the pilot crate

**State 2026-10-01:** ✅ B.1–B.9 on `test`; `contentSize` was kept (B.7).

1. **RO-Crate 1.2**: update constants and all documentation references while keeping Process Run Crate **0.5** as the pilot pin.
2. **`version`**: use the tool's version field, not `softwareVersion`.
3. **Stable tool identifier**: prefer the immutable release URL, e.g. `https://github.com/ufal/atrium-<tool>/releases/tag/v<version>`.
4. **Stable run identifier**: add `run_uuid` at run start and carry it through paradata; use it in the crate when present, with the old second-resolution `run_id` retained only for backwards compatibility.
5. **Tool authors as `creator`**: move authors from the root `author` arrangement to each tool's `creator`, retaining ORCID ids where available.
6. **Fragment mode**: `--fragment` plus programmatic `fragment=True` must emit entities without a second dataset root/metadata descriptor so AMČR can embed the provenance into its own record crate.
7. **File size**: add `contentSize` if AMČR confirms the report requirement; otherwise explicitly drop it from the issue/log rather than silently omitting it.
8. **Hub-only validator**: install/use `rocrate-validator` in `hub-self-check.yml`; validate the real final crate against `ro-crate-1.2` and `process-run-crate-0.5` in separate checks. Validate fragments only after embedding them in a test stub root.
9. Keep exporter output deterministic. `run_uuid` must originate from the record/run context, not be freshly randomised inside the exporter.

### C — Make every production service contribute its own `CreateAction`

**State 2026-10-01:** ✅ C.1–C.5 in ocr-postprocess, keyword-extract, nlp-enrich and digital-convert (released) and in translator and page-classification (`test`). C.6: services return no action on an error response today; the AMČR question stays open.

1. Extend the shared `atrium_service.py`/paradata path with one canonical action builder.
2. Required fields should be stable across the six-stage production map: `@id`, `@type=CreateAction`, `agent`, `actionStatus`, `instrument`, timestamps, tool/version identity and the output/input references agreed with AMČR.
3. `agent` must identify the processing actor/account chosen by AMČR (`ATRIUM_RUN_AGENT` or its final agreed equivalent); do not invent an agent identity locally.
4. Each service populates the response `paradata` field with its own action.
5. Add one API contract test per production repository that requires the action keys.
6. Decide separately how failed calls expose `FailedActionStatus`: as service `paradata` or as AMČR-owned failure provenance. Do not implement one interpretation without AMČR agreement.

### D — Seeded end-to-end test: the proof

**State 2026-10-01:** 🟡 D.1, D.2, D.4 and D.5 built; D.3 waits for `api-digital` (digital-convert#2, was llm-enrich#28). D.6 is not met: no green run yet.

1. Add `fixtures/e2e/SEED/<AMČR-style-id>.document.json` containing only the seed fields.
2. Add a seeded variant of `e2e-pipeline-smoke.yml`, with the first stage receiving the seed.
3. Add the corresponding born-digital seeded path once `api-digital` is the production first stage.
4. Extend `tools/e2e/e2e_assert.py` after every stage:
   - `doc_id` unchanged;
   - `source.sha512` unchanged;
   - `source.origin` written only by the actual source reader;
   - the stage's `CreateAction` present and complete;
   - program id accepted through the successor map where a repository transition is being exercised.
5. Build the final record crate from the final record and run the two validator profiles.
6. Done only when the seeded E2E is green end-to-end.

### E — Land the contract as one shared window

**State 2026-10-01:** ✅ landed in one window: re-vendored into all six tool repositories (para-drift green on their `test` heads), hub `v1` moved to `b0128bc`.

The schema, successor map, shared document/paradata modules and RO-Crate builder are hub-owned changes. Re-vendor them together into **all production service repositories participating in the pilot**; the final production map is six stages, so do not preserve the old fixed count of five as a contract assumption.

The service-level `CreateAction` returns follow in the same migration window, and `para-drift` must reject stale shared modules.

## Verification / done-criteria

1. *Identity survives*: seeded E2E is green and the assertion fails when any stage mutates `doc_id` or `source.sha512`.
2. *Each service contributes provenance*: every production repository has a contract test plus one live response showing a valid `CreateAction`.
3. *Crate conforms*: hub CI validates the final seeded crate against RO-Crate 1.2 and Process Run Crate 0.5.
4. *Validator covers production output*: validation runs on the final record generated by the seeded E2E, not only on synthetic samples.
5. *Successor migration is contract-safe*: old and new program ids are both understood through the canonical map, and the renamed OCR service no longer silently reports the legacy repository as its primary provenance.
6. *The work is genuinely end-to-end*: the test crosses the real production-stage chain rather than composing isolated service tests only.
