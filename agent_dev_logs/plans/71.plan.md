## Context
The pilot hands AMČR one record per document and one `CreateAction` per run. AMČR seeds the record before the first stage (`doc_id` = its file id, `source.sha512` = the Fedora digest, file name, media type), calls the services from Temporal, and writes the result once. Until services return their own provenance, AMČR composes the paradata file from the response and the job data (grounding report, item 3). The grounding report calls seeding *working* once the seeded end-to-end run is green, and pins **RO-Crate 1.2 with Process Run Crate 0.5**, the newest pair the validator can check.

Two consequences shape this plan:
1. **Most of the identity half is already true.** A bare seed opens, `sha512` survives, `source` is first-writer-wins and `origin` has one originator per document. What is missing is the *statement* of it (schema, documentation) and the *test* of it (a seeded E2E). The provenance and packaging halves are real work.
2. **It is contract work in shared modules.** `atrium_rocrate.py`, `atrium_document.py`, the schema and `atrium_service.py` are held byte-identical in five repositories by `para-drift`. Each change lands once in the hub, is re-vendored with `scripts/revendor_shared.sh`, and reaches CI when `v1` moves. It is batched, not done repository by repository, and shares one schema round with [#73](https://github.com/ufal/atrium-project/issues/73).

## Strategic actions

### A — Pin the seed contract: schema, definition, one warning fewer
1. **`source.sha512`**: optional, pattern `^[a-f0-9]{128}$`, beside `sha256` in `atrium_document.schema.json`. Under the freeze rule it lands with a `POST_FREEZE_CHANGES` entry, a changelog section in `docs/document_schema.md` and its producer shapes: additive, still `doc-schema-v1`, no `SCHEMA_VERSION` bump. It goes in the **same round as #73's block**: one changelog date, one register update, one re-vendor, one `v1` move.
2. **Define *seed*** in `document_schema.md`: `schema_version`, `record_type`, `doc_id`, `source`, nothing else. Say plainly that a seed is valid *input*; a record a tool *emits* stays under the full schema. `DocumentRecord.open()` already behaves this way, so the change is the definition and a test that pins it, not new logic.
3. **Pin the keep rule** in the same place: `doc_id`, `sha512`, file name and media type from the seed are never changed; a tool adds `sha256` and `origin`.
4. **The WARNING.** With an AMČR seed, the file name a tool derives from the upload (`x.pdf`) will differ from the seed's on nearly every call, and `set_source()` logs a WARNING each time. That is correct behaviour reported as if it were a fault. Proposal: when the existing value came from a seed, log it at NOTE level, or have the tool not pass `filename` when the baseline already has one. Decide with the tool owners; it does not block the acceptance criteria.
5. **Test** (hub `tests/`): a seed with an AMČR-style `doc_id` and `sha512` goes through `open()` → `set_source()` → a block → `finalize()`; the record out carries the tool's block, the seed's four fields, and a `sha256`. Extend the same test to every tool's document hook where it is cheap.

### B — R4: align `atrium_rocrate.py` with the AMČR record crate
1. **RO-Crate 1.2**: the three constants (`ROCRATE_VERSION`, `ROCRATE_CONTEXT`, `ROCRATE_CONFORMS_TO`, `:80-82`), and the versions quoted in `docs/rocrate_export.md` (`:57,92,234`) and `docs_site/contracts/rocrate.md:25`. **Process Run Crate 0.5 is already the pin** (`:88`); its comment asks to verify it. Verify it against the profile name the validator ships (`process-run-crate-0.5`) and delete the caveat.
2. **`version`, not `softwareVersion`**, on every `SoftwareApplication` (`:386,465,622`).
3. **Stable identifiers.**
   - *Tool:* the release URL, `https://github.com/ufal/atrium-<tool>/releases/tag/v<version>`, instead of a name-derived id.
   - *Run:* a `urn:uuid:` minted when the run starts and carried in paradata as a new `run_uuid`, beside the second-resolution `run_id` that can collide across parallel workers (`_run_id_for`, `:260-261`). The crate uses `run_uuid` when present and falls back to today's id for records written before it.
4. **Authors per tool.** The ATRIUM authors leave the root's `author` (`:311,541`) and become each tool's `creator`. ORCID `@id`s stay.
5. **Fragment mode.** `--fragment` on the CLI (`:926`) and `fragment=True` on `document_crate` / `run_crate` emit the entities without the root dataset and the metadata descriptor, so AMČR embeds them in its own record crate. The root stays `./` (`ROOT_ID`).
6. **File size.** `contentSize` on `File` entities (`:361-364,574-576`). The report's item 1 asks for it; the issue does not list it. Add it here (cheap, additive) and say so on #71, or ask David to drop it from the report.
7. **The validator, in the hub only.** A `hub-self-check.yml` job installs `rocrate-validator` and runs it **twice** on real output, once with `ro-crate-1.2` and once with `process-run-crate-0.5`, never merged into one run. Inputs: the module's self-test crates, and the crate built from the seeded E2E's final record (action E), which is the "production crate output" of the acceptance criteria.
   - **A fragment cannot be validated alone**, since it has no root. Validate it embedded in a stub root, and say so in the test.
   - **Reconcile the docs**: `rocrate_export.md` §8 and §9 say not to add a validator dependency to the repos. The hub job satisfies that: the validator lives in the hub's CI, not in any tool's `requirements`. Rewrite §8 to say so, and mention the pin (1.2 / 0.5, move to 1.3 / 0.6 when the validator can).
8. **Determinism stays.** The module's self-test asserts byte-identical output; `run_uuid` must therefore come from the record, never from `uuid4()` inside the exporter.

### C — R2: one `CreateAction` per service call
1. **A shared builder**, `create_action(paradata, object, result, status)`, in `atrium_rocrate.py`, from a finished `ParadataLogger` run:
   - `instrument`: the tool's `SoftwareApplication` (with `version`) and `containerImage`, the image the service runs as (`ATRIUM_RUNNER_IMAGE`, `atrium_paradata.py:49`). The report wants the tag the registry really carries; the `sha-<short>` tag is the stable one, and #69's B3 (runner image from the metadata step) is what makes it true in the tool repositories.
   - `object`: the input file(s) and the seed record; `result`: the output file(s) and the record.
   - `agent`: from an `ATRIUM_RUN_AGENT` setting (named today only in the model's description, `atrium_service.py:612`). It is a new environment variable, so it joins the env contract (`test_env_contract.py`) and `/info`, like every other setting.
   - `startTime` / `endTime` from the run, not the single `at` stamp (`:433-436`).
   - `actionStatus`: `CompletedActionStatus` or `FailedActionStatus`, with `error` on failure.
   - the paradata 2.0 fields as properties of the action.
2. **Every service fills the slot** it already declares:

   | Tool                | Today                                                     | Work                                                                                                                             |
   |---------------------|-----------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------|
   | page-classification | `paradata=None` (`api.py:563`)                            | create a `ParadataLogger` in the service; return the action                                                                      |
   | alto-postprocess    | `paradata_ref=""`, field declared (`text_api.py:311,854`) | return it; stop pointing anything at a working-directory `paradata/` folder                                                      |
   | translator          | "always absent" (`api.py:155`)                            | the JSON part of the multipart response; an XML-only response gets it only when the client asks for multipart (decide in review) |
   | llm-enrich          | "always absent" (`api.py:204`)                            | return it; the current `paradata_ref` points at a temp folder gone when the response leaves (`:635-646`)                         |
   | nlp-enrich          | merged pipeline-run record (`api.py:578-588`)             | wrap it as the action: same fields, plus the members it lacks                                                                    |

3. **Contract test per repository** (`tests/test_api_contract.py` or equivalent) asserts the action's required keys; the OpenAPI document already types the slot, so the release gate's `compare` sees a change in its shape.
4. **A failed run.** The action with `FailedActionStatus` is only useful if it reaches the caller. The typed error body declares no `paradata` member (`ErrorBody`, `atrium_service.py:500-521`, though it allows extra fields); decide whether a failed call carries it in the error body or AMČR records the failure itself from the status and reason code. Ask AMČR before building either.

### D — Seeded end-to-end test: the proof (acceptance criterion 5)
1. **Fixture**: `fixtures/e2e/SEED/<AMČR-style id>.document.json`: the four seed fields, nothing else.
2. **Workflow**: a seeded variant of `e2e-pipeline-smoke.yml` in which stage 1 receives the seed; likewise `e2e-digital-smoke.yml` with the born-digital converter as the first stage ([atrium-llm-enrich#28](https://github.com/ufal/atrium-llm-enrich/issues/28)).
3. **`tools/e2e/e2e_assert.py`** gains, after every stage: `doc_id` and `source.sha512` unchanged; `source.origin` written by the reading tool only; the stage's `CreateAction` present in the response with its required keys.
4. **Last step**: build the record crate from the final record and run the validator profiles of action B7 on it. This is the one test that covers identity, provenance and packaging together.
5. *Done when* (the report's): **the seeded end-to-end run is green.**

### E — Land it in one window
The hub module changes, the schema round shared with #73 and the builder are re-vendored into the five tool repositories together; the per-service returns (C2) follow in the same window. `para-drift` fails any repository that lags, so the order matters (see Order).

## Order
```
A.1-3  schema round: sha512 + seed definition (+ #73's keywords/quality)   (hub)
│
B      atrium_rocrate.py: 1.2 · version · ids · creator · fragment · contentSize   (hub)
│      └─► B.7 validator job on self-test crates
C.1    CreateAction builder (needs run_uuid, ATRIUM_RUN_AGENT)   (hub)
│
E      revendor ─► five tool commits in one window ─► C.2 services return the action ─► move v1
│
D      seeded E2E (fixture, workflows, e2e_assert) ─► B.7 on the final record   ── #71 done
A.4    the WARNING wording: any time, does not block
```
Beside this chain: **#72's release hardening** (immutable tags) should precede the next tool releases, so the tags AMČR builds from cannot move, and the recorded image tag is trustworthy; **#69's B3** puts the real tag into `ATRIUM_RUNNER_IMAGE`.

## Verification / done-criteria
Mapped one to one onto the issue's acceptance criteria:
1. *An AMČR-seeded document passes the chain without losing identity or `sha512`*: the seeded E2E is green, and `e2e_assert.py` fails when any stage changes `doc_id` or `source.sha512` (test the failure once by hand).
2. *Each service contributes its own machine-readable run provenance*: each repository's contract test asserts the action's keys; one live response per service is attached to #71.
3. *The record crate conforms to the baseline*: the validator passes `ro-crate-1.2` and `process-run-crate-0.5`, run separately.
4. *The validator runs in CI against production crate output*: the hub job runs on the seeded E2E's final record, not only on a sample.
5. *Covered by an end-to-end test, not only isolated service tests*: action D.
