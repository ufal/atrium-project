## 1. Strategic intent

One research question, answered with reproducible evidence:

> **On representative archaeological documents, how do exact-version out-of-the-box document-understanding models compare with the established ATRIUM pipeline on reading order, text, image regions and key-value fields, and how much representation detail do they need?**

This is a benchmark and evidence track, not a production stage. The production chain works without #22, and a benchmark result informs later decisions without rewriting the production route.

## 2. What is settled

- **Timing:** deferred until after the pilot. The blocker is the missing in-domain gold set, not code. Specifications may be written now; no model run counts toward the pilot.
- **Corpus:** an ATRIUM archaeological gold set is mandatory. Public benchmarks (OmniDocBench, CHURRO-DS) give context only.
- **Canonical record:** `atrium_document` is the record of truth. Markdown is a derived, regenerable model input and never carries earlier model answers (`json_to_md` does not read `enrichment`).
- **Harness:** `sample_stratify.py`, `bench_compare.py` and `eval_metrics.py` in digital-convert, as research tools kept out of every image (#72).
- **Detail profiles:** `full` (default), `standard`, `minimal`. The text is identical across the three; only the cues differ.
- **Boundaries:** the OCR-engine bake-off is AMČR's. The Docling/MinerU complex-layout bake-off is #22's, deferred with it (10-12).

## 4. Format decision (answers "MD vs JSON")

**Proposal:** JSON for gold and scoring, Markdown for model output, with one converter in each direction.

```text
                gold (page JSON + KV sidecar)  ◄── annotators
                          ▲
record ──► record→gold JSON (baseline)            scorer: compares JSON with JSON
                          ▲
model ──► Markdown (+ HTML tables) ──► MD→JSON parser
```

1. **Gold format:** OmniDocBench-style page JSON. Per element: `category`, polygon or bbox, reading-order index, and `text`, or `html` for tables. Key-value fields go in a sidecar: `field_id`, `label`, `value`, `value_type`, bbox, mirroring the record's `forms` row so the baseline maps across 1:1. _Check the element fields and category list against the pinned OmniDocBench release before freezing._
2. **Record → gold JSON:** a small benchmark-side converter, used only to score the baseline. Lines become text elements in `page_index`/`line` order; `tables` + `lines` become HTML tables (`rowspan`/`colspan`); `forms` becomes KV rows. ALTO `Illustration`/`GraphicalElement` boxes become untyped regions. They are not in the record today, so read them from the source ALTO, as `xml_to_md.py` does.
3. **Markdown → JSON:** a benchmark-side parser for model output. It reads `## Page N` sections, headings, paragraphs, GFM and HTML tables, `![alt](src) <!-- BBOX -->` figure placeholders and key-value lines. It must also parse `json_to_md`'s own output, which gives a round-trip test: record → MD → JSON → compare with record → JSON.
4. **HTML tables in our own Markdown:** `json_to_md` writes GFM tables, which cannot express merged cells. Propose an HTML-table option to digital-convert (default unchanged) rather than changing the renderer here.
5. **No schema change.** Regions and object segments have no record block. If the benchmark proves them useful, propose the block under #71 (shared with page-classification#58).

## 5. Benchmark design

### 5.1 Unit and stratification

The page is the primary unit. Quality statistics are per page, failures are often partial, and hard pages stay visible. Document-level aggregates are a secondary view.

Use the `sample_stratify.py` tiers unchanged:

| Tier        | Rule                                                   |
|:------------|:-------------------------------------------------------|
| `clean`     | `avg_quality_score` ≥ 0.85 and valid-line ratio ≥ 0.50 |
| `degraded`  | ≥ 0.60, not `clean`                                    |
| `hard`      | < 0.60                                                 |
| `text_poor` | no scoreable `Clear`/`Noisy` lines                     |

Changing a threshold after model runs start defines a new benchmark version.

### 5.2 Annotation layers

| Layer        | Content                                         | Pages                                                      | Metric (§7)              |
|:-------------|:------------------------------------------------|:-----------------------------------------------------------|:-------------------------|
| A. Text      | UTF-8 text per element, reading order preserved | all gold pages                                             | CER, WER, NED            |
| B. Order     | element ids in reading order                    | all gold pages (cheap once A exists)                       | order NED                |
| C. Regions   | typed regions with bbox/polygon                 | a subset, rich in `PHOTO*`/`DRAW*`/mixed pages             | IoU P/R, mAP, area error |
| D. Key-value | form fields (label, value, type)                | form-like pages (`LINE_*` labels from page-classification) | field F1, ANLS           |
| E. Tables    | HTML table structure + cell text                | pages with tables                                          | TEDS                     |
| F. Entities  | `TYPE<TAB>surface` sidecar, CNEC/TEATER types   | an agreed subset                                           | entity F1                |

**Region taxonomy (to agree in W0):** start from OmniDocBench/DocLayNet categories and keep only what ATRIUM acts on: text block, title, table, photo, drawing/map, caption, page header/footer, handwriting, stamp/label. A coarse list that annotators can apply consistently beats a fine one.

### 5.3 Sampling protocol

1. Freeze the corpus snapshot and the quality-statistics snapshot.
2. Generate the tier manifest with a fixed seed and check that every tier the corpus contains is present.
3. Size the sample by annotation capacity, never by a desired outcome.
4. Annotate A and B first, then C–F on their subsets.
5. Checksum the manifest and the gold bundle.
6. Never swap pages after seeing results without recording a new benchmark version.

## 6. Baseline

The current deterministic path on the same manifest, frozen as named predictions:

```text
OCR/text input ─► atrium-ocr-postprocess ─► atrium-nlp-enrich (UDPipe + NameTag + TEITOK) ─► atrium_document
```

Born-digital fixtures enter through digital-convert. The baseline is scored through the record → gold JSON converter (§4.2). The baseline has no typed regions, so check 3 reports it as "untyped ALTO boxes only", not as zero.

## 7. Metrics (answers "scoring methods")

| Check          | Metric                                                                                                                                                 | Code                                                          |
|:---------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------|
| 1. Order       | NED between the gold and predicted sequences of matched element ids; elements are matched by text similarity, plus bbox IoU when both sides have boxes | new; reuses `eval_metrics.levenshtein()` (takes any sequence) |
| 2. Text        | CER, WER, NED, by tier and overall                                                                                                                     | `eval_metrics.cer/wer/normalized_edit_distance`               |
| 3. Regions     | per-type P/R at IoU ≥ 0.5; COCO mAP@[.5:.95] where predictions carry scores; per-type area-ratio error of matched pairs                                | new                                                           |
| 4. Key-value   | field P/R/F1 on (key, normalised value); ANLS for values with OCR noise; per-key breakdown                                                             | new                                                           |
| Tables         | TEDS and TEDS-structure                                                                                                                                | `eval_metrics.teds_score()` once `table_teds.py` is vendored  |
| Entities       | micro P/R/F1 on (type, normalised surface)                                                                                                             | `eval_metrics.entity_prf()`                                   |
| Representation | characters, tokens with the exact model tokenizer, runtime                                                                                             | `scripts/detail_budget.py` + run paradata                     |

Rules:
- Report every metric by tier and overall; a macro average must not hide a collapsed tail.
- Missing predictions are counted, never dropped (`bench_compare.py` already does this).
- Page-reference/citation validity stays a diagnostic until the output contract is fixed.

## 8. Candidates and the representation bake-off

**Selection:** a small, interpretable matrix:
- one domain-relevant compact model;
- one general multimodal model;
- one lightweight model;
- the baseline;
- one large model only to test a stated hypothesis about the hard tiers.

The earlier names (CHURRO-3B, Qwen2.5-VL, SmolDocling) are starting points; re-validate them when #22 resumes. Each candidate must be:
- open-weight or locally runnable;
- pinnable;
- licence-compatible with the data;
- runnable on the hardware actually available: the cluster, the Grace Hopper machine via Viktor (stranak, 06-19), or a Spark-class unit (see page-classification#58).

**Per-run record:**
- model and tokenizer revisions;
- inference backend and version;
- prompt version;
- input representation (`image`, `full`, `standard`, `minimal`);
- image preprocessing;
- context limits and decoding parameters;
- hardware and batch settings;
- runtime and cost proxy;
- container and commit;
- licences.

All of it is written as paradata.

**`--detail` bake-off:** the same model, record, prompt and settings with `full` / `standard` / `minimal`; only the profile changes. The size half is measured (digital-convert `docs/reference/markdown.md`); the quality half needs the gold set. `full` stays the default until quality evidence says otherwise.

**Docling/MinerU:** on the born-digital subset, scored with checks 1, 3 and tables against the same gold. dc#5's heading counts are input evidence, not a result.

## 9. Outputs of a completed run

```text
benchmark/
├── manifest.csv, manifest.sha256
├── gold/          text/  order/  regions/  forms/  tables/  entities/
├── predictions/   baseline/  <candidate>/ …   (raw output + parsed JSON)
├── page_scores.csv, aggregate_scores.csv
├── report.md
└── run_paradata.json
```

The report contains:
- the sample summary;
- the benchmark version and checksum;
- per-tier and overall scores for each check;
- the representation cost;
- the run configuration;
- missing outputs and failures;
- licence and resource notes;
- qualitative failures linked to page ids;
- what the data do not support.

## 11. Risks and controls

| Risk                                                | Control                                                                           |
|:----------------------------------------------------|:----------------------------------------------------------------------------------|
| Sample becomes model-driven                         | Freeze the manifest before any candidate is scored                                |
| Four annotation layers exceed capacity              | A + B on all pages; C–F on declared subsets; report subset sizes                  |
| Region taxonomy too fine to annotate consistently   | Coarse list in W0; measure inter-annotator agreement on a pilot batch             |
| MD → JSON parser hides model errors or adds its own | Round-trip test on `json_to_md` output; keep raw model output next to parsed JSON |
| Gold format drifts from OmniDocBench                | Pin the release; record the version in the gold bundle                            |
| Benchmark forces a schema change                    | Benchmark-side layers only; a schema proposal only after evidence (#71)           |
| OCR quality mistaken for DU quality                 | Use quality scores for stratification only                                        |
| Model sees earlier answers                          | Render from the source record; `enrichment` never read                            |
| Characters mistaken for tokens                      | Measure tokens with the exact tokenizer                                           |
| Hard pages vanish from averages                     | Tiered reporting; missing counts visible                                          |
| Research code leaks into images                     | Harness stays out of the image closure (#72)                                      |

## 12. Work packages

### W0: protocol, before resumption (can start now)

Already written: scope and exclusions, ownership map, scoring inventory, candidate criteria, the `--detail` experiment, the paradata template.

**New from the 10-29 body edit:**
1. **Gold-format spec** (§4.1): the element JSON fields, the region taxonomy, the KV sidecar, a pinned OmniDocBench reference. One page in `atrium-project/docs/`.
2. **Metric specs** for checks 1, 3 and 4 (§7): matching rule, thresholds, edge cases (empty pages, unmatched elements, duplicate keys), and how each aggregates per tier.
3. **Converter specs**: record → gold JSON, and Markdown → JSON, with the round-trip test as acceptance.

The issue owner decides these three. Code may follow before the pilot only if it is research code outside the image closure; no run is scored before W1.

### W1: curate the gold set

Freeze the snapshot, generate the manifest, review coverage, annotate layers A–F per §5.2, checksum. **Gate:** no candidate scoring before the gold set is versioned.

### W2: baseline

Run on the W1 manifest and export through record → gold JSON. **Gate:** baseline predictions frozen.

### W3: candidates

Pin revisions, run on identical inputs, keep raw and parsed outputs, record failures. **Gate:** every missing page explained in `run_paradata.json`.

### W4: representation and layout bake-offs

`full`/`standard`/`minimal` with one model, and Docling/MinerU against digital-convert's reader on the born-digital subset. **Gate:** only the variable under test changes.

### W5: score and review

All checks of §7, per tier and overall, plus cost and qualitative review. One Markdown report and machine-readable tables.

### W6: decision

Use the evidence to decide any of:
- whether `full` stays the default;
- whether a lighter profile suits a defined task;
- whether a DU model joins a research or production tier;
- whether routing is worth investigating;
- whether to start fine-tuning;
- whether to propose a regions block (#71).
