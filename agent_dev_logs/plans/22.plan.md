## 1. Strategic intent

#22 should answer one research question with reproducible evidence:

> **On representative archaeological historical documents, how do exact-version out-of-the-box document-understanding models compare with the established ATRIUM pipeline, and what document representation detail is actually needed to retain useful quality?**

The work is therefore a **benchmark and evidence track**, not a new production stage.

The plan deliberately separates four layers that were previously mixed together:

1. **Source/document acquisition and canonicalisation** — handled by the current ATRIUM stages and the `atrium_document` record.
2. **Model-facing representation** — optionally rendered as annotated Markdown from the record.
3. **Document-understanding inference** — the candidate OOTB models/tools being benchmarked.
4. **Evaluation** — gold annotations, deterministic baselines, metrics, cost/resource measurements and the final comparison report.

The production pipeline must remain usable without #22. A benchmark result may inform later architecture choices, but it does not directly rewrite the production route.

## 2. What is already settled

### 2.1 Timing

- #22 is **deferred until after the AMČR pilot**.
- The immediate blocker is not missing benchmark code; it is the absence of the in-domain gold set needed to make any result meaningful.
- Preparation may continue, but no benchmark execution or production-routing change should be represented as part of pilot completion.

### 2.2 Benchmark corpus principle

A generic benchmark is useful for external context but is not sufficient for the project decision. The evaluation needs an **ATRIUM-specific archaeological/historical gold set** with enough variation to exercise the real failure modes of the corpus.

Earlier research identified CHURRO/CHURRO-DS as a more domain-relevant external reference than OmniDocBench for this problem family. That remains useful background, but it does not replace the project gold set.

### 2.3 Canonical representation

The current architecture settles the internal hierarchy:

```text
original input / OCR output / born-digital input
                    │
                    ▼
             atrium_document
                    │
        ┌───────────┼────────────┐
        ▼           ▼            ▼
    NLP/TEITOK   keywords    Markdown (optional)
                               │
                               ▼
                              LLM
```

`atrium_document` is the record of truth. Markdown is a **derived, regenerable projection** for model input; it is not a second database and must not contain hidden prior model answers.

### 2.4 Current Markdown detail profiles

The model-facing Markdown renderer now supports:

- `full` — default, preserves the complete supported cue set;
- `standard` — drops selected low-value layout cues;
- `minimal` — drops more layout cues while preserving the same source text.

The current implementation explicitly keeps the **text identical across profiles**; only cue/detail content changes. This makes the profile comparison suitable for a controlled quality/cost experiment.

### 2.5 Benchmark harness

The existing harness already has the right overall shape:

- `sample_stratify.py` — deterministic quality-tier sampling;
- `bench_compare.py` — manifest + gold + named predictions → reproducible report;
- `eval_metrics.py` — CER, WER, normalized edit distance, entity F1 and optional TEDS.

The harness presently lives in `atrium-digital-convert/test` as migration/research material inherited from `atrium-llm-enrich`. That is acceptable as an interim location; it is not a reason to extend the converter's production image with the research stack.

## 4. Benchmark design

### 4.1 Unit of evaluation

The primary unit should be the **page**, because:

- the existing quality statistics are page-based;
- the current sampler stratifies pages;
- historical documents contain mixed-quality pages;
- a model can fail on only part of a document;
- page-level evaluation keeps difficult/tail cases visible instead of hiding them in document averages.

A document-level aggregate should still be produced as a secondary view where a complete document run is available.

### 4.2 Difficulty stratification

Use the current `sample_stratify.py` mechanism as the starting point, with the four existing tiers:

| Tier        | Default rule                                             |
|:------------|:---------------------------------------------------------|
| `clean`     | `avg_quality_score >= 0.85` and valid-line ratio >= 0.50 |
| `degraded`  | `avg_quality_score >= 0.60` and not `clean`              |
| `hard`      | scored below `0.60`                                      |
| `text_poor` | no scoreable `Clear`/`Noisy` lines                       |

The sampler is seeded and deterministic. Keep the manifest itself under version control or another immutable research location once the benchmark resumes.

Do not silently change the tier thresholds after model runs have started. Any changed thresholds define a new benchmark manifest/version.

### 4.3 Annotation scheme

The gold set should have three annotation layers, with only the layers needed for a given metric:

#### A. Transcription gold

Plain UTF-8 text in page reading order, using the same canonical path convention as `bench_compare.py`.

This is the minimum required annotation and the only part needed for CER/WER/NED.

#### B. Entity gold (subset or full set, depending on annotation effort)

Sidecars in the harness format:

```text
TYPE<TAB>surface text
```

Types should follow the already-used CNEC/TEATER-compatible representation. The benchmark should not invent a second archaeological entity taxonomy merely for #22.

#### C. Table gold (subset)

Only annotate tables where a structured table comparison is worthwhile. Use TEDS as the established structural metric, and keep the optional scorer isolated from the core transcription benchmark.

Do not create a new, elaborate page-layout annotation language merely to keep #22 open. Complex-layout geometry comparison is already being handled separately in `digital-convert#4`.

### 4.4 Gold-set sampling protocol

The first resumed run should:

1. freeze the source corpus/version and quality-statistics snapshot;
2. generate the tier manifest with a fixed seed;
3. verify that all four tiers are represented where the corpus contains them;
4. choose the final annotation count based on annotation capacity, not on a desired model outcome;
5. annotate transcription first;
6. add entity/table annotation to the agreed subset;
7. publish a checksum/version for the manifest and gold bundle;
8. never substitute a different sample after seeing preliminary model results without recording it as a benchmark change.

The page-classification repository provides the methodological precedent for deterministic dataset construction, but #22's own manifest remains the authoritative benchmark sample.

## 5. Baseline definition

The baseline must be frozen before candidate-model scoring.

### Historical description

The original issue described the baseline as:

```text
ABBYY ALTO → ALTO post-processing → nlp-enrich
```

That wording is retained only for lineage.

### Current repository description

The benchmark should identify the baseline as the **current deterministic ATRIUM processing path**, using the current repository identities:

```text
OCR/text-bearing input
      │
      ▼
atrium-ocr-postprocess
      │  quality / categorisation / ordered text
      ▼
atrium-nlp-enrich
      │  UDPipe + NameTag + TEITOK
      ▼
atrium_document / TEITOK-derived reference
```

Where the benchmark uses a born-digital fixture, `atrium-digital-convert` provides the canonical record first; the downstream contract remains the same.

The baseline should be run once on the **final gold manifest** and frozen as named predictions. Do not let the baseline implementation change between candidate runs without opening a new benchmark version.

## 6. Candidate-model track

### 6.1 Candidate selection principle

The benchmark should compare a small, interpretable set rather than every available VLM.

The previous research named CHURRO-3B, Qwen2.5-VL and SmolDocling as candidates. Because the benchmark is deferred and model ecosystems continue to move, these names are **starting candidates, not a frozen lineup**.

When #22 resumes, re-validate candidates against these constraints:

- open-weight or otherwise locally runnable where feasible;
- exact version/revision pinnable;
- reproducible inference;
- suitable for the actual page/document input mode under test;
- no hidden dependence on a hosted provider whose behaviour or model version cannot be frozen;
- licensing compatible with the research data and intended evaluation use;
- sufficient context/input capacity for the chosen task;
- feasible on hardware actually available to the project.

A minimal candidate matrix should contain:

1. one domain-relevant compact candidate;
2. one general-purpose multimodal candidate;
3. one lightweight/efficient candidate where a meaningful cost comparison is possible;
4. the established baseline.

A larger model should be added only when it tests a concrete research hypothesis (for example, whether a high-parameter model materially changes the failure profile on the hard/text-poor tiers).

### 6.2 Exact reproducibility record

For every candidate run, record at least:

- model name and exact revision/checkpoint;
- tokenizer revision where applicable;
- inference backend/version;
- prompt/template version;
- input representation (`image`, `full`, `standard`, `minimal`, etc.);
- image resolution / preprocessing;
- context/input limits;
- decoding parameters;
- hardware type and GPU count;
- batch/concurrency settings;
- runtime and a comparable cost/resource proxy;
- output format/version;
- software/container image and commit;
- data/model licences or access constraints.

This should be written as benchmark paradata, not left only in an interactive shell history.

## 7. Metrics

### 7.1 Core metrics already implemented

Use the existing metrics without changing their semantics:

| Metric                     | Purpose                                                                        |
|:---------------------------|:-------------------------------------------------------------------------------|
| CER                        | Character-level transcription fidelity.                                        |
| WER                        | Word-level transcription fidelity.                                             |
| Normalized edit distance   | Length-normalized error, useful for comparison across varied pages.            |
| Entity precision/recall/F1 | Typed archaeological entity extraction when gold and model outputs support it. |
| TEDS                       | Table structure/content similarity on the explicitly annotated table subset.   |

Report all primary transcription metrics **by tier and overall**. Macro averages should not hide whether the hard/text-poor tail has collapsed.

### 7.2 Representation-detail metrics

The `--detail` experiment should add representation size next to model quality:

```text
profile | chars | approx tokens (when measured) | CER | WER | NED | entity F1 | citation/page locator result | runtime
```

Character reduction is already known from the current `detail_budget.py` measurements. Token counts should be added only with a clearly documented tokenizer/model context; do not equate character reduction with token reduction by assumption.

### 7.3 Page grounding / citations

Page-level citations were a major reason for retaining page markers and layout cues in the original design. Therefore, where a candidate produces explicit page references, record citation correctness as a separate diagnostic.

Do not fabricate a quantitative citation score before deciding what the candidate output contract actually is. The benchmark can start with exact page-reference validity on candidates that support it and later promote that check into a formal metric if the annotation/output scheme stabilises.

## 8. Representation-detail bake-off

### 8.1 Existing evidence

The current renderer shows real input-size reductions:

| Fixture/input      |   `standard` reduction |    `minimal` reduction |
|:-------------------|-----------------------:|-----------------------:|
| two real hub scans | ~35% / ~53% characters | ~52% / ~64% characters |
| digital fixtures   |                ~20…41% |                ~52…63% |
| DOCX               |                    ~0% |                    ~0% |

The numbers differ by document, so they should be reported as ranges rather than as one “global token saving”.

### 8.2 Required missing experiment

Use the final gold set to run the **same model** with:

```text
full
standard
minimal
```

under identical inference settings.

Measure whether any reduction in input detail causes a statistically or practically meaningful deterioration in:

- CER/WER/NED;
- entity F1 where available;
- page/citation grounding where available;
- table quality on the annotated table subset.

The benchmark should not promote `standard` or `minimal` to a new default merely because it is smaller. `full` remains the current default until the quality evidence justifies a change.

### 8.3 Important implementation rule

The three renderers must receive the **same canonical record** and must not see `enrichment`, previous keywords, or other model-generated answers. Otherwise the experiment becomes contaminated.

## 9. Evaluation outputs

A completed benchmark run should produce at least:

```text
benchmark/
├── manifest.csv
├── manifest.sha256
├── gold/
│   ├── text/
│   ├── entities/          # when used
│   └── tables/            # when used
├── predictions/
│   ├── baseline/
│   ├── candidate_a/
│   ├── candidate_b/
│   └── ...
├── page_scores.csv
├── aggregate_scores.csv
├── report.md
└── run_paradata.json
```

The report should contain:

- corpus/sample summary;
- exact benchmark version and manifest checksum;
- per-tier results;
- overall results;
- representation-size/cost table;
- model/runtime configuration;
- known missing outputs and failures;
- licensing/operational notes;
- qualitative failure examples linked back to page/document ids;
- an explicit statement of what conclusions the data do and do not support.

## 11. Work packages and order

### W0 — Freeze the research protocol before resumption

**Status:** ⏸️ deferred until the pilot release.

Prepare only the documentation now:

- benchmark scope and exclusions recorded;
- current repository ownership mapped;
- scoring implementation inventoried;
- candidate-selection criteria written;
- gold-set annotation protocol drafted;
- representation-detail experiment specified;
- reproducibility/paradata template drafted.

### W1 — Curate the gold set

**Owner:** project-level coordination, with domain annotation responsibility agreed before execution.

When #22 resumes:

1. freeze corpus/source snapshot;
2. generate quality-tier manifest;
3. review sample coverage;
4. annotate transcription;
5. annotate the agreed entity/table subset;
6. checksum/version the gold bundle.

**Gate:** no candidate scoring until the gold set is versioned and the annotation protocol is frozen.

### W2 — Freeze and run the baseline

Run the current deterministic pipeline on the exact W1 manifest. Export page predictions in the `bench_compare.py` format.

**Gate:** baseline predictions are complete enough for the selected metrics and are frozen as a named benchmark input.

### W3 — Run the OOTB candidate matrix

For each candidate:

- pin exact model revision;
- record all inference settings;
- run on the identical W1 input;
- preserve raw outputs and normalized prediction files;
- record failures rather than silently dropping hard pages.

**Gate:** every missing/failed page is explained in `run_paradata.json` and is visible in the final report.

### W4 — Run the representation/detail experiment

On the same source records, run the selected model with `full`, `standard` and `minimal` where that input mode applies.

**Gate:** the same record, prompt, model and inference settings are used across profiles; only the representation profile changes.

### W5 — Score and review

Run:

- CER/WER/NED;
- entity F1 where available;
- TEDS where gold tables exist;
- representation cost/size;
- resource/runtime summaries;
- qualitative error review by tier.

Produce one reproducible Markdown report plus machine-readable score tables.

### W6 — Post-pilot architectural decision

Use the evidence to decide whether there is a concrete reason to:

- keep `full` as the model-facing default;
- adopt a lighter detail profile for a defined task;
- add a dedicated DU model/tool to a supported research or production tier;
- investigate routing between deterministic and multimodal processing;
- begin a fine-tuning experiment.

These are **subsequent decisions**. A benchmark result does not itself change the production architecture.

## 12. Research packaging

## 13. Risks and controls

| Risk                                                     | Control                                                                                                            |
|:---------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------|
| Benchmark sample becomes model-driven                    | Freeze the quality-based manifest before candidate scoring.                                                        |
| Generic benchmark replaces in-domain evidence            | Keep the archaeological gold set mandatory; external benchmarks are context only.                                  |
| OCR quality and DU quality are conflated                 | Use `ocr-postprocess` quality only for stratification; do not treat it as the DU score.                            |
| Parser selection gets duplicated across issues           | Keep Docling/MinerU in `digital-convert#4`.                                                                        |
| Model sees prior semantic answers                        | Render Markdown from the source record without reading `enrichment` or prior keywords.                             |
| Character reduction is mistaken for token/cost reduction | Report character counts separately; measure tokens with the exact model tokenizer when meaningful.                 |
| Easy pages dominate the aggregate                        | Always report clean/degraded/hard/text_poor tiers.                                                                 |
| Missing hard-page predictions disappear                  | Preserve missing/failure status and expose it in reports.                                                          |
| Candidate model versions drift                           | Record exact revisions and inference metadata.                                                                     |
| Research code leaks into production images               | Keep the benchmark stack off the production image closure under #72.                                               |
| Benchmark becomes a second keyword implementation        | Keep #73/`keyword-extract` as the production owner and benchmark semantic outputs only where independently scored. |

## 14. Exit / closure criteria for #22

#22 can move from deferred/open research preparation to a completed benchmark record only when all of the following are true:

- [ ] AMČR/pilot explicitly permits the benchmark work to resume.
- [ ] An in-domain archaeological gold set exists and is versioned/checksummed.
- [ ] The final sample manifest is frozen and covers the intended difficulty tiers.
- [ ] The baseline predictions are generated from the same final manifest.
- [ ] At least the agreed OOTB candidate matrix has been run with exact reproducibility metadata.
- [ ] The `full` / `standard` / `minimal` quality comparison is measured wherever Markdown is part of the task.
- [ ] Primary scores (CER/WER/NED) are reported overall and by tier.
- [ ] Entity F1 is reported for the annotated entity track, if that track is included.
- [ ] TEDS is reported only for the annotated table subset, if that track is included.
- [ ] Representation size/cost is reported separately from quality.
- [ ] Failures, missing outputs and licence/resource constraints are visible in the report.
- [ ] The conclusions are reproduced from the committed/archived benchmark artefacts rather than from an ad-hoc interactive run.
- [ ] A post-pilot decision is recorded for whether any heavier DU model, lighter representation, routing or fine-tuning work should proceed.
