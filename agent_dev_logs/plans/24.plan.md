## 🎯 Strategic intent

Issue #24 began as a broad bucket for LLM applications to archival data: local inference, remote inference, document understanding, controlled-vocabulary tagging and related data transformations. The engineering that grew from it proved useful, but the 2026-09-30 architecture decision changed the correct completion strategy.

The target is no longer “finish a standalone `atrium-llm-enrich` service”. The target is:

1. **keep the useful LLM capability**, especially controlled-vocabulary keyword extraction, under one current production owner;
2. **remove the duplicate LLM/vocabulary implementation** from the born-digital converter;
3. **keep the canonical record as the source of truth** and treat Markdown/TEITOK as purpose-specific projections;
4. **keep research and heavyweight inference separate from pilot production images** unless the agreed service contract explicitly requires them;
5. **finish the concrete work in the owning repositories** and leave #24 deferred until the pilot provides a reason to reopen the broader LLM-applications scope.

The plan is therefore a **coordination and convergence plan**, not a new repository/build-out plan.

## 1. Current production architecture

The current production path is the six-stage architecture recorded in [#72](https://github.com/ufal/atrium-project/issues/72):

| Stage                                        | Repository                   | Production responsibility                                                           |
|----------------------------------------------|------------------------------|-------------------------------------------------------------------------------------|
| 1. Page categories                           | `atrium-page-classification` | image/page routing and page-content category prediction                             |
| 2. OCR output / quality                      | `atrium-ocr-postprocess`     | OCR parsing, text extraction and line-quality categorisation                        |
| 3. Born-digital conversion                   | `atrium-digital-convert`     | PDF/DOCX/etc. → `atrium_document`, text-layer checks, `needs_ocr`, digital geometry |
| 4. NLP / TEITOK                              | `atrium-nlp-enrich`          | UDPipe, NameTag, TEITOK generation and record projection                            |
| 5. Keywords / controlled semantic enrichment | `atrium-keyword-extract`     | statistical keywords and controlled AMČR/TEATER LLM keywords                        |
| 6. Translation                               | `atrium-translator`          | XML/ALTO and XML-metadata translation                                               |

`atrium-project` is the coordination/governance hub, not a seventh production stage.

The old identities are historical:

```text
atrium-llm-enrich
    ├── keyword/LLM/vocabulary responsibility → atrium-keyword-extract
    └── born-digital conversion responsibility → atrium-digital-convert

atrium-alto-postprocess → atrium-ocr-postprocess
```

This map should be treated as the baseline for every #24-related reference from now on.

## 4. Convergence rule: one maintained LLM/vocabulary owner

This is the most important concrete consequence of the repository split.

### Desired state

```text
                     ┌──────────────────────────┐
record after NLP ───▶│ atrium-keyword-extract   │
                     │                          │
                     │ statistical             │
                     │ + controlled LLM/vocab  │
                     └──────────────────────────┘
                                │
                                └── keyword/enrichment record data
```

There must not be another independently maintained copy of the same LLM/vocabulary implementation in `digital-convert`.

### Required convergence steps

1. **Compare the two current implementations.**
   `keyword-extract` already carries the research LLM/vocabulary code; `digital-convert` still carries the inherited copy from `llm-enrich`.
2. **Resolve any delta explicitly.**
   Any functionality that is still needed for controlled keywords must be brought into the current keyword owner and tested there.
3. **Delete the duplicate from `digital-convert`.**
   This includes the inherited LLM clients/configuration/vocabulary/build code and the old keyword-service routes.
4. **Keep research-only heavy inference separate.**
   The `keyword-extract` `-llm` target can remain a research target; the production `-api` image should contain only the runtime needed by the actual service contract.
5. **Extend parity/drift checks where the code is intentionally shared.**
   #72 already establishes drift-checked shared layers; #24 should not introduce an ungoverned third copy.

### Anti-pattern to avoid

Do **not** solve the migration by leaving `digital-convert`'s copy “just in case”. That recreates exactly the architecture #72 is trying to remove.

## 5. Controlled LLM path: production contract vs research target

`atrium-keyword-extract` now contains the controlled LLM path, but its state is not the same as the released statistical API.

### Current production baseline

- service: `POST /extract_keywords`;
- `kind=statistical` is released;
- KeyBERT is the default statistical method;
- YAKE is selectable;
- the legacy KER method remains available;
- method, score and rank are returned;
- successful runs carry the common `CreateAction` / paradata.

### Current controlled target

The controlled path still needs:

- integration of the LLM/vocabulary runtime into the service boundary;
- a completed evaluation/rubric gate from `keyword-extract#2`;
- the final record-level `keywords` block under #73;
- the versioned vocabulary asset;
- hub E2E coverage once the controlled path is actually serviceable.

The controlled implementation should remain **separate from the statistical method semantics**. The response/record must make the source/method of each keyword explicit rather than mixing model-selected vocabulary terms with statistical scores.

### LLM execution boundary

The current direction is to treat the LLM as a capability consumed by the keyword stage rather than as a reason for the hub to host a general-purpose “LLM service”. Heavy local weights should remain on research/inference infrastructure or an approved runtime path; the statistical production API image should not inherit the full GPU research stack merely because the repository contains it.

OpenRouter routing, Ollama and local `transformers`/vLLM remain useful implementations for experimentation and evaluation. Their presence does not change the production stage boundary.

## 6. Vocabulary governance

The vocabulary is now a first-class shared production artefact, not an incidental prompt file.

### Required state

- AMČR + TEATER vocabulary material is declared CC0 in the current keyword stage;
- vocabulary construction is owned by `keyword-extract`;
- the validated result is published as a **versioned release asset**;
- production consumers use the released/pinned asset rather than silently rebuilding from moving sources;
- provenance and run metadata identify the vocabulary release used for an inference run.

### Current gap

The code can build the vocabulary, but the release asset is still open. The controlled-vocabulary work in `keyword-extract#2` is active and currently has an evaluation/rubric gate, so the project should not treat every generated vocabulary snapshot as a production baseline.

### Relation to #24

The original #24 question was “how do we apply an LLM to the archaeological vocabulary?” The current answer is more concrete:

> **the keyword stage owns the vocabulary and the controlled-LLM application; the vocabulary is versioned and the LLM output becomes record data.**

The broader question of using LLMs for arbitrary document understanding remains deferred under #22/#24.

## 7. The three-format architecture remains, but the record is canonical

The 2026-08-01 decision should remain the stable conceptual model:

```text
source / OCR / born-digital
              │
              ▼
       atrium_document JSON
              │
       ┌──────┴───────┐
       │              │
       ▼              ▼
 Markdown         TEITOK XML
 (LLM input)      (spatial/NLP view)
```

### JSON

The record is the authoritative place for:

- source identity;
- page and line geometry;
- OCR text and quality;
- page categories;
- NLP/NER enrichment;
- statistical keywords;
- controlled vocabulary keywords/enrichment;
- provenance and cross-record identifiers.

### Markdown

Markdown is an input projection for models and humans. It should preserve useful source/layout cues, but it should not become a second database of model outputs.

Therefore the stress criterion is:

- preserve source text;
- preserve page order;
- preserve line order;
- preserve required spatial/layout cues;
- do **not** require entities/keywords to be duplicated into the Markdown projection.

### TEITOK

TEITOK remains the visually/spatially faithful NLP representation. Its normal output keeps the agreed NLP layer and geometry; page categories, line quality and keyword facts remain record data unless an explicit projection mode is used.

This distinction is important for #24 because otherwise the old LLM pipeline can quietly become responsible for several competing copies of the same semantic information.

## 8. Born-digital conversion is now a separate stage

The converter side of the old LLM repository is being completed under `atrium-digital-convert`.

### Required target

```text
born-digital file
      │
      ▼
POST /reformat
      │
      ▼
atrium_document
      │
      ├── normal downstream NLP
      ├── keyword-extract
      └── pages marked needs_ocr → OCR route
```

### Important constraints

- `digital-convert` preserves the `digital-convert` record program id;
- its production API is `/reformat`, not `/extract_keywords`;
- it must not call page-classification or OCR services itself; orchestration stays outside the converter;
- it must preserve seeded `doc_id` and `source.sha512` under #71;
- it reports explicit OCR/text-layer reasons;
- OCR-required pages are handed to the OCR stage and merged back into the same record;
- it does not produce or own keywords;
- its production image must not contain the old LLM/keyword service as an active path.

The current `test` tree is still visibly transitional. That is expected as migration state, but it is exactly why #24 should not describe the old LLM repository as the current production implementation.

## 9. Shared-reader and quality boundary

#72 assigns the shared document-reader responsibility to `ocr-postprocess` and requires governed pins for consumers.

The #24 strategy should follow that rule:

- the converter can use approved/pinned shared reader components;
- the OCR stage remains the owner of OCR-side line quality semantics;
- no second quality model should be introduced simply to support an LLM;
- the record is the hand-off surface between stages.

This is especially important for born-digital inputs: a local text-layer diagnostic in `digital-convert` is not a replacement for the downstream OCR quality stage when a page is reprocessed.

## 10. Document Understanding remains deferred

The original #24 description was broad enough to include general “LLM applications to data”, but the project has since separated **controlled keyword enrichment** from **broader document understanding**.

The broader DU path is represented by:

- [atrium-project#22](https://github.com/ufal/atrium-project/issues/22) — benchmark/evaluate out-of-the-box document-understanding tools;
- [atrium-digital-convert#3](https://github.com/ufal/atrium-digital-convert/issues/3) — conversion/stress validation for model-facing Markdown;
- [atrium-digital-convert#4](https://github.com/ufal/atrium-digital-convert/issues/4) — PDF/DOCX/other DU input handling.

The AMČR baseline in #67 explicitly places the broad DU work in **defer**. Therefore #24 should not silently absorb a new Docling/Marker/Grobid/OmniDocBench implementation as part of current pilot completion.

A future post-pilot phase can reuse the current three-format and evaluation infrastructure if the project decides that broader DU has sufficient value.

## 11. Inference-resource boundary

The old plan made local multi-GPU inference a major #24 workstream. The current project baseline does not.

The project-level #26/#27 multi-GPU/H100 issues were stopped/de-scoped from the pilot. The remaining local LLM implementation can still support single-GPU and research multi-GPU execution where useful, but:

- multi-GPU is **not** an acceptance criterion for #24;
- H100/GPU-runner infrastructure is **not** part of #24 completion;
- no new cross-repo CUDA/inference infrastructure should be introduced under #24 without a separate project decision.

This keeps the LLM research capability available without turning the pilot architecture into an infrastructure project.

## 12. Research vs production release line

The current architecture has to maintain a hard boundary between experimental LLM work and deployable services.

### Research can contain

- model registries and prompts;
- vocabulary experiments;
- evaluation/rubric tooling;
- local `transformers`/vLLM targets;
- OpenRouter/Ollama experimentation;
- DU benchmark utilities.

### Production images should contain only

- the approved service entrypoint;
- the current typed contract;
- the required stage logic;
- governed shared components;
- approved runtime dependencies.

For `keyword-extract`, the `-llm` research target is acceptable as a research surface. For `digital-convert`, the inherited LLM stack must leave the production release line altogether.

The production image manifest and hub E2E are therefore part of the real architecture, not merely packaging cleanup.

## 13. Execution order

The work should proceed through the owning issues in this order.

### Phase A — preserve the current decision boundary

1. Keep #24 **deferred**.
2. Stop adding new standalone LLM service work under the hub issue.
3. Point all concrete implementation references to the owning repository issues.
4. Keep this plan as the architectural umbrella and post-pilot reassessment document.

### Phase B — converge LLM/vocabulary ownership

1. Compare `atrium-digital-convert`'s inherited LLM/vocabulary implementation against `atrium-keyword-extract`'s current `test` implementation.
2. Bring any required deltas into `keyword-extract`.
3. Run its tests/release gates.
4. Remove the duplicate from `digital-convert`.
5. Remove the old keyword/LLM service endpoints and production metadata from `digital-convert`.
6. Update hub/release metadata so there is one current production owner.

### Phase C — finish the controlled keyword service

1. Complete the evaluation/rubric work from `keyword-extract#2`.
2. Wire the controlled vocabulary path into `POST /extract_keywords` while keeping statistical and controlled outputs distinct.
3. Implement the record-level `keywords` block from #73.
4. Publish the versioned CC0 vocabulary asset.
5. Extend the production API closure manifest only with code genuinely reachable by the service.
6. Turn the hub keyword E2E into a green, release-pinned path.

### Phase D — finish the digital-convert production boundary

1. Replace the inherited `/extract_keywords` API with `POST /reformat` under `digital-convert#2`.
2. Preserve #71 seeded-record identity and paradata.
3. Complete the production format/input contract.
4. Create the final `...-api` production image and retain the batch `...-digital` path.
5. Clean all old `llm-enrich` service/image/CITATION/README/OpenAPI metadata.
6. Remove the LLM/GPU research stack from the production converter image.
7. Ensure the hub digital E2E consumes the new stage identity.

### Phase E — validate the three-format boundary

1. Build one fully enriched canonical record fixture.
2. Build one format-2 TEITOK fixture with complex page/line/entity edge cases.
3. Run JSON→MD and TEITOK→MD conversions.
4. Assert no loss of source text, page order, line order or spatial cues.
5. Assert entities/keywords remain in the record rather than demanding Markdown duplication.
6. Keep this validation under `digital-convert#3` and use its results as evidence for #24.

### Phase F — release and trust hardening

Consume #72 rather than rebuilding its contracts:

- immutable releases;
- reviewed workflow SHA pins;
- shared-layer parity checks;
- versioned vocabulary asset;
- correct image provenance;
- predecessor repository retirement/archiving;
- final six-stage service map.

## 15. What must not be reintroduced

1. **No second LLM repository.** The project does not need another umbrella repo between the hub and `keyword-extract`.
2. **No LLM ownership in `nlp-enrich`.** Its production role is LINDAT + TEITOK/record projection.
3. **No keyword ownership in `digital-convert`.** It is the born-digital converter.
4. **No service-to-service calls from the converter for orchestration.** Temporal/the hub workflow owns the stage sequencing.
5. **No default duplication of record facts into TEITOK/Markdown** merely because an LLM might consume them.
6. **No production dependency on unreleased vocabulary snapshots.** Pin the release asset.
7. **No hidden multi-GPU acceptance requirement.** The pilot baseline explicitly removed it from #24.
8. **No assumption that “working converter” equals “solved document understanding”.** The DU benchmark remains a separate deferred question.

## 16. Exit / reassessment criteria for #24

Because the issue is intentionally deferred, its completion should not be declared merely because the repository split happened. Reassess the issue after the pilot when the following evidence exists:

- a stable six-stage production map is running end-to-end;
- `keyword-extract` has a tested controlled-LLM path or a documented decision not to ship it;
- there is one maintained LLM/vocabulary code owner;
- the vocabulary has a versioned release artefact;
- `digital-convert` no longer carries the inherited LLM/keyword production code;
- the three-format conversion stress suite has closed its current acceptance questions;
- the broader DU benchmark question has either been completed in #22's successor work or explicitly dropped;
- AMČR has enough pilot evidence to decide whether further LLM applications belong in S2/post-pilot scope.

At that point the project can choose one of three documented outcomes for #24:

1. **close** because the useful LLM scope has been absorbed into concrete service issues;
2. **reopen with a narrower post-pilot scope** for broader DU/LLM applications;
3. **keep deferred** if there is still insufficient evidence or priority.

No new implementation branch should be created merely to keep #24 “active”.
