# Strategy — Issue #58: honour `$PORT` and `$HOST` in all five `api` images

> Issue [\#58](https://github.com/ufal/atrium-project/issues/58) · Labels: `bug`, `development`, `integration` · Type: `Task` · Milestone: WP4 — Pre-Closure Architecture Review · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor VII, plan item **A**)
> **Status: 🟢 Implemented 2026-09-11 — 37 files across all six repos, delivered for review and NOT pushed to any remote. Evidence in [`../digests/58.digest.md`](../digests/58.digest.md); findings 7-9 there came out of the build itself.**

## Context

`docs/templates/k8s/atrium-service.deployment.yaml:55-56` — the manifest ARÚP/ARÚB deploy from under [\#55](https://github.com/ufal/atrium-project/issues/55) — declares `env: PORT: "8000"`. Only alto-postprocess honours it. The other four bake `--port 8000` into an exec-form `ENTRYPOINT`, where no shell exists to expand a variable.

#53 sequenced this first, not because it is the largest finding but because it is the only one sitting on a **live acceptance path**: `docs/k8s_acceptance_runbook.md` has five unchecked partner boxes, and the document those boxes are checked against advertises a knob that does not work. It also framed the honest alternative — delete `env: PORT` and declare the port fixed — which #58 correctly declines.

A verification pass (2026-09-10, on the issue) corrected two things in the issue body, and this pass adds three more. The most important: **fixing the four services without also fixing the manifest makes the manifest newly broken.** Today `PORT` is inert, so the manifest works. After this change `PORT` is live, and the manifest's *other four* hardcoded `8000`s — one `containerPort` and three probe ports — silently disagree with it. A partner who changes the one line the manifest invites them to change gets a restart-looping pod. That is a worse failure than the one we are fixing, and it lands on the acceptance round.

So the scope is not "4 × Dockerfile + 4 × `service/api.py`". It is that, **plus the manifest, plus the CI probe**.

## Strategic actions

### A — Use `python -m service.api`, not `python service/api.py`

The issue's prescribed entrypoint crashes all four containers at import. `python service/api.py` puts `sys.path[0]` at `/app/service` with no package context: nlp-enrich and llm-enrich die on `from .atrium_service import …` (`ImportError: attempted relative import with no known parent package`), translator on `from main import …` (`ModuleNotFoundError`). Both reproduced from scratch. alto's identical-looking line works only because `text_api.py:21-45` inserts the repo root and `service/` into `sys.path` before the first first-party import — the entrypoint does not carry that bootstrap, and copying the line without it copies the inert half.

```dockerfile
ENTRYPOINT ["python", "-m", "service.api"]
```

fixes both classes at once and needs **no `__init__.py`** (PEP 420 — verified identical with and without; nlp-enrich and llm-enrich happen to have one, translator and page-classification do not, and it makes no difference) and **no import rewrites**. Under `WORKDIR /app` it gives `sys.path[0] = /app`, which is exactly the environment `uvicorn service.api:app` already runs in — so every repo-root import keeps resolving as it does today. All six root-level modules were confirmed present at their repo roots.

Do not add `__init__.py` files "for safety". They are not load-bearing here, and adding two changes what `pytest` collects.

### B — One `__main__` block, identical in all four

Append to `service/api.py` in nlp-enrich and translator; **replace** the existing partial blocks in llm-enrich (`:519-522`) and page-classification (`:348-361`).

```python
if __name__ == "__main__":
    import logging
    import os
    import sys

    import uvicorn

    # (12-factor XI, issue #61) Logs are an event stream: emit to stdout and let the
    # supervisor route them. Library modules only getLogger(); this is the one place
    # allowed to configure handlers. Format is alto's, verbatim, in all five — a
    # partner tailing five services wants one shape, and format drift is never
    # fixed later.
    logging.basicConfig(
        level=os.getenv("LOG_LEVEL", "INFO").upper(),
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
        stream=sys.stdout,
    )

    # (12-factor VII, issue #58) The service exports itself by binding a port, and
    # which port is configuration. These were baked into an exec-form ENTRYPOINT
    # array, where no shell exists to expand a variable — while the k8s manifest we
    # hand ARÚP/ARÚB declares `env: PORT` and service/healthcheck.py:49 already reads
    # it. Setting PORT therefore moved the health PROBE and not the listener, and the
    # container reported unhealthy forever.
    #
    # The app reference is derived, not hardcoded: under the container entrypoint
    # (`python -m service.api`) __spec__.name is "service.api" and uvicorn gets an
    # import string, so RELOAD works; under a direct `python api.py` (service/README.md
    # step 1) __spec__ is None and it gets the object, which resolves from any cwd.
    # Hardcoding the string would break the documented README path; hardcoding the
    # object would make RELOAD a silently-dead knob — the exact bug class this issue
    # exists to close.
    _app_ref = f"{__spec__.name}:app" if __spec__ is not None else app

    uvicorn.run(
        _app_ref,
        host=os.getenv("HOST", "0.0.0.0"),
        port=int(os.getenv("PORT", "8000")),
        reload=os.getenv("RELOAD", "false").strip().lower() in ("true", "1", "yes", "on"),
        # (12-factor IX, issue #55) Disposability: this is the `--timeout-graceful-shutdown 20`
        # that moved off the ENTRYPOINT line. serve_lifecycle() adds its own drain on top;
        # docs/k8s_deployment.md carries the full budget the two have to fit inside.
        timeout_graceful_shutdown=int(os.getenv("GRACEFUL_SHUTDOWN_S", "20")),
    )
```

Three notes on why this block and not alto's verbatim:

1. **`__spec__` replaces the object-vs-string decision.** The issue's point 4 says page-classification deliberately passes the app object because `service/README.md:251` documents `python3 api.py` run from `service/`, where `"service.api:app"` does not resolve. That path was checked and genuinely works (`service/inference.py:10` appends the repo root before `from model_registry import …`), so the reasoning is real. `__spec__` *generalises* it rather than making page-classification an exception — verified across all three launch contexts. It also removes the double-execution in Finding 5, where the module body runs once as `__main__` and again under its real name.
2. **The logging lines are [\#61](https://github.com/ufal/atrium-project/issues/61)'s, carried here on purpose.** #61's digest already concludes *"#58 first, or together"* because this is the same block. alto's template contains it; dropping it means writing this block twice. **Say so on both issues** so #61 is closed deliberately for these four repos, not by accident.
3. **`timeout_graceful_shutdown` is a real `uvicorn.run()` keyword in both forms**, so #55's drain contract survives whichever app reference is chosen. `reload=True` with an object makes uvicorn warn and disable reload — which is why the derivation above matters.

### C — Dockerfile `api` stage, four repos

Beside the existing `EXPOSE 8000` / `STOPSIGNAL SIGTERM`:

```dockerfile
ENV PORT=8000 GRACEFUL_SHUTDOWN_S=20
ENTRYPOINT ["python", "-m", "service.api"]
CMD []
```

- Keep `EXPOSE 8000`. It is metadata only — `-p 9000:9000` works regardless — and it correctly documents the default. Add a one-line comment saying it tracks the default, not the effective port.
- The `ENV` and the code default are deliberately redundant, as in alto: `ENV` makes `docker inspect` self-documenting and gives `healthcheck.py` a value even if the code default ever drifts.
- **Delete the `--timeout-graceful-shutdown` comment block above each old `ENTRYPOINT` only after moving its content.** Each of the four carries a repo-specific paragraph about why its slow work can outlive the budget (translator's per-chunk LINDAT calls, llm-enrich's per-line LLM calls, page-classification's `MAX_PDF_PAGES` loop, nlp-enrich's separate `/jobs` mechanism). That reasoning is not boilerplate and must move to the `GRACEFUL_SHUTDOWN_S` line, not vanish with the flag.
- nlp-enrich's `api` stage has no `CMD []` where the other four do. Behaviour is identical (`ENTRYPOINT` resets an inherited `CMD`); add it for consistency while the file is open.

### D — Fix the manifest, or ship a worse bug than the one being fixed

`docs/templates/k8s/atrium-service.deployment.yaml` hardcodes `8000` in four places the `env:` block does not reach: `containerPort` (`:52`) and all three probes (`:72`, `:85`, `:98`), plus the commented Service (`:146-148`). A partner changing `value: "8000"` to `"9000"` gets a container on 9000 and three probes on 8000 — the startupProbe never passes and the pod restart-loops.

The named port already exists at `:53` and nothing uses it. Point the probes at it:

```yaml
ports:
  - containerPort: 8000     # must equal env PORT below — the only pair that has to agree
    name: http
env:
  - name: PORT
    value: "8000"
```

…and change the three `port: 8000` probe fields to `port: http`. That reduces five places to two, with a comment naming the pairing. Do the commented Service block too, or delete the `8000`s from it.

Then add `PORT`, `HOST` and `GRACEFUL_SHUTDOWN_S` to `docs/k8s_deployment.md`, which mentions `PORT` **nowhere today** (grepped: zero hits). One paragraph, not a table — the full table is [\#60](https://github.com/ufal/atrium-project/issues/60)'s job, and this is the pointer it will replace. Include the `HOST` asymmetry: `healthcheck.py` always probes `127.0.0.1` and never reads `HOST`, so `HOST=127.0.0.1` is the one plausible value that yields a container reporting *healthy* while being unreachable from outside.

#53's Files line for this item already listed both of these files. #58's dropped them; restore them.

### E — Add the CI probe as a second start, not an edit to the first

`docker-tool.reusable.yml`, job `docker-build-smoke`, step *"Run container and wait for HEALTHCHECK"* (`:338-423`). The existing probe runs `docker run -d -p 18080:8000` and must stay **exactly as it is** — it is what proves the default path and every existing probe keep working unchanged, which is the issue's own second acceptance bullet.

Add a second, shorter step after it, gated on the same `if: contains(fromJSON(inputs.probe-targets), matrix.target)`:

```bash
cid=$(docker run -d -e PORT=9000 -p 18080:9000 "$IMAGE")
```

then reuse the existing wait-for-healthy loop, and stop there — no `/ready`, no SIGTERM assertion, those belong to the default-port probe and duplicating them doubles the job's slowest phase for nothing.

**This is why the assertion is nearly free**: Docker's `HEALTHCHECK` runs `python /app/service/healthcheck.py` *inside* the container with the container's environment, and `healthcheck.py:49` reads `PORT`. So a container that reaches `healthy` with `PORT=9000` has proved, in one status transition, that the listener moved **and** that the in-container health probe found it. That is exactly the comment's *"run `healthcheck.py` inside the container at a non-default port, not just curl it"* — with no new script. Add one `curl -sf http://127.0.0.1:18080/health` afterwards so the published-port half is asserted too.

Budget: reuse the same 330s deadline and its comment. Two probes stay far inside `timeout-minutes: 45`.

Nothing changes in the five callers' `.github/workflows/docker.yml` — all already pass `probe-targets: '["api"]'`.

### F — Verify by breaking it, as the issue asks

The acceptance text says to confirm the job goes red. Do it concretely and record the run link on the issue:

1. On one repo's branch, set the `api` `ENTRYPOINT` back to the old exec-form `uvicorn … --port 8000` line.
2. Push. The **new** step must fail at "container did not report healthy within the timeout" (the server sits on 8000, `healthcheck.py` probes 9000), while the **old** step stays green.
3. Revert.

A probe that has never been observed failing is not evidence. Note that the failure surfaces as a *timeout*, not an immediate error — the 330s budget makes that a five-and-a-half-minute red, which is worth stating in the step's comment so a future reader does not mistake it for a slow runner.

## Verification / done-criteria

Per repo, from a clean checkout:

```bash

docker exec p1 python /app/service/healthcheck.py      # -> healthy: http://127.0.0.1:8000/health returned HTTP 200

docker run -d --name p2 -e PORT=9000 -p 9000:9000 atrium-probe:local
docker exec p2 python /app/service/healthcheck.py      # -> healthy: http://127.0.0.1:9000/health returned HTTP 200

docker inspect --format='{{.State.Health.Status}}' p2  # -> healthy  (the real assertion)

# 3. #55's drain contract did not regress
time docker stop --time 30 p2 ; docker inspect --format='{{.State.ExitCode}}' p2   # -> 143, well inside 30s
```

## Rollout order

1. **Hub first**: manifest (§D) and reusable workflow (§E). Both are backward-compatible — the manifest still defaults to 8000, the new probe step is inert until a repo opts in via `probe-targets`, which all five already do. Landing them first means the four repo PRs are each validated by CI as they land, instead of four PRs merging blind and the probe arriving afterwards.
2. **One tool repo end to end** — page-classification, because it is the only one whose `__main__` already exists *and* whose README documents an alternate launch path, so it exercises every branch of §B. Do §F's deliberate breakage here.
3. **The other three**, as one change each. The `__main__` block is byte-identical across all four; diff them against each other before pushing.
4. **Close #61's four-repo half** in the same commits (§B note 2), and comment on both issues.
5. Hand `PORT`, `HOST`, `GRACEFUL_SHUTDOWN_S`, `RELOAD`, `LOG_LEVEL` to [\#60](https://github.com/ufal/atrium-project/issues/60), which is now unblocked.

## Out of scope

- **`service/healthcheck.py`.** Already correct, already reads `PORT`, already byte-identical in five repos. Changing it would pull this issue into the para-drift set for no gain. Named here so it is not "fixed".
- **alto-postprocess's `__main__` and entrypoint.** Green, working, and outside the issue's four-repo code scope. The `__spec__` rule would silently disable its `RELOAD` (its entrypoint is a *path*, so `__spec__` is `None`), so leaving it alone is the correct call, not neglect. The five share the *pattern* — an env-honouring `__main__` — which is what the issue title asks for. Worth one sentence on the issue so the divergence is not later read as drift.
- **The env-var reference table.** [\#60](https://github.com/ufal/atrium-project/issues/60). This issue feeds it and unblocks it.
- **`LOG_LEVEL` in alto and the non-`__main__` logging work.** [\#61](https://github.com/ufal/atrium-project/issues/61) keeps the rest; only the four `__main__` blocks are absorbed here, and only because they are literally the same lines.
- **Multi-platform images / `EXPOSE` semantics / `docker run -P`.** Nothing in the ecosystem uses `-P`; roadmap H8 owns the platform question.
- **Making `containerPort` itself templated.** The manifest is a reference document with `<tool>` placeholders, not a chart. Two lines that must agree, with a comment saying so, is the right cost here; a Helm values file is a different issue.
