## Strategic actions

### A — Run the deliberate breakage, as a pull request into `test`

This is the only item holding the issue open, and it needs **no hub change**: the callers pin
`ufal/atrium-project/.github/workflows/docker-tool.reusable.yml@v1`, and `v1` already resolves to
`f675943`, which carries the probe.

**Where.** `atrium-translator`. It has the fewest matrix legs and no CI-level torch or
HuggingFace-cache inputs (`.github/workflows/docker.yml:30-37`: `build-targets: '["base", "api"]'`,
no `pre-install-torch`, no `hf-model-cache`), so it is the cheapest of the four `-m` repos to burn a
deliberate red on, and its import class (`from main import …` → `ModuleNotFoundError`) is exactly
the one the fix exists for. `atrium-nlp-enrich` is the alternate; page-classification is the worst
choice (torch pre-install plus a keyed model cache).

**What to break — one line.** Restore the pre-fix exec form at `translator/Dockerfile:116`:

```dockerfile
ENTRYPOINT ["uvicorn", "service.api:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Leave `ENV PORT=8000 GRACEFUL_SHUTDOWN_S=20` at `:108` in place.** This is the part that is easy
to get wrong: the `ENV` is what keeps the *default-port* step green, and a breakage that reds the
default step produces **no evidence at all**, because a failed step skips the ones after it in the
same job. The digest records precisely that shape — pc run `34679959094` (2026-09-12), where the
default health step went red and the `PORT=9000` step never executed.

**Why a PR and not a push.** `docker-build-smoke`'s gate (`docker-tool.reusable.yml:292-295`) admits
`pull_request`, and translator's caller fires on PRs into `test` (`docker.yml:7-8`). Meanwhile
`build-and-push`'s gate (`:623-626`) admits only tags, releases and pushes to `refs/heads/test`, so
**a PR cannot publish anything to GHCR** — the broken image never leaves the runner.

**Expect three signals, not one.** Record all three; together they are a stronger proof than the
acceptance asks for:

| Signal                 | Where                                                                                               | Expected                                                                                                            |
|------------------------|-----------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| Default-port start     | *"Run container and wait for HEALTHCHECK (issue #55)"* (`:368`)                                     | 🟢 green — uvicorn on 8000, `healthcheck.py` reads `PORT=8000` from the `ENV`                                       |
| Non-default-port start | *"Run container on a NON-DEFAULT port (issue #58)"* (`:492`)                                        | 🔴 red at the 330 s deadline with *"container did not report healthy at PORT=9000 within the timeout"* (`:539-542`) |
| Static guard           | `test` job, `tests/test_service_entrypoint.py:141` `test_api_entrypoint_does_not_hardcode_the_port` | 🔴 red                                                                                                              |

The third one is free and worth capturing: `docker-build-smoke` declares **no `needs:`** (compare
`:269` with `build-and-push`'s `needs: test` at `:605`), so the red unit test does **not** suppress
the container evidence. Both layers of the guard fire, independently, on the same one-line
regression.

**Cost and shape of the red.** Roughly 5.5 minutes of runner time, spent waiting — the failure
surfaces as a *timeout*, not an immediate error, and the step's own comment says so at `:507-509`.
Do not mistake it for a slow runner, and do not shorten the budget to make the demo quicker: the
budget is `--start-period 180s` + 3 × `--interval 30s` + one interval of slack, and it is shared with
the default-port step.

**Then close the PR unmerged.** There is nothing to revert on `test`; the branch carries the
breakage and dies with the PR. Link both the red run and the green control run in the issue comment
(§C).

### B — Give `HOST` the runtime probe it never got

`grep -n HOST .github/workflows/docker-tool.reusable.yml` returns nothing. `HOST` is therefore the
one variable in the deployment contract that is *documented* (`docs/k8s_deployment.md:110-115`),
*asserted in source* (`tests/test_service_entrypoint.py:59`) and **never executed**. And it is the
one whose failure is silent by construction: `service/healthcheck.py:48-49` always probes
`127.0.0.1` and never reads `HOST`, so a loopback bind reports `healthy` to Kubernetes while serving
nobody.

A third start after the `PORT` step (`:551`) and before the `LOG_LEVEL` step (`:553`) closes it, as
the exact inverse of the `PORT` assertion:

```bash
cid=$(docker run -d -e HOST=127.0.0.1 -p 18080:8000 "$IMAGE")
# 1. reuse the same wait-for-healthy loop and the same 330s budget: the in-container
#    probe targets 127.0.0.1, so a HOST-honouring container still reaches `healthy`.
# 2. the published interface must NOT answer — this is the half that proves the bind moved:
if curl -sf --max-time 5 http://127.0.0.1:18080/health; then
  echo "HOST=127.0.0.1 was ignored: the service is still reachable on the published" >&2
  echo "interface, so the bind address is not configuration." >&2
  exit 1
fi
```

Both halves are load-bearing and must stay in that order. Asserting `healthy` **first** is what
stops a container that simply failed to start from masquerading as "`HOST` honoured" — a negative
assertion on its own passes for every possible reason. Bound the `curl` with `--max-time` so the
negative half cannot hang the job.

**Sequencing, and why this must not hold #58 open.** This is a hub edit with a blast radius of all
five repos, and the callers pin `@v1`, so it only reaches them after
`git tag -f v1 <sha> && git push -f origin v1` (`docs/docker_gha.md:87`). That retag lag is exactly
what delayed the `PORT` probe by three days — the 09-11 13:04 comment describes runs referencing a
`v1` that predated the step. Acceptance bullet 3 is already met by construction and statically
guarded, so: **land §A, close on §A, and let this ride the next hub change** rather than reopening
the retag cycle for it alone.

  the job still skipped on push would have silently stopped publishing `:test`). So a red
  `PORT=9000` step today does **not** stop `:test` from being published. Making it blocking is
