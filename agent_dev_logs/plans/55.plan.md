## Strategic actions

### A — Correct the premise before building: Kubernetes never reads `HEALTHCHECK`
The kubelet uses `livenessProbe`/`readinessProbe`/`startupProbe` from the **pod spec** and ignores
an image's `HEALTHCHECK` entirely. `HEALTHCHECK` is still worth adding — it is what
`docker`/`compose`/`podman` read, it documents the probe contract inside the image, and it is what
CI can assert — but it cannot by itself make `/health` "visible to a Kubernetes liveness probe".
The Kubernetes half had to be a **probe contract plus a reference manifest**:
[`../../docs/k8s_deployment.md`](../../docs/k8s_deployment.md) and
[`../../docs/templates/k8s/atrium-service.deployment.yaml`](../../docs/templates/k8s/atrium-service.deployment.yaml).
Both confirmed present; the manifest's `startupProbe`/`readinessProbe` target `/ready` and
`livenessProbe` targets `/health`, matching the design in D below exactly.

### B — Publish an API image for the four repos that had none
Only nlp-enrich published a runnable server image. alto, translator and page-classification reached
FastAPI **only** through a `docker-compose entrypoint:` override on the *batch* image, and
llm-enrich's `api` stage was declared but excluded from `build-targets` (roadmap **B5**). With the
handoff boundary fixed at *"a Docker image, run at ARÚP/ARÚB's own Kubernetes"* (#40, 2026-08-02,
motyc), there was nothing for the partner to pull. Each of the four now has an `api` target in
`build-targets`, and each compose `api` service builds `target: api` instead of overriding the
entrypoint — which also deletes the duplicate copy of the start command. Confirmed in all four
repos' `docker-compose.yml`/`.yaml` and `.github/workflows/docker.yml`.

### C — Make the services shutdown-capable first (the prerequisite, not a tidy-up)
Two defects made a graceful shutdown impossible before either directive could matter:

1. **Three services blocked the event loop** during inference (pc's per-page loop, alto's
   `process_alto`, translator's per-chunk LINDAT calls, all called inline in an `async def`).
   uvicorn's `SIGTERM` handler is an event-loop callback, so it could not run until the request
   returned — `--timeout-graceful-shutdown` had nothing to measure. All three now use
   `asyncio.to_thread` — confirmed at `service/text_api.py:414` (alto), `service/api.py:229-238`
   (translator), `service/api.py:275` and `:324` (page-classification).
2. **nlp-enrich's shallow `/health` ran a subprocess on every probe.** Its hand-rolled handler
   called `run_pipeline.py --dry-run` *before* checking the `deep` flag, from an `async def`, with
   no `timeout=`. A 30s-interval `HEALTHCHECK` aimed at it would have spawned a subprocess every
   interval and stalled the loop each time. It now uses the shared `attach_health` with the
   dry-run moved behind `?deep=true` and bounded by `timeout=30` — confirmed at
   `service/api.py:322-347` (handler) and `service/enrichment.py:369-376` (`subprocess.run(...,
   timeout=30)`).

### D — Land the contract once, in the shared module, and re-vendor
All service-side behaviour went into
[`../../docs/templates/shared/atrium_service.py`](../../docs/templates/shared/atrium_service.py) —
`ServiceState`, `attach_inflight_middleware`, `serve_lifecycle`, an extended `attach_health` — plus
a new canonical `healthcheck.py`. Additive and backward-compatible: `attach_health(app)` and
`attach_health(app, deep_check)` behave exactly as before, and shallow `/health` is byte-identical,
which is what keeps the five existing `test_health_shallow_ok` assertions and
`skill-validate.reusable.yml`'s live probe green untouched. Confirmed: all five service repos carry
a byte-identical vendored copy of this module.

The **probe split is the load-bearing design choice**: `/health` (liveness) stays 200 *even while
draining*; the new `/ready` (readiness) goes 503 the instant `SIGTERM` lands. A liveness probe that
fails during a graceful shutdown gets the pod `SIGKILL`ed before the drain finishes — the same
failure this issue exists to fix, one layer up. Confirmed in all five repos'
`tests/test_api_contract.py` (`test_liveness_stays_200_while_draining_but_readiness_does_not`).

`serve_lifecycle` installs a signal handler that **chains to** the previously registered one rather
than replacing it. Verified empirically against a real uvicorn 0.52 subprocess: the captured
"previous" handler is uvicorn's own `Server.handle_exit`, and calling it is what keeps uvicorn's
graceful drain working. Also verified: a tracked background job survived a real `SIGTERM` and ran
to completion before the process exited.

### E — Track detached work, because a request counter cannot see it
nlp-enrich's `POST /jobs` returned `{"status": "queued"}` and left the job in a bare
`asyncio.create_task(...)` whose result was discarded. The request was gone while the job ran, so
uvicorn saw zero in-flight requests and exited — **literally the issue's "a rolling restart kills
in-flight work"**, and unreachable by `--timeout-graceful-shutdown` or by in-flight-request
middleware. Jobs now register with `ServiceState.track()` (confirmed at `service/api.py:516`,
inside `submit_job`), which the drain waits on. `_run_job_background` gained the
`asyncio.CancelledError` branch it never had (confirmed at `service/api.py:260-271`: sets
`job.status = "failed"` with an explanatory message, then re-raises), so a job cut off by the drain
budget stops reporting `"running"` forever.

### F — Prove it in CI, which had never started one of these containers
`docker-build-smoke` built images with `push: false` and **no `load: true`**, so nothing was even in
the local daemon (roadmap **B9**: *"no Dockerfile ENTRYPOINT is ever exercised anywhere in CI"*). It
now `docker run`s the image, waits for Docker's own `HEALTHCHECK` to report `healthy`, curls
`/health` and `/ready`, then `docker stop`s it and asserts a clean exit inside the grace period.
Opt-in per stage via a `probe-targets` input (`required: false`, default `'[]'`) — batch CLI
targets must not be probed. **Confirmed running, not just written:** `probe-targets: '["api"]'` is
set in all five service repos' `.github/workflows/docker.yml`, and the resulting `Docker Build &
Publish` job has been green on every push in all five repos since the change landed.

### G — Create the acceptance vehicle, which did not exist
`digests/55.digest.md` pointed at *"hub #56 and the standing partner ask ... in the workplan's §7"*.
Neither covers this: **#56 is DOG/Switchboard registration**, and there is no workplan document in
the hub at all. `docs/arub-p_contacts.md` is five email addresses and no process. New:
[`../../docs/k8s_acceptance_runbook.md`](../../docs/k8s_acceptance_runbook.md), modelled on
`skill_acceptance_runbook.md`, whose two acceptance columns are exactly what this issue needs
confirmed — probes behave, and a rolling restart drops nothing. Confirmed present, and its
five-repo checklist was already posted to the issue as a follow-up comment on 2026-09-07 — this is
no longer just a plan, it's live on the issue.

## Out of scope
- The remaining eleven factors of #53's checklist — this is the factor-IX carve-out.
- **Durable job records.** `nlp-enrich/service/jobs.py` stays an in-memory dict: the drain now waits
  for a running job, but a client polling `/jobs/{id}` across a restart still gets 404. That is a
  backing-service change (#53, factors IV/VI). Stated explicitly so it is not mistaken for done.
- **Guaranteeing every request survives a restart.** Grace periods are finite; a synchronous request
  longer than the budget is still cut. The defaults protect a typical request and the trade-off is
  documented per repo, rather than papered over.
- Changing *what* any `deep_check` checks. (Noted for #53: alto's is vacuous — `device` is set to
  `"cpu"` in `__init__` before `load_models()`, so it can never report degraded.)
- Roadmap **B8** needed no fix — it was already resolved in code; the stale claim is corrected in
  `docker_gha_roadmap.md` §8 instead.
- Branch protection / required checks for the new job — repo settings, [\#40](https://github.com/ufal/atrium-project/issues/40).
