## 2026-10-02 — Post-split baseline

### Decision

The 2026-09-30 #10 comment is the governing decision:

> reshape this into a bounded CI quality check rather than a general-purpose LLM code reviewer.

The check may inspect a defined set of repository properties, but it must remain deterministic enough for CI and must **not become an additional production-quality gate** for ATRIUM services.

### Repository topology

The production caller set is now:

1. `ufal/atrium-page-classification`
2. `ufal/atrium-ocr-postprocess`
3. `ufal/atrium-digital-convert`
4. `ufal/atrium-nlp-enrich`
5. `ufal/atrium-keyword-extract`
6. `ufal/atrium-translator`

`ufal/atrium-project` is the **hub**: it owns the shared workflow, shared contract templates, workflow-linting, E2E infrastructure and documentation. It is not counted as a seventh production-stage caller.

This distinction must stay explicit in all future plans; the old pre-split wording treated six repositories as if the hub and five tools were the same unit.

## 1. Target architecture

```text
                         ufal/atrium-project
                              │
              .github/workflows/llm-review.reusable.yml
                              │
             ┌────────────────┼────────────────┐
             │                │                │
      page-classification  ocr-postprocess  digital-convert
             │                │                │
             ├────────────────┼────────────────┤
             │                │                │
        nlp-enrich      keyword-extract      translator
             │                │                │
             └──────── six thin callers ──────┘
```

The reusable workflow is the single implementation. Each production repo gets only a thin caller workflow and any repository-local variable/secret declaration that is necessary.

The workflow should follow the pattern already established by `api-contract.reusable.yml`, `para-drift.reusable.yml` and the other hub-owned reusable checks.

### Hub / caller split

| Responsibility                   | Hub                                                                | Six tool repos                           |
|----------------------------------|--------------------------------------------------------------------|------------------------------------------|
| Review prompt / rubric           | ✅                                                                  | —                                        |
| Input assembly rules             | ✅                                                                  | —                                        |
| LLM invocation                   | ✅                                                                  | —                                        |
| Output schema / parser           | ✅                                                                  | —                                        |
| Secret names / provider contract | ✅                                                                  | repo secret supplies the value           |
| Trigger                          | reusable `workflow_call`                                           | PR into `test` + manual dispatch         |
| Repository-specific context      | shared brief + checked-out caller tree                             | caller repo is the checked-out tree      |
| Advisory result policy           | ✅                                                                  | —                                        |
| Workflow governance              | ✅ `workflow-lint`, minimal permissions, timeout/concurrency policy | thin caller validated by same hub linter |
| Production merge gate            | ❌                                                                  | ❌                                        |

A future LLM review of hub code itself is a separate concern. Do not make the hub call its own reusable workflow in #10's first implementation.

## 2. Review unit: one pull request, not one repository

### Trigger

The first implementation should run on:

* `pull_request` targeting `test`;
* `workflow_dispatch` for maintainer-controlled test runs.

Do **not** schedule it. A scheduled LLM scan would recreate the open-ended review loop that #10 is explicitly replacing.

### Concurrency

Use a PR-aware group, for example the equivalent of:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true
```

The old ecosystem review found that a push could cancel a scheduled run and leave no useful failure signal. The new workflow has no schedule, but the same principle still applies: concurrency must be scoped so two different PRs never cancel one another.

### Input scope

The LLM receives:

1. the PR diff;
2. the changed-file names and small surrounding context;
3. the current version/metadata files relevant to a changed service or release path;
4. the canonical shared file from `atrium-project/docs/templates/shared/*` when a PR changes a vendored/shared copy;
5. the current `atrium_document.schema.json` / related record-contract context when a PR touches record fields, block ownership, provenance or schema-facing code;
6. the current `service/openapi.json` and route implementation when an API surface is changed;
7. the directly relevant workflow / Docker / release file when CI or image behaviour is changed.

Do **not** load the whole repository by default. The point is to make the check bounded, reviewable and repeatable.

### Why the extra context is allowed

A raw PR diff can look locally correct while contradicting the canonical record/API contract. The previous review rounds found exactly this class of bug. The extra context is therefore **contract context**, not a licence for a general repository crawl.

## 3. Review brief

The model should be instructed to look only for concrete findings in the following classes.

### A. Record identity, provenance and block ownership

Check changed code for violations of the current record baseline:

* `doc_id` unexpectedly derived from a local filename rather than inherited from the seeded record;
* `source.sha512`, source filename or media type overwritten unexpectedly;
* `source.origin` written by a stage that does not own the source reader;
* blocks or fields written by the wrong production repository;
* `assembled.blocks[*].program` / contributor provenance becoming inconsistent with the actual writer;
* a merge path that returns the seed rather than the processed record;
* re-keying or truncation that discards accumulated document content.

These are semantic checks. The model should cite the exact changed line and the relevant contract table/file when possible.

### B. Production-stage boundaries after the 2026-09-30 split

The current six-stage ownership is:

| Stage                    | Repository          | Critical review boundary                                                                                              |
|--------------------------|---------------------|-----------------------------------------------------------------------------------------------------------------------|
| Page perception          | page-classification | classification informs routing; it is not the positional-plane originator                                             |
| OCR/text input + quality | ocr-postprocess     | owns OCR/text-bearing positional-plane originator semantics and quality categorisation                                |
| Born-digital originator  | digital-convert     | creates the positional plane for born-digital inputs; reports `needs_ocr`; does not own OCR service calls or keywords |
| NLP                      | nlp-enrich          | morphosyntax, NER and TEITOK projection; no return of the old keyword/LLM stage                                       |
| Keywords                 | keyword-extract     | owns statistical + controlled keyword extraction and the future `keywords` block                                      |
| Translation              | translator          | terminal output branch; translation does not become an upstream dependency of another stage                           |

A PR should be flagged when it creates a new cross-stage dependency, duplicates a shared engine/reader without the governed mechanism, or silently reintroduces a predecessor architecture.

### C. API / OpenAPI semantics

Do not duplicate the deterministic API check. Instead inspect whether a changed API implementation contradicts the declared contract.

Examples:

* endpoint path or service id does not match the committed spec;
* error behaviour changes without the registered reason-code / status being updated;
* response fields are dropped while the spec still promises them;
* the code returns a record with an identity different from the seeded input;
* OpenAPI is refreshed mechanically but the underlying implementation still exposes a stale endpoint;
* a repository move changes the image/service id without synchronising `para_config`, manifests, docs and OpenAPI.

### D. Silent fallback, truncation and false-success paths

This class is central to #10 because the 2026-08-06 and 08-19 reviews repeatedly found green mechanisms that did not exercise the intended property.

Flag changed code that:

* catches a broad exception and silently continues when the output contract should fail;
* falls back to an empty/default/stub record without recording that fallback;
* checks that a helper exists instead of checking its returned property;
* merges from the wrong key/path;
* accepts an empty result where the contract requires a produced block;
* converts a genuine error into an HTTP 200 with an `error` field;
* turns a test into a mock-only check of the code path while the real service path changed.

### E. Tests and coverage relevance

Do not demand a percentage from the model. Ask whether a changed behaviour has a test that can actually execute the changed path.

Flag:

* tests that only mock the very function whose contract changed;
* newly added code with no executable test where the behaviour is critical;
* a test renamed/moved without updating all references;
* a new optional dependency guarded with `importorskip` while no CI lane installs it;
* CLI tests that exercise subprocess plumbing when an in-process parser/API test is available and the PR itself changes the parser contract.

The deterministic coverage threshold remains the repository's CI responsibility.

### F. CI, Docker and release semantics

Review only changed workflow/container/release lines and their immediate contract context.

Flag:

* a scheduled workflow whose concurrency can be cancelled by push runs;
* permissions broader than the job needs;
* a `workflow_call` caller that points at the wrong hub channel/ref;
* release/tag/version changes where tag, `CITATION.cff`, `para_config` and release metadata diverge;
* a Docker change that removes the runtime package or model actually required by the service;
* a production image renamed in one place but not in manifests/Compose/docs;
* a workflow that is green because the intended test set is empty or skipped.

Again, do not duplicate `workflow-lint` or security scanning. The LLM identifies semantic inconsistencies on a changed diff.

### G. Licensing and provenance

Flag a change that:

* introduces a model/data/vocabulary dependency without a declared licence/provenance entry;
* changes a vocabulary source or generated artefact while leaving the recorded source/licence metadata stale;
* changes record provenance while keeping the old tool/program identity;
* copies code from another stage without preserving its provenance/ownership mechanism.

Do not ask the model to decide legal questions. The expected finding is "metadata/provenance is now inconsistent with the dependency change", with a link to the relevant project policy/file.

### H. Repository-transition hygiene

This is a new explicit class for the post-split ecosystem.

When a PR changes files inherited from an old repository, look for stale references such as:

* `atrium-llm-enrich` / `llm-enrich` where the role has moved to `digital-convert` or `keyword-extract`;
* `alto-postprocess` where the production service is now `ocr-postprocess`;
* old GHCR image names;
* old service ids in OpenAPI, `/info`, `para_config`, Compose, manifests, deployment docs or paradata;
* documentation that says the old repository is still the production owner.

The check must distinguish historical references (release notes, migration notes, predecessor tables) from live/runtime references.

## 4. Output contract

The model should produce a small structured result that the workflow converts into GitHub review comments.

Suggested logical shape:

```json
{
  "findings": [
    {
      "path": "service/api.py",
      "line": 123,
      "severity": "bug|risk|contract",
      "summary": "Seeded record identity is replaced by the upload-derived id.",
      "evidence": "...",
      "expected": "...",
      "confidence": 0.0
    }
  ]
}
```

Rules:

* zero findings is valid;
* every finding must point to an actually changed line or a directly implicated changed file;
* `severity` is descriptive, not a repository score;
* confidence is for triage, not an overall quality rating;
* no whole-repository summary paragraph is required;
* a finding must explain the violated property and, where possible, the relevant contract source;
* comments must remain advisory and must not change PR approval/merge state.

The workflow should reject malformed model output and report a neutral infrastructure failure rather than inventing comments.

## 5. Model and budget

The first implementation should use **one configured model**, not a model ensemble.

Configuration belongs in repository variables, for example:

```text
ATRIUM_LLM_REVIEW_MODEL
ATRIUM_LLM_REVIEW_MAX_TOKENS
ATRIUM_LLM_REVIEW_TIMEOUT_MINUTES
```

The provider secret is a repository Actions secret. The workflow should enforce one bounded invocation per PR event.

The exact provider/model is intentionally not fixed in this issue: the point of #10 is the **CI mechanism and review contract**, not another model bake-off.

### Forks and Dependabot

No provider secret is available to an untrusted fork or Dependabot PR. In that case:

* the caller still starts;
* the reusable job reports `skipped / no review secret` as a neutral outcome;
* the workflow is not red;
* no attempt is made to infer a review from a model that was not run.

This behaviour is part of acceptance, not an implementation detail.

## 6. Implementation sequence

### Phase 0 — lock the current scope

**Done:**

* six production repositories identified after the split;
* hub identified as workflow/policy host;
* current record/API/ownership contracts available;
* open-ended review rounds retired from #10.

### Phase 1 — implement the reusable workflow in `atrium-project`

Add `.github/workflows/llm-review.reusable.yml` with:

1. `workflow_call` inputs for model/config and optional review mode;
2. PR metadata + diff acquisition;
3. bounded contract-context collection;
4. one LLM call;
5. strict output parsing;
6. review-comment creation;
7. neutral handling for no-secret / no-findings / malformed-response cases as appropriate;
8. minimal permissions: `contents: read`, `pull-requests: write`;
9. explicit timeout and PR-scoped concurrency;
10. no schedule trigger.

Also add a deterministic test or linter coverage for the reusable workflow inputs and the output parser. The model call itself should not be required for the hub's unit tests.

### Phase 2 — create six thin callers

Add a caller workflow to each:

* `atrium-page-classification`;
* `atrium-ocr-postprocess`;
* `atrium-digital-convert`;
* `atrium-nlp-enrich`;
* `atrium-keyword-extract`;
* `atrium-translator`.

The caller should target `test` PRs and expose `workflow_dispatch`.

Do not duplicate the review prompt in each repository.

### Phase 3 — wire the governance checks

Extend the hub `workflow-lint` rules so the new caller conforms to:

* minimal permissions;
* pinned reusable-workflow ref policy;
* valid concurrency;
* required timeout;
* no unapproved schedule;
* expected secret usage.

Add the reusable workflow itself to the hub's self-check coverage.

### Phase 4 — controlled real-PR validation

Run the workflow on at least one real PR for **each of the six tool repositories**.

Record for each:

| Repo                | PR | LLM invoked | Findings | Malformed output | Time | Notes                      |
|---------------------|----|-------------|---------:|-----------------:|-----:|----------------------------|
| page-classification | —  | —           |        — |                — |    — | —                          |
| ocr-postprocess     | —  | —           |        — |                — |    — | —                          |
| digital-convert     | —  | —           |        — |                — |    — | migration-heavy diff       |
| nlp-enrich          | —  | —           |        — |                — |    — | reduced stage boundary     |
| keyword-extract     | —  | —           |        — |                — |    — | new service/repository     |
| translator          | —  | —           |        — |                — |    — | API/production integration |

Use real PRs with meaningful changes; do not manufacture six artificial PRs just to tick a box.

### Phase 5 — negative-path validation

At minimum, exercise:

1. a fork PR with no secret → neutral skip;
2. a Dependabot PR with no secret → neutral skip;
3. a PR with no findings → clean advisory result;
4. a malformed model response → safe neutral/error handling, no fabricated comment;
5. a PR that changes a record/API contract → at least one correctly line-anchored finding if the implementation is inconsistent;
6. a PR that changes only documentation → no invented runtime defect.

### Phase 6 — release the reusable workflow

Once all six callers and the negative paths are green:

* move the hub reusable workflow to the immutable `@v1` channel;
* update the six callers to that immutable ref;
* record the released SHA in the digest;
* close #10 only after the six-repo acceptance criterion is satisfied.

Do not move `v1` first and fix callers afterwards. The ecosystem already uses the hub tag as a trust boundary.

## 7. Done criteria

#10 is done when **all** of the following are true:

* [ ] `llm-review.reusable.yml` exists in `atrium-project` and is governed by hub CI.
* [ ] Six and only six production tool callers exist.
* [ ] The trigger is PR→`test` plus manual dispatch; there is no schedule.
* [ ] The review is advisory and cannot fail/approve the production service by model opinion.
* [ ] The scope is a bounded PR diff plus directly relevant contract context.
* [ ] The output is strict enough to generate file/line comments and safely handle zero findings.
* [ ] Provider/model budget is fixed per run; no model ensemble is required.
* [ ] Fork and Dependabot behaviour is neutral when no secret is available.
* [ ] At least one real PR in each of the six production repositories has been reviewed within budget.
* [ ] At least one real semantic inconsistency is detected or the negative-path suite demonstrates the output contract reliably (the check must not be declared "working" solely because it ran).
* [ ] `workflow-lint` and the relevant repository CI jobs are green.
* [ ] The immutable hub ref is used by the six callers.

Then #10 closes.

## 9. Working rules

* **Review the diff, not the repository.** Broader context is allowed only when the changed code depends on a shared contract.
* **The LLM is advisory.** Deterministic CI owns correctness and merge gating.
* **Report properties, not opinions.** A finding must identify a concrete mismatch, bypass, silent fallback or missing executable coverage.
* **Never score or rank repositories.** The workflow produces findings, not quality ratings.
* **Do not duplicate deterministic checks.** The API/OpenAPI, schema, para-drift, lint and release workflows are already the gates.
* **Treat repository moves as semantic migrations.** Historical references may stay; live service/image/program references must not be stale.
* **Use the seeded record as the identity authority.** Local filenames are not a substitute for `doc_id` or source identity.
* **A new mechanism is not evidence that the intended property is enforced.** The model should explicitly look for that distinction.
* **No schedule.** The old open-ended review cadence is exactly what this issue is replacing.
* **No premature `@v1`.** Land and exercise all callers before changing the immutable hub channel.
* **Re-check live state before refreshing this plan again.** The project has repeatedly changed repository boundaries within days; stale tables are a known risk.

## 10. Refresh conditions

Refresh this plan when:

* the reusable workflow is implemented or its contract changes;
* the set of six production repositories changes;
* the `atrium_document` ownership / API baseline changes;
* a new recurrent false-positive/false-negative class appears in real CI runs;
* AMČR changes the scope of the pilot.

Until then, this is the working strategy for #10.
