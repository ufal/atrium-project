# Strategy — Issue #56: Register with the Digital Object Gateway (DOG), then Language Resource Switchboard

### 2026-10-02 — Re-baseline after the repository split ([#72](https://github.com/ufal/atrium-project/issues/72))

**Bucket: ⏸️ defer.** The earlier #67 decision remains: do not start the registration work before the AMČR pilot has settled the production service surface. The important change is that the service topology is now different, so the old plan's “five configs” and “pilot against page-classification, then copy four times” are no longer sufficient.

The current product baseline is **six service repos**: page-classification, ocr-postprocess, translator, nlp-enrich, keyword-extract and digital-convert. `atrium-project` is coordination only; `alto-postprocess` and `llm-enrich` are historical/archived repositories and should not be new registration targets.

A second issue surfaced while checking the actual DOGlib source: its current public `repo_config` schema and examples describe registered **repositories/PID resolution**, not generic processing-service registration. Because #56 explicitly says “one `repo_config` JSON per service” and “no PID”, the plan now starts with a **DOG applicability/format gate**. Do not spend the November review window submitting six artefacts in a format that DOGlib does not actually consume.

## Context

This is an external onboarding task, not a code feature. The final deliverable is a set of accepted external registrations whose metadata must match the current six-service production topology.

There are now two different registration mechanisms to keep straight:

1. **DOG** — the DMP-mandated dependency named by #56. Current public DOGlib documentation describes registered repository configurations used to resolve resources from PIDs, so the exact ATRIUM service-registration artefact must be confirmed upstream first.
2. **Language Resource Switchboard** — a separate tool registry, [`clarin-eric/switchboard-tool-registry`](https://github.com/clarin-eric/switchboard-tool-registry), with a current v2 JSON specification, logo files, PR-based review, beta verification and an explicit master→production publication step. The Switchboard application itself says the tool registry is maintained separately.

The issue's original “start November” review-cycle note therefore becomes a scheduling constraint: by then the service identities and external metadata need to be frozen, while the actual external submissions can remain sequenced rather than six-way parallel.

## Strategic actions

### A — Freeze the registration set and delete the old mental model

Use the six current service repos as the working registration set:

* `atrium-page-classification`
* `atrium-ocr-postprocess`
* `atrium-translator`
* `atrium-nlp-enrich`
* `atrium-keyword-extract`
* `atrium-digital-convert`

Treat `atrium-alto-postprocess` and `atrium-llm-enrich` as historical successors only. Do **not** create new DOG or Switchboard entries under those archived identities.

Update the issue checklist only after the registration format has been confirmed, so the issue does not keep advertising an obsolete five-service topology.

### B — Resolve the DOG registration format before drafting six configs

Read the current upstream DOGlib sources again immediately before implementation:

* `doglib/static/repo_configs/schema/repo_config_validation_schema.json`
* several real configs under `doglib/static/repo_configs/`
* current DOGlib README and current DOG beta/API documentation

The public material currently shows repository/PID-oriented configuration (`HDL`, `DOI`, URL parsing, repository/parser metadata), while #56 requires service entries with no PID.

Send a short upstream question to the DOG maintainers before preparing a six-file PR. The question should contain one concrete ATRIUM example (preferably page-classification) and ask which of these is expected:

1. a normal DOGlib `repo_config` despite the “no PID” requirement;
2. a newer/different DOG service-registration artefact;
3. a DOG-side schema/registry change that ATRIUM should participate in.

Record the answer in #56 and in the next dated digest round. Do not silently reinterpret the DMP requirement.

### C — Freeze the pilot service from the current API contract

Use `atrium-page-classification` as the initial pilot **only after B is answered**. It is currently the cleanest service for this purpose: dedicated repository, stable service id, published API image, `/info` contract, no repository migration in progress, and the main endpoints are already coherent.

For the pilot metadata, take the values from the current release/OpenAPI rather than from hand-written notes:

* service id and repository URL;
* human-readable name/description;
* current public base URL;
* supported input media types and language assumptions;
* authentication requirement;
* endpoint/invocation shape;
* size/processing limits from `/info`/`limits`;
* current release/version;
* homepage and maintainer/contact metadata;
* logo where required.

### D — Validate the pilot and use upstream review as the template

If DOG confirms that the requested `repo_config` format is indeed the correct artefact:

1. draft the page-classification config;
2. validate it against the **current** DOGlib schema used by the upstream repository;
3. run any available DOGlib/static tests locally;
4. open the pilot PR;
5. capture every reviewer correction as a reusable rule for the remaining five configs.

The purpose of the first submission is to settle the format once, not to duplicate six uncertain submissions.

### E — Re-baseline each of the other five services from their final public contract

After the pilot format is accepted, build the remaining registration metadata in this order:

1. **translator** — current id `atrium-translator`; preserve the production `replace` decision and `/translate` contract.
2. **ocr-postprocess** — current id `atrium-ocr-postprocess`; carry the old `atrium-alto-postprocess` name only where the external registry supports a predecessor/alias field. Do not register the archived repo as a separate tool.
3. **nlp-enrich** — describe only the post-split LINDAT NLP stage; explicitly remove old keyword/LLM claims and stale dependency expectations.
4. **keyword-extract** — wait for a coherent final output contract: both statistical and controlled modes, the record `keywords`/`enrichment` ownership from #73, the versioned vocabulary asset, and the hub E2E path.
5. **digital-convert** — register only after the current `test` OpenAPI/service identity has moved away from `atrium-llm-enrich` and the intended `api-digital` / `/reformat` converter surface is actually present.

### F — Produce a single registration manifest in the hub

Before external submission, add a small hub-side manifest or issue checklist containing, for every service:

* repository URL;
* current service id;
* current version/tag;
* public API URL;
* supported inputs and languages;
* authentication status;
* registration artefact filename/PR;
* upstream review state;
* successor/previous service id where relevant;
* Switchboard registry filename/logo;
* beta verification result;
* production-publication result.

This should be derived from the current service repositories and release artefacts, not copied from the six static rows above.

### G — Do the Switchboard registration as a separate, explicit registry flow

Use [`clarin-eric/switchboard-tool-registry`](https://github.com/clarin-eric/switchboard-tool-registry), not the main Switchboard application repository. The current registry instructions require one JSON description and a logo, validation against the v2 schema, a PR into `master`, beta-instance verification, and then a separate request to promote the accepted change from `master` to `production`.

For each ATRIUM tool description, prepare at minimum:

* `formatVersion: "2"`;
* unique tool id/name;
* task description;
* `deployment`;
* `integrationType`;
* concise description;
* logo;
* homepage/contact/creator metadata;
* input media types and languages;
* output mediatypes where useful;
* web application root URL;
* query/path parameter bindings matching the actual service invocation interface.

The important technical check is the last one: the current Switchboard v2 specification binds an input to `dataurl`, media type, language or limited inline content. Existing ATRIUM APIs are mostly upload-oriented FastAPI services, so the registry JSON must be checked against the actual Tool Call API rather than assuming a bare `/process` or `/translate` endpoint is Switchboard-compatible.

### H — Verify beta, then request production publication

For each merged registry entry:

1. verify the tool appears and is matchable in beta;
2. exercise the actual invocation with representative input;
3. confirm the result is returned in the expected way and the public URL is stable;
4. open the registry issue requesting `master` → `production` publication;
5. record the production state back in #56.

Do not mark “Switchboard registered” merely because the JSON PR merged into `master`.

### I — Track the external review clock

The issue itself says the upstream review cycle starts in November. Once B is resolved and the pilot is submitted, keep #56 active with dated status rounds rather than waiting silently.

Use a compact checklist such as:

```text
DOG format confirmed        [ ]
DOG pilot submitted         [ ]
DOG pilot accepted          [ ]
DOG remaining configs       [ ] [ ] [ ] [ ] [ ]
Switchboard JSONs validated [ ] [ ] [ ] [ ] [ ] [ ]
Switchboard master merged   [ ]
Switchboard beta verified   [ ]
Production publication     [ ]
```

The exact row count must stay at six current services; historical repositories should not return to the checklist.

## Verification / done-criteria

The issue is complete when all of the following are true:

* The registration baseline is explicitly the six current service repositories, with archived `alto-postprocess`/`llm-enrich` identities removed from the active checklist.
* DOG upstream has confirmed the correct service-registration artefact and its relationship to the DMP's “`repo_config`, no PID” wording.
* The pilot service registration is accepted by DOG using the current upstream validation path.
* All six current service registrations are accepted/merged through the agreed DOG process.
* Every registered service id and public URL matches the current post-split service contract; no entry points at the archived repositories or stale `atrium-llm-enrich` API identity.
* Switchboard tool descriptions and logos pass the v2 schema, are merged into `master`, and have been exercised successfully in the beta Switchboard.
* The accepted Switchboard entries are promoted to `production` through the registry's publication workflow.
* #56 contains links to the resulting upstream PRs/issues and records the final production publication state.
