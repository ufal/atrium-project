# Strategy — Issue #72: Production architecture, dependency and release hardening

> Issue [#72](https://github.com/ufal/atrium-project/issues/72) · Labels: `dependencies`, `development`, `enhancement` · **Status: 🚧 IN PROGRESS / PLANNED**
> _Plan prepared 2026-09-30 from the grounding report. The implementation target is the S2 pilot baseline; the GPU runner is deliberately excluded._

## Context

The issue combines several cleanup tasks that are related by one production boundary:

- each processing stage gets one production service/image;
- shared concerns are governed instead of duplicated ad hoc;
- experimental LLM work stays off the production release line;
- production dependencies and licences are internally consistent;
- trusted releases cannot be silently retargeted.

The plan should be executed as one architectural change with several independently verifiable workstreams.
Do not reopen the already-settled API/runtime design from #32/#53/#55/#58.

---

## Workstream A — Establish the production service map

### A1. Freeze the production stage map

Record the production service set explicitly:

1. `page-classification`
2. `alto-postprocess`
3. `nlp-enrich`
4. `translator`
5. `llm-enrich`
6. `api-digital`

`digital-convert` remains the born-digital implementation owned by `llm-enrich` until it is promoted into `api-digital`.

### A2. Define the production/research boundary

For every repository, distinguish:

- production endpoint/runtime code;
- required model/resource artefacts;
- shared governed code;
- experiments, benchmarks, research clients and exploratory tooling.

The production image must contain only the first three categories that are actually required to serve the production contract.

### A3. Keep the release core minimal

The production core is:

- the endpoint AMČR calls;
- the `atrium_document` record hook;
- the production paradata response;
- the health/info/runtime contract already established by #32/#53/#55/#58.

Anything not needed for that path stays outside the release image.

### Verification

- Each production repository has one clearly identified production entry point.
- The image contents can be explained from the production service map without referring to an experimental benchmark path.
- The stage list agrees with the AMČR pipeline plan.

## Workstream B — Govern the three shared layers

### B1. Shared document reader

Identify the document-reading functionality that must be common to the born-digital and OCR-facing paths.

Do not create a new distribution mechanism merely to move code. First identify the existing copies and define one canonical implementation
plus the mechanism by which repositories receive and verify it.

### B2. Shared LLM engine/client

Use the `llm-enrich` implementation as the production-side LLM boundary and remove the competing release-line implementation
from `nlp-enrich`.

Keep backend-specific research clients and benchmark code in the research area.

### B3. Versioned vocabulary artifact

Make the production vocabulary a versioned artefact with explicit provenance rather than a silently copied source tree.

The artifact must be the same logical production input for the services that consume controlled vocabulary.

### B4. Extend `para-drift`

Extend the current drift governance from the eight existing contract modules to the shared production layers where identical
copies remain temporarily necessary.

The check should make divergence visible; it must not hide genuine repository-specific code behind a forced copy.

### Verification

- The shared-layer inventory is explicit.
- `para-drift` identifies all governed copies.
- `nlp-enrich` no longer carries its independent production LLM/vocabulary implementation.
- A release build of `llm-enrich` does not pull research-only modules accidentally.
- The vocabulary consumed by production code is versioned and traceable.

## Workstream C — Dependency and licence hardening

### C1. Replace `PyMuPDF`

Page-classification currently installs `PyMuPDF`, which introduces AGPL-3.0 code that is not represented in the intended licence
configuration.

Compare the agreed candidate dependency behaviour against the labels used by the current classifier input path, then replace it
with `pypdfium2`.

The comparison should be retained as a small engineering record so that the dependency choice is auditable.

### C2. Correct vocabulary licensing

The agreed source classification is:

- AMČR vocabularies: CC0;
- TEATER: CC0.

The translator already reflects this declaration. Apply the same correction to `nlp-enrich` and `llm-enrich`.

### C3. Resolve `flexiconv`

Record the upstream licence response for `ufal/flexiconv`.

Do not infer or copy a licence from another dependency. The result belongs in the shared project licence inventory.

### C4. Preserve per-run licence resolution

Do not collapse non-commercial model/service licensing into the MIT code licence.

The runtime result can only be treated according to the models, resources and external services used in that run.

### Verification

- No production page-classification image installs the removed AGPL dependency.
- The dependency/licence rationale is recorded.
- AMČR vocabularies and TEATER are consistently declared CC0 where used.
- `flexiconv` has an explicitly recorded upstream licence.
- The existing `para_licenses`/paradata mechanisms still describe model/service licence contributions per run.

## Workstream D — Release immutability and repository protection

### D1. Branch protection

Apply the accepted branch-protection policy to the hub `main` and `test` branches:

- changes through pull requests;
- required status checks;
- no force pushes;
- the canonical templates and shared files cannot be bypassed by direct pushes.

The current #40 issue combines this with GPU infrastructure; for #72 only the repository-governance half is in scope.

### D2. Immutable production releases

Enable immutable release/tag behaviour for the production repositories.

The trust-gate model depends on the reviewed tag continuing to identify the exact source that was checked.

The downstream ARUP-CAS gate remains responsible for its own trusted image tags, but the upstream release must not silently move after review.

### D3. Workflow reference hygiene

Reusable workflows used for production release paths must be referenced immutably where they carry write permissions or production
build logic. Moving major tags can remain part of the controlled release process only where that mutability is intentional and
governed.

### Verification

- Direct pushes to protected production branches are rejected.
- A published production release cannot be silently retargeted.
- The trust-gate process can compare the reviewed release tag against the exact source used to build the trusted image.
- Release documentation states the distinction between upstream immutable releases and downstream trusted image tags.

---

## Workstream E — Cross-repository integration check

After A–D, run one production-oriented consistency pass across the repositories.

### E1. API contract consistency

Confirm that the architecture cleanup did not change the already-adopted typed contract:

- request/response models;
- stable error reasons;
- configurable limits;
- `/info`;
- release `openapi.json`.

Any genuine API change belongs to #32, not as an undocumented side effect here.

### E2. `atrium_document` ownership

Confirm that each service still owns only its own blocks and that shared code changes do not introduce new cross-stage ownership.

The frozen `doc-schema-v1` baseline remains the schema reference.

### E3. Production image closure

For every production image:

- identify imported first-party modules;
- identify model/resource artefacts;
- identify external dependencies;
- verify no research-only component is included accidentally.

### E4. Trust-gate compatibility

Confirm that the resulting release still satisfies the processing-side trust gate:

- contract tests pass;
- security/licence scans pass;
- release diff review can compare the new tag against the previous trusted tag;
- committed `openapi.json` is available for review.

## Execution order

### Phase 1 — inventory

- freeze the six-stage service map;
- inventory shared reader/LLM/vocabulary copies;
- inventory production vs research modules;
- inventory dependency/licence findings.

### Phase 2 — architecture

- establish the shared-layer boundaries;
- remove the duplicate LLM/vocabulary implementation from `nlp-enrich`;
- isolate research code from `llm-enrich` release images;
- extend `para-drift`.

### Phase 3 — dependencies/licences

- replace `PyMuPDF`;
- align CC0 declarations;
- record the `flexiconv` result;
- rerun licence/paradata checks.

### Phase 4 — release governance

- enable branch protection;
- enable immutable production releases;
- verify workflow reference hygiene.

### Phase 5 — cross-repository verification

- build every production image;
- run the common contract suite;
- run licence/security checks;
- compare release `openapi.json`;
- perform the processing-side trust-gate review.

## Out of scope

- GPU runner provisioning and GPU CI scheduling — remains separate from the architecture/release cleanup.
- Record-only mode per tool — explicitly deferred until a concrete integration task requires it.
- Custom NER and annotation tooling — later extension phase.
- Broader document-understanding / LLM applications — later extension phase.
- Galaxy production orchestration — Galaxy remains a sandbox around released images.
- Rewriting the typed API baseline already covered by #32.
