| ocr-postprocess     | `v1.14.0-beta`   | a blank line is an `Empty` line numbered with the rest wherever the batch keeps one; `reading_order=alto` reads the page with alto-tools, as `--method alto-tools`; a page's `quality_score` is the mean of its `Clear` and `Noisy` lines |

**What a blank line is** (motyc asked): ALTO has no element for one; the extraction writes it where the layout breaks.
`--method layoutreader` (the default) writes one where the next line in reading order starts more than 1.5 line
heights below the previous one, or more than one line height above it (a new column); `alto-tools` writes one before
each `<TextBlock>`. In a text-lines input (PDF text layer, DOCX, plain text) it is a line with nothing visible on it,
such as an empty paragraph; both sides drop those unless `[TEXT_INGEST] KEEP_BLANK_LINES = true`, which the service
now reads too. Whether born-digital inputs should keep them by default is not decided (the default stays `false`).

**Found on the way:** the service's `reading_order=alto` kept the ALTO order but broke lines as the LayoutReader path
does, while `--method alto-tools` starts a paragraph at each text block and joins a hyphenated line to the next, so its
lines differed from the batch's; the service now runs the vendored alto-tools over its hardened parse.
`alto_tools.py` (Apache-2.0) joins ocr-postprocess's production image list and release bundle.

**The page score:** the batch's definition (`aggregate_STAT.py`, what the 307 collections carry) is kept; the service
and `score_record.py` used to average `Trash` lines too. A page of `Trash` alone has a band and no score on both sides.

**Why four releases failed, and what now fails first.** Each tag published its images, and the GitHub release stopped
on a release-only step. Tags are immutable, so every fix was a new patch release:

- page-classification `v1.10.0`–`v1.10.3`: the release bundle's `cp` list missed `page_inputs.py` →
  `tests/test_release_bundle.py` (the closure check on every push). `v1.10.4`: a torch-only test's stand-in classifier
  lacked `top_n_predictions`; the test is skipped where torch is absent → the suite is run with torch before tagging.
- ocr-postprocess `v1.13.0`: the bundle missed `record_scoring.py`, and `score_record.py` was added to
  `production-image.json` by mistake (Workflow Policy Lint red) → the same bundle test.
- keyword-extract `v1.5.0`: the vocabulary sidecars were still stamped `v1.4.0-beta` → `tests/test_vocab_release_stamp.py`.
- translator `v1.6.0`: the bundle was installed with the runner's Python 3.14, for which `fasttext-wheel` 0.9.2 has no
  wheel → `setup-python` 3.11 first, and a test that fails an install step placed before it.

**Open questions (for the team, not blocking):**

1. page-classification: should the service put a transparent image on white, as the command line does, and should both
   sides average the ensemble the same way? Today they are documented differences.
2. ocr-postprocess: blank ALTO lines. The command line keeps them as `Empty` rows, numbered with the rest; the service
   drops them and numbers only the lines with text, so `line_num` differs for the same page. A page's `quality_score`
   also averages different categories (`Clear` + `Noisy` against `Clear` + `Noisy` + `Trash`). Should these be aligned
   before AMČR stores records made by both?
