### Corrected facts

- **Warm-up (code/doc mismatch, not changed in code).** `service/api.py` loads all models inside FastAPI's `lifespan` before the service accepts a connection. During a first-run download (about 2.44 GB) neither `/health` nor `/ready` answers: the connection is refused. The runbook's endpoint table said `/health` is "200 always" and `/ready` "503 until model warmup finishes". Now stated in § Start, § At a glance (Ready after), § Endpoints (the `/health` and `/ready` rows), § Known limits, and in the README's Quick start and Limits. The shared 503 "starting" exists in `atrium_service.py` but cannot be seen here. The image's `HEALTHCHECK --start-period=180s` is named in Known limits.
- **Shutdown.** The old text said the image's `ENTRYPOINT` passes `--timeout-graceful-shutdown 20`, and told operators to raise that flag. The Dockerfile's `ENTRYPOINT` is `python -m service.api`; the 20 s comes from `GRACEFUL_SHUTDOWN_S` (default 20), read by `service/api.py`. Both sentences now name `GRACEFUL_SHUTDOWN_S`.
- **Models and caches** pointed to Known limits for "a model that cannot be loaded is left out of the ensemble"; that text is in § Partial results. The link now goes there. The weights are saved under `/app/model` after the Hub download (`service/inference.py`); added to the "Into" cell and the Volumes cell (the hub's Operations page says the same).
- **`setup/setup_api_service.sh` (code, not changed).** It fetches `v1.3`..`v5.3`, not the `v1.4`..`v5.4` the service loads, and its relative paths assume it runs from `setup/` while it looks for `run.py` in the working directory. The old runbook said to run it from the repository root and that it "downloads the model weights". `docs/usage.md` § Run the service from a checkout gives explicit commands and says to prefer them.
- **Copy-paste markup in code blocks.** `git clone [https://...](https://...)` and the `nvm` `curl` line in the old runbook were not runnable; now plain URLs.
- **The directory tree** in the old runbook omitted `service/pdf_render.py`, `document_json.py`, `atrium_service.py`, `healthcheck.py` and `openapi.json`; the new one in `docs/development.md` lists them.
- **CONTRIBUTING's removed table** called RegNetY "the recommended default (`main` branch)" while the Hub's `main` resolves to `v4.3` (see `docs/reference/models.md`); and claimed ensembling "significantly improves accuracy on ambiguous pages", while `docs/evaluation/results.md` says the ensemble has no held-out figure and can lower accuracy on ambiguous pairs. Neither is carried over.
- **Open question for the maintainer.** Start says `--gpus all` on a GPU node, but the Dockerfile's default build installs the CPU wheel of torch and the GPU overlay needs `--build-arg TORCH_INDEX_URL=...cu126` (`docs/usage.md` § Run it in Docker). Whether the published `-api` image carries CUDA wheels is not documented in this repository (`docker.yml` passes `pre-install-torch` to the hub workflow). At a glance says "a CUDA GPU is used when torch finds one" and the runbook keeps the `--gpus all` comment as it was.

### Terms for the glossary

Used on the pages I edited and missing from the hub glossary:
- **reading order**: the order in which a person reads the text lines of a page, which in a multi-column page is not the order they are stored in the OCR file.
- **perplexity**: how surprising a line is to a language model; ocr-postprocess computes it with Qwen2.5-0.5B and uses it as one measurement of a line's quality.
- **gold set**: lines labelled by hand and used to measure the categories (2,067 lines for ocr-postprocess).
- **corpus diff**: a comparison of the categories two configurations give over whole collections (`tools/corpus_change.py`).
- **document passes**: the batch pipeline's corrections that use the rest of the document (identical-text vote, surrounded `Trash`, page context, inverted-scan sweep); the service does not run them.
- **LayoutReader**, **FastText**: the layout model that orders ALTO lines (CC BY-NC-SA 4.0 as a component) and the language-identification model (CC BY-NC 4.0).

### Terms for the glossary

- **text layer** — the text stored inside a PDF or office file, as opposed to text read from an image; digital-convert gives each page a verdict (`digital`, `garbled`, `ocr`, `none`, `blank`).
- **seed record** — the small record AMČR sends with a file (`doc_id`, `source.sha512`) so the converter adds to it instead of starting a new one.
- **light engine** — digital-convert's default reader (pdfplumber, python-docx and others, no model); the opt-in Docling engine is the heavy alternative.
- **VLM** — vision-language model: a model that reads a page image and its text together.
- **CER, WER, NED** — character error rate, word error rate, normalised edit distance: the scores of the benchmark harness.

### Terms for the glossary

The hub glossary lacks these terms, which the translator's pages use (none is new in this round, but they sit in the
README opening, limits or runbook):

- **OAI-PMH**: the harvesting protocol AMČR's API answers; a request returns records wrapped in an envelope.
- **XPath**: a path expression that names the elements of an XML document; the translator's metadata mode translates the
  fields a list of XPaths names.
- **FastText (language identification)**: the model that guesses a text's language; the translator uses it only with
  `source_lang=auto`.
- **bake-off**: a comparison of several candidates on the same sample, here the 2026-10-19 comparison of translation
  backends.
- **degenerate reply**: a translation that is empty, runaway, cut short or a loop of one word; the guard asks again.
- **working records**: the maintainers' notes in `agent_dev_logs/` (not documentation for readers).
