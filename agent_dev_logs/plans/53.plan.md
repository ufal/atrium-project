## 4. AMČR Factor III contract — keep, do not reopen

The AMČR requirement added on 2026-09-26 is now part of the permanent baseline.

### The contract

For every operational service limit:

1. **Environment setting** — the caller can set it without editing source/config files.
2. **No silent truncation** — an over-limit request is rejected with the harmonised error, or the service processes it in full and records how the limit shaped the result.
3. **Effective `/info` value** — callers can inspect the current value and its source metadata.

### Shared implementation

- `atrium_limits.py` provides `limit()`, `resolve_limit()` and the associated `LimitSet`/error/note machinery.
- Each service declares its limits in `tool_limits.py`.
- `.env.example` marks the published limits.
- `service/README.md` has the corresponding `## Limits` table.
- `/info` exposes `limits` and `limits_meta`.
- Contract tests compare the declaration, environment example, README and runtime `/info` view.

### Current service inventory

The original five services have complete implementations. The current successor trees also visibly carry the same scheme:

| Service               | Current limit surface relevant to the baseline                                     |
|-----------------------|------------------------------------------------------------------------------------|
| `page-classification` | upload, PDF pages, render DPI, image pixels                                        |
| `ocr-postprocess`     | upload, input/archive/page/line limits, reader timeout                             |
| `nlp-enrich`          | concurrent/queued jobs, upload, words, timeout, rescale and derived encoder limits |
| `keyword-extract`     | upload, document words, keyword count, KeyBERT chunk limits                        |
| `translator`          | upload/request, LINDAT/UDPipe, LLM and CT2 budgets                                 |
| `digital-convert`     | upload and inherited LLM/runtime limits in the current transitional tree           |

A future `keyword-extractor` repository must carry the same contract when the split happens.

The important architectural boundary is that **algorithmic tuning constants remain out of scope**. A setting becomes #53-relevant when it can refuse, truncate, bound or otherwise materially cap a service operation. Pure model/scoring constants can stay in their configuration layer under the repository's documented contract.

## 10. Final strategic rule

After #58 closes, #53 should become a **closed baseline/reference issue**.

Future service work should be reviewed against the following inherited checklist rather than reopening #53:

```text
service API
├── PORT / HOST / GRACEFUL_SHUTDOWN_S / RELOAD are runtime-configurable
├── /health is liveness; /ready is readiness
├── SIGTERM drains safely; Docker has STOPSIGNAL + HEALTHCHECK
├── /info reports identity, capabilities, effective limits and metadata
├── limits are environment-configurable and never silently truncate
├── errors use the shared status/reason/detail/limit contract
├── external endpoints are configurable backing services
├── production image contains only the intended stage
├── runtime does not resolve mutable dependencies
├── logs are emitted as streams
└── admin/batch/research work stays outside the production process

architecture
├── one production service per stage
├── shared reader / LLM / vocabulary layers have one governed owner
├── para-drift covers every governed shared layer
├── repository identity changes are declared and schema-compatible
├── immutable releases and trust gates apply to the production image
└── seeded record / paradata / RO-Crate work goes through #71
```

This preserves the value of #53 without keeping a finished audit artificially open while the project changes its repository topology.
