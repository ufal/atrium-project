## Context
The issue lists all twelve factors and all six repos with no further scoping — a checklist, not a plan.
The 09-07 edition of this file therefore proposed starting from the only two factors that had
*evidenced* violations from unrelated prior work, and treating the other eight as unaudited.

That was the right call at the time, but the premise no longer holds. A measured sweep on **2026-09-09**
(recorded in [`../digests/53.digest.md`](../digests/53.digest.md)) covered all twelve factors directly
against the six working trees. It closed one of the two reds the old plan was built around (B8/factor IX,
via #55), closed factor II ecosystem-wide, and turned up a **new red in factor VII** that the old plan
could not have known about — one that contradicts the partner-facing manifest #55 itself produced.

So this plan is re-sequenced. It no longer asks "which factors should we audit?" — that is done. It asks
"in what order do we fix what the audit found?", and the answer is led by the finding that sits directly
on a live acceptance path.

## Strategic actions

### A — Factor VII: resolve the handover contradiction (do this first)
Not because it is the largest, but because it is the only finding sitting on a **live acceptance path**:
`docs/k8s_acceptance_runbook.md` has five unchecked ARÚP/ARÚB boxes, and the manifest they will deploy
from declares a `PORT` variable that four of five services silently ignore.

Two honest resolutions, pick one:

1. **Make the services honour `$PORT`.** Either give each of the four a `__main__` block reading
   `os.getenv("PORT", "8000")` and switch the entrypoint to `python service/api.py` (exactly alto's shape,
   `Dockerfile:107` + `text_api.py:549-550`), or move to shell form so the variable expands. The first is
   preferable: it is already the ecosystem's own pattern, keeps one entrypoint idiom, and puts `HOST` under
   the same treatment.
2. **Drop `env: PORT` from `docs/templates/k8s/atrium-service.deployment.yaml:54-56`** and state in
   `docs/k8s_deployment.md` that the port is fixed at 8000 by the image.

Do not ship the current combination. A configuration knob that four of five services ignore is worse than
no knob: it reads as supported, fails silently, and the probe ports would keep working at 8000 while the
declared setting did nothing.

**Files**: 4 × `Dockerfile` (`api` stage ENTRYPOINT) · 4 × `service/api.py` · `docs/templates/k8s/atrium-service.deployment.yaml` · `docs/k8s_deployment.md`.

### B — Factor V: close roadmap B9
`.github/workflows/e2e-pipeline-smoke.yml:274` installs `alto-tools` from `refs/heads/master.zip` inside
the published image at run time, contradicting the commit pin in `atrium-alto-postprocess/setup/requirements.txt`.
Fix the pinned install so the published image already carries a working `alto-tools` — then delete the
runtime patch. Separately, retire the `--entrypoint` overrides (`:272`, `:289`, `:311`, `:336`) where the
real entrypoint can now be exercised; #55's `docker-build-smoke` (`load: true` + `probe-targets`) proved
the mechanism.

This is the last of the roadmap's §2.1 live breakages still open, and it is the clearest possible
build/release/run violation: a release artifact that re-resolves its own dependencies at run time.

### C — Factor I: put `atrium_rocrate.py` under `para-drift`
`atrium_rocrate.py` landed on 09-09 for #54, is vendored byte-identical to all five tool repos, and is
declared in `scripts/revendor_shared.sh` — whose `SELFTESTS` array comment states it "Mirrors the
`--selftest` steps in para-drift.reusable.yml". `para-drift.reusable.yml` has no rocrate step of any kind.
Add the parity step and the `--selftest` step alongside `atrium_vocab.py`'s, and add the file to
`tools/skill_drift_check.py`'s `SHARED_FILES`.

Cheap, mechanical, and exactly the pattern `docker_gha_roadmap.md` §2.2 names as *why drift returns*: the
guardrail cannot see what it is supposed to hold. Doing it now costs minutes; doing it after the five
copies diverge costs a reconciliation.

### D — Factor IV: fix the two asymmetries, not the whole factor
Both are one-file changes, and in both cases the repo already contains the correct pattern:

- `atrium-nlp-enrich/api_util/call_udpipe.py:73` posts to a module constant. Give it the `--url` argument
  defaulting to `os.environ.get("UDPIPE_URL", …)` that its sibling `call_nametag.py:203` already has.
  `config_api.txt:19-20` already declares both URLs; only the shell path reads them.
- `atrium-translator/processors/lemmatizer.py:40` and `processors/translator.py:129` hold LINDAT URLs as
  class constants; `service/api.py:215` re-hardcodes one into paradata. Make them configurable the way the
  same repo's LLM backend already is (`LLM_BASE_URL`).

Explicitly **not** in scope here: converting every algorithmic parameter to an env var. Twelve-factor III
is about *deployment-varying* config. Thresholds, model registries and chunk sizes are fine in files.

### E — Factor VI/VIII: decide what nlp-enrich `/jobs` promises
`service/jobs.py:19` is a process-local dict; `service/enrichment.py:39` writes workspaces to container-local
disk. Either is fine for a single replica and wrong for two. The reference manifest does not say which.
Decide and write it down:

- **Cheap**: document "single replica" for nlp-enrich in `docs/k8s_deployment.md` and set `replicas: 1`
  explicitly in the manifest with a comment saying why.
- **Correct**: move the registry and workspace root to shared state.

The cheap option is probably right for the project's remaining lifetime — but it has to be *stated*, because
today the uniform manifest implies all five services scale identically, and one of them does not.

### F — Factors III / X / XI: the tidy-ups
Batch these; none is urgent alone.

- **III**: an `.env.example` per repo (alto's 4-line file is the template), plus an environment-variable
  section in `docs/k8s_deployment.md` — which currently contains the string "env" zero times, while the
  manifest it documents sets one.
- **X**: `atrium-translator/.github/workflows/scheduled-smoke.yml:51` → 3.11, matching the image and every
  other lane; and fix nlp-enrich's `docker-compose.gpu.yaml` header, which still instructs `.yml` paths for
  `.yaml` files (roadmap B7).
- **XI**: remove `logging.basicConfig()` from `atrium-page-classification/service/inference.py:22` — a
  library module configuring the root logger at import. alto's `service/text_inference.py:51-55` documents
  the rule this breaks. Consider whether nlp-enrich's per-workspace `processing.log`
  (`service/enrichment.py:234`) should also go to stdout.

### G — Settle the relationship to issue #10
Unchanged from the previous edition, and still needs @K4TEL, who opened both. #10's rounds keep producing
lettered findings across every repo; #53 is a named methodology over the same ground. #55 demonstrated the
workable pattern — carve a factor out as a sub-issue with a real acceptance criterion. Whether #53
**absorbs** #10's process or runs **alongside** it should be stated rather than left for the two issues to
overlap silently.

If the answer is "absorbs", V and VII are the two obvious next sub-issues.

## Verification / done-criteria

  the deployment doc no longer claim it can.
- **B**: the E2E alto stage runs with no `pip install` in its command and no `--entrypoint` override, and
  passes.
- **C**: `para-drift` fails on a deliberately modified `atrium_rocrate.py` in one tool repo. (Test it by
  breaking it, not by reading the workflow — this ecosystem has twice been caught by a green check that
  was measuring something else.)

- **E**: `docs/k8s_deployment.md` states nlp-enrich's replica constraint, or `/jobs` survives a
  two-replica rollout.
- **IX** (already green): closes when ARÚP/ARÚB tick the five boxes in `docs/k8s_acceptance_runbook.md`.
  Nothing in this repo can close it.
