# Strategy — Issue #53: Follow best practices in all repos - `12 Factor` rules

> Issue [\#53](https://github.com/ufal/atrium-project/issues/53) · Labels: `enhancement`, `development` · Milestone: Q1-27 [WP4: Pre-Closure Architecture Review] · **Status: 🆕 Just opened, no discussion, no prioritization yet**

## Context
The issue lists all twelve factors and all six repos with no further scoping — it reads as a
checklist to be filled in, not a plan. Rather than starting a from-scratch audit of all twelve
factors across six repos (a large, low-signal-per-hour exercise), this plan starts from the two
factors that **already have concrete, evidenced violations** from unrelated prior review work
(`docs/docker_gha_roadmap.md`, issue #10's rounds), and treats the rest as genuinely unaudited —
not assumed clean, just not yet looked at through this lens.

## Strategic actions

### A — Close the two known violations first (cheap, evidenced, no audit needed)
1. **B9 (build/release/run)**: stop patching `alto-tools` at container runtime; either fix the
   pinned commit in `setup/requirements.txt` so the published image already has a working install,
   or move whatever the runtime patch was compensating for into the build stage.
2. **B8 (disposability)**: replace alto-postprocess's `uvicorn --reload` production entrypoint with
   a plain `uvicorn service.text_api:app --host 0.0.0.0 --port 8000` (no reload), and fix the
   `sys.path[0]` dependency the reloader's subprocess currently masks (`text_api.py:309-311`).

### B — Finish the Dependencies sweep (II)
B1 (no ASGI server declared) is fixed in page-classification and nlp-enrich. Check the remaining
three tool repos (alto-postprocess, translator, llm-enrich) and the hub itself for the same class
of gap — a service's Dockerfile/compose invoking an executable that isn't declared in any
requirements file it actually installs.

### C — Scope the Config audit (III)
Rather than treating "store config in the environment" as binary, inventory which settings in each
repo's `*_config.txt`/`config.txt` are (a) genuinely deployment-varying (backend selection, API
keys, upload limits — good env-var candidates) vs. (b) fixed algorithmic parameters (thresholds,
model registries — fine to stay file-based, twelve-factor doesn't require these in the
environment). Only flag (a)-class settings that are file-only today as gaps.

### D — Decide the relationship to #10 explicitly
Before auditing the remaining eight factors from scratch, get an explicit answer (from @K4TEL, who
opened both) on whether #53 is meant to **absorb** #10's ad-hoc lettered-finding process under a
named methodology, or run **alongside** it as a separate, narrower pass. Running both
independently risks the same finding being logged twice under two different labels.

### E — Audit the remaining eight factors, once A–D are settled
Codebase (I), backing services (IV), processes (VI), port binding (VII), concurrency (VIII),
dev/prod parity (X), logs (XI), admin processes (XII) — genuinely unaudited. Low priority relative
to A–C, since none has a known live violation; sequence after the cheap wins land, not before.
