# Strategy — Issue #63: make the UDPipe and LINDAT endpoints attachable resources

> Issue [\#63](https://github.com/ufal/atrium-project/issues/63) · Labels: `enhancement`, `development`, `integration` · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor IV)
> **Status: 🟡 Not started. Four call sites, two repos, and the correct pattern already present in both. Evidence in [`../digests/63.digest.md`](../digests/63.digest.md).**

## Context

Factor IV asks that a backing service be attachable: swappable by configuration, with no code change. Both target repos already do this on purpose somewhere — nlp-enrich for NameTag (`api_util/call_nametag.py:202-206`), translator for its LLM backend (`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`) and even for LINDAT's *transport* (`LINDAT_MIN_INTERVAL_S`, `LINDAT_MAX_RETRIES`, `LINDAT_BACKOFF_BASE_S`). The gap is not a missing capability; it is four call sites that never got the treatment their neighbours did.

This is the smallest and least ambiguous issue in the #53 family. The only real decisions are variable naming and one provenance line.

## Strategic actions

### A — Settle the variable names before writing code

The issue proposes `UDPIPE_URL` / `LINDAT_BASE_URL`. Half of that is right.

- **`UDPIPE_URL` and `NAMETAG_URL`** are already the ecosystem's names — declared in `atrium-nlp-enrich/config_api.txt:19-20` and read by `call_nametag.py`. The translator must reuse `UDPIPE_URL` for its lemmatizer endpoint. Two spellings of one service is exactly the kind of thing [\#60](https://github.com/ufal/atrium-project/issues/60)'s table then has to apologise for.
- **`LINDAT_BASE_URL` names a provider, not a role.** The point of factor IV is that the service is swappable; a self-hosted or mirrored translation service is not "LINDAT". Recommend **`TRANSLATION_URL`**, leaving the existing `LINDAT_*` transport variables (interval, retries, backoff) untouched — those genuinely describe behaviour tuned for LINDAT's shared public endpoint, and renaming them is churn.

Decide this in the issue thread before the first commit. It is the one choice here that is expensive to reverse, because it lands in `.env.example` files, `k8s_deployment.md`, and paradata records.

### B — nlp-enrich: mirror the sibling exactly

`api_util/call_udpipe.py` — add the argument in `call_nametag.py`'s shape, and thread it through to the `session.post` at `:73`:

```python
parser.add_argument(
    "--url",
    default=os.environ.get("UDPIPE_URL", UDPIPE_URL),
    help="UDPipe API endpoint URL.",
)
```

`process_chunk()` currently reads the module constant directly; it needs the URL as a parameter. Check every caller — the function is called from the script's own `main()`, and possibly from `run_pipeline.py`'s stage orchestration; a signature change that misses a caller fails at runtime in a pipeline stage, not at import.

Then resolve the precedence question: `config_api.txt:19-20` already declares `UDPIPE_URL`, and the shell path reads it. After this change there are two ways to set it. **Environment wins** is the factor-III-consistent answer; write that in `config_api.txt` next to the key rather than leaving it to be discovered.

### C — translator: constants to env, with the paradata line in the same commit

Replace the two class constants with env reads defaulting to the current values — `processors/lemmatizer.py:40` and `processors/translator.py:129`. Follow the file's existing `_env_float`/`_env_int` idiom (`:119-123`) for consistency; a plain `os.getenv` with the literal as default is fine for strings.

**`service/api.py:215` must change in the same commit.** It writes the translation endpoint into paradata as a literal, inside a `backend_name == "lindat"` guard. Once the URL is configurable, that line records a host the request may not have gone to — and paradata is this project's provenance claim. A provenance record that is confidently wrong is a data-integrity defect, not a cosmetic one. Report the **effective** URL the backend actually used: read it from the backend instance rather than re-deriving it, so the two cannot diverge again.

While there, check whether any other paradata field carries a hardcoded endpoint. The pattern at `:215` was added to fix finding M1 (per the comment at `:214`) and may not be the only one.

### D — Hold the line on scope

The issue's out-of-scope clause is load-bearing and should survive contact with implementation: **do not** convert algorithmic parameters to environment variables. Thresholds, model registries, chunk sizes and language lists are correctly in files. Factor III asks for *deployment-varying* config only, and five config surfaces get worse, not better, if this issue turns into a sweep.

## Verification / done-criteria

Test by redirection, not by reading — point each site at a local stub and confirm the stub receives the request:

```bash
python3 -m http.server 9999 &      # or a stub that logs the path and body
UDPIPE_URL=http://localhost:9999/x python api_util/call_udpipe.py --input … 2>&1 | tail
# the stub's log must show the hit; the code must NOT reach lindat.mff.cuni.cz
```

- [ ] `UDPIPE_URL=…` redirects `call_udpipe.py`, verified from the stub's log.
- [ ] `--url` on the command line overrides the environment, matching `call_nametag.py`'s precedence.
- [ ] `UDPIPE_URL=…` redirects the translator's lemmatizer; `TRANSLATION_URL=…` redirects its translation calls.
- [ ] The paradata written for a redirected run names the **redirected** endpoint, not the LINDAT literal. This is the bullet that catches the `service/api.py:215` regression, and it is the one most likely to be skipped.
- [ ] **Defaults unchanged**: with no variables set, all four sites reach the same hosts they reach today. Confirm by running the existing test suites in both repos unmodified.
- [ ] `config_api.txt` states the env-over-file precedence for `UDPIPE_URL`.

## Out of scope

- **Converting algorithmic parameters to env vars.** See §D.
- **Renaming the `LINDAT_*` transport variables.** They describe tuning for a specific shared endpoint and are correct as named.
- **Documenting the new variables.** That is [\#60](https://github.com/ufal/atrium-project/issues/60); this issue feeds it. Do add them to each repo's `.env.example` if #60 has already landed, otherwise hand the names over.
- **nlp-enrich's `NAMETAG_URL`.** Already correct. Named here only so it is not "fixed" a second time.
