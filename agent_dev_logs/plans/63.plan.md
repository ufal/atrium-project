## Context

Factor IV asks that a backing service be attachable: swappable by configuration, with no code change and no rebuild. Both target repos already did this on purpose somewhere — nlp-enrich for NameTag, translator for its LLM backend (`LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY`) and even for LINDAT's *transport* (`LINDAT_MIN_INTERVAL_S`, `LINDAT_MAX_RETRIES`, `LINDAT_BACKOFF_BASE_S`, `processors/translator.py:128-132`). The gap was never a missing capability; it was call sites that never got the treatment their neighbours did.

The 09-10 edition of this plan counted four sites and called this the least ambiguous issue in the #53 family. The count was wrong, and **the reason it was wrong is the durable lesson**: three of the extra sites are invisible unless you *run* the thing. Read the code and NameTag looks finished. Run it and NameTag never receives a redirected request at all, because `source config_api.txt` overwrites the operator's exported value before Python sees it — and the stage **exits 0** while doing so.

The question has now changed again. It is no longer "what do we fix?" and no longer "what did we miss?" It is: **what stands between this issue and `closed`, given that the code has been finished for four days?** The answer is entirely documentary. Two defects in this issue's own records — a present-tense description of a pre-fix tree, and an evidence citation pointing at a file that exists nowhere — made the closure look unsupported. Both are fixed in the refreshed [digest](../digests/63.digest.md); this plan records what to do with that.

### C — Say the one thing the issue got wrong about its own premise

Worth a sentence in the closing comment, because it is the finding most likely to be useful to somebody else later.

The issue treats `api_util/call_nametag.py` as the reference implementation to copy. Its Python body genuinely was correct. **The feature was not**, and fixing #63 required editing the file the issue called finished — `call_nametag.py:206` had to move from `os.environ.get("NAMETAG_URL", NAMETAG_URL)` to `os.environ.get("NAMETAG_URL") or NAMETAG_URL`, because the compose passthrough is `${NAMETAG_URL:-}` and a container therefore always carries the variable, blank when unset. A two-argument `get()` returns `""` there and the script would POST to the empty string.

That is the general rule this issue established and it is stated in three places now (`call_udpipe.py:140-144`, `call_nametag.py:203-205`, `config_api.txt:22-29`): **empty counts as unset, at every layer** — bash's `${VAR:-default}`, Python's `or`, and the translator's `_env_str()` (`processors/translator.py:118-124`, "first non-empty value among *names*") all implement the same rule. Leaving one script empty-safe and its sibling not would have been the exact asymmetry this issue exists to remove.
