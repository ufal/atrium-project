# Strategy — Issue #63: make the UDPipe and LINDAT endpoints attachable resources

> Issue [\#63](https://github.com/ufal/atrium-project/issues/63) · Labels: `enhancement`, `development`, `integration` · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor IV)
> **Status: 🟢 Strategy settled and implemented. Nine surfaces, four repos — the issue named four sites in two. Evidence in [`../digests/63.digest.md`](../digests/63.digest.md); acceptance transcript below.**

## Context

Factor IV asks that a backing service be attachable: swappable by configuration, with no code change. Both target repos already do this on purpose somewhere — nlp-enrich for NameTag (`api_util/call_nametag.py:202-206`), translator for its LLM backend (`LLM_BASE_URL`/`LLM_MODEL`/`LLM_API_KEY`) and even for LINDAT's *transport* (`LINDAT_MIN_INTERVAL_S`, `LINDAT_MAX_RETRIES`, `LINDAT_BACKOFF_BASE_S`). The gap is not a missing capability; it is call sites that never got the treatment their neighbours did.

**The earlier revision of this plan counted four sites and called this the least ambiguous issue in the #53 family. The count was wrong, and the reason it was wrong is the interesting part: three of the four extra sites are invisible unless you *run* the thing.** Reading the code, NameTag looks finished. Running it, NameTag never receives a redirected request at all.

## The finding that changes the shape of the issue

`api_2_udp.sh:5` and `api_3_nt.sh:5` begin with `source "${ATRIUM_CONFIG:-config_api.txt}"`, and `run_pipeline.py:120` hands the stage `dict(os.environ)`. **Bash retains the export attribute of an already-exported variable across re-assignment**, so:

```
UDPIPE_URL unset in env  → sourced value stays a plain shell var → python sees nothing → module constant
UDPIPE_URL set in env    → sourced value OVERWRITES it, still exported → python reads the FILE's value
```

The second case is the one deployments are in, and it is the one that broke. `UDPIPE_URL=http://host docker compose run nlp` went to LINDAT regardless.

This is why the issue's acceptance criterion is not sufficient on its own: it invokes `call_udpipe.py` **directly**, which never touches the shell layer. That test passes on the unmodified tree once the `--url` flag exists, while the deployed pipeline stays unattachable. Measured on the pristine checkout, the stage-level checks fail exactly as predicted:

```
FAIL  UDPIPE_URL survives `source config_api.txt` in api_2_udp.sh   exit 1; stub saw 0 request(s)
FAIL  NAMETAG_URL survives `source config_api.txt` in api_3_nt.sh   exit 0; stub saw 0 request(s)
FAIL  the deep-health probe dials the redirected hosts              0 hit(s) on both stubs
```

Note the second line: **exit 0**. The NER stage reported success while sending its data to a host the operator had explicitly redirected away from. A silent wrong answer, not a failure.

### NameTag was never "already correct"

The issue and the previous revision of this plan both treat `call_nametag.py` as the reference implementation to copy, and its Python body genuinely is. But NameTag depends on three layers that were all broken:

- **The shell layer** clobbers `NAMETAG_URL` before `call_nametag.py:203` can read it (above).
- **`api_3_nt.sh:37-42` never passed `--url`**, so `config_api.txt:20`'s `NAMETAG_URL` was inert too. Both declared config surfaces were decorative: neither the file nor the environment reached the request.
- **`service/enrichment.py:327-351`** parses `nametag_url` out of the config file text, and `service/api.py:341-346` HEAD-probes it. The probe would have dialled one host while the pipeline called another.

"Already correct" was true of one file and false of the feature. Every change below is applied to UDPipe and NameTag in lockstep.

## Decisions taken

### A — Variable names

- **`UDPIPE_URL` / `NAMETAG_URL`** reused verbatim in both repos. One service, one spelling.
- **`TRANSLATION_URL`** is the documented name for the translation endpoint, with **`LINDAT_BASE_URL` accepted as an alias**. §A of the earlier revision argued the role name is right — a self-hosted or mirrored service is not "LINDAT" — and the issue text proposes `LINDAT_BASE_URL`. Honouring both costs one line in one resolver and leaves [\#60](https://github.com/ufal/atrium-project/issues/60) a single name to table.
- **The `LINDAT_*` transport variables keep their names.** They describe tuning for a shared public endpoint and renaming them is churn.

### B — Precedence, stated rather than discovered

`--url` / constructor argument **>** environment **>** config file **>** module constant, everywhere. `config_api.txt` states it in a comment next to the keys, and nlp-enrich's README documents it under *Backing Service Endpoints*.

### C — One resolver per endpoint

`resolve_udpipe_url()` and `resolve_translation_url()` are module functions, so the class constructor and every paradata writer resolve identically and cannot drift. Where a live backend instance exists (`service/api.py`), the effective URL is read off the instance — the same object that issues the requests.

**Ordering caught in review:** `LindatTranslator.__init__` called `self._fetch_models()` as its first statement, and that call reads the endpoint. Resolving the URL afterwards would send the process's very first request to the default host while every later request obeyed the configuration — a bug that hides behind correct-looking behaviour. `tests/test_backing_service_urls.py::test_endpoint_is_resolved_before_the_first_request` pins it; reverting the two lines makes exactly that test fail.

### D — Paradata, in the same commit as the constants

`service/api.py:215` and `main.py:58` now record the endpoint the run resolved, normalised to keep the historical trailing slash so an unconfigured run's record is **byte-identical** to the pre-#63 literal. `main.py` additionally gains the `backend_name == "lindat"` guard that `service/api.py` has had since finding M1 — before this, every CLI run on the LLM or CT2 backend claimed a LINDAT endpoint it never contacted. Both nlp-enrich stages now record `udpipe_url` / `nametag_url` alongside the model they already recorded.

### E — Scope held

No algorithmic parameter became an environment variable. Thresholds, model registries, chunk sizes and language lists stayed in files, as the issue's out-of-scope clause requires.

### F — Reaching a deployment, and the repo next door

Two things surfaced after the code half landed.

**The variables never reached a container.** Compose injects only what a service's `environment:` block lists, and neither repo listed them — the endpoints were attachable inside the process and unreachable from outside it, the same shape of bug #58 fixed for `PORT`. Added as `${VAR:-}` passthrough on every service whose entrypoint calls out: nlp-enrich `nlp` and `nlp-api`; translator `api`, `translator`, and **`translator-batch`, which had no `environment:` block at all** and is the one service that both calls the backing services and writes the paradata. `nlp-llm` is untouched — different pipeline.

The empty default is what keeps the LINDAT literal in one place, and it has one risk, checked explicitly: a container then always *carries* the variable, blank when unset. Bash's `${VAR:-default}` and the translator's resolvers already treat blank as unset, but `os.environ.get(key, default)` returns `""` — so `call_udpipe.py` and `call_nametag.py` moved to `os.environ.get(key) or DEFAULT`. That means editing the file #63 called "already correct"; leaving one script empty-safe and its sibling not is the exact asymmetry this issue exists to remove.

**`KOREKTOR_API`** (`atrium-alto-postprocess/tools/quality_model/correct.py:49`) is the same defect in a third repo, and the same shape `call_udpipe.py` had: `KorektorRestBackend.__init__` already accepted `base_url`, `_make_backend:306` never passed it, and there was a `--korektor-model` flag but no `--korektor-url`. Now `--korektor-url` / `KOREKTOR_URL`, same precedence, with tests that fail when the threading is reverted. It stays out of `.env.example` — #60 scopes those to the service layer, and this is a batch tool.

**#60's inputs are ready**: `.env.example` in nlp-enrich and translator, built on alto-postprocess's template, each a *verified* superset of that repo's `service/` reads (16 and 10 variables), with `MAX_UPLOAD_BYTES` named deprecated rather than offered as a second knob. The other three tool repos remain #60's to complete. `docs/k8s_deployment.md` was deliberately left alone: `:117` already defers the full reference to #60, and duplicating it is what makes the two drift.

**One correction to my own earlier handover**: `ATRIUM_<XX>_URL` is *not* a competing convention. It names where a skill's client finds the ATRIUM service (inbound); these variables name where that service finds its backing APIs (outbound). Orthogonal — one clarifying sentence in `agent_skill_strategy.md` and `SKILL.template.md`, no rename.

## Out of scope

- **Converting algorithmic parameters to env vars.** See §E.
- **Renaming the `LINDAT_*` transport variables.**
- **Documenting the new variables cross-repo.** That is [\#60](https://github.com/ufal/atrium-project/issues/60); this issue feeds it. Per-repo docs that *duplicate the changed lines* were updated, since leaving them would make them wrong.
- **`call_nametag.py`'s own body.** Genuinely correct; the file is untouched. Every layer it depends on is not.
- **`main.py:322`'s config-file-beats-env precedence for `TRANSLATION_BACKEND`** — a real inconsistency with the rest of both repos, but a different variable and a different issue.
