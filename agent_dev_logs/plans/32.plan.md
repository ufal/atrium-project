## §2 — Contract already frozen by #32 / #53 / #67

Do not reopen these decisions unless a concrete implementation constraint makes one impossible.

### 2.1 `/info`

Every service exposes:

```json
{
  "service": "<repository/service id>",
  "version": "<app version>",
  "endpoints": ["..."],
  "limits": {},
  "limits_meta": {}
}
```

Capability fields remain service-specific.

`version` is read from the repository's `para_config.txt` / `setup/para_config.txt`, stripping a leading `v`.

### 2.2 `/health` and `/ready`

- `GET /health` is liveness; `?deep=true` may inspect external/model dependencies.
- `GET /ready` reflects whether the service accepts new work.
- The shared lifecycle helper owns the drain semantics.
- Deployment health probes use these endpoints rather than inferring readiness from process existence.

### 2.3 Error envelope

The published error body is:

```json
{
  "status": 422,
  "reason": "invalid_record",
  "detail": "..."
}
```

Additional members such as `limit`, `errors`, `accepted` or `cause` are allowed when the reason needs them.

The current registry is:

| `reason`                 | Statuses      |
|:-------------------------|:--------------|
| `limit_exceeded`         | 413, 422, 504 |
| `busy`                   | 429           |
| `unsupported_media_type` | 415           |
| `invalid_record`         | 422           |
| `ocr_text_layer`         | 422           |

Additions are made in the canonical shared helper and therefore propagate through `para-drift`. A published reason code is never renamed or removed.

### 2.4 Record

All primary APIs use the shared `AtriumDocument` component derived from the frozen `doc-schema-v1`.

Where a stage returns a document record, the field name is `document_json`.

`CreateAction` is an optional typed `paradata` slot in every primary response. The field exists even where the service still returns `null`; that prevents the R2 paradata change from becoming another API-breaking schema migration.

### 2.5 Limits

Every operational limit is reported in `/info`. Limit settings are declared in `tool_limits.py` and surfaced as:

- effective `limits`;
- `limits_meta`;
- `limits_applied` when a limit shapes a successful result;
- `limit_exceeded` for refusals.

Do not reintroduce per-service hardcoded upload constants.

### 2.6 OpenAPI artefact

Every current service that claims API conformance must carry:

```text
service/openapi.json
```

and release:

```text
openapi.json
openapi.json.sha256
```

The committed spec is checked for freshness. `atrium_openapi.py` performs:

```text
export
check
stamp
baseline
compare
digest
```

The release comparison uses pinned `oasdiff` rules and fails breaking changes unless the service major version changes.

For `0.x`, a breaking change requires `1.0`.

## §5 — Work sheet: `atrium-keyword-extract`

### W10 — Treat the repository as the sole keyword API

The current service is already on the correct contract path:

```text
POST /extract_keywords
POST /extract_keywords_text
```

and the current service id is:

```text
atrium-keyword-extract
```

New activities must call this service rather than nlp-enrich.

### W11 — Keep the two keyword kinds separate

The service is responsible for both:

- statistical keywords: KeyBERT, YAKE, legacy KER;
- controlled vocabulary keywords: AMČR / TEATER + LLM.

Each output keyword must retain method-specific metadata. Statistical keywords are document- and page-aware. Controlled keywords remain a distinct kind and must not be silently merged into the statistical list.

#32 only governs their transport contract; vocabulary-specific decisions stay in #2.

### W12 — Finish the controlled/record work without reopening #32

The remaining work from #1/#2/#73 includes:

- wiring the controlled API to the production service path;
- publishing the versioned vocabulary asset when it becomes a production dependency;
- writing the eventual `keywords` record block;
- preserving the `enrichment`/entity successor ownership;
- keeping `CreateAction`, reason codes, limits and `AtriumDocument` unchanged.

The current `v1.0.0-beta` statistical service is therefore contract-compliant but not the final closure of the whole keyword stage.

## §10 — Work sheet: shared release/compatibility enforcement

### W21 — Every active API repository carries the same release sequence

For each current service:

```text
1. export
2. check
3. stamp
4. baseline
5. compare
6. package/release
```

`baseline` means the highest earlier release that already carries a contract asset.

For a **new service/repository** with no previous spec:

- no baseline is a normal bootstrap;
- the first release is the initial contract;
- the second release is the first meaningful compatibility comparison.

This is especially important for:

- `atrium-keyword-extract`;
- the future `api-digital` release.

### W22 — Treat `openapi.json` as part of the trusted release

The release contains:

```text
openapi.json
openapi.json.sha256
```

The deployment image must expose the same spec.

The trust gate should compare:

```text
trusted release asset
        =
built image /openapi.json
        =
/info.open_api_sha256
```

with the actual property name `openapi_sha256`.

### W23 — Version changes

Use the already-adopted rule:

```text
breaking change
    → major version increase

0.x breaking change
    → 1.0
```

This is now relevant to nlp-enrich because the keyword fields are explicitly being retired.

A service-id successor is different from a breaking response change when `x-atrium-service-previous` declares the old identity and the release gate is satisfied.
