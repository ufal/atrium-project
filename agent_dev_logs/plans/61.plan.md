# Strategy — Issue #61: logs as an event stream

> Issue [\#61](https://github.com/ufal/atrium-project/issues/61) · Labels: `enhancement`, `development` · Parent: [\#53](https://github.com/ufal/atrium-project/issues/53) (factor XI)
> **Status: 🟡 Not started. Small, and gated on [\#58](https://github.com/ufal/atrium-project/issues/58) by a shared edit site. Evidence in [`../digests/61.digest.md`](../digests/61.digest.md).**

## Context

Factor XI asks for logs on stdout, configured once, at the entrypoint. alto-postprocess does exactly this and documents the rule in the module that obeys it (`service/text_inference.py:51-55`). Two places break it, and a third fact — measured, not in the issue — makes the case: `LOG_LEVEL` is read in **one** place across all six repos (`alto/service/text_api.py:538`). Four of five services have no log-level control at all.

The work is a few lines. The value is that a partner debugging on their own cluster can raise verbosity without a new image.

## Strategic actions

### A — Sequence behind #58 (do this first, because it costs nothing to get wrong twice)

#61's page-classification fix is "move the root-logger config into `__main__`". #58 is simultaneously creating or rewriting that `__main__` block in four repos' `service/api.py`, including page-classification's. Two changes, one function.

Land **#58 first**, then #61 writes into a block that exists and is stable. Or land them as one change. Do not land #61 first — its `__main__` will be rewritten by #58 and the logging config is exactly the kind of line that gets dropped in a rewrite.

### B — Remove the import-time `basicConfig` (page-classification)

`service/inference.py:22` → delete the `basicConfig` call, keep `logger = logging.getLogger(__name__)`.

Two things to check while there, because this line is load-bearing by accident:

1. **Anything relying on it.** It has been configuring the root logger for every importer of `inference.py`. Removing it means any module that logged "for free" now logs to a root logger with no handlers — output disappears rather than moving. Grep for `logging.getLogger` across the repo and confirm the entrypoints configure the root logger before those loggers are used.
2. **The try/except import block above it** (`:15-20`) means this module is imported under two different names depending on path. Both paths must reach a configured root logger.

Then configure the root logger in `service/api.py`'s `__main__`, in alto's exact shape (`text_api.py:537-541`): level from `os.getenv("LOG_LEVEL", "INFO").upper()`, `stream=sys.stdout`, and the same format string.

### C — Give the other three a single configuration point

nlp-enrich, translator and llm-enrich configure the root logger nowhere. Add the same block to each `__main__` — the one #58 creates. Use alto's format string verbatim in all five: a partner tailing five services wants one shape, and format drift is never fixed later.

### D — Decide what `processing.log` is, then act on the decision

`service/enrichment.py:234` sets `LOG_FILE` to `<workspace>/out/processing.log` inside a config dict handed to a subprocess. Three possibilities, three different fixes:

1. **A pipeline artifact** the caller downloads with their results → keep the file, and mirror the same records to stdout so the service's own event stream is complete. Document it as an artifact in the API docs.
2. **Service logging that landed in a file by accident** → stdout only, delete the config key.
3. **Subprocess output the parent never sees** → the real fix is that the parent should be relaying the subprocess's stdout, which is a different (and better) change.

Check which before writing code: the file is produced by a subprocess configured through substituted values, so the subprocess's own logging setup determines what actually lands there. Coordinate with [nlp#35](https://github.com/ufal/atrium-nlp-enrich/issues/35) — whether this file can be relied on at all is partly a question about `/jobs`'s replica promise, which #35 owns.

## Verification / done-criteria

- [ ] `grep -rn "basicConfig" --include=*.py` across the five tool repos matches only `__main__` blocks and test fixtures. (Today: two matches outside that set — `pc/service/inference.py:22` and alto's legitimate one.)
- [ ] `LOG_LEVEL=DEBUG docker run …` visibly increases output for **all five** services, and `LOG_LEVEL=WARNING` visibly decreases it. Test both directions — a level that is read but ignored passes a one-directional test.
- [ ] Removing the `basicConfig` from `inference.py` does not make page-classification's logs **disappear**: run the service, exercise an endpoint, confirm records still reach stdout.
- [ ] All five emit the same format string.
- [ ] Nothing a partner needs to diagnose a failed request is written only to a file inside the container.
- [ ] #55's shutdown records still appear on stdout — the drain path logs, and it is the one place where losing a log line costs a diagnosis during a rollout.

## Out of scope

- **Structured/JSON logging.** Factor XI asks for an event stream on stdout, not a schema. Named here so it is not proposed as the natural extension.
- **Log aggregation, retention, or shipping.** Explicitly the execution environment's job under factor XI — the app writes to stdout and stops caring.
- **The `API_JOBS_ROOT` workspace design.** That is [nlp#35](https://github.com/ufal/atrium-nlp-enrich/issues/35). This issue only decides what happens to the *log* inside it.
- **Publishing `LOG_LEVEL` in the env contract.** That is [\#60](https://github.com/ufal/atrium-project/issues/60), and it must wait until this issue makes the variable real in more than one repo.
