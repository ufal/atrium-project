## 4. Record-writing rules

1. **One current owner per tool.** Reuse `YParYU` and `j9fqxo`; create only the converter record.
2. **The newest release, not `test`.** Every sheet names a release tag; nothing that exists only on `test` is described.
3. **Research named as research.** A component that is not in the release's production surface is described as such, in
   the present tense, without promising when it will change.
4. **Licence rows from `para_config.txt` at that release**, in the July table shape (Component · License · Status ·
   Compliance Details; 🟢 Friendly, 🔴 Problematic, 🟡 Depends). A row states the component's licence, where the tool
   uses it, and its established terms of use (for example non-commercial). **No row and no sentence infers the licence
   of an output** (motyc, #4 and #6, 2026-10-19): every table ends with the one sentence that the rights in the outputs
   follow from the source documents' rights and the services' terms, not from the component licences.
5. **Durable wording.** No defaults, command-line flags, configuration keys, issue numbers or dates in a description; model
   names only where the model is the service (UDPipe, NameTag, CUBBITT) or in the licence table; the version field is the
   only release-bound value.
6. **No chain narrative in a tool record.** Relate `0xSpVP`; name neighbouring ATRIUM tools only where the tool calls or
   reads them.
7. **Lineage in one sentence**, only where a name changed (`YParYU`, `j9fqxo`); historical repositories never appear as
   current owners.
8. **Image names as published:** `ghcr.io/ufal/atrium-<tool>-api` (the hub's `docker-tool.reusable.yml`), not the
   `…:<version>-api` form some service READMEs still use.

**Description:**

````markdown
Reads documents that were created on a computer rather than scanned, and writes their text with its structure into the ATRIUM document record (JSON), without OCR: pages, text lines in reading order grouped into blocks, and the headings, running headers and footers, footnotes and tables the format carries. The two kinds of input differ. From a PDF it takes the page geometry: the size of each page and the position of every line, with headings recognised from the size and weight of the type. From an office document (DOCX, ODT, ODS, XLSX, RTF, and the legacy DOC and XLS through LibreOffice) it takes the structure the format declares, with no positions on the page. The type is recognised from the file's content, not its extension.

The text layer of every page is checked.
