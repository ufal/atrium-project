## 1. Decisions and constraints from the issue thread

- Maintain **one current SSHOMP tool record per repository**. The six repositories are page-classification, ocr-postprocess, digital-convert, nlp-enrich, keyword-extract and translator.
- The whole AMČR chain stays in workflow [`0xSpVP`](https://marketplace.sshopencloud.eu/workflow/0xSpVP). The new/rebuilt workflow records for translator and page classification describe only their respective tool-local workflow and link `0xSpVP`; do not duplicate the chain.
- Reuse existing records where they map to current tools: `RER7Fw` page-classification, `YParYU` ocr-postprocess, `EMhu3X` nlp-enrich, `j9fqxo` keyword-extract, `CizIUW` translator. Create one digital-convert record only if no equivalent already exists. Do not create a second converter record or a second full-chain workflow.
- Each tool record describes its newest **released** version, not features only present on `test`. A record must be revised only if the release changes the durable description, supported formats, endpoints, image names or component-license entries.
- Keep software/model/service terms separate from rights in derived documents or annotations. A component licence does **not** by itself determine output rights. For LINDAT-hosted models/services, name the model/software licence separately from [LINDAT Terms of Use](https://lindat.mff.cuni.cz/en/terms-of-use). The human-readable explanation is [Licences and paradata](https://ufal.github.io/atrium-project/ecosystem/licences/).
- The controlled-vocabulary keyword results must remain explicitly **experimental and not yet evaluated**. Distinguish statistical keywords (method, score, rank) from vocabulary-controlled results (term, Czech/English labels, confidence, vocabulary record IDs).
- For NLP/TEITOK, distinguish actual word boxes preserved from ALTO from positions estimated within born-digital line geometry. For digital conversion, distinguish PDF page/line geometry from office-document structure, which generally carries no page positions.
- Keep the born-digital branch inside `0xSpVP` (as step 6), not as a second full AMČR workflow. Preserve the step 6 PDF-extraction/GROBID context when its links/formats are updated.

**Description to paste:**

> Reads documents that were created on a computer rather than scanned, and writes their text with its structure into the ATRIUM document record (JSON), without OCR: pages, text lines in reading order grouped into blocks, and the headings, running headers and footers, footnotes and tables the format carries. The two kinds of input differ. From a PDF it takes the page geometry: the size of each page and the position of every line, with headings recognised from the size and weight of the type. ### G. `13eHAZ` — Translating XML documents with a protected domain vocabulary

**Source narrative:** `https://ufal.github.io/atrium-project/workflows/translator/`
**Repository:** `https://github.com/ufal/atrium-translator`
**Related:** `CizIUW`, `0xSpVP`, LINDAT Translation `1wLXFh`, UDPipe `i6piia`; no separate workflow release/version.

**Overview to paste:**

> Archival collections hold text inside XML: OCR transcriptions in ALTO XML, and structured metadata records such as those of the Archaeological Map of the Czech Republic (AMČR). This workflow translates that text — into English by default — and writes it back into the same document, so that tags, namespaces, attributes and, for ALTO, the position of every word survive; a record translated in place stays valid against its schema. Domain terms can be held to their established translations from a controlled vocabulary, so that an archaeological term is rendered the same way in every document.
>
> The steps are carried out by the ATRIUM XML translator (CizIUW). In the AMČR text workflow (0xSpVP) this is the translation step. Full narrative: https://ufal.github.io/atrium-project/workflows/translator/

Step plan:

| # | Step                                   | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | In → out    | Related                     |
|---|----------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-------------|-----------------------------|
| 1 | Prepare a domain vocabulary (optional) | The translator takes Czech–English term pairs of the AMČR vocabularies and the TEATER thesaurus from the curated vocabulary that ATRIUM keyword extraction publishes, each pair pointing back to the concept it came from; a vocabulary of one's own in the same CSV form works as well. Both vocabularies are CC0.                                                                                                                                                                         | → CSV       | `CizIUW`                    |
| 2 | Choose the mode and the fields         | ALTO transcriptions are translated in ALTO mode, which works on the words of each text line. For metadata records, list the fields to translate as XPaths; the tool handles namespaces and OAI-PMH envelopes itself.                                                                                                                                                                                                                                                                        | ALTO, XML   | `CizIUW`                    |
| 3 | Identify the source language           | A language-identification model detects the language of each text block (ALTO) or field (metadata), so a record that mixes languages is handled piece by piece. A guess is used only when it is confident and names a language the backend translates; otherwise the element's own language label, the document's language, then a configured default decide. Naming the source language skips detection and keeps the model out of the run.                                                | —           | —                           |
| 4 | Protect domain terms (optional)        | Vocabulary terms found in the text are replaced by placeholders before translation and restored as their agreed translations afterwards; multi-word terms are matched first, single words by lemma (UDPipe, through the LINDAT service). | 5 | Translate                              | The text goes to the chosen backend: LINDAT Translation (CUBBITT), a self-hosted CTranslate2 model, or an OpenAI-compatible language-model API. Each backend's licence and terms are listed in the tool record.                                                                                        | —           | LINDAT Translation `1wLXFh` |
| 6 | Rebuild and validate the document      | ALTO: each text block is translated as a whole and line by line; the fluent whole-block translation is then divided among the original lines and written into the original word elements, replacing their text or added beside it as an alternative. Metadata: the translation replaces the source text, or is added beside it with language labels. Metadata output can be validated against an XSD schema, such as the AMČR schema, which accepts replaced records and not appended ones. | → ALTO, XML | `CizIUW`                    |

### H. Page-classifier workflow — Sorting archive pages for content-specific processing

**Source narrative:** `https://ufal.github.io/atrium-project/workflows/page-classification/`
**Repository:** `https://github.com/ufal/atrium-page-classification`
**Related:** `RER7Fw`, `0xSpVP`; no separate workflow release/version.

**Overview to paste:**

> Archival documents mix typed reports, handwritten notes, printed forms, tables, drawings, maps and photographs, and each kind of page needs a different treatment: OCR for printed or typed text, handwritten text recognition for manuscripts, table extraction for forms, image extraction for drawings and photographs. This workflow looks at every scanned page and assigns it one of eleven categories, so that each page can be sent to the processing chain that suits it before any of that processing is run. It works on the page image alone, so the language of the page does not matter.
>
> The steps are carried out by the ATRIUM page classifier (RER7Fw). In the AMČR text workflow (0xSpVP) this is the page-classification step. Full narrative: https://ufal.github.io/atrium-project/workflows/page-classification/

Step plan:

| # | Step                    | Description                                                                                                                                                                                                                                                                                                                         | In → out        | Activity    | Related  |
|---|-------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------|-------------|----------|
| 1 | Prepare the page images | Render scanned PDFs to one image per page with the converter bundled with the tool. Name each image after its document and page number, `<document>-<page>.png`: the number after the last separator becomes the page number in every result.                                                                                       | PDF → PNG, JPEG | Converting  | `RER7Fw` |
| 2 | Choose the model        | Use one fine-tuned model — a named revision of `ufal/vit-historical-page` on the Hugging Face Hub — or the ensemble, which averages the scores of Vision Transformer, RegNetY and EfficientNetV2 models. Naming a revision explicitly keeps results reproducible.                                                                   | —               | —           | —        |
| 3 | Classify the pages      | Each image is resized to the model's input size, scored for all eleven categories, and the scores are turned into probabilities. The highest-ranked categories are kept with their scores, best first. A single page, a folder or a whole tree can be processed; the tool also runs as an HTTP service that accepts a PDF directly. | PNG, JPEG → CSV | Identifying | `RER7Fw` |
| 4 | Review the results      | The result table gives each page's best category and its confidence. A low top score with a close second marks a page worth a human look; a table of all eleven scores and, with the ensemble, one vote per model make disagreement visible.                                                                                        | CSV → CSV       | —           | —        |
| 5 | Route the pages         | The category decides the next processing step; in the AMČR text workflow this routing is described in `0xSpVP`.                                                                                                                                                                                                                     | CSV → —         | —           | `0xSpVP` |
| 6 | Record provenance       | Every run records its provenance (paradata): the tool version, configuration, statistics, skipped files and the components it used, each with its licence. On request it also writes its block of the ATRIUM document record, which later stages build on.                                                                          | → JSON          | —           | —        |

Confirm activity/input/output concepts and the workflow-text licence in SSHOMP; do not invent unavailable controlled terms. The workflow version belongs on `RER7Fw`, not the workflow.
