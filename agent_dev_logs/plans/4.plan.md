## 5. Record-writing rules

### 5.1 One current owner per tool

A repository rename or functional split does not justify duplicate current records when a persistent SSHOMP item can be edited. Reuse:

- `YParYU` for OCR post-processing;
- `j9fqxo` for keyword extraction.

Create one new record only for the genuinely new current owner:

- `atrium-digital-convert`.

### 5.2 Released functionality first

The public tool record is not an issue tracker. Use open issue scope only to understand direction and ownership. Do not turn an issue's acceptance criteria into a claim that the released tool already satisfies them.

Examples:

- `digital-convert#2` mentions broader AMČR-supported inputs and `/reformat`; only advertise them when they are part of the release being represented.
- `keyword-extract#2` is a research/controlled-vocabulary item; do not describe its production status as settled if the service still returns a research-target state.

### 5.3 Stable-core prose for changing tools

Reuse the hub Workflows pages as the canonical public wording for `ocr-postprocess`, `digital-convert`, `nlp-enrich` and `keyword-extract` until those workflows settle enough for full narratives.

### 5.4 Version discipline

When a record is edited:

1. use the latest **released tag** that the record describes;
2. do not copy a branch-only `test` version number if the change is unreleased;
3. update the version again at every future release;
4. avoid version numbers inside workflow prose.

### 5.5 Licence discipline

The machine-readable licence facts belong to the repository-side `para_config.txt`/licence documentation. The SSHOMP description should explain the output-licence rule at a user-readable level without inventing a blanket licence when the run-dependent result is component-specific.
