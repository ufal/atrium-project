## Purpose

The ATRIUM shared-code architecture is **largely working**, with valuable checks already implemented. The next task is to establish a **sustainable policy for owning, versioning and adopting shared components**, not to remove vendoring or reorganise all six repositories again.

I reviewed the current hub manifest, re-vendoring script, canonical/sibling drift workflows, consumer pin tests, production-image declarations and the status of [#59](https://github.com/ufal/atrium-project/issues/59) / [#72](https://github.com/ufal/atrium-project/issues/72).

**Current baseline (20 October 2026):**
- [`docs/templates/shared/MANIFEST.json`](https://github.com/ufal/atrium-project/blob/main/docs/templates/shared/MANIFEST.json) describes **24 hub-canonical files** (10 implementation modules, 11 tests, 3 schemas), copied into six tool repositories (144 tracked copies). This is not inherently a problem: the published services are meant to remain independently buildable.
- [`scripts/revendor_shared.sh`](https://github.com/ufal/atrium-project/blob/main/scripts/revendor_shared.sh) and [`para-drift.reusable.yml`](https://github.com/ufal/atrium-project/blob/main/.github/workflows/para-drift.reusable.yml) use that single manifest; [#59](https://github.com/ufal/atrium-project/issues/59) fixed the earlier hand-maintained lists.
- Tool-to-tool owners are also reasonably clear: **OCR post-processing owns `text_formats.py`**, consumed by digital-convert; **NLP enrichment owns TEITOK readers and geometry helpers**, consumed by digital-convert and keyword-extract; **keyword-extract publishes the curated vocabulary as a versioned release artifact**, consumed by translator (a data artifact, not code vendoring). See [#72](https://github.com/ufal/atrium-project/issues/72).
- Consumer tests pin file SHA-256 values: [digital-convert reader](https://github.com/ufal/atrium-digital-convert/blob/main/tests/test_vendored_reader_parity.py), [digital-convert TEITOK](https://github.com/ufal/atrium-digital-convert/blob/main/tests/test_vendored_teitok_parity.py), [keyword-extract TEITOK](https://github.com/ufal/atrium-keyword-extract/blob/master/tests/test_vendored_teitok_parity.py). Recent [digital-convert](https://github.com/ufal/atrium-digital-convert/actions/runs/39312936671) and [keyword-extract](https://github.com/ufal/atrium-keyword-extract/actions/runs/39316728396) drift jobs are green.

**What remains unclear is the *adoption contract*, not the copying mechanics.** Byte parity establishes identical files, but not compatible behavior, a justified upgrade date, or an unambiguous source revision for a consumer release.

## Specific issues to address

1. **A pinned copy is still required to follow a moving owner branch.** The sibling `vendored-parity` job clones owners at `vendored-ref: test` and treats any mismatch as a failure, although the consumer's own test pins a file digest. An owner committing a change to `test` can thus break a consumer CI run *without any change to that consumer*. This is a deliberate drift-detection strategy, but it needs an explicit policy: a correctly pinned, unchanged release should not silently become invalid just because a newer upstream exists. Distinguish **unauthorised local modification / mismatch against an adopted source** (blocking) from **a newer owner revision available** (visibility and planned upgrade), with an explicit exception for jointly coordinated or urgent fixes.
2. **Sibling components have several partial inventories.** `revendor_shared.sh`'s `SIBLING_FILES` lists `text_formats.py`; TEITOK-related copies, fixtures, checksums and upstream paths are managed separately in consumer tests, while [`.github/production-image.json`](https://github.com/ufal/atrium-digital-convert/blob/main/.github/production-image.json) records the runtime subset. This works now but leaves multiple places to update by hand. Choose **one authoritative, machine-readable source/consumer mapping** (or clearly defined ownership between existing inventories), from which checks or consistency tests can derive. Avoid creating a second parallel registry unless genuinely necessary.
3. **Hub-canonical files are coupled to the hub ref, not independently versioned.** Today the canonical drift check reads the hub via `hub-ref` (default moving `v1`). [#40](https://github.com/ufal/atrium-project/issues/40) / [#72](https://github.com/ufal/atrium-project/issues/72) already plan SHA-pinned reusable workflows and matching `hub-ref`; **finish that plan there**. Once pinned, consumer code copies and their checked canonical baseline should advance together through reviewed updates, not via a surprise retag.
4. **Code, contract, tests and data assets are different things.** The hub manifest currently mandates the entire set of 24 files in every tool, including tests and schemas. Review whether all consumers really need every item, and document which items are runtime dependencies, integration contracts, test fixtures, release tooling or versioned vocabulary assets. Do **not** prune working copies just to reduce counts; remove unnecessary coupling only when evidence justifies it.
5. **Parity is not compatibility or correctness.** A shared change can be byte-identical across tools and still alter the meaning of an `atrium_document` field, its provenance/RO-Crate representation or a service response. These interfaces need semantic contract tests and a controlled compatibility review. The licensing semantics currently discussed in [#6](https://github.com/ufal/atrium-project/issues/6) are a concrete example of why identical code is not automatically correct. Resolve those semantics there, not in this issue.

## Deliverable: a short policy and component map

Create **`docs/shared_components.md`** (or improve an equivalent existing, authoritative hub page) with a **one-page set of rules plus a compact owner/consumer map**. Link to the existing manifest and scripts; do not copy their full inventories into a new prose document or build another elaborate framework.

The policy should say:

- **One owner per implementation/contract.** A shared component has a named owning repository, intended consumers and a defined public contract; consumers do not make local behavioral changes to vendored copies. Place upstream fixes with the owner and then adopt them downstream. Ownership of the AMČR ↔ ÚFAL exchange contract is *jointly governed*: technical changes may originate at ÚFAL, but changes affecting agreed record meanings, schemas or external behavior must be discussed with AMČR.
- **Record the adopted upstream revision.** For code copied between tools, track at least owner repository + immutable source commit/release + digest of adopted files (existing hashes can be reused). For hub-canonical files, use the agreed hub commit and synchronized `hub-ref` from #40/#72. For vocabulary or other published data, use release version + asset checksum rather than treating it as a source-code copy.
- **Adoption is deliberate and reviewable.** An owner change triggers an upgrade notice or coordinated PR; the consumer updates the copy, source revision, pin, tests and relevant image declaration in one reviewable change. A green consumer release stays reproducible with its adopted version; it need not follow upstream `test` immediately. For breaking changes, explicitly coordinate the rollout and compatibility window.
- **Classify changes by impact.** (a) implementation-only/internal; (b) backward-compatible behavior/contract addition; (c) breaking or meaning-changing contract change. The third category needs schema/version handling, affected-tool review, integration tests and partner agreement where AMČR-facing semantics change. The current schema 'freeze' means **no uncoordinated interface churn**, not that justified changes are forbidden.
- **Test behavior as well as identity.** Keep byte-parity and source-digest checks, but require relevant unit/API/record/RO-Crate tests and representative cross-tool integration for externally observable changes. Distinguish *contract compatible* from merely *same source bytes*. No green tests achieved solely by suppressing or silently skipping required checks.
- **Preserve release self-containment.** Each released image and source tag must contain a fixed snapshot of its shared code and declare its origin; production runs must not retrieve mutable source from GitHub at startup. Do not introduce a central runtime dependency just to avoid source duplication.
- **Keep the process lightweight.** Reuse `MANIFEST.json`, the re-vendor script, consumer pin checks, `production-image.json` and the CI policy proposed in [#81](https://github.com/ufal/atrium-project/issues/81). Add new metadata or tooling only to close a demonstrable gap. Maintain licence/copyright attribution for copied components; rights of generated data are separately handled by #6.

## Bounded execution (pilot stage)

**Now — policy, not migration:**
- [ ] Publish the short owner/consumer map and the rules above. Include hub-canonical contracts/modules, OCR reader, NLP TEITOK helpers and the versioned vocabulary; distinguish production and experimental paths.
- [ ] Decide whether `vendored-parity` should compare to an **adopted immutable owner revision** (blocking) while signalling owner-`test` advances separately. Demonstrate on digital-convert `text_formats.py` or TEITOK without weakening the check against changed local copies.
- [ ] Ensure the existing consumer pins identify a reproducible **source revision**, not just a digest and approximate date; integrate this with the existing check/re-vendor path, avoiding hand-edited duplicate inventories.
- [ ] Write a 5–7-item shared-component PR checklist covering owner, source/ref, scope, contract impact, consumer updates, tests and rollout.

**Only when warranted:** simplify propagation or introduce a standalone shared Python package **if** actual update frequency, testing failures or deployment cost justify it. Do not turn the pilot into a package-manager/repository restructuring exercise.

## Acceptance criteria

- [ ] For each production-used shared component, a maintainer can answer **who owns it, which release/revision this consumer uses, how it is updated and what contract it promises** without searching multiple unrelated tests and comment histories.
- [ ] Consumers reject local changes that disagree with their adopted pins, but an unrelated upstream branch advance alone does not masquerade as a defect in an unchanged, pinned consumer release.
- [ ] A representative update is exercised end-to-end: owner change → consumer adoption PR → source/digest check → compatibility tests → release (or documented rollback).
- [ ] Externally visible changes have a documented compatibility and AMČR review rule; schema evolution is possible but coordinated.
- [ ] No mass package migration, loss of present drift checks, or duplicate implementation of #40/#59/#72/#81.
