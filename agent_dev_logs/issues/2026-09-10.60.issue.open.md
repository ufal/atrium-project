# [\#60 Issue](https://github.com/ufal/atrium-project/issues/60) `open`: CONFIG: publish the env-var contract — .env.example per repo and an env section in k8s_deployment.md
**Labels**: `enhancement`, `development`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-10 12:11](https://github.com/ufal/atrium-project/issues/60):

The code reads config from the environment in 178 places across the six repos (alto 50 · nlp 47 · translator 30 · llm 29 · pc 11 · hub 11), roughly 40 distinct service-layer variables. The *contract* is undocumented:

- Exactly **one** `.env.example` exists in the ecosystem — `atrium-alto-postprocess/.env.example`, 4 lines (`ATRIUM_VERSION`, `ATRIUM_RUNNER_REF`, `ALLOWED_ORIGINS`, …). The other five repos have none.
- `docs/k8s_deployment.md`, the partner-facing deployment reference, contains the string "env" **zero times** — while the manifest it documents sets one (`docs/templates/k8s/atrium-service.deployment.yaml:54-56`) and comments out two more (`ALLOWED_ORIGINS`, `MAX_UPLOAD_MB`).

A partner deploying from that manifest cannot discover `LOG_LEVEL`, `GRACEFUL_SHUTDOWN_S`, `API_JOBS_ROOT`, `MAX_UPLOAD_MB`, `ALLOWED_ORIGINS`, `HOST`/`PORT` or the backing-service URLs except by reading five source trees.

Some deployment-varying values are still in files rather than the environment, and should be named as such: `atrium-nlp-enrich/config_api.txt:19-20` (`UDPIPE_URL` / `NAMETAG_URL`) and `atrium-translator/config.txt` (`input_path`, `output`, `translation_backend`).

### Scope

1. An `.env.example` in each of the five tool repos, using alto's as the template: every variable the **service layer** reads, with its default and a one-line comment. Not batch-pipeline knobs.
2. An environment-variable section in `docs/k8s_deployment.md` — one table, the variables common to all five plus a short per-repo delta, cross-referenced from the manifest's `env:` block so the two cannot drift silently.
3. Land this **after** the Factor IV (backing services) sub-issue, so the URL variables it introduces are documented once rather than twice.

### Acceptance

- Each of the five repos has an `.env.example` whose variable names are a superset of the service-layer `os.getenv`/`os.environ` reads under `service/` in that repo — check this with a script and keep it, or the tables rot within a release.
- `docs/k8s_deployment.md` documents every variable the reference manifest sets or comments out, and every variable a partner needs for the acceptance runbook.
- Someone deploying from the manifest alone can find every knob without opening a source tree.
