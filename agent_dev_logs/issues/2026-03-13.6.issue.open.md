#### <img src="https://avatars.githubusercontent.com/u/20186892?u=81493d22a8cb5fce679ac0e5e32fd98a04d777c6&v=4" width="50">[motyc](https://github.com/motyc) commented at [2026-10-19 23:01](https://github.com/ufal/atrium-project/issues/6#issuecomment-6279241231):

Thanks, Kate and Pavel. I have reviewed the discussion and the current implementation in more detail.

I fully agree with Pavel that the licence of software used to process data does not automatically determine the licence of the resulting data. I also agree with Kate that we need to correct the current `para_licenses` behaviour.

However, I would not yet approve the proposed rule that only components whose content enters the record (models, data, vocabularies, etc.) determine its effective output licence. This is a useful distinction, but it does not fully solve the underlying problem. A model's licence does not necessarily apply to its inference outputs, while the rights of the original data and the terms of external services may be decisive.

I think we should separate three concerns:

1. **Execution evidence:** Every tool should record the actual software, models, datasets, vocabularies and external services used in each run, including their versions, licences or terms, and references to authoritative information. We need this independently of any interpretation of the resulting data's rights.
2. **Processing policy:** Tools and deployments should be configurable to evaluate known restrictions and determine which processing routes are permitted, especially when sending data to external services. These decisions should be explicit and included in the paradata.
3. **Output rights:** The licence or rights statement of a derived output should be a separate assertion, supported by its source rights and the applicable conditions. It should not be generated simply by selecting the most restrictive component licence. An unknown legal status should remain unknown, not be automatically converted into NC-SA restrictions.

For AMČR, source rights and processing permissions are determined by AMČR. Our pipeline uses Temporal, while AMČR remains responsible for storing and publishing the results. Different derived distributions may require different rights statements.

**What I suggest we decide now is the data contract rather than every possible legal interpretation.**

Could we prepare a small proposal for extending our existing paradata and document records to capture these concerns separately? Ideally:

- a versioned, machine-readable structure, with a JSON Schema;
- compatibility with our existing RO-Crate 1.2 / Process Run Crate 0.5 approach;
- a component inventory that distinguishes software, models, datasets, vocabularies and services;
- configurable processing policies, with an explicit record of the policy and its outcome;
- a separate, optional and properly attributed rights assertion for each output;
- a migration strategy for the existing `provenance.license` and `license_detail` fields.

One particularly important correction is in `atrium_rocrate.py`, which currently exports the calculated component licence as the root dataset licence. We should stop making that assertion unless it is supported by the actual data-rights information.

We should also preserve historical paradata, but distinguish the old calculated values from authoritative licence assertions.

The exact implications of the LINDAT services and their models can remain open under #78 until we have sufficient evidence. This should not prevent us from improving the recording and configuration mechanisms now.

I would be happy to review a concise proposed schema and implementation approach with you before we change the shared modules. We should avoid implementing a quick fix that would only replace one inaccurate interpretation with another.

Meanwhile, the factual component inventories and the SSH Open Marketplace updates can proceed, provided they do not present inferred output licences as established legal facts.

I would also suggest looking at the principles and conventions of the [REUSE Specification](https://reuse.software/spec-3.2/), especially `REUSE.toml` and SPDX-based file licensing.

REUSE provides a well-established, machine-readable approach to recording copyright holders and licences for individual files, including mixed-licence packages. I think we should adopt these principles wherever appropriate instead of inventing another licensing vocabulary.

For resources included directly in the tool repositories, REUSE declarations could provide the authoritative licensing information. For external dependencies, models and services, we would need a complementary structured inventory, following similar conventions but also recording versions, service terms and supporting evidence. Runtime paradata would identify which of these components were actually used.

It could also be valuable to support generating a `REUSE.toml` for an exported collection of derived files, based on the rights actually established for those files. This should complement the existing RO-Crate metadata and be generated from the same authoritative information, not from a mechanical combination of component licences.

Finally, I would not treat the current document-schema freeze as an obstacle to this work. Its purpose is to stabilise the shared interface and prevent uncoordinated changes. We can deliberately revise the schema now if needed, provided we agree on the semantics and make the changes consistently across the tools and their consumers.

I would therefore prefer a coherent proposal for the relevant schemas and configuration formats over a narrowly scoped change in `para_licenses.py`.
