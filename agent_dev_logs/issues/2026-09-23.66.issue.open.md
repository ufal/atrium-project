#### Answers from Mark regarding the Galaxy setup we have:

1. Which Galaxy: DARIAH's own instance or [ssh.usegalaxy.eu](http://ssh.usegalaxy.eu/)?

> In the long run we would like to get tools into the [ssh.usegalaxy.eu](http://ssh.usegalaxy.eu/) instance. This would give them better visibility and more resources. The DARIAH instance is essentially a sandbox we can test in without worrying if we break it, but the job runners are quite resource limited

2. Which route: a PR to `atrium-galaxy-tools`, or ToolShed + `usegalaxy-eu-tools`?

> The hope is that we migrate tools into the tool shed eventually so that they can be adopted easily by any galaxy instance. In the short term we are happy to collect the wrappers together into the atrium-galaxy-tools repo: changes to this are picked up by DARIAH's galaxy instance so this route is good if you are wanting to test there.

3. Our tools ship as GHCR Docker images, not conda packages. Is that acceptable?

> That "should" be fine. A tool wrapper can define a docker image as the tool requirement. The only downside is that support isn't guaranteed on every galaxy instance -- it is available on our instance and I believe on [ssh.usegalaxy.eu](http://ssh.usegalaxy.eu/). In theory a docker image should be easier to wrap given there will be no complex requirements to deal with.

4. Jobs need outbound network (LINDAT APIs, Hugging Face) or pre-staged models. Which one?

> That's a bit tricky to answer given there are so many possible ways you can get models into galaxy and the tools. There is support for loading models from hugging face, for instance, and it is also possible to design tool wrappers to use models that are loaded into the galaxy instance (i.e. so that it's downloaded once, not once per user). It is also possible to call out to web service APIs etc.

5. Is a GPU available?

> Not on the DARIAH instance but I believe there are some attached to the [ssh.usegalaxy.eu](http://ssh.usegalaxy.eu/) instance although I've not yet tried accessing them.

The error came from our image, not your command: its entrypoint passed Galaxy's `/bin/sh …/tool_script.sh` to `run.py`. Since `ghcr.io/ufal/atrium-page-classification:1.10.5-beta` the entrypoint runs a command it is given (options still go to `run.py`), and the wrapper uses that image, so your command works as it is:

    planemo test --docker --galaxy_branch v26.1.1 tools/atrium_page_classification/page_classification.xml

The tests download one model (v4.4, about 0.5 GB) from the Hub.

Weights on the instance: a data manager, *ATRIUM page-classification models*, downloads the five models once (about 2.5 GB) into a data table, and the tool reads them offline. The destination needs the data manager's data path as a read-only Docker volume. Downloading inside the job stays as a fallback.

Also new: PDF input, the five-model ensemble with each model's vote, and one workflow (`workflows/ATRIUM_page_classification.ga`). The tool's README has the admin steps.

We ran `planemo lint`, `workflow_lint`, and the job scripts the way Galaxy starts them under Docker, with the new entrypoint. `planemo test` itself could not run on our side, so yours will be the first full run.
