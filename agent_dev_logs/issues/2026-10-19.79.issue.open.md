## Problem

Documentation across the six ATRIUM tool repositories has become technically extensive but unnecessarily difficult to **read, navigate and use**. This is a recurring problem, not a complaint about one repository or one recent change.

The clearest example is [ocr-postprocess#5](https://github.com/ufal/atrium-ocr-postprocess/issues/5): the updated `README.md` and `docs/categorization_logic.md` are substantially complete and supported by tests, yet they remain hard to understand as *documents for human readers*. The README mixes first orientation with extensive algorithms, configuration tables, migration notes, experiment results, output licensing and implementation history; the categorisation reference interleaves the current behaviour, detailed rule cascade, edge cases, test cases, calibration history and decisions. Both are very long, heavily decorated and difficult to skim.

Similar issues recur elsewhere: emoji-heavy headings, long nested tables of contents, large technical references before a quick start, repeated material across README/service documentation, and historical or experimental details competing with the current workflow. This makes adoption, integration, review and maintenance harder than necessary.

**Completeness of information is not the same as quality of documentation.** Tests can confirm that a technical explanation matches code, but they cannot establish that someone unfamiliar with the tool can understand it.

We need **one coordinated editorial standard, applied to all tools**, instead of repeated ad hoc requests in individual issues.

## Scope

Apply the standard to the current six repositories:

- [atrium-page-classification](https://github.com/ufal/atrium-page-classification)
- [atrium-ocr-postprocess](https://github.com/ufal/atrium-ocr-postprocess)
- [atrium-digital-convert](https://github.com/ufal/atrium-digital-convert)
- [atrium-nlp-enrich](https://github.com/ufal/atrium-nlp-enrich)
- [atrium-keyword-extract](https://github.com/ufal/atrium-keyword-extract)
- [atrium-translator](https://github.com/ufal/atrium-translator)

The [ATRIUM project documentation hub](https://github.com/ufal/atrium-project) should provide the common orientation and link to each tool; it should not duplicate every tool's technical manual. Retired predecessor repositories need no rewrite.

## Expected documentation architecture

Use a common **reader-first hierarchy**, adapting filenames to the tool and reusing existing files where sensible. We do **not** need a large new document set in every repository.

| Layer / audience | What belongs there | What does **not** belong there |
| --- | --- | --- |
| **README — first-time visitor** | What the tool does and why; where it fits in ATRIUM; main inputs/outputs; current maturity/limitations; one working quick start and expected result; concise links to the rest | Full algorithm, parameter catalogue, old design debates, detailed test history, extensive release-by-release commentary |
| **Getting started / usage — user or integrator** | Prerequisites, practical local/API examples, choosing a mode, understanding the returned result, ordinary troubleshooting | Source-code internals and research notebooks |
| **Operations / API reference — deployer or integrator** | Supported endpoints and formats, auth/configuration/limits/errors, deployment, exact request/response schemas and examples; link to OpenAPI or the canonical source | Duplicate, subtly inconsistent API specifications spread through several READMEs |
| **Technical reference — developer or expert** | Detailed algorithms, formulas, processing stages, parameters and defaults, edge cases, invariants and authoritative schema links | Marketing-style introduction or long narrative about every historical attempt |
| **Evaluation / limitations** | What has been validated, datasets and metrics, reproducibility, known failure modes, difference between measured accuracy and tests of implementation behaviour, experimental features | Claims that successful unit tests prove model quality |
| **Development / history** | Contributing, tests, research procedures, changelog/migrations and decisions (ADRs or dated notes where useful) | Historical experiments embedded throughout the primary user guide |

### Suggested file locations and naming

These are **suggested paths, not a mandatory template**. Reuse and improve existing files when they already serve the purpose; do not create empty boilerplate or copy an API specification just to match a filename.

| Location in each tool repository | Intended content |
| --- | --- |
| `README.md` | **Short entry point**, ideally about 100–250 lines (guideline only): what/why, role in ATRIUM, input → output, supported ways to run it, one verified quick start with expected result, major limitations, and a small documentation map. |
| `docs/getting-started.md` **or** `docs/usage.md` | A reproducible first run, prerequisites, example inputs and outputs, common user tasks and troubleshooting. |
| `docs/architecture.md` **or** `docs/how-it-works.md` | Human-readable processing flow, components and design rationale, with a simple diagram where useful. Explain concepts before introducing low-level rules. |
| Existing `service/README.md` **or** `docs/api.md` | API usage, endpoints, requests/responses, errors, limits and operational considerations. Point to the actual OpenAPI specification/schema as the definitive contract rather than maintaining a second copy. |
| `docs/configuration.md` and/or `docs/reference/` | Complete parameter tables, supported formats, schemas, algorithms, decision gates, thresholds, diagnostic fields and other exhaustive reference material. |
| `docs/development.md` and/or `docs/testing.md` | Developer setup, project structure, contribution/testing instructions, fixtures, CI and release verification. |
| `docs/evaluation/`, `docs/research/` and/or `docs/decisions/` | Validation reports, calibration runs, benchmarks, experimental options, rejected alternatives and dated decision records. Preserve evidence and reproducibility, but keep the operational path free of history. |

**Suggested README sequence:** (1) What it does and when to use it; (2) inputs and outputs; (3) quick start with expected result; (4) role in the ATRIUM workflow (link to the [published hub](https://ufal.github.io/atrium-project/)); (5) important limitations and maturity; (6) where to find usage, API, configuration, technical reference and development docs; (7) licensing, citation and acknowledgements. If a section does not matter for a particular tool, adapt it rather than adding filler.

**Concrete first exemplar — OCR post-processing:**

- Shorten README Step 4 to a readable explanation of the five category meanings, the main scoring stages, representative examples and **prominent practical limitations** (including multilingual behaviour and the service/batch distinction).
- **Substantially edit `docs/categorization_logic.md` for readability too.** Do not merely move the existing long text unchanged. It should be a clear explanation/navigation entry point, with the detailed rule/threshold material moved to something like `docs/reference/categorization_rules.md` and historical calibration/measurements to something like `docs/evaluation/categorization.md` and `docs/decisions/`. Exact names and the division can be adjusted in the PR.
- Link precise statements to the existing code, regression tests and gold-set evidence rather than pasting full test/experiment histories into the narrative. Preserve the distinction between “tests match code” and “classification accuracy has been independently validated.”
- When moving or renaming sections, repair incoming links and GitHub Markdown anchors (particularly headings that currently contain emojis); provide a short old-section → new-location map in the PR.

**Ownership and duplication:** cross-tool architecture and the full AMČR chain belong in the [ATRIUM documentation hub](https://ufal.github.io/atrium-project/); each tool owns its tool-specific help and precise references. Keep the current `service/README.md`, published schemas and API definitions wherever they are already authoritative. A reader should never need to consult multiple drifting copies of the same contract.

For OCR post-processing specifically: make Step 4 in the README a short *explanation of what the categories mean, the processing stages and important limitations*; retain the detailed gate-by-gate logic in a separate reference; move long calibration and decision histories into a dedicated evaluation/decisions section. A new user should not have to understand every threshold to use the classifier.

## Editorial and presentation rules

1. **Write for the reader, not the implementation history.** Start with the problem solved, the result produced, and the next action the reader can take. Use plain, precise English, short paragraphs, direct verbs and consistent terms. Avoid hype, conversational filler, and repetitive “this script does...” paragraphs.
2. **Establish progressive disclosure.** The main README should be **short enough to skim in two minutes**; a rough target is 100–250 lines, not a hard limit. Prefer clear links to focused references over an enormous all-in-one page. A developer still needs complete technical documentation, but should *opt in* to that depth.
3. **Remove decorative emojis from headings and running text.** Avoid excessive badges, icons, exclamation marks and nested callouts. Keep standard Markdown headings with stable anchors. Use emphasis sparingly for actual distinctions or warnings, not visual noise.
4. **Use headings, tables and diagrams intentionally.** A good heading tells readers what question is answered. Use tables for genuine comparisons or reference data, not as a substitute for readable explanation. Prefer one simple architecture/data-flow diagram when it clarifies a complex interaction; do not add graphics merely for decoration.
5. **Keep facts and levels of certainty distinct.** Separate current released behaviour from optional/research functionality, planned changes, empirical findings, and known limitations. State meaningful restrictions near the relevant user instructions; link to detailed evidence rather than burying it.
6. **Make examples practical and checkable.** Each tool should have at least one minimal **copy-and-run example** (CLI or API, as appropriate) with an example input, the expected output/result, and any necessary configuration or external-service warning. Verify examples against a released version.
7. **Have one authoritative home for each technical contract.** Reuse OpenAPI/JSON Schema, configuration reference, component inventory and shared paradata documentation. Cross-link instead of copying descriptions into multiple locations that will drift.
8. **Separate timeless guidance from change history.** Keep current instructions current; move dated calibration rounds, superseded methods, decisions and release-specific notes to changelogs, release notes, ADRs or evaluation appendices. Do not erase the evidence; relocate it.
9. **Treat documentation as an editorial deliverable.** Machine-generated or code-synchronised details are useful as *technical inputs*, not as the finished narrative. Each major page needs human editorial review for clarity, logical order, length and consistency. Maintain links and examples when functionality changes.

The documents do not have to be identical or artificially short. What should be consistent is **where a reader expects to find a kind of information**, and how quickly they can reach it.

## Execution — bounded, reviewable work

1. **Agree on a short common style/structure guide** in `atrium-project/docs/documentation-style.md` (or an equivalent hub path), with a small documentation checklist and a proposed README skeleton. Use recognised documentation practice (tutorial / how-to / explanation / reference, e.g. [Diátaxis](https://diataxis.fr/)) as guidance, not a rigid template.
2. **Pilot the restructuring on `atrium-ocr-postprocess`** (README + categorisation documentation). Use this as a concrete before/after example; preserve all factual technical material in appropriate locations. The goal is a substantial editorial rewrite, not just splitting files at arbitrary line numbers.
3. **Apply the approach to the other five tools**, one repository/PR at a time, with a small inventory of which pages to keep, merge, move or rewrite. Reuse existing `service/README.md`, `docs/`, OpenAPI references and documentation hub pages rather than duplicating them.
4. **Review each tool's documentation from a newcomer’s perspective**: somebody familiar with research software and APIs, but not this particular codebase. Check that the quick start runs, links work and the released behaviour is described correctly.
5. Keep this issue as the **single tracker for the documentation overhaul**. Link per-repository PRs here. Avoid scattering the same stylistic feedback across technical issues.
6. **Keep it readable after the overhaul:** add a lightweight documentation check to relevant PRs/releases: current behaviour and limitations, working examples, appropriate document location, link/anchor integrity, and no duplicate technical source of truth. No new documentation framework is required.

## Acceptance criteria

- [ ] A short shared documentation style/structure guide and README outline are available.
- [ ] All six current repositories have a clear, reasonably concise README answering: **what is this, when would I use it, what does it take/produce, how do I run it, what should I be careful about, where is the detailed reference?**
- [ ] All six offer a verified minimal example and an easy path to API/CLI, configuration, formats/schema, deployment, limitations and development information as applicable.
- [ ] Detailed algorithms, long parameter lists, calibration history and decision records are in appropriately titled reference/evaluation/history pages, not mixed indiscriminately into fast orientation or usage instructions. **Information is preserved, not discarded.**
- [ ] Decorative emojis, redundant badges, excessive callouts, repetitive prose and unnecessary giant tables are removed or substantially reduced.
- [ ] Cross-links, tool names, endpoints, supported formats, maturity statements and examples reflect the current released code; there is one canonical source for shared technical contracts.
- [ ] At least one other human reviewer can follow the quick start and locate the relevant deeper technical details without prior knowledge of the codebase.
- [ ] Each repository PR provides a short **content relocation map** (old section → new file/section) and confirms that critical caveats, contracts, examples and empirical evidence were preserved.
- [ ] The shared style guide is linked from the hub and from the tool READMEs; README/documentation link destinations and anchors are checked after restructuring.
- [ ] The first-run examples work from a clean checkout or a clearly described environment, with sample data and expected outputs.
- [ ] Links to the completed documentation PRs are collected here.
