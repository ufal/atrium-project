# [\#71 Issue](https://github.com/ufal/atrium-project/issues/71) `open`: End-to-end record contract, paradata and RO-Crate
**Labels**: `documentation`, `enhancement`, `development`, `integration`, `pipeline`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-30 07:18](https://github.com/ufal/atrium-project/issues/71):

Bring the AMČR ↔ ÚFAL record, provenance and packaging contract to the agreed pilot baseline.

Scope:
- accept the AMČR-seeded `atrium_document` record as the input to the first processing stage;
- preserve `doc_id`, `source.sha512`, file name and media type through the complete chain;
- keep `source.origin` owned by the tool that reads the source;
- make every production service return its run paradata in the agreed Process Run Crate `CreateAction` shape;
- align `atrium_rocrate.py` with RO-Crate 1.2 and Process Run Crate 0.5;
- use stable run/tool identifiers and tool versions;
- represent tool authors as `creator`;
- support an embeddable RO-Crate fragment without a second root;
- validate the relevant RO-Crate profiles in CI.

Acceptance criteria:
- an AMČR-seeded document can pass through the production chain without losing its identity or `source.sha512`;
- each service contributes its own machine-readable run provenance;
- the resulting record crate conforms to the agreed RO-Crate / Process Run Crate baseline;
- the validator runs in CI against the production crate output;
- the behaviour is covered by an end-to-end integration test rather than by isolated service tests only.

Out of scope:
- record-only execution mode, which remains deferred until a concrete use case requires it.
