### S2 deployment handover: executable acceptance examples and a lasting operator-documentation rule

Following a cross-repository review, I would **fold the remaining deployment-configuration findings into this existing issue**, rather than reopen the completed configuration work in [#53](https://github.com/ufal/atrium-project/issues/53) / [#60](https://github.com/ufal/atrium-project/issues/60) or create another umbrella issue. The six services already have a generally sound environment-variable contract, `/info` limits and Compose passthrough.

Please correct the following items in [`docs/k8s_acceptance_runbook.md`](https://github.com/ufal/atrium-project/blob/main/docs/k8s_acceptance_runbook.md), the [reference manifest](https://github.com/ufal/atrium-project/blob/main/docs/templates/k8s/atrium-service.deployment.yaml), and the linked operator pages **before the AMČR S2 handover**:

1. **Provide a complete, usable Kubernetes example.** The runbook applies the YAML template, but its `Service` resource is completely commented out while the next command requires `kubectl port-forward svc/atrium-nlp-enrich-api`. Either include a real Service resource and apply it, or explicitly port-forward the Deployment in that example. Explain which Kubernetes objects an operator must actually create.
2. **Make smoke checks prove success.** Commands such as `curl -s ...` can return exit status 0 for HTTP 4xx/5xx. Use `--fail-with-body` or check the HTTP code, and assert an expected response body/status. For restart tests, demonstrate that the request *was still executing* when the restart began; merely `wait`ing for a backgrounded curl process is insufficient. Record the actual outcome, not just a green shell exit.
3. **Cover all six production stages.** The acceptance runbook still lists only five services and omits `atrium-digital-convert`. Add an appropriate smoke request and results row, distinguishing `/reformat` from `/describe` and declaring any optional stage dependencies. Verify the published `-api` image, not merely a local checkout.
4. **Make NLP job semantics testable without inventing persistence.** `nlp-enrich` uses an in-memory job registry and local workspaces; after restart, a job may have completed during draining but no longer be retrievable via `GET /jobs/{id}`. The runbook currently couples the restart test to post-restart polling. Separate the actual **in-flight drain guarantee** from **durable asynchronous-job status/result retrieval**, which is *not* currently guaranteed. Adjust acceptance accordingly, or explicitly mark that scenario unsupported; do not claim job persistence as a side-effect of graceful shutdown.
5. **Refresh stale operational statements and links.** In [`docs_site/operations.md`](https://github.com/ufal/atrium-project/blob/main/docs_site/operations.md), page-classification's `MAX_PDF_PAGES = 50` is still described as hard-coded even though [`tool_limits.py`](https://github.com/ufal/atrium-page-classification/blob/main/tool_limits.py) now resolves it from the environment. Likewise, the Kubernetes reference's “raise the Dockerfile's `--timeout-graceful-shutdown`” wording is outdated: the documented knob is `GRACEFUL_SHUTDOWN_S`. Update these from the code/`.env.example` contract rather than copying old explanations, and keep the hub operations page consistent with all six services.

**Release/tag mapping is deliberately excluded from this comment:** source tags, GHCR tags, image digests, and tag protection are being clarified under [#72](https://github.com/ufal/atrium-project/issues/72). Here, simply apply the convention agreed there when repairing executable examples.

### Permanent lightweight handover policy

Please put a *brief* rule/checklist into the existing handover documentation—not a new configuration framework:

- **Executable examples are acceptance artifacts.** Starting from a clean checkout and documented prerequisites, the copy/paste commands must work with only named substitutions. A failing HTTP response must not be reported as a successful smoke test.
- **Current operational configuration has one authority.** The code, `tool_limits.py`, `.env.example`, and effective `GET /info` values determine the actual contract. Explain precedence between code defaults, Compose overrides, deployment `env`/Secrets and operator choices. Do not confuse service deployment knobs with research/algorithmic parameters.
- **State prerequisites and boundaries.** For each tool specify model acquisition/cache, storage, ingress/egress and backing services, required secrets, applicable limits, and relevant single-replica or non-durable-job restrictions. The reference manifest is an example, not an AMČR-specific production deployment; ÚFAL CI must not access or assume AMČR infrastructure.
- **Handover needs evidence, not just instructions.** The S2 page should identify the six approved image revisions/digests, link the runbooks and contacts, and provide a per-service acceptance matrix recording actual tests on the receiving Kubernetes environment. Reuse the existing acceptance-runbook structure; avoid duplicate tables.
- **Keep it maintainable.** Add inexpensive checks for genuinely broken examples/links or an omitted service if useful, and have a reviewer who did not write the service walk through the documented path. Leave actual cluster rollout/drain verification with AMČR operators. Coordinate human-readable structure with [#79](https://github.com/ufal/atrium-project/issues/79), and release/CI assertions with [#81](https://github.com/ufal/atrium-project/issues/81).

**Acceptance for this addition:** the runbook can be followed without reading the implementation, covers all six service images, correctly distinguishes proven behavior from limitations, and reports real pass/fail results. No broad changes to the six services, no Helm/operator project, and no new configuration umbrella are needed.

@K4TEL — please incorporate these checks into this issue's S2 handover plan, fix the concrete documentation inconsistencies, and flag anything requiring an AMČR-side acceptance decision before treating it as completed.
