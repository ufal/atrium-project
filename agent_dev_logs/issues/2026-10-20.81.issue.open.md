## Why this issue

Across the six ATRIUM tools the CI is largely operational, and considerable hardening work has already been done. **This is not a request to remove useful tests or start another wholesale CI rewrite.** The remaining problem is that CI has become hard to understand, review and maintain, with complicated workflow responsibilities and no short, authoritative policy governing new additions.

Concrete examples checked against current repositories:

- [`docker-tool.reusable.yml`](https://github.com/ufal/atrium-project/blob/main/.github/workflows/docker-tool.reusable.yml) is **1,068 lines** and combines test setup/coverage, Docker build smoke, runtime probes, security assessment, image publication and tag promotion. Some 410 lines are historical/explanatory comments; many are valuable evidence but do not belong in the executable workflow.
- The two hub [scanned-document E2E](https://github.com/ufal/atrium-project/blob/main/.github/workflows/e2e-pipeline-smoke.yml) and [born-digital E2E](https://github.com/ufal/atrium-project/blob/main/.github/workflows/e2e-digital-smoke.yml) workflows have **682 and 654 lines**, respectively. Their distinct test paths are justified; their readability, test provenance and responsibility boundaries still warrant review.
- Each tool has its own `.github/workflows/release.yml` (roughly 150–250 lines), with substantially similar version/OpenAPI/release machinery. The Docker and GitHub Release workflows both react to a version-tag push **independently**. This requires an explicit decision on what a “successful release” promises: approved source/assets, publishable image(s), or both; the current workflows do not enforce a dependency between them.
- Tool workflows still use the hub's **moving `@v1`** reference. The commit-pin plan and tooling already exist in [#40](https://github.com/ufal/atrium-project/issues/40) and [#72](https://github.com/ufal/atrium-project/issues/72); **implement that existing decision there**, not as duplicate work here.
- Some check implementations can finish green without exercising their apparent promise: e.g. [`api-contract.reusable.yml`](https://github.com/ufal/atrium-project/blob/main/.github/workflows/api-contract.reusable.yml) deliberately converts pytest exit code 5 (“no tests collected”) to success, while some Docker workflow jobs are intentionally skipped on branch pushes. Valid optional/skipped cases exist, but they must be visible and must not be mistaken for required validation.

Recent GitHub Actions runs are mostly green. This is principally **maintainability and trustworthy signalling**, not an assertion of widespread CI breakage. See the [completed CI roadmap #69](https://github.com/ufal/atrium-project/issues/69) for improvements that must not regress.

## Deliverable: a short, enforceable CI/CD policy

Add **`docs/ci_policy.md`** in the hub (short and normative; not another huge report). Link to it from the current [`docs/docker_gha.md`](https://github.com/ufal/atrium-project/blob/main/docs/docker_gha.md) and relevant tool development instructions. Keep the existing [`docs/release_trust.md`](https://github.com/ufal/atrium-project/blob/main/docs/release_trust.md) authoritative for tag/release/ref protection; **do not maintain competing copies** of those instructions.

The policy should establish the following rules for future changes:

1. **Define purpose and assurance level before adding a check.** Every check has a named owner, precise failure mode/guarantee, execution tier, trigger, required inputs, and status (**blocking, advisory or explicitly optional**). A check may be expensive only when its value warrants it.
2. **Four explicit CI tiers:** (a) fast, deterministic PR validation; (b) integration validation against a known set of candidate revisions/images; (c) controlled release validation and artifact publication; (d) scheduled external-service, dependency, model or published-image monitoring. GPU/network work must not silently enter the fast PR tier. Keep the GPU runner deferred under #40, not a pilot prerequisite, and never require access to AMČR infrastructure from ÚFAL CI.
3. **A green check must have a defined meaning.** Mandatory checks must fail if nothing relevant ran; an optional unavailable backend, missing test collection or skipped probe is labelled as such in the job summary. Do not turn a missing test into success without a reason clearly visible to consumers. Distinguish unit/contract conformance, container readiness, actual integration and empirical model quality.
4. **Keep workflows orchestration-focused.** Prefer small tested scripts under `tools/ci/` for nontrivial logic, and thin tool-repository callers for genuinely shared behavior. Avoid duplicate and inconsistent checks or long inline shell/Python programs. Split giant workflows by **responsibility and failure domain when this materially simplifies review**, not merely to lower line counts or create additional workflow layers.
5. **Keep YAML comments about intent and invariants**, not a running incident report. Preserve significant historical explanations, failures and decisions in existing reports or `docs/decisions/` (ADR-style only where useful). Names, summaries and error messages must make sense to someone who did not develop the workflow.
6. **Reproducible dependencies.** Shared reusable workflows used by tool repos are pinned to a reviewed commit SHA, including any matching `hub-ref`; changes propagate through reviewed pin updates, not silently by moving `v1`. Continue least-privilege permissions, audited tag rules, immutable release assets, safe secret handling and vulnerability scanning under #40/#72.
7. **Unambiguous release semantics.** Decide and document whether a GitHub Release certifies *source/contract assets only* or also its corresponding GHCR image(s). If both are promised, make the publication jobs dependent on the same required checks and verify the resulting commit, tag and image digest; do not mark a release complete with a required artifact still failed or absent. If source and images are intentionally independent, show their separate statuses explicitly. Preserve the existing **scan-by-digest before release-tag promotion** and the AMČR right to rebuild and check from an immutable source tag in its own environment.
8. **A reproducible integration baseline.** Keep `:latest` E2E useful for monitoring published services and `:test` for development, but do not equate a mixed set of moving tags with a reproducible, jointly approved pilot/release. Capture source revisions and image digests (or a small version manifest) for the combination that passed integration.
9. **Minimise duplication and noise.** Avoid running the same expensive check repeatedly for the same guarantee without justification. Review schedule/PR triggers, caches, automatic issue creation on recurring failures and unnecessary parallel publication. Prefer actionable, deduplicated failures to alert floods.
10. **Changes require proof and a rollback route.** A shared CI-template change must be checked against actual representative tool callers, including permissions and skipped/required behavior, before broad rollout; provide a tested rollback path. Tests of the linter alone are not sufficient to prove the full workflow works.

## Simple CI responsibility map

Add a **small matrix** to `docs/ci_policy.md` (or an existing suitable hub reference; do not create a second giant document) with the following columns:

| Check / workflow | Tier and trigger | Blocking? | What it *actually* proves | Where to inspect failures |
| --- | --- | --- | --- | --- |
| Fast unit + pre-commit | PR | Yes | Source tests and style | Test report / relevant job |
| API / schema / vendored drift | PR | Yes, when applicable | Declared interface and shared-file consistency | Contract job |
| Real container probe | PR or candidate | Yes for the production API target | Startup, health, port/shutdown behavior | Container smoke |
| Cross-stage E2E | Integration / scheduled | According to purpose | Selected stages work together under recorded versions | E2E job + version manifest |
| Security / release gates | Tag / scheduled | Blocking on defined release thresholds; scheduled is monitoring | Image assessment and release eligibility | Security summary / release job |
| GPU, research and live-service checks | Scheduled / manual | Explicitly stated | Backend/inference behavior when actually run | Dedicated job |

This is an illustrative outline, **not a declaration that every existing workflow already meets it**. Identify and correct false or ambiguous assertions instead of blindly adding checks.

## Acceptance

- [ ] A maintainer can understand, from one short policy and responsibility map, what each important green/red/skipped CI result means.
- [ ] The release/source/image guarantee is explicit, consistent in all six tool repositories and verified on a real or dry-run release path (including a simulated failure).
- [ ] Required checks cannot silently pass without exercising their stated guarantee; optional skips are visible.
- [ ] `@v1` pinning, immutability and branch/tag administration have **one implementation owner and tracker** (#40/#72), with evidence cross-linked here.
- [ ] Any structural refactor reduces duplicated responsibility or complexity, retains security checks and is regression-tested against actual tool workflows.
- [ ] A lightweight CI change checklist becomes the norm: **why is this check needed, what exactly does it prove, when does it run, what blocks, what is the cost, and where is its canonical implementation?**

**Boundaries:** no new requirement for ÚFAL to access AMČR infrastructure; no immediate GPU runner dependency; no withdrawal of working security or provenance gates; no reopening completed #69 tasks solely because the YAML remains long.
