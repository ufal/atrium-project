What is already in place is a very consistent pattern across the five `agent-skill` branches: a full repo snapshot trimmed to the service layer, a lightweight stdlib client script, and branch-local skill guidance. The main difference is how much of the “server” is truly local versus backed by an external service.

**`atrium-page-classification`** is the cleanest local/remote split. The branch keeps `service/`, `scripts/`, `setup/`, `Dockerfile`, `docker-compose*.yml`, `SKILL.md`, and the core inference code (`classifier.py`, `ensemble.py`, `model_registry.py`, `parallel_best.py`, `run.py`, `utils.py`). The server exposes `GET /info`, `GET /health`, `POST /predict_image`, and `POST /predict_document`; `scripts/server.sh` can start Docker CPU, Docker GPU, or local uvicorn. The client is `scripts/atrium_classify.py`, and there is also a local inference-only `run.py` path for batch work. Remote use is already documented via `--base-url` / `ATRIUM_PC_URL`. ([[GitHub](https://github.com/ufal/atrium-page-classification/tree/agent-skill)][2])

**`atrium-translator`** follows the same packaging style, but it is the one repo where the server itself is explicitly tied to an external translation backend. The branch keeps `processors/`, `scripts/`, `service/`, `SKILL.md`, `main.py`, `translation_backends.md`, and the AMCR config files. The API exposes `GET /info`, `GET /health`, `POST /translate`, plus a minimal frontend at `/frontend`. `scripts/atrium_translate.py` is the lightweight client, and the docs say translation runs against the remote LINDAT API, so the server needs outbound network access at request time. Remote deployment is still supported through `--base-url` / `ATRIUM_TR_URL`. ([[GitHub](https://github.com/ufal/atrium-translator/tree/agent-skill)][3])

**`atrium-alto-postprocess`** is already shaped as a local service plus local client. The branch keeps `scripts/`, `service/`, `setup/`, `SKILL.md`, `atrium_paradata.py`, `text_util_langID.py`, and the Docker Compose files. The service exposes `GET /info`, `GET /health`, `POST /process`, and `scripts/server.sh` can start Docker Compose `api`, GPU overlay, or local uvicorn. The client is `scripts/atrium_postprocess.py`, and the docs already show remote use through `--base-url` / `ATRIUM_AP_URL`. The first server start downloads FastText, LayoutReader, and the Qwen2.5-0.5B perplexity model. ([[GitHub](https://github.com/ufal/atrium-alto-postprocess/tree/agent-skill)][4])

**`atrium-nlp-enrich`** has the richest API surface. The branch keeps `api_util/`, `ker_data/`, `scripts/`, `service/`, `SKILL.md`, `api_1_manifest.sh`, `api_2_udp.sh`, `api_3_nt.sh`, `api_4_stats.sh`, `atrium_paradata.py`, and the service setup files. The server exposes `GET /info`, `GET /health`, `POST /enrich`, `POST /enrich_text`, `POST /rescale`, plus the async jobs API (`POST /jobs`, `GET /jobs/{id}`, `GET /jobs/{id}/result`, `DELETE /jobs/{id}`). The client `scripts/atrium_enrich.py` supports sync calls, async jobs, stdin lines, and workspace ZIP mode. Remote use is documented with `--base-url` / `ATRIUM_NE_URL`, and the first start prefetches the KeyBERT embedding model. ([[GitHub](https://github.com/ufal/atrium-nlp-enrich/tree/agent-skill)][5])

**`atrium-llm-enrich`** is also already split cleanly into a local client and a service wrapper, but its backend choice is more flexible. The branch keeps `api_util/`, `scripts/`, `service/`, `SKILL.md`, `llm_client_shared.py`, `llm_config.txt`, `ollama_client.py`, `openrouter_client.py`, `requirements_remote.txt`, and `vocab_manager.py`. The service exposes `GET /info`, `GET /health`, `POST /extract_keywords`, `POST /extract_keywords_text`, plus a minimal `/frontend`. The client is `scripts/atrium_keywords.py`, the quick start says to set `OPENROUTER_API_KEY` or run Ollama locally, and the docs describe Docker Compose `api` mode versus a torch-free local venv. Remote deployment is documented via `--base-url` / `ATRIUM_LE_URL`. ([[GitHub](https://github.com/ufal/atrium-llm-enrich/tree/agent-skill)][6])

Net: the “lightweight local client” requirement is already satisfied in all five branches; the main follow-up is standardizing the server startup and remote-hosted wording so the skill docs read the same way across repos. The only real architectural outlier is `atrium-translator`, where the service itself depends on outbound access to LINDAT at request time, while the other four can more naturally support either a local server or a hosted one. ([[GitHub](https://github.com/ufal/atrium-translator/tree/agent-skill)][3])
