#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) commented at [2026-09-29 06:04](https://github.com/ufal/atrium-project/issues/32#issuecomment-5884649640):

The three items landed on 28 September on the `test` and default branches of all five tool repositories and the hub, and CI is green. No release carries them yet: the next tag of each tool is the first with a spec.

**1. Typed requests and responses**
- Each primary endpoint's 200 response is a named model in the spec, and so is `/info`, with the effective limits (#53) as `limits` and `limits_meta`:
  - page-classification `/predict_image`, `/predict_document`;
  - alto-postprocess `/process`;
  - translator `/translate` with `response_format=json` (opt-in; the XML and multipart answers are unchanged);
  - nlp-enrich `/enrich`, `/enrich_text`, `/rescale` and the jobs API;
  - llm-enrich `/extract_keywords`, `/extract_keywords_text`.
- The record is one component, `AtriumDocument`, built from the `doc-schema-v1` schema. `x-atrium-record-schema` in each spec gives its `schema_version` and sha256.
- Every primary response has an optional `paradata` field typed as the `CreateAction` of #67 R2. Until R2, nlp-enrich puts its current run record there (transitional) and the others return `null`.
- What the services send has not changed: the tests validate real responses against the published schema.
- alto-postprocess now takes and returns `document_json` like the others. `document_record` and `document_json_out` still work and are marked deprecated.

**2. One error model with registered reason codes**
- Every error body is `{status, reason, detail}`, plus `limit`, `errors`, `accepted` or `cause` where they apply. Every route declares the error statuses it can return, and the 422 in the spec is the body we actually send.
- The registry is in each spec as `x-atrium-reason-codes`, with the statuses each code comes with:

  | `reason` | status |
  |---|---|
  | `limit_exceeded` | 413, 422, 504 |
  | `busy` | 429, with `Retry-After` |
  | `unsupported_media_type` | 415, with `accepted` |
  | `invalid_record` | 422 |
  | `ocr_text_layer` | 422 |

- `reason` is `string | null` in the schema, not an enum, so a code added later does not break a generated client. A published code is never removed or renamed: our tests freeze the list, and the release gate fails if one disappears.
- `invalid_record` is one code beyond my list. It covers a `document_json` part that is not JSON, not an object, or has an unsupported `schema_version` major, and it is refused before any model runs. A record that parses but fails the schema is still accepted and returned with `document_json_schema_error`, so an R1 seed stays valid input.
- A finer cause, such as alto-postprocess's reader codes, goes into an unregistered `cause` member. The activities can branch on `reason` and log `cause`.
- The statuses are harmonised. These change what an existing caller sees, so each tool's next release notes will list them:
  - an unsupported media type is 415 in all five (it was 400 or 422);
  - caller errors that ended as 500 are 422;
  - alto-postprocess answers 501 for a missing optional dependency;
  - page-classification refuses an unknown `version` with 422 up front, and a page it cannot classify is a 500 instead of an `{"error"}` inside a 200.
- `ocr_text_layer` is registered; `api-digital` itself comes with ufal/atrium-digital-convert#4 W1.

**3. The spec as a release artefact**
- Each repository commits `service/openapi.json`. A test fails when the code no longer produces it, and the spec does not depend on deployment settings (limits, CORS origins, model paths).
- Every release attaches `openapi.json` and `openapi.json.sha256`. Before publishing, the release job compares the spec with the previous release's asset, with oasdiff on stricter rules plus our own checks:
  - a breaking change fails unless the major version went up (0.x included, so a 0.x tool needs 1.0);
  - a removed reason code, a changed service id, or a record-schema change without a `schema_version` major always fails.

  The same comparison runs on every push, so a break shows up in the change that makes it. Each tool's first tag becomes the baseline for its next one.
- To check a running service: `/info` reports `openapi_sha256`, which equals the release's `openapi.json.sha256`, and `sha256sum -c openapi.json.sha256` verifies the downloaded asset. Our Docker CI runs this check on every image build (the served `/openapi.json` must be the committed spec, and `/info` must report its digest). The page-classification image, whose tests otherwise use a stub, has passed it.
