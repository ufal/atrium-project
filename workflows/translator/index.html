    Translating XML documents with a protected domain vocabulary¶

    The translator workflow. Tool section: translator.

    Purpose¶

    Archival collections hold text inside XML: OCR transcriptions in ALTO XML, and structured metadata records such as those of the Archaeological Map of the Czech Republic (AMČR). This workflow translates that text — into English by default — and writes it back into the same document, so that tags, namespaces, attributes and, for ALTO, the position of every word survive, and the result stays valid against its schema. Domain terms can be held to their established translations from a controlled vocabulary, so that an archaeological term is rendered the same way in every document.

    At a glance¶
    In ALTO XML pages, or any well-formed XML with a list of the fields to translate (XPaths), told apart by their root element unless a mode is named; files, folders or lists of URLs; optionally a vocabulary (CSV)
    Out the translated document (same format); a translation log pairing source and target text (CSV); a paradata log (JSON); the ATRIUM document record (JSON). The service returns the log and the record on request (include_log, include_record)
    Runs as a command-line tool (main.py); a container image; an HTTP service image (POST /translate); an Agent Skill
    Compute CPU; a GPU only for a self-hosted translation model (Qwen3.8-27B was measured on one 96 GB GPU)
    Network the LINDAT translation service (the default backend) and the LINDAT UDPipe service (vocabulary matching), or the server of a language-model backend; the Hugging Face Hub for the language-identification model on first use, from a checkout (the published images carry it); GitHub when the vocabulary is fetched from keyword-extract's release
    Code licence MIT
    Component licences a default run uses CUBBITT through the LINDAT service (a CC BY-NC-SA 4.0 model, under LINDAT's terms of use) and, when the source language is detected, FastText (CC BY-NC 4.0); a run with only permissive components can be assembled (see below). These do not by themselves set the rights in the output: Licences and paradata
    Records SSH Open Marketplace tool CizIUW and workflow 13eHAZ

    Steps¶

    # Step What happens In → out Activity
    1 Prepare a domain vocabulary (optional) Czech–English term pairs from the AMČR vocabularies and the TEATER thesaurus, each pointing back to the concept it came from. The project keeps one curated list, which keyword-extract publishes with each release: load_vocab.py --from-release builds the CSV from that asset, checked against its .sha256, and adds the concept's description where there is one. The bundled harvester collects pairs from the live sources instead (AMČR over OAI-PMH, TEATER over GraphQL). The shipped data_samples/vocabulary.csv is keyword-extract's v1.3.0-beta list: 4,715 pairs, 1,961 with a description. A vocabulary of one's own in the same CSV form works as well. → CSV Collecting
    2 Choose the mode and the fields ALTO transcriptions are translated in ALTO mode, which works on the words of each text line. For metadata records, the fields to translate are listed as XPaths; namespaces and OAI-PMH envelopes are handled by the tool. The file's root element decides the mode (an <alto> root is ALTO, any other is metadata) unless one is named: --alto, --xpaths or --formats on the command line, is_alto in the service (since v1.6.0-beta). ALTO, XML —
    3 Identify the source language A language-identification model detects the language of each text block (ALTO) or field (metadata), so a record that mixes languages is handled piece by piece. A guess is used only when it is confident and names a language the backend translates; otherwise the element's own label, the document's language, then a configured default decide. A confident guess of a language the backend cannot translate is reported for review. Naming the source language skips detection. Before anything is translated, the named language, or the default, is checked against the backend: a pair it cannot translate is refused (exit 1 on the command line, 422 unsupported_language_pair from the service) and is never rerouted. — —
    4 Protect domain terms (optional) Vocabulary terms found in the text are replaced by placeholders before translation and restored as their agreed translations afterwards; multi-word terms are matched first, single words by lemma. Language-model backends receive the matching terms as a glossary in the prompt instead; the OpenAI-compatible backend can add each term's description as context (off by default). The command line takes the vocabulary with --vocabulary; the service applies one only when VOCABULARY_PATH names it. CSV Lemmatizing
    5 Translate The text goes to the chosen backend: the LINDAT translation service (CUBBITT, the default), an OpenAI-compatible language-model API (such as Qwen3.8-27B on one's own vLLM server), or a self-hosted CTranslate2 model. Long texts are split at sentence boundaries first. Every reply is checked against its source: one that is empty, runaway, cut short, looping, or mixes Latin and Cyrillic letters in a word is requested again, re-run at the end of the document if it still fails, and never written. — Translating
    6 Rebuild and validate the document ALTO: each text block is translated as a whole and line by line; the fluent whole-block translation is then divided among the original lines and written into the original word elements — replacing their text, or added beside it as an alternative. Metadata: the translation replaces the source text, or is added beside it with language labels. Metadata output can be validated against an XSD schema, such as the AMČR schema, which accepts replaced records and not appended ones: --xsd on the command line, XSD_PATH in the service (since v1.6.0-beta). → ALTO, XML —
    7 Review and record provenance A translation log beside each output pairs source and target text line by line or field by field, with a status saying whether each was translated normally, recovered by a re-run, placed approximately, kept as source, or translated from a fallback language because the backend cannot translate the detected one. The paradata log records what was run, with each component's licence; the document record notes the languages, the backend, the translated file and the same component licences. → CSV, JSON —

    Which backend. LINDAT stays the default. The recommended self-hosted alternative is openai_compatible with Qwen3.8-27B (Apache-2.0) on one's own vLLM server: in the bake-off of 2026-10-19 it kept numbers and vocabulary terms about as well as LINDAT (terms 0.978 against 0.987) and failed no segment. ct2 with EuroLLM is no longer recommended, because it drops short segments (see Limits). The bake-off compares the backends without reference translations. Its script is eval/bakeoff.py, its results are in eval/results/issue4_bakeoff_2610/, and the decision is in the tool's docs/translation-backends.md.

    The vocabulary step is its own workflow on Pipelines — W7, vocabulary harvesting and review.

    What you get¶

    • The same document in another language — <name>_<target language>.<extension>, every tag and namespace in place; for ALTO, every line where it was.
    • A review log — <name>_log.csv, with the source and the translated text side by side, and a status per line that points a reviewer at what was recovered, approximated, left untranslated or translated from a fallback language.
    • Consistent terminology — every protected term carries its agreed translation, and the paradata counts the protected terms per document.
    • A provenance record — the paradata log of the run, with each component's licence, and a document record per file, <name>.document.json.

    The translator's output is an end product: an edition for readers and for publication. No later stage of the pipeline reads it; the document record refers to it.

    Limits¶

    • Word positions in translated ALTO are approximate. Line boundaries are exact; how the words of a line are spread over its word elements is constructed, because a translation has a different number of words.
    • Schema validation applies to metadata output. ALTO output keeps the structure of its input — and is valid ALTO in either mode — but is not validated by the tool. The command line takes a schema file or URL (--xsd); the service, since v1.6.0-beta, only a local file its deployment names (XSD_PATH), and answers xsd_valid (or refuses with xsd_strict).
    • Appended AMČR records are not valid AMČR. The AMČR schema allows neither a language label on the translated fields nor a second copy of them; a record that must validate is translated in replace mode.
    • Language coverage is the backend's. Into English, LINDAT translates from Czech, German, French, Polish, Russian and Ukrainian. A pair the backend has no model for is refused, not routed through Czech; other pairs need another backend.
    • Placeholders protect terms only for the LINDAT backend. Language-model backends get a glossary instead, and the self-hosted neural translation models receive no vocabulary.
    • EuroLLM on ct2 drops short segments. In the bake-off EuroLLM-9B ran on past the source in 96 of 1,230 segments, almost all a number or a single word. The guard keeps their source text and logs them untranslated.

    Provenance and licence¶

    Each run writes <stamp>_translator.json, the paradata log; the service returns the same provenance, with the same keys since v1.7.0-beta, in its response instead of writing a file. The paradata lists the components the run actually used, each with its licence or terms, as declared in the tool's para_config.txt:

    Component Licence Used when
    language-identification model, FastText (fasttext) CC BY-NC 4.0 the source language is detected, not given
    LINDAT translation, CUBBITT (lindat_cubbitt) CC BY-NC-SA 4.0 the default backend, lindat, is used
    UDPipe 2 engine / models (udpipe2_engine, udpipe2_models) MPL 2.0 / CC BY-NC-SA 4.0 LINDAT applies a vocabulary (terms matched by lemma)
    AMČR vocabularies, TEATER thesaurus (amcr_vocab, teater_data) CC0 a vocabulary is applied
    OpenAI-compatible language-model API (llm_api) LLM provider ToS openai_compatible is used without LLM_LICENSE_COMPONENT
    Qwen3.8-27B or -FP8, self-hosted (qwen3_8) Apache-2.0 openai_compatible with LLM_LICENSE_COMPONENT=qwen3_8
    CTranslate2 engine (ctranslate2) MIT the ct2 backend is used
    EuroLLM, MADLAD-400 (eurollm, madlad400) Apache-2.0 a ct2 model of these families
    NLLB-200 (nllb200) CC BY-NC 4.0 a ct2 NLLB-200 model
    Opus-MT (opus_mt) CC BY 4.0 a ct2 Opus-MT model

    A hosted language-model API is recorded with its provider's terms of service (LLM provider ToS). The paradata's computed label, the most restrictive of the licences listed, treats terms it does not know as the most restrictive. The label is not the licence of the output: Licences and paradata.

    A run with only permissive components needs both: a self-hosted model under a permissive licence and the source language named explicitly. The recommended model is Qwen3.8-27B through openai_compatible, recorded with LLM_LICENSE_COMPONENT=qwen3_8; a ct2 model of the EuroLLM, MADLAD-400 or Opus-MT family also qualifies. The AMČR and TEATER vocabularies are CC0 and do not stand in its way. How the label is computed is on Reference → Licence.

    In the document record the tool owns the translations block and records the translated file as derived_from.translated_xml. The block also counts the segments in a language the backend cannot translate (unsupported_source_langs).

    Where it sits¶

    • Translation branch of the scanned-document pipeline — Pipelines → W1. It reads the per-page ALTO that ocr-postprocess writes; its output ends that branch.
    • Translation step of the AMČR text workflow 0xSpVP, where it translates AMČR metadata records.
    • Also used in W4 (as a service), W5 (from a coding agent), W6 (the end-to-end test) and W7 (the vocabulary).
